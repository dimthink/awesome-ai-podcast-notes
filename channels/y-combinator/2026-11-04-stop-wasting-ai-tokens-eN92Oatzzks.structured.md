# 停止浪费 AI Token：Weave 智能路由与软件工厂的实践

**来源**：Y Combinator 视频访谈

## 开场与 Weave 介绍

**主持人**：欢迎 Weave 的创始人，祝贺他们从 Sander Capital 获得 A 轮融资，以及发布新产品 Weave Router。欢迎各位。

**嘉宾**：谢谢。

**主持人**：首先，请介绍一下 Weave 是什么？

**嘉宾**：Weave 是一个工具，可以将任何软件公司变成**软件工厂**。我们构建模型来度量工程工作，并利用这些模型优化人类和代理，以及人类与代理之间的协作。

**主持人**：现在谁在使用 Weave？介绍一下公司的现状。

**嘉宾**：我们有幸与许多优秀客户合作，比如 **Robinhood**、**Posthog**、**Telnyx**、**Extra Space Storage**、**Reducto**，从只有几个人的初创公司到财富 100 强企业都有。

**主持人**：你们今年表现非常出色，因为 AI 编码越流行，Weave 对公司就越关键。能谈谈今年的进展吗？

**嘉宾**：是的，非常棒。我们最近完成了 A 轮融资，直接得益于增长。原因是我们之前为人类度量工作、理解工作内容并优化工作方式的一切，都可以轻松应用于**编码代理**。随着人们大量使用编码代理，这项业务自然爆发式增长。

## Weave Router：智能路由节省成本

**主持人**：你们最近发布了 **Weave Router**，能谈谈它是什么以及如何帮助人们省钱吗？

**嘉宾**：Weave Router 的作用是将每个任务发送给最适合该任务的模型。你将它插入编码代理，所有内容都会发送给路由器。路由器决定每个提示或任务的最佳模型，并将其路由到该模型。你无需思考这个该用 Opus、Astra 还是 DeepSeek，一切自动处理。我们训练了一个模型，在充分利用每个模型方面比任何人类或现有任何东西都更好。在最近的基准测试中，我们能以**一半的成本和两倍的速度**达到 Astra 级别的性能。

**主持人**：我可以与哪些编码代理一起使用它？

**嘉宾**：Claude Code、Codex、Open Code、Py，以及任何在**命令行界面（CLI）** 中工作的工具，只需一条命令即可直接插入。

## 如何保证不会降低性能

**主持人**：我如何知道它不会让我的编码代理变得更差，比如路由到一个只会写 bug 的愚蠢模型？

**嘉宾**：这是个好问题。这是做这件事最大的潜在问题之一。实际上我们有一种有趣的能力来确保不会发生这种情况，因为我们的整个产品都专注于理解工程团队的工作方式，理解速度和质量。我可以直接谈谈我们自己的团队。我们都在使用路由器，我们的产出持续加速。根据我们自己的数据，我们位于所有团队的前 1%，并且引入的 bug 数量或进入产品的质量问题没有增加。这是我能想到的最有力的证明。

## 开源与订阅计划

**主持人**：现在谁可以使用？我需要整个团队都加入吗？任何人都可以安装吗？它是开源的吗？

**嘉宾**：是的，完全开源。任何人都可以尝试。我们通过托管版本让使用变得非常简单；如果需要自托管，设置会多一点，需要配置所有密钥。但这完全可行。我们也有订阅计划。如果有人想从每个模型中获得最佳效果，可以注册 **Max** 或 **Boost** 计划。

**主持人**：假设我有订阅计划，优化会有点复杂，因为我希望在开始将请求发送到其他模型之前，最大化利用我的 Claude 计划和 OpenAI 计划。你们会考虑这一点吗？

**嘉宾**：当然。这是一个巨大的需求，尤其是早期初创公司非常希望最大化这些补贴。趁还能用的时候尽量用。我们完全可以帮助解决这个问题。你可以登录多个不同账户，我们会在这些订阅之间路由，尽可能利用所有补贴，然后在开源模型表现最佳的地方混入开源模型。

**主持人**：如果我已经在支付 Anthropic 和 OpenAI 每月 **200 美元**的计划，我是一个重度用户，已经将这两个计划用到极限，还想进一步扩展。如果使用 Weave，在实践中模型会如何处理？到月底我的总产出会有什么变化？

**嘉宾**：首先，在相同花费下，你的使用量大约会**翻倍**。我们这样做的方式是：如果你是这样的人，你可能会把所有请求发送给最大的模型，这可以理解——既然有补贴，为何不用最聪明的模型。但问题是，你并不总是需要“大炮”，有时“手枪”就够了。例如，你在探索代码库时，可能只需要 **Luna** 来弄清楚认证功能在哪里实现。那么那个子代理或这部分对话就会路由到更便宜的模型，对你毫无影响，最终结果相同，甚至更快，但消耗的用量限额更少。因此你不会那么频繁地达到用量上限。它还可以在不同计划之间切换，无需你反复登出登录。

## 开源模型的崛起与路由优势

**主持人**：你们节省成本的很大一部分不仅来自 OpenAI 和 Anthropic 的更便宜模型，还来自开源模型。能谈谈开源模型的爆发以及这如何改变格局吗？你们会将请求路由到哪些开源模型和提供商？

**嘉宾**：开源模型的爆发反映了这样一个事实：它们虽然不在最前沿，但离前沿也不远。而且它们的**成本性能比**基本上无与伦比。如果你想象一条**帕累托曲线**，它们位于非常便宜的一侧，但以如此低的价格获得的性能令人难以置信。所以你不会把构建一个用于分类十亿张图像的机器学习系统这样的任务交给 DeepSeek，那种任务你可能需要 Astra 来处理。但像居中一个按钮，或者实现一个执行 **CRUD（增删改查）** 操作的后端，DeepSeek 能做得很好。至于实际使用的模型，最大的几个是 **DeepSeek**、**Kimi** 和 **GLM** 模型。这些在我们自己的内部测试和基准测试中表现最好，因此我们将大量流量路由到这些模型来处理一些较简单的任务。这相当惊人。我认为对于几乎所有业余项目，你不需要超出开源模型。至少根据我的经验，我在业余项目上只用开源模型就能走得很远。

## 与其他路由器的比较

**主持人**：这与其他模型路由器相比如何？比如与使用 **OpenRouter** 相比？

**嘉宾**：好问题。关键区别在于我们是进行**智能路由**。OpenRouter 或许更适合被称为 OpenGateway。他们的整个思路是让你访问尽可能多的模型，由你选择使用哪个模型，他们只是让这件事变得简单并提供所有回退方案，这很好也很有价值。我们所做的是自动为你选择模型，并且专门针对**编码代理**用例。这一点至少在他们的基准测试中，你用 OpenRouter 无法做好。他们有一个自动路由器，但效果不太好，那也不是他们的重点。

**主持人**：你们的自动路由器是如何工作的？如何知道该路由到哪个模型？

**嘉宾**：我们在数十万个编码代理会话上训练了路由模型。我们不仅关注编码代理会话本身以及什么有效、什么无效，还关注所有下游影响，因为我们可以看到这些影响如何反映在生成的 **PR（拉取请求）** 中、合并到生产后如何、一个月后如何。因此我们能看到哪些模型在哪些类型的工作上有效。在此基础上我们还会做大量额外训练：我们测试将任务发送到不同模型的路径，如果成功完成任务就给予奖励。通过结合大量真实会话的训练和大量测试来了解不同模型的优势所在，我们能够更好地把握每个模型的强项，并自动学习。这不是我们人工判断“这个任务适合 DeepSeek”，而是我们训练的机器学习模型在做这件事。

## 从度量工程工作到智能路由器

**主持人**：你们之所以能构建智能模型路由器，而其他公司包括 OpenRouter 尚未能做到，是因为你们在过去一年半里一直在做不同的事情。现在正好回顾一下你们是怎么走到今天的。让我们回到 YC 批次时期。你们当时是 Winter 25 批次，当时你们只做了现在所做事情的一部分。能谈谈批次期间的情况吗？

**嘉宾**：是的。回到 2025 年 1 月，感觉像是很久以前。我们当时只专注于理解和度量工程工作。历史上这几乎是不可能做到的：真正理解工程师的工作、他们的生产力以及他们创造了多少 bug。过去你只能数代码行数或 PR 数量。PR、同行评审指标，这些都是很花哨的指标，只是为了让高管感觉良好。因此我们创造了一种真正度量生产力的方法，并构建了模型来实现。在批次期间，我们很快意识到这是第一个 **Cursor** 开始起飞的批次。人们第一次用 Cursor 编写所有代码，他们开始要求我们展示 Cursor 对他们生产力的影响。这成为我们进入“需要弄清楚如何度量编码代理，而不仅仅是人类工程师”的入口。

**主持人**：我记得那是一个疯狂的时期，因为同时发生了两件由 AI 引起的事情。第一件由 AI 引起的事情是，第一次有可能度量人类表现，因为你们不再只是数代码行，而是让 AI 模型查看代码、真正阅读代码并理解人实际在做什么，从而第一次能够获得团队中不同工程师生产力的真实指标。同时，使你们能够做到这一点的同一批**大语言模型（LLM）** 也在改变工程师编写代码的方式。这两大转变同时发生。2025 年真是个疯狂的时期。你们让我想起，那是我们第一次对批次进行调查，发现相当多的人说他们的大部分代码是由大语言模型而不是人类写的。

**主持人**：这在当时令人震惊。Twitter 上有很多争议，大家说：“什么？他们在做什么？”

**嘉宾**：是的，我记得我们发了关于这个的推文，网上有很多愤怒的声音，说“程序员怎么能让 AI 帮他们写代码”。

**主持人**：在 2025 年初这个环境下销售早期的 Weave 是什么感觉？当时 Claude Code 还没有推出，我印象中 Claude Code 刚刚推出但没人使用，所有人都在用 Cursor。

**嘉宾**：当时是研究预览版。是的，这非常有趣，因为显然有很多人想要度量软件工程，但我们接到的每个电话都充满了怀疑：“我不相信你真的能做到。”因此我们不得不用他们自己的数据来证明。我们连接他们的数据，向他们展示实际效果，并问：“这符合你的预期吗？”当我们开始能够证明时，那就是真正的起飞时刻。除此之外，我们意识到我们合作的许多增长最快的初创公司，因为他们正在使用编码代理，这给了我们始终领先的优势——我们总是领先曲线 6 个月，因为我们知道处于最前沿的人在做什么。

**主持人**：这很有意思，因为像 YC 批次公司这样的早期公司，可能不太关心度量工程师表现，因为他们没有工程师。但他们处于使用编码代理的最前沿；而你们销售对象是拥有大型工程团队的公司，他们真正面临这个问题，但在使用编码代理方面落后 6 个月到一年。

**嘉宾**：没错，直到今天我们仍然看到这一点。我们始终领先于人们通常需要达到的水平大约 6 个月，因为我们持续与这些快速增长的公司或早期初创公司合作。对于他们来说，最大的需求就是度量编码代理的有效性，以及它是否真的比他们自己输入代码更快。我们总是能证明这一点，所以他们持续在 token 和编码代理上投资。

## 工程管理问题的演变

**主持人**：你们的核心工作是帮助工程经理了解他们工程团队中发生了什么。工程经理向你们和你们产品提出的问题从 2025 年初到现在有何变化？

**嘉宾**：一开始非常明确：我们的速度有多快，与一般基准相比如何。然后变成：AI 真的让我们更快吗？接着是：好，我们如何更高效地使用 AI？这就是今天我们所在的位置——如何更高效地使用。每个人都在用 AI 写全部代码，也许不是每个人，但至少我们合作的大多数人是这样。现在需要弄清楚如何优化。这正是引导我们开发路由器的原因，因为优化方法之一就是为每个任务选择正确的模型。但还有其他方面，比如你如何提示、如何进行代理并行化、如何处理代理任务。这些就是我们帮助团队理解和看清的内容。

**主持人**：总体而言，团队更兴奋于如何提高团队生产力、推动人们采用 AI、实现 token 最大化、使用更多 AI、写出更多代码？还是更担心其他事情，比如如何确保人们不是只写出 AI 垃圾、破坏代码库、如何确保他们没有在像 **Fable** 这样的工具上花费巨资却看不到实际 **ROI（投资回报率）**？

**嘉宾**：这像一条**转型曲线**。一开始人们非常关心采用 AI，尽可能多地采用。然后进入 **token 最大化**阶段，就是尽可能多地花钱。接着进入**优化层**：现在每个人都在使用 AI，是 AI 原生、AI 优先，如何微调以确保我们没有在诸如 Fable 之类的工具上浪费不必要的 token。对我们来说，初创公司通常仍处于 token 最大化阶段，他们不太关心成本优化，更关心生产力优化。我们也有很多后期公司、一些私募股权所有的公司，它们处于曲线的优化层。

## 具体案例与洞察

**主持人**：能举出一些具体例子，说明 Weave 帮助人们实现目标的方式吗？Weave 的妙处在于，无论你在采用曲线的哪个位置，它都能帮助你实现目标。也许你可以给出几个处于不同阶段的人的例子。

**嘉宾**：我最喜欢的一个是 **Uncountable** 公司。他们正在使用 Weave 构建一个软件工厂。他们正在比较实际构建和使用的软件工厂与人类工作的表现，以及哪些工作可以继续转移到“熄灯工厂”，而不是由人类完成。

**嘉宾**：另一个很常见的例子是，当人们第一次连接数据并由我们带他们查看时，经常会出现一些相当惊人的正向异常值。人们第一次打开充满数据的 Weave 仪表板、看到工程团队的全貌时，最常见的反应之一是：“我完全不知道那个人原来如此高效。”如果你没有看到每一个 PR，就很难知道。但当你看到数字时，就变得非常清晰。例如，团队中可能有人每月花费 1 万美元甚至更多，但 ROI 确实存在——他们同样也在交付大量成果，合理利用了这些资金。这对人们来说非常令人兴奋，因为它提供了一个蓝图：这就是好的样子，现在我们知道了。接下来可以一方面使用 Weave 深入到单个提示级别，查看这个人做了什么才如此有效；另一方面在系统层面，如何将这种做法推广到整个组织。这是我认为人们在首次连接所有数据并查看时获得的最令人兴奋的一类洞察。

**主持人**：当人们看到那些在 token 花费上是巨大异常值、因此也是团队中最昂贵的人时，结论通常是“哇，这些是我们最好的表现者，很高兴有他们在团队里，我想让每个人都像他们一样”，还是“哇，这个人刚刚花了 10 万美元，我应该和他们谈谈如何更智能地使用这些模型”？

**嘉宾**：我们展示的主要指标之一是**每单位输出成本**，即你在 AI 上花了多少美元，换来了多少单位的输出。当我们谈论输出时，可以把它理解为一名人类工程师实际完成一小时工作的量。这个指标之所以重要，是因为它直接回答了这个问题：有人可能花了 1 万美元，但如果他们获得了 1 万小时的工作量，那么每工作小时只花 1 美元，这是非常划算的。但也有另一种情况：有人花了 1 万美元，却只获得 10 小时的工作量，那么每工作小时就是 1000 美元，这是非常糟糕的。这时就需要有人介入，纠正他们，指出“你使用了错误的模型”或“你有一个奇怪的代理循环在消耗 token 却没有带来真正的生产力”。所以你需要这两类数据结合起来，才能准确判断这究竟是否划算。

## 如何传播顶级实践

**主持人**：你之前提到，人们使用 Weave 分析的一种方式是传播团队中顶级表现者的知识。我知道这不是你们产品直接做的事，但我很好奇，你们是否观察到团队中的最佳实践，人们如何实际做到这一点，提升整个团队，让每个人像那一两个顶级表现者一样出色？

**嘉宾**：是的。我认为我们看到的**最高杠杆的单一因素**就是一个人**并行化的能力**。这在一定程度上是直觉性的：如果你是单线程，能做的就有限；如果你是多线程，能做的就多得多。问题在于，并行化并不只是简单地启动 10 个 Claude Code 会话然后让它们自行其是。难点在于如何建立正确的防护栏和框架，确保这些代理在做正确的工作，并且你是在正确的时机而不是错误的时机被拉进来。我会说这是一门不断演变的艺术，每次新模型发布都会改变，因为模型能力变化了，人类注意力需要介入的地方也变了。最常见的情况是，我们看到某人真正掌握了并行化。他们擅长同时处理多件事，并将自己的注意力投入到最高杠杆的时刻。传播这种能力是什么样子呢？往往是分享防护栏、分享某个技能，或许是重构代码库的某个部分以匹配某种对代理来说更熟悉、更舒适的架构。这因人而异、因公司而异。但我会说并行化是头号最高杠杆的事情。

**嘉宾（补充）**：我们的产品实际上做的就是这件事。它会查看你所有的提示和进入生产的内容，为你提供具体的技能建议，告诉你如何更好地使用这些工具。并且它有一个**教练**来实际执行这件事。

**主持人**：给我一些教练可能会告诉我的例子。

**嘉宾**：它会查看你每一个会话，并给出各种小提示。比如安德鲁刚才讲到的如何用代理处理任务，或者如何更好地反驳你的代理——现在人们不够经常告诉代理“你错了”。或者它可能会说，你应该更频繁地重启会话，而不是继续在当前会话中运行，因为会话成本会随着上下文窗口增大而不断增加。

## 软件工厂与自主编码

**主持人**：我们来谈谈软件工厂。如果掌握 AI 编码的基础是学习如何并行运行 10 个 Claude Code 会话，那么下一个层次可能是学习建立软件工厂，在你的工程团队睡觉时仍然在编码。你看到最佳团队在那里做什么？他们的软件工厂实际上在做什么？那是一个很容易在低 ROI 的事情上花费大量 token 的地方，因为这些系统经常在没有任何人类的情况下自主运行。Weave 如何帮助我确保我的软件工厂真正在正常运行？

**嘉宾**：我认为任何尝试过编码代理的人都知道，它们可以按要求生成大量代码。所以关键不只是衡量输出，还在于理解**验证**。我认为构建软件工厂最难的部分就是理解如何正确验证，因为代理可以把任何你想要的东西投入生产，但如果质量不好，那就毫无价值。人们通常做的是将工作交给代理，即软件工厂。然后在 Weave 中你可以看到一个非常直接的比较：好，这是我们软件工厂代理获得的成果，这是它们引入的 bug 数量，这是来自它们所做工作的客户报告数量。你可以非常直接地与之前的情况或一个没有使用这种自主系统的并行团队进行比较。当你了解问题所在时，你就能构建系统来避免整类问题。这就是一种持续的迭代循环：把东西放进系统，看它在哪里失败，然后修复那个问题。

**主持人**：Weave 今天自己运行哪些软件工厂？现在你们在这里录制播客时，什么程序正在编码？

**嘉宾**：对于构建产品，我们认为最高杠杆的事情是选择正确的工作内容。其次是构建一个系统，尽可能好地为我们构建产品。一方面是如何确保我们确定正确优先级并获得正确的产品功能集；另一方面是如何确保它不是垃圾，而是对人类或使用平台的代理真正有用的东西。基本做法是：我们既可以在本地也可以在云端运行编码代理。我们为这些编码代理提供了非常好的指导。我们有各种工具，例如一个自定义 CLI，它会以非常节省 token 的方式为代理提供构建新功能、修复 bug 或根据 CI 或测试反馈进行迭代所需的上下文。另一面是验证那些人类高级软件工程师在审查 PR 时会做、但其他情况下没人做的事情。我认为这包含两个部分。第一是**发现 bug**。我认为很多现成的审查工具在这方面都做得很好。我们在每个 PR 上使用四个工具，其中两个是 YC 公司——**Cryptile** 和 **Parameter**。然后我们还使用 **Cursor Bug Bot**。哦，实际上是三个，还有 **Cubic**。所以每个 PR 上有四分之三的工具来自 YC 公司。

**主持人**：每个 PR 的美元成本是多少？

**嘉宾**：基本上，只要每个工具都能发现其他工具没有发现的问题，那就值得。这就是我们的计算方式。我预计随着时间推移，这些工具会趋同，我们将不得不选择最好的，这可以用我们自己的产品来观察。但目前我们仍然可以在自己的产品中看到每个工具都在发现其他工具没有发现的独特问题。这是一类。另一面是，除了单个 PR 的狭隘目标之外，我们如何确保这个 PR 能很好地融入系统，具有可扩展的架构，便于未来的贡献。我认为这是“熄灯软件工厂”方法最大的失败之处，因为每个 PR 在局部逻辑上都是合理的，但你把它们放在一起，整体就变得疯狂，充满各种糟糕的一次性变通方法。因此，我们为此构建了自己的**检查系统**。你可以把它看作是软件工厂的 **QA（质量保证）**。我们定义 Weave 团队中专家软件工程师真正关心的所有事情，这类事情如果我们在每个 PR 上进行人工审查，他们通常会提出，工程师应该随着时间学习而不再需要被提醒，但代理永远不会学习，因为它们没有那样的记忆。然后我们将这些纳入每次 PR 运行的检查中。例如，编码代理经常做的一件事是**过度抽象**。它需要做一件事，却构建了一个永远不会被使用的庞大抽象系统。所以我们有一个检查来防止过度抽象，并提供上下文和示例说明什么是好的、什么是坏的。有时代理可以从代码库中提取正确的模式，有时提取错误的模式，然后问题就复杂化了。这是对这种现象的反向压力。这也在不断演变，正如我所说，每次新模型发布都会稍微改变游戏参数。但这就是我们目前所做的。我认为结果很好。根据我们自己的产品，在最竞争激烈的细分市场（即小型初创公司细分市场）中，我们位于前 1%。这很好。

## 未来展望与建议

**主持人**：今天大多数人编写代码的方式是设置一个模型，比如 Claude Code 或 Codex，然后一直使用它，直到手动从下拉菜单中更改。你认为未来会如何运作？

**嘉宾**：我认为到目前这个阶段，不断跟进每个模型擅长什么、不擅长什么、优势和劣势是非常累人的。这就是为什么我认为每个人都会转向这种**路由器方法**。会有像我们这样的公司——希望你直接用 Weave——来利用所有这些数据，准确理解每个模型的优势，这样你永远不必切换模型，它一直在为你自动完成。其次，同样的概念会引向更深一层：如果你真正理解每个模型的优势，你实际上可以开始构建一个**比任何单个模型都更强大的路由器**。你可以汇集每个模型的优势，从而真正超越当前的前沿。

**主持人**：如果你要给一个团队中的工程师提建议，他们想成为团队里最厉害、最“AI 化”的人，带动团队其他人一起升级，你会给出什么建议？他们该怎么做？

**嘉宾**：这是个好问题，我的建议可能有点讽刺或奇怪。那就是：**不要忘记你实际在做什么**。我们不断看到，最擅长使用这些工具的工程师，也是那些最理解自己在做什么、从而能最好地引导和指挥这些工具的人。我曾非常尊敬的一个人告诉我，最好的工程师理解他们当前工作上下两个抽象层次。我认为在 AI 世界这仍然 100% 成立，只是你默认工作的抽象层次向上移动了一两个级别。当你与实际发生的事情失去联系时，你就很难避免被“垃圾浪潮”卷走。

**主持人**：自从你们创立 Weave 以来的一年半里，AI 编码发生了巨大变化。你们创立时，Cursor 是大家都在用的热门工具，现在我们生活在一个全新的宇宙。你们认为未来会怎样？一年半后 AI 编码会是什么样子？

**嘉宾**：我们总体上认为，运营一个工程团队将成为一种 **token 分配**的练习。你会找到那些最善于观察世界、感知机会并部署他们的 AI 群体来利用这些机会的人。他们有品味、有判断力，能够非常有效地驾驭这些代理。我认为，顺着模型持续改进的曲线推演，最终优秀的人未必是最擅长反转二叉树的人，而可能是那些最擅长观察世界、发现需要解决方案的问题、知道如何构建解决方案并确保其真正交付的人。

**主持人**：这是一个很好的结束点。非常感谢你们今天的分享。

**嘉宾**：谢谢邀请。
