## 开篇引入

如果有一位精通技术的工程师告诉你——他可以在同一时间让十几个 AI 代理并行开发 15 个功能，互相之间零冲突，每个代理都能产出高质量代码，自带视觉化"成果证明"，并且在合并之前会通过一个外部 AI 代码审查员持续把关，直到拿到满分的信心评分才会交给你审核——你会不会觉得这已经是科幻小说的情节？

这恰恰是"软件工厂"（Software Factory）这个正在全网病毒式传播的概念的核心。

在 Greg Isenberg 的这期播客中，Mickey 带着他的终端、PR（Pull Request）页面和一套精心设计的 Markdown 文件走进镜头，完整公开了他自己运转中的软件工厂。这不是抽象的概念科普，而是一份可以直接上手的实操指南。更重要的是，它彻底改变了我对"用 AI 写软件"这件事的认知——从前我们以为自己在指挥 AI，实际上我们只是在和一台打字机来回拉扯。

看完这期视频你会发现，"软件工厂"根本不是某个昂贵的 SaaS 产品，不是某个神秘的"超级工具"，而是——**一叠 Markdown 文件**。就是这么简单，也正因为如此简单，它才如此强大。

## 详细内容

### 软件工厂：为什么这个概念正在席卷而来 `[章节 1.1-1.2]`

**核心观点**

"软件工厂"本质上是一套让你用 AI 代理（AI agents）以"装配线"方式批量交付高质量软件的工作流程。它与具体模型、具体工具完全无关，它关乎的是你的工作流、技能包和领域知识。

**深度阐述**

Mickey 在开场就给出了一个非常直接的判断：软件工厂之所以病毒式传播，是因为它抓住了每个人心中最理想的那个开发场景——"如果你能够创造这个工厂，它能构建有价值的软件，并且日复一日地创造多个能产生收入、能改变人们生活的应用，那听起来确实太诱人了。" `[章节 1.1]`

但"软件工厂"并不是一个严谨的技术术语，它更像是对一种全新软件开发范式的比喻。Mickey 特别强调，自从这个说法火了之后，出现了很多号称"软件工厂"的初创公司。他并不想攻击任何人，但需要划清一条界限：

> "a software factory is completely harness and model agnostic meaning it doesn't matter what model you use. It doesn't matter what harness you use... a software factory is more about someone's workflow, skills, and domain knowledge and it's packed up in specific skills that they use in their development process." `[章节 1.1]`
> （一个软件工厂是完全不依赖特定工具链和模型的——你用哪个模型不重要、你用哪个框架不重要。软件工厂更关乎一个人的工作流、技能和领域知识，它被封装成开发过程中使用的特定技能。）

这段话是理解全片的基础。绝大多数人使用 AI 编程的方式可以用一条线来概括：打开 Codex、Claude Code 或 Cursor，输入需求，AI 生成代码，你看了一眼不满意，微调，AI 修改，再不满意，再修改……循环往复，直到哪天你觉得"差不多能用了"，然后部署上线。

Mickey 承认：这就是大多数人的全部流程。而"软件工厂"的意义恰恰在于——**在每个开发步骤中，我们如何最好地最大化模型的能力以获得最优输出？**"因为当我们使用"工厂"这个词时，就意味着存在某种结构、速度和流水线性质，让我能够在不丢失质量的情况下尽可能快地出货。" `[章节 1.1]`

如果非要给软件工厂一个更严谨的定义，Mickey 用了一句自嘲式的说法——"这是迈克尔·舒马赫（指极致速度）式的冗长解释了。"

**延伸思考**

这让我想到一个类比：上一波 AI 编程就像"个人手工作坊"，你有了一台强力缝纫机（模型），但你仍然是一次做一个订单，做一件衣服交流一次。软件工厂则是把缝纫机布置成工业流水线——布料进来，自动裁剪、缝制、质检、包装，最终交付。你会发现，模型代替的不只是"写代码"这个工种，而是整个软件开发流程中的每一个环节。

### 为什么重要：当智能变得普遍，效率成了分水岭 `[章节 1.2]`

**核心观点**

随着模型智能持续提升（视频中提及 GPT 6 Astra 等新模型），好的软件工厂能将模型的潜力系统化地释放，而不是让使用者在无休止的对话往返中消耗智能红利。

**深度阐述**

Greg 在听完定义后问了一个关键问题："为什么这事如此重要？" Mickey 的回答非常精炼：因为"智能正在持续提高"。拥有好模型是一回事，但你使用的是"系统化的高效率方式"还是"来回打字的聊天方式"，产生的结果天差地别。

他说："我们有令人惊叹的模型，比如 GPT 6 Astra。一个好的软件工厂允许你系统化地、以非常高效的方式使用这些模型，而不是仅仅输入文本然后继续来回反复。" `[章节 1.2]`

这句话其实内涵很深。模型的真实潜力不仅仅取决于模型本身的智商，还取决于你如何"指挥"它。绝大多数用户在低效使用模型——反复纠错、上下文丢失、让 AI 覆盖掉自己已有的工作——而少数人（比如 Mickey）已经在搭建一个完整的"指挥体系"来榨干模型每一步的效率。

**个人感受**

Mickey 在说这段话时的语气带着很强的实践者自信。他不是在讲什么宏大叙事，而是"我建议你直接看我怎么干"。这种"说不如做"的态度贯穿了整期节目，也让人更愿意听下去。

**延伸思考**

这背后是 Agentic World 的一个核心命题：将来"会不会使用 AI"不再是竞争壁垒，"会不会组织 AI"才是。就像有了工业电力之后，真正的赢家不是买更多灯泡的工厂，而是重新设计流水线的工厂。

### 进入工厂车间：Mickey 的"六文件体系" `[章节 2.0]`

**核心观点**

Mickey 的整套软件工厂只依赖五六份 Markdown 文件，其中最核心的是 `agents.md`——每当你和代理对话时，这份文件会先被注入对话上下文中，从而规范代理的行为方式。

**深度阐述**

Mickey 很慷慨地把自己的技能文件全部免费提供出来，但他同时也划了一条界线："我不想让你盲目地复制我。我希望你思考、理解这个过程，然后自己应用。"

他的软件工厂由大约 5 到 6 个文件组成，其中最重要的一个叫 `agents.mmd`。

如果你不熟悉这个文件，Mickey 解释了它的机制："它是一个 Markdown 文档，每次你与代理沟通时都会被注入到代理聊天中。每次我说'嗨'，在'嗨'发送之前，`agents.mmd` 文件会被发送。" `[章节 2.0]`

这样做的效果是：你可以通过这个文件"遥控"代理的行为方式。

Mickey 特别指出一个大多数人都会犯的错误——很多人把自己的 `agents.md` 写得毫无用处，因为他们在里面描述"代码长什么样"、描述代码库中代理已经能自己获取到的信息。还有一部分人写这个文件是为了"告诉 agent 用 TypeScript"这类基础指令。Mickey 说：如果你看我的 `agents.md`，里面是一个简单的工作流，而**这个工作流对代理来说并不是原生的**——它清楚地解释了怎么做，代理本来不知道怎么自动做这件事。这正是最有价值的地方：**你写入的应该是流程，而不是信息。**

也就是说，这个文件的本质是"给 AI 的 SOP（标准作业程序）"。

**视觉/结构信息描述**

Mickey 在介绍时不止一次暗示"在 Greg 的频道上永远会有图表"，随后果然画出了完整的流程图。这张图以"我开发的 App"作为起点，左边是一个时间轴（从最开始输入 prompt 到部署上线并获得数千用户），右侧则是"开发过程中每一步的优化"示意。用肢体语言配合图纸，他很快讲清了：大多数人的流程是一条线——依次推进每一个功能（逐个功能排队）。当你试图在同一个分支上并行推进多个功能时，冲突和混乱就爆发了——比如"我的代理删了这个文件""我的代理覆盖了这个文件"。

**延伸思考**

把人类的"作业标准书塞进 prompt 里"这个思路，听起来简单，但它代表了使用 AI 的根本态度转变：模型不是无所不知的神谕，它只是一个能力超强但没有纪律的实习生。你要做的不是问它问题，而是给它一套行为准则，让它按规矩办事。

### 第一步：隔离（Isolate）——终结代理间的"领地冲突" `[章节 2.1]`

**核心观点**

任何新功能开发都必须在独立于 `main` 分支的全新 Git Work Tree 中开始，这样多个代理可以并行工作互不侵占。这是解决"代理互相覆盖文件"问题的第一步。

**深度阐述**

在 Mickey 的 `agents.mmd` 里，第一个工作流步骤叫"隔离"（Isolate），配合一个名为 `new feature` 的技能。

他给代理的定义指令很简洁：

> "Every new feature starts in a fresh git work tree branched from origin main so agents can work in parallel without conflicts. Never build on main." `[章节 2.1]`
> （每个新功能都从 origin main 分支的一个全新 git work tree 开始，让代理可以并行工作而没有冲突。绝不在 main 上构建。）

为什么"绝不在 main 上构建"？ 这需要理解 Mickey 的深层担忧。

他做了一个非常直观的比喻。假设 App 的代码仓库是一份主文档，整个项目历经多次迭代走到今天。大多数人和 AI 代理的合作模式是"同一个 main 分支上不断堆功能"。你让代理改一下落地页，又让代理优化 API 调用速度，AI 代理和人类一样会"自作主张"——它发现"这些页面调用 API 的方式好烂啊，我来删掉重写吧"，结果当你另一个功能也在同一分支上修改时，灾难就发生了。

他说："如果你在 Twitter 上看到人们发帖，'天哪，我刚才在工作，代理删了一堆东西'——几乎总是因为人们让他们的代理在同一分支上处理不同的功能。" `[章节 2.1]`

代码之道在于，代理会完全按你说的做。它不会因为担心"可能破坏其他人的工作"而犹豫。因此技术上必须给予隔离。

**技术细节：什么是 git work tree？** 你可以把它理解为"代码仓库的一份独立副本"。Mickey 用了一个文本类比：

"你可以把它想象成复制一段文本、粘贴到一个新文档、在那个文档上工作、然后在某个时刻把它合并回原文档。" `[章节 2.1]`

当 Greg 想改落地页时，代理会创建一个全新的 branch/work tree——相当于从当前时间切片复制了一份 App 的完整副本。Greg 在这个副本上随便改。与此同时，Mickey 想优化 API 调用，也有自己的副本。这两个代理在同一时间、同一个项目里干活，但**互相完全隔离**。当双方都完成时，再各自把分支合并回主文档，自然不会冲突——因为从来没在同一个工作副本上动过手。

这种工作方式带来的能力跃迁是显著的。Mickey 现场打开自己的终端（Bezel 终端）展示：**四个标签页在跑，三个已经完成了任务——他同时在同一个 App 上开发四个不同的功能：一个做一个邮件客户端、一个做一个 Linux 计算机环境、一个在做落地页更新。** 而他的工作流程中还有 15 个不同的代理子代理同时在推进 15 个功能。

"这能让我的多个代理并行快速出货。" `[章节 2.1]`

**个人感受**

Greg 在这个过程中插了一句非常有意思的话。他说："如果你真的有一个工程师团队，你显然不会让所有人都在 main 分支上直接 push。说不通。现在的关键是——大量非技术人员开始构建应用，他们撞上了这个墙。你说的不仅仅是'代理重叠'的技术问题，而是如何把与代理合作的方式结构化，让它更像一个团队。"

Mickey 听完先是半开玩笑地承认："你说得太对了，'团队（team）'比我起的'隔离（isolate）'这个名字好多了……隔离听起来像是什么乳清蛋白。" 两人一笑，Greg 风趣回应："所以我是做营销的，你是做工程的。" `[章节 2.1]`

这段对话道出了非技术创业者当前最大的痛点：他们被 AI 赋了能，却不知道如何"管理"AI。隔离/分支这个动作，恰好是把"AI 团队协作"落到实处的第一步。

**精华收获**：不要在一个分支上同时让代理干多件不相干的事。每一次功能开发，都应该是一个独立的"工作副本"，完成后再合并。

### 第二步：构建（Build）——"能跑"不等于"写得好" `[章节 2.2]`

**核心观点**

在"构建"阶段，Mickey 用 `code structure` 技能要求代理以"服务层架构"（Service Layer Architecture）的方式编写代码。这是为了让代码易于人类开发者接手、易于其他 AI 代理快速理解，避免模型产出"不可维护的脏代码"。

**深度阐述**

Mickey 说，模型们在"做事"上非常强，但"方式"不一定是最好的。"尤其是在写代码的时候。"

他点评了几个模型的表现："Fable（音译）可以说是第一批真正让我觉得'这写得比我见过的一些最好的工程师还棒'的模型之一。但即使是 Astra——那个工作马、最强大的模型、我最喜欢的模型——它有时做出的代码质量决策也让人挠头（hmm）。” `[章节 2.2]`

这是一个很深刻的观察：一个天才，如果不给出清晰的编码规范，也会写出乱七八糟的代码。模型和人类没有区别。

> "The model is just getting it done and if it could get it done in a sloppy way it'll get it done in a sloppy way." `[章节 2.2]`
> （模型只是想把事情做完；如果它能用草率的方式做完，它就会用草率的方式做完。）

那 `code structure` 技能究竟做了什么呢？Mickey 解释了：它要求代码以所谓的"服务层架构"来编写。他没有深入展开（"不把大家讲无聊"），但点明了核心收益：

> "基本上就是，如果某天你需要人类干预，雇一个开发者，他很容易上手；或者你自己是开发者，你也很容易接手。甚至对你的代理而言，它们回到代码里阅读时也会说，'哦，这合理啊。'" `[章节 2.2]`

他分享了一个亲身体验：他曾经让 GPT 5.6 Soul（转录名称）写了一段代码，代码能运行、能实现功能。可是当他让 Fable 审查这段代码时，Fable 的评价是："这真恶心——有重复代码、函数散落各地、有死代码。" 然后 Mickey 总结出一句贯穿全片的话：

> "Just because it works doesn't mean it's written well." `[章节 2.2]`
> （能跑，不代表写得好。）

代码结构技能给了代理"如何写代码"的准则，让它在“能跑”的基础上"按照规范写"。

他补充了一个具体例子：他正在开发一个 App，其中有个功能是做一个"技能仓库"，让多个代理连接并把技能存储到 App 中。他告诉代理"给我构建这个"。代理在写代码时不断引用 `code structure` 技能，于是生成的代码结构清晰。Mickey 说："万一我需要雇个人来审查代码，它不会是一堆让人摸不着头脑的垃圾，然后让人过度收费。它写成了一种开发者能理解的方式。"他还强调："我发现在没有你代码库上下文的另一个代理，也能非常容易理解这个代码。" `[章节 2.2]`

**个人感受**

Mickey 并不是在推销某种复杂的企业架构，他的核心思路是"让代码干净到无需解释"。服务层架构不一定是最先进的架构，但它足够约定俗成，能让人类和 AI 都快速建立心智模型。这体现了一个重要的务实原则：开发的真正目标不是写出"最聪明的代码"，而是写出"最容易理解和验证的代码"。

**延伸思考**

这一步让我意识到，AI 生成代码的可维护性问题正在成为实际瓶颈。"能跑就行"已经不再够用。如果一个项目的代码混乱到连另一个 AI 代理都无法阅读理解，那它就不可能进行大规模的并行开发。**代码结构本质上是一种"沟通协议"**——你不仅是在和计算机交流，也是在和未来的 AI 协作伙伴交流。

### 第三步：证明（Prove）——代理不能只发"口头承诺" `[章节 2.3]`

**核心观点**

代理必须具备"证明自己工作"的环节：要么录制修复前后的视频或截图（视觉证据），要么给出可衡量的数字/测试结果。这一步用"眼见为实"取代了"我以为它工作了"。

**深度阐述**

在构建完成后，第三个步骤是"证明"。Mickey 对这个步骤表达得极为生动：> "Agents can't pinky promise." `[章节 2.3]` （代理不能跟你拉钩上吊。）

他解释说，大多数模型（GPT 6 Astra 是个例外——那是"最不容易幻觉的模型"，是一个能力的巨大飞跃）你都能推动它们撒谎。有时候它们甚至直接坦白："哦，我意识到我实际上没做这个工作。" 所以，你必须在流程中强制代理"证明它做了它说的那件事"。

这个步骤核心有两个技能：

**技能一：Evidence-Driven Testing（证据驱动的测试）**
如果机器有录制屏幕能力，它会真实记录"前状态"和"后状态"。比如在修 bug 时，它会先录下 bug 复现的过程；修完后，再录一个能跑通的版本。Mickey 说："因为你会很惊讶——有时候代理写了代码，以为它能跑，但实际上它根本没测试过、没证明过，它只是告诉你它跑通了。" `[章节 2.3]`

**技能二：Before & After（前后对比）**
如果机器不具备录制能力，代理会用截图或视频来展示改动前后的界面。Mickey 现场打开了一个 PR（Pull Request）来演示——这不是他做的，是他的代理做的。

这个 PR 要求代理"创建一个管理员邮箱页面并连接到我有过的邮箱服务"。代理在 PR 里展示了 before 状态——那个页面根本不存在；以及 after 状态——页面出现了，而且连上了服务。

"我开发的每一个功能，做的每一个 PR，都会得到 before 和 after。这帮助我……说实话，我现在不读我所有的代码了。可能随便看看：'哦它做完了，随便看一眼'。" `[章节 2.3]`

Greg 插话总结："这是在浏览一下情况。" Mickey 坦然承认："老实说，现在我连翻阅代码的次数也越来越少了。我花更多时间在前端工作中，确保它遵循我的代码结构技能，并确保拿到 before 和 after 截图。" `[章节 2.3]`

他接着又展示了一个更极端的例子：一个"给代理一台电脑"的功能。第一次运行完全失败——"什么也没跑起来"（画面上什么都没发生）。Mickey 对代理说："这没成功。使用技能，使用工厂机制。"然后代理回去重写，再次提交时就提供了"实际正在使用 App"的 after 截图。

更有意思的是，这个"证明"环节是自我强化的：代理提交 before 和 after 后，有时它会发现"噢，我看了下 after 截图/视频，我其实没真正完成这个功能。" 然后它自己做回"构建"步骤——继续干。它不需要 Mickey 下指令，因为技能规则写得很清楚：当前后对比标准没满足，就得回去继续构建。

**非可视化证据的例子**

Mickey 预料到观众的疑问："如果这个更改不是视觉化的呢？" 他立刻演示了一个性能优化场景。有个 App 点击不够跟手（not snappy）。他让代理修复。代理交上来的 PR 里包含了一个速度测量：优化前，某页面加载耗时 **815 毫秒**。Mickey 痛心疾首地评论："这在 Web 开发中是种罪过。这种事不该发生。" 这个代码还是 GPT 5.6 Soul 写的——很强大的模型，但它制造了 815ms 的加载时间。代理优化后把数字降到了 **60ms**（中间还有 81、76 等数据）。于是 PR 里有了确凿的数字证明：815 → 60。

**视觉/结构信息描述**

视频中 Mickey 展示了好几张 PR 截图。第一张展示一个"避免重复工作"的 PR：描述区顶部是 before 截图（大量空白或报错状态），紧接着是 after 截图（系统正常工作）。第二张是一段 Cursor Cloud Agent 的使用录像，视频名为 "Proof of Improvement"（改进证明）。第三张是 Greptile（代码审查代理）对 PR 的反馈面板，上面有它的审阅意见和"置信度（Confidence）"评分。最后一张是性能优化 PR，里面有浏览器开发者工具的加载时间数据。这些截图让人直观地看到：软件工厂的"产出物"不仅是代码，而是一套"可视化的可信度档案"。

**个人感受**

这一段是整个节目最令人兴奋的部分。Mickey 把"代码审查"这个通常在专业团队中才存在的角色，提炼成了 AI 代理的可执行任务。他彻底解决了"非技术人员如何信任 AI 产出"的难题——你不需要理解代码，你只需要看截图、看数字。就像他在和 Greg 的对话中说的："这几乎是给千禧一代和 Z 世代准备的东西，像刷 Instagram 或 Snapchat 的照片墙一样。" Greg 随即补了一句画龙点睛的话："它就是像挨个点击 stories 一样。" `[章节 2.3]`

**延伸思考**

这个"证明"环节对于 AI 时代的软件工程有深远意义：它第一次让"过程可审计"成为可能。传统软件开发的信任建立在"人"之上——看这个人靠不靠谱；而 AI 时代，我们建立在"证据"之上——只看它干的事，而不是听它说的话。这也正是 AI 代理真正可以规模化替代人类工程师的关键：它们能不能自我证明，决定了它们能不能被赋予更大的自主权。

### 第四步：发布（Ship）——用 AI 审查 AI，形成质量闭环 `[章节 2.4]`

**核心观点**

在"发布"阶段，Mickey 使用第三方代码审查代理（如 Greptile）来评估 PR，获得一个 1 到 5 的"信心分数"。如果分数低于 5，代理会自动回到"构建"步骤修改，再"证明"，再提交审查，循环直到满分——然后 Merge 按钮会留给人类按下。

**深度阐述**

Mickey 将自己最后一个步骤称为"Ship"，对应技能叫"GP Loop"（采用 Greptile，转录中写作 Gretile/Grapeile/Gravile）。GP Loop 是 Greptile 提供的一个技能。Mickey 强调："你并不需要一定要用一个代码审查代理，但如果你真的认真地构建一个会被用户使用的软件，我强烈建议你用某种代码审查代理。" `[章节 2.4]` 他的最爱是 Greptile，但他也提到 CodeRabbit、Macroscope 等很多优秀的选择。

**GP Loop 的工作方式**：
1. 代理打开一个 PR，在描述里嵌入 before/after 的证明——每当变更存在"可见表面"时，提供截图；没有可见表面时，提供数字或测试结果（measure numbers or output pairs）。
2. Greptile 会自动对 PR 做出评审：给予摘要、给出反馈建议。
3. Greptile 会给出一个信心分数——5 分制（转录为 five out of five）。
4. 如果分数是 3/5，这意味着"代理错过了某些东西，需要去看看"。
5. GP Loop 的技能会自动触发一个循环流程：`Build → Prove → Ship → 获得新分数 → 如果分数还低，回到 Build`。这是一个**自动循环**，不需要人类写"GP Loop"命令。如果你改了 10,000 行文件的代码，还有一种 "gre loop apps" 变体自动激活。
6. 当 Greptile 报告 5/5 时，就意味着所有已提出的评论都得到解决。代理最终只做一件事：展示 PR 链接。
7. 而人类（Mickey）的任务非常轻量：**点击 Merge 按钮**。合并后，代码回到主版本中。

Mickey 用一张流程图清晰地展示了这一循环：Ship → 跑 Greptile → 拿到反馈和评分 → 如果评分低于5，回到 Build → 改完再 Prove → 再 Ship → 等待新分数。反复递归，直到拿到五瓜满分，才把交接棒交还给人类。

这其实是把 "CI/CD"（持续集成/持续交付）中"代码审查"这一环节，完全自动化、代理化了。

他在视频中还展示了一个实际的 PR 实例：Greptile 对某个 PR 的初始反馈指出了一些问题——分页有问题、某些菜单空间没有保留（"some menu space wasn't preserved"）。Greptile 给出的初始信心分数是 3/5。然后 Micky 的代理自动消化了这个反馈，回去修改，再次提交后，分数变成了 4/5。又抓到了一些问题，循环再转一轮，最后达到 5/5。而且在这些循环中，**人类从不参与技术修改**——只有审批人（Mickey）看到满分的时刻才出场。

Mickey 随后给出了这个体系如何撑起"并行规模"的数据："我在同时处理 15 个不同的功能、不同的代理和子代理时，用的就是这个流程。" `[章节 2.4]`

**个人感受**

这一段最令人震撼的不是技术本身，而是它传递的态度：**模型写出的代码必须经过"独立评审员"的验证才可以合入。** 这与许多 AI 创业者"写了就上线"的随意态度形成了鲜明对比。Mickey 的态度近乎匠人："我们提供服务时很认真；但为什么一到写软件就仿佛毫不关心？" `[章节 2.4]`

**精华收获**：使用代码审查代理（Greptile, CodeRabbit, Macroscope）是成本极低、收益极高的习惯。许多这类服务有慷慨的免费额度，对严肃的产品开发是纯赚。

### 工厂全面运转：四步闭环的可视化 `[章节 3]`

**核心观点**

把四个步骤串起来后，软件工厂就像一条流水线：隔离 → 构建 → 证明 → 发布，且"发布不达标"会自动回流到"构建"。从逻辑上讲，这是对一家现代软件公司的完整模拟。

**深度阐述**

Greg 在听完 Mickey 的完整讲解后，给出了一个非常有洞察力的总结——他把软件工厂重新翻译成了一座**实体工厂**的运转逻辑：

> "第一步 isolate 就像工厂接受一个定制订单，给它一个独立的工作站，保证它不会干扰生产线的其他部分。" `[章节 3]`
> "第二步 build 就是装配线——代理在切割、焊接、组装、接线。在软件中，就是写代码、改文件、添加结构。" `[章节 3]`
> "第三步 prove 就是质量控制——在货物出厂前，必须有人测试：它能通电吗？合身吗？压力下会坏吗？" `[章节 3]`
> "第四步 ship 就是产品出大门。可能还要合并 PR、部署、写 release notes，如果没过质检，就回流再来一轮。" `[章节 3]`

Mickey 听了之后甚至有点自嘲地承认："我可能真的要把所有名字改成你说的这套说法，因为我忽然意识到我的命名确实不太行。Greg 说的就是这个逻辑。" `[章节 3]`

随后他进一步补充了一个当今奇特的现实：

> "a software factory is literally just a bunch of markdown files." `[章节 4]`
> （一个软件工厂，真的就只是几个 markdown 文件。）

他强调自己并不是在贬低那些做"软件工厂产品"的初创公司——但他要讲清楚概念的本质：**软件工厂不是产品，不是特殊的框架，不是某个公司"做了一个软件"的事，它就是你工作流里的几份提示词文档。** 然后他随口丢下了另一个炸裂观察：

> "Some startups are now an agent with a couple markdown files." `[章节 4]`
> （有些初创公司现在已经成了一个AI代理 + 几个Markdown文件。我们已经真正进入那个时代了。）

**延伸思考**

这段对话最醍醐灌顶的地方在于：**当你把软件开发拆解为"款式设计（Agent.md）→分配工位（隔离）→加工装配（构建）→质检（证明）→独立质检机构（代码审查）→包装发货（合并部署）"之后，软件工厂的精髓不再是代码生成，而是管理结构。** 你在用文档定义了一个组织的行为准则，而模型只是组织里可替换的工人。不管以后模型升级到第几代，这套工厂流程都能适配——这就是"模型无关（model-agnostic）"的真正含义。

### 深入指南：如何开始搭建你自己的软件工厂 `[章节 2.1-2.4 综合]`

**核心观点**

你不需要购买任何新工具，不需要写几万行代码，只需要准备几份 Markdown 文件，并按"隔离 → 构建 → 证明 → 发布"四步来设计你的代理行为。

**深度阐述**

这一节是给想要立刻行动的人准备的"操作地图"。整套系统完全可以用你现有的工具组合来实现：

1. **你的 Agents.md 文件应该写什么？**
   - 不要写代码库中已有的信息（代理想查自己会查）。
   - 要写"代理原生的不自然会做"的工作流指令。
   - 核心是流程纪律：如何分支、如何写代码、如何证明、如何发布。

2. **隔离的落地方法：**
   - 在 `agents.md` 中写入：所有新功能都从一个新的 git work tree 开始，从 origin/main 分支。绝不在 main 上构建。
   - 这样做的结果：你可以同时开多个代理、多个终端，每个代理有自己的独立副本。
   - 不要在一个分支/一个工作副本上同时给代理分配多个任务。

3. **构建的落地方法：**
   - 在系统提示或技能文件中，明确指定代码结构标准（如 Service Layer Architecture）。
   - 示例指令："代码需要分层；业务逻辑写在服务层；控制器/路由层保持薄；不允许有重复函数、死代码。"
   - 目标：让代码"人类可读、AI 可读、可维护"。

4. **证明阶段的落地方法：**
   - 写一个 `evidence-driven-testing` 技能：要求代理在操作系统支持时录制屏幕前后状态。
   - 无法录制时，要求通过截图/视频提供 before/after 证据。
   - 如果是性能改动，要求给出量化对比（x 毫秒 → y 毫秒）。
   - 设定规则：如果代理在自检后认为证据不合格，必须自动回到构建步骤。

5. **发布的落地方法：**
   - 集成 Greptile（或任意代码审查代理）作为第二道质检。
   - 代理在 PR 描述里嵌入证明，让 Greptile 用 1~5 分的信心分数来反馈。
   - 在流程中写入规则：当评分未达 5/5 时，代理自动进入"构建→证明→发布"的循环。
   - 只有当 5/5 出现，人类才去点击 Merge。

**关键注意点：**
- Mickey 特别说明，他的所有技能文件都是免费公开的，但他不希望观众"盲目照抄"。这套体系是从他自己的开发习惯里生长出来的，别人必须理解后内化成自己的方式。
- "模型无关"和"harness 无关"意味着这套方法可以搭配 Cursor、Claude Code、Codex 等任何前端工具，任何模型都适用。
- 推荐的模型（转录中原话）：GPT 6 Astra（"最强大的模型，我的最爱"）、Fable（"写出过我看过最好代码的模型之一"）。转录中还提到 GPT 5.6 Soul 等。
- 推荐的代码审查代理：Greptile（最爱）、CodeRabbit、Macroscope。

**延伸思考**

软件工厂的规模限制在哪？Mickey 目前已经并行 15 个功能。理论上，只要有足够的算力和清晰的仓库管理，这个数字还能继续扩展。但真正的瓶颈可能是**人类的审批带宽**——即便你只看截图、点 Merge，上百个代理同时产出时，你还是会应接不暇。所以，我猜测下一代软件工厂会把"Merge"这个动作也完全自动化，让人类只处理那些"5/5 但仍然不符合业务意图"的边缘情况。也许那个时候，我们连看 stories 都不用了。

## 总结：软件工厂是通往 Agentic 世界的一小步

这期视频给我的最大冲击是：**你不需要等到未来的某个工具出现，才能建立自己的 AI 软件工厂。** 你已经拥有跑通整套流程的一切条件——Markdown 文件、Git 分支、一个终端、几个代理，和一份高质量的外部评审。

Mickey 不仅公开了他的整个方法论，而且态度极其务实——他大方地把技能文件免费放出来，却坚持强调："不要盲目复制我，要成为你自己的工厂主。" 这份分享精神非常珍贵。

Greg 在节目结尾说了一句很有分量的话："像你这样的人愿意分享这些，太酷了——因为它是真正值得分享的东西。" `[章节 4]`

最后，记住 Mickey 反复强调的那句格言：**"能跑，不代表写得好。"** 在 AI 代编码的时代，这句话比以往任何时候都更有分量。软件工厂的真正目的，不是生产更多代码，而是**生产更多值得上线的软件**。
