# 搭建真正可用的软件工厂：从隔离到交付的完整实战指南

## 什么是软件工厂？为什么它会爆红？

**软件工厂**，本质上是一个让你能够借助 AI 智能体（Agent）真正交付软件的概念——而且交付的软件丝毫不粗糙。你可以把它想象成一条**组装流水线（assembly line）**：只不过你生产的不是实体产品，而是软件。

> 如果你能创建这样一座工厂，让它持续产出有价值的软件，并打造出多个能创造收入、为人们生活增添价值的应用——那听起来确实很棒。

在今天的节目中，Greg Isenberg 请来了 **Ross Mike（Mickey）**，由他完整讲解整个流程。看完这期节目，你将学会如何亲手搭建自己的软件工厂。

> 这个概念会爆红是有原因的。我们片尾见。

## 软件工厂的定义：不是产品，而是一套工作流

当“软件工厂”这个词出现后，已经有不少创业公司开始用它。Mickey 强调，他无意贬低任何人的事业，但：

> **软件工厂与工具链和模型完全无关**——你用哪个模型不重要，你用哪个工具链（harness）也不重要，它都应该能正常工作。

为什么？因为软件工厂本质上关乎一个人的**工作流（workflow）、技能（skills）和领域知识（domain knowledge）**，并且被封装成开发流程中使用的特定技能。

Mickey 让大家回想一下最近一次构建应用的过程：

1. 你打开 **Codeex、Claude Code、Cursor** 之类的工具
2. 直接输入：“我想构建这个”
3. 它帮你搭建了出来
4. 你看了一眼，不满意，然后做了一些修改
5. 再看看改动，也许满意了
6. 部署到 **Vercel** 或发到生产环境，搞定
7. 或者继续不断迭代

这就是整个过程。

软件工厂的全部意义在于：**在开发流程的每一个步骤中，如何最大限度地发挥模型的能力，获得最好的输出？同时，又如何保持速度？**既然用了“工厂”这个词，就意味着存在某种结构、速度和流水线属性——让我能在不牺牲质量的前提下尽可能快速地交付。

> 这就是“软件工厂”那种又长又啰嗦的 Michael Schumalis 式翻译版定义。希望还没把大家讲晕。

**Greg**：非常完美，我完全理解了。

## 软件工厂的地基：agents.mmd 文件

Mickey 的软件工厂由大约**五到六个文件**组成。其中一个是 **agents.mmd 文件**。

什么是 agents.mmd 文件？它本质上是一个文档、一个 Markdown 文件，**每次你与智能体通信时，它都会被注入到智能体的对话中**。也就是说，每次 Mickey 说“你好”，在“你好”被发送之前，agents.mmd 文件会先被发送进去。

这个文件最酷的地方在于：**你可以用它来规定智能体应该如何行动。**

Mickey 提到，他们不久前做过一期视频，讲的是大多数人的 agents.mmd 文件其实没什么用——因为人们把“代码长什么样”这种智能体本就可以从代码库里获知的信息写进去了。但 Mickey 的文件里是一个**简单的工作流**。这个工作流不是智能体天生就懂的，所以文件清晰地说明了该怎么做。

接下来，他逐步拆解了这个工作流的每一个步骤。

## 第一步：隔离（Isolate）

有一个技能叫 **new feature（新功能）**，它的规则是这样的：

> 每个新功能都从**全新的 Git 工作树（fresh git work tree）**开始，从 origin/main 分支出来，这样智能体就能并行工作而不会产生冲突。永远不要在 main 分支上直接构建。

如果你知道 Mickey 会出现在 Greg 的频道上，就一定知道：**这里总要画图的**。所以，我们要开始画图了。

### 为什么需要隔离？

用一张图来理解：假设你正在开发一个应用，从一开始提示词起步，到后来上线生产环境，拥有了几千名客户。

大多数人使用智能体的方式是：在应用发展的每一步中，一个功能接一个功能地构建——这是一个非常**线性**的过程：一次一个功能，一次一个功能。

而一旦你尝试同时处理多个功能，就会出现冲突、出现各种问题：比如“我的智能体删掉了这个文件”“它覆盖了这个文件”……

步骤一“隔离”解决的就是这个问题。

### 隔离的运作方式

假设 Greg 说：“我真的不喜欢我们的落地页。”而 Mickey 说：“我们的 API 调用可以再快一点。”

当 Greg 开始做他的功能时，智能体会根据 agents.mmd 的指示，去创建一个**新分支（branch）**。

可以把分支理解为应用在那一刻的**复制粘贴**。分支上的工作树（work tree）基本上就是应用的一份副本——就像你复制一段文本、粘贴到新文档里，在那个新文档上编辑，最后再把结果合并回原文档。

所以 Greg 有了他的新文档，在那个文档里开发这个功能。与此同时，Mickey 还有另一个功能要开发——他可以同时进行，也可以不同时间进行，因为 Mickey 也有自己的分支。

**关键点在于**：Mickey、Greg，或者第三个人，甚至你一个人同时开 **50 个智能体**，都可以并行处理多个功能，而不会出现一个智能体越界覆盖另一个智能体工作的情况。

### 问题为什么会发生？

这种情况经常发生。如果你在 Twitter 上看到有人说“我正在做什么，结果智能体删了一堆东西”——几乎总是因为：**他们让所有智能体在同一个分支上处理不同的功能**。

要知道，智能体会百分之百按你说的做。你让它更新落地页，又让它加速 API 调用；它于是发现：“哦，这些页面调用 API 的方式太糟糕了，让我删掉重写。”可它同时又在改那个页面的设计。于是问题开始出现。

**隔离**让 Mickey 能够在同一时间**并行处理多个功能**，而不会出现智能体互相踩踏的情况。

这是 Mickey 工作流的第一步，而且这一步**不是智能体原生具备的能力**，所以它非常适合写进 agents.mmd 文件里。

当 Greg 或 Mickey 完成时，只需把这些改动合并回主文档。因为大家最初都是在副本上工作的，所以合并时不会产生冲突。

### 现场演示：四个并行的功能

Mickey 现场展示了终端：他的 **Bezel** 终端开了四个标签页，其中三个已经完成——他同时在一个应用上开发 **四个不同的功能**：

- 一个在做**邮件客户端**
- 一个在做**计算机环境（Linux 环境）**
- 一个在做**落地页更新**

正因为有了隔离，他才能自信地并行推进这些工作。这不是智能体天生的能力，而是 **agents.mmd 加 new feature 技能**赋予他的。

### Greg 的共鸣：这就像一支真正的工程师团队

**Greg**：我完全明白了。我是这样理解的：如果你真的有一支工程师团队在开发应用，你显然不会让所有人直接往 main 分支上推送代码——那根本说不通。我是非技术背景，而现在突然有大量非技术背景的人开始开发应用，然后撞上这个问题。

你说“偶尔会发生智能体覆盖东西”——其实真相是，**95% 的情况下，只要你一直在开发，智能体就会搞砸、就会覆盖东西**。所以这一步对我来说非常有意义。而且它背后有一个更大的想法：**如何把你与智能体协作的方式，结构化得真正像一支团队，而不是一盘散沙。**

**Mickey**：没错。而且“团队（team）”这个名字比“隔离（isolate）”更好。（笑）

**Greg**：所以我是做营销的，你是做工程师的嘛。（笑）

**Mickey**：对，本质上就是这样。“隔离”听起来像某种乳清蛋白粉……如果你们去看链接的话，很快会看到一次改名更新。但这个能力真正的作用是：让我可以同时让多个智能体处理不同任务，而不会互相越界。

他补充说，还有一个清理流程他没有展开：一旦分支上的工作被合并，工作树就会被删除，诸如此类。

**这就是步骤一。**

## 第二步：构建（Build）

步骤二是**实际的构建工作**。这里用到的技能叫 **code structure（代码结构）**——Mickey 很早就分享过这个技能，现在它已经成了他工作流的一部分。

### 为什么模型写代码需要准则？

我们很快会聊到模型。但先说一点：**模型很擅长“把活干完”，但未必会以最好的方式完成它——尤其是在写代码的时候。**

- **Fable** 可以说是第一个让 Mickey 惊叹“这比我见过的一些最优秀工程师写得还好”的模型，它写出来的代码质量真的很高
- 但即便是 **Astro**——那个“工作马”般最强大的模型、Mickey 最喜欢的模型——它做出的某些代码质量决策也令人皱眉

这不是模型能力不够，而是模型只求“把事做完”。如果能用潦草的方式完成，它就会用潦草的方式完成。

### code structure 技能做什么？

这个技能要求按照**服务层架构（service layer architecture）**来写代码。不深入细节，简单说就是：代码以一种**任何人都容易接手**的方式被组织起来——

- 如果需要人工介入，你雇一个开发者，他能很快上手
- 如果你自己就是开发者，你也能很快上手
- 甚至你自己的智能体，回过头来读这些代码时，也会觉得：“哦，这写得很有道理。”

Mickey 举了个例子：他让 **GPT-5.6 Soul** 写过代码——功能可以跑，能达到目的。但当他让 Fable 来审查时，Fable 的评价是：“**这写得太糟糕了。**到处都是重复代码，函数散落一地，还有死代码。”

> **能跑，不代表写得好。**

这个技能就是给智能体一套**写代码的准则**。

### 实战案例：技能仓库功能

回到那张图：在开发一个新功能时，第一步是隔离，第二步就是构建。在构建过程中，会用到 code structure 技能。

Mickey 正在做一个应用，其中一个想做的功能是**技能仓库（skills repository）**：让他不同的智能体连接到这个应用，并把技能存储进去。他告诉智能体：“帮我构建这个。”

在写代码时，智能体持续参考 code structure 技能，于是代码以一种 Mickey 自己可以审查的方式被写出来。万一他需要雇人来审查代码，也不会面对一堆乱七八糟、让人困惑、趁机乱收费的“垃圾代码”——代码是按开发者容易理解的方式写的。

而且他发现：即使你用另一个对这个代码库没有上下文的智能体来接手，它也能理解得很好。

所以流程是：

1. **第一步：隔离**（名字确实起得不好）
2. **第二步：构建**

所有这些步骤都以一种**有主见（opinionated）**的方式执行，让智能体能够快速行动，并且尽可能地把事情做到最好。

## 第三步：证明（Prove）

**Greg**：继续说。

**Mickey**：步骤三叫“**证明（prove）**”。关键在于：**智能体是不能发“君子协定（pinky promise）”的。**

如果你不断逼问，大多数模型（先说明，GPT-6 Astra 之所以是模型能力上的一大跃升，就是因为它几乎是最少幻觉的模型——这很了不起）是可以被推着去撒谎、或者相信某个根本不存在的成果的；有时候它会直接坦白：“哦，我发现我其实没做这项给你。”

所以 Mickey 要求智能体去**证明它做过的工作**。这可能是他最喜欢的技能。

这部分涉及两个技能：

### 技能一：基于证据的测试（Evidence-driven Testing）

如果机器有能力执行，它会：

1. **记录“之前”的状态**——比如在修复一个 bug 之前，把 bug 实际发作的过程录下来
2. **记录“之后”的状态**——修复完成之后，记录一个正常工作的版本

这就是基于证据的测试：它**证明了修复确实发生了**。

因为你会惊讶地发现：有时候智能体写了代码，自认为它能跑，但它既没有测试、也没有证明它能跑，就口头上告诉你“它好了”。

Mickey 必须确保智能体真正证明它的工作。

### 技能二：前后对照（Before and After）

但如果你的机器没有能力做上述记录呢？那还有另一个技能叫 **before and after（前后对照）**。

Mickey 现场打开了一个 PR 来演示：

> 这是一个我的智能体创建的 PR，不是我做的。

他当时的任务是：让智能体创建一个**管理员邮件页面**，并连接到他自建的一个邮件服务。看看智能体做了什么：

- 它展示了**之前的状态**——页面根本不存在
- 它展示了**之后的状态**——页面存在了

因此，他开发的每一个功能、提交的每一个 PR，都会附带一份**“之前 vs 之后”**的对照。

### 为什么这能帮上忙？

Mickey 很坦诚：**他现在已经不怎么读代码了。**他可能会想：“好，它做了这个……让我看看……”但其实只是随便扫一眼。

> 老实说，现在连扫都扫得越来越少了。他目前主要做的是前端工作：确保代码符合 code structure 技能，确保拿到前后对照截图。

他还展示了另一个更典型的例子：他在做一个**“给智能体一台计算机”**的功能，但最初就是跑不起来。第一次运行失败——他甚至还没有搭好自己的软件工厂。他在另一台机器上工作，代码推上去却不工作，截图里什么都没有。

他对智能体说：“没成功。用那些技能，用工厂流程。”然后就有了“之后”的截图——功能真的跑起来了。

### 工厂的自我修正循环

所以这些技能——proof 和 before and after——**迫使智能体给出事实性的、可视化的前后对照证据**，无论是视频还是截图。

而且有时候会发生这种情况：智能体先做了“之前”，再做“之后”时，它会自己发现：“哦，我看了之后的截图（或视频），我其实并没有真正完成这个功能。”

于是它会回到哪一步？回到——**构建**。

> 这就是工厂的循环特性。Mickey 不需要说：“你前后对照失败了，去把它做完。”技能的描述本身就写得让智能体知道：前后对照的标准还没达到，我必须继续构建。

这让 Mickey 能拿到一份**可视化的成果呈现**。这让评审变得容易得多——尤其是对非技术背景的人：你只需要看看几张截图或一段视频就够了。

所以，在构建过程中，最终他会收到一个带前后对照的 PR。即使他可能看不懂里面那些“技术黑话”，PR 也会解释、也会展示出可视化的证据，证明工作已经完成。

### 非可视化怎么办？性能优化的案例

Mickey 知道有人会问：“如果证据不是可视化的呢？”

于是他展示了另一个性能优化的 PR。他正在开发的一个应用里，**点击不够跟手**。现在大家看到的已经是一切都很灵敏、加载很快的样子——但直到他告诉智能体“修好它”之前，都不是这样的。

智能体修好了，并且确实给出了截图。但如果某种改动无法用截图展示呢？**智能体就会编写测试，然后给出测试结果。**

在这个案例中：

- 它测了页面加载速度的“之前”状态：其中一页花了 **815 毫秒**
- 这在 Web 开发里简直是一种罪恶，这不该发生
- 需要注意的是，这段代码是由 **GPT-5.6 Soul** 写的——好模型，但依然需要审查
- “之后”状态：加载时间被降到了 **60/61 毫秒**

于是，在评审过程中，Mickey 又拿到了智能体“确实做到所说之事”的实际证据。

### Greg 的洞察：智能体管理者与“刷故事”

**Greg**：如果你要建立一个软件工厂，**信任**显然是其中非常重要的一部分。我想你真正在说的是：如果你要让这么多智能体去构建功能、构建应用，你就必须能够信任它们创造出来的东西。

所以，你展示的这几个技能，让你可以扮演**智能体管理者（agent manager）**的角色——在这个场景里，Mickey，你就是那个管理者。你不再深扎在代码里，你只是在看发生了什么。

而且前后对照这种可视化素材，对千禧一代和 Z 世代、对习惯刷 Instagram 快拍或 Snapchat 快拍的人来说特别友好。**这几乎就像你在一条一条地点着看快拍。**

**Mickey**：是的，没错，就是这样——它完全是碎片化（bite-size）的信息。这让我能够与智能体建立信任。

## 第四步：交付（Ship）

最后一步是交付（ship）。

前面已经提到了 before and after，但这里还有一个叫 **GP loop** 的技能，它使用一个第三方服务——**Grepile**（代码审查智能体）。你并不一定非要用代码审查智能体，但如果你是认真的，要构建一个面向真实用户的软件，Mickey **强烈建议**使用某个代码审查智能体：

- **Grepile** 是他最喜欢的
- 市面上还有很多优秀选择：**CodeRabbit、Macroscope** 等等

### GP loop 如何运作？

用实例说明：Grepile 会在 PR 上留下总结，然后给出反馈。

比如，在某一次 PR 上，它给出了最初的反馈，指出了一些问题：

- 分页（pagination）有问题
- 一些菜单的间距没有被保留

这些反馈意味着写代码的智能体漏掉了这些细节。这没关系——人也会漏。

关键在于：**Grepile 不仅给反馈，还会给一个置信度评分（confidence score）。**

- 现在这个 PR 是 **5/5**——因为反馈被处理后，可以看到 Mickey 的名字以及那一行注释，说明反馈已经被解决
- 但在反馈被解决之前，评分是 **3/5**

这个评分告诉智能体：“你漏了东西，你需要去看一看。”

### GP loop 技能的自动化流程

GP loop 技能（顺带一提，这一切都是**自动发生**的——不需要有人去写“gp loop”，智能体会自动执行）会这样运作：

1. 打开 PR，并在描述中嵌入**前后对照的证据**
   - 当改动有可见界面时：给出截图或视频
   - 当改动没有可见界面时：给出测量数值或输出配对
2. 运行 GP loop 或 **GP loop apps**
   - 区别在于：如果你的文件变更超过 10,000 行，gp loop apps 技能就会激活
   - 你完全不用担心，智能体会自己判断并执行
3. 在 Grepile 给出 5/5 之前，持续处理未解决的评论
4. 最后，以**提交 PR 链接**作为完成标志

这意味着：智能体拿到反馈后，会回到**构建**。

### 一个良性的循环

我们来看这个循环：

- 我们在“构建”阶段，然后进入“交付”，运行 Grepile
- 收到反馈评分 **3/5** → 接下来会发生什么？回到**构建**
- 智能体回到步骤二，重新构建
- 构建完之后做什么？**证明**
- 然后呢？**交付**
- 接着自动等待新的评分：Grepile 给出 **4/5**——“我们抓到了几个问题，但最后还有一个漏掉了。”→ 再回构建
- 构建 → 证明 → 交付
- 最终拿到 **5/5**

当拿到 5/5 时，剩下的就是 Mickey 自己出场了：**点一下合并（merge）**。

他现场展示了一个开放的 PR：他要做的只是点击 Merge。点击合并后，改动终于回到应用的主版本（main copy / main version）里。

而这一切，是在他同时推进 **15 个不同功能**、使用不同智能体和子智能体的情况下完成的。

### 软件工厂的本质

这就是工厂的循环属性。它让一个智能体：

- 拥有一个**隔离的实例**，可以独立工作
- 拥有**构建的准则**
- 拥有**证明自己工作的方法论**
- 拥有一个**外部服务**来验证、检查它的工作
- 一旦工作不达标，它就必须**继续循环**，直到达到标准

**一旦拿到 5/5，Mickey 才真正进入画面。**

> 这就是软件工厂。注意：我们全程没有讨论模型，也没有讨论工具链。软件工厂全部由**工作流、技能，以及一点点领域知识**组成。

不是每个人的工作方式都一样。这是 Mickey 的方式，而他使用这套方式获得了很好的结果。

## 用实体工厂类比软件工厂

**Greg** 分享了他脑海中浮现的画面——实体工厂的类比：

### 步骤一：隔离 = 定制订单的独立工位

就像工厂接下一个定制订单，然后给它一个独立的工位，让它在不干扰其他生产线的情况下作业。在软件里，你叫它 branch、work tree、隔离环境——基本概念是一样的。

### 步骤三：证明 = 质检

**Mickey**：基本上就是这样。**任何东西离开工厂之前，都必须有人测试它。**你不能造出一个产品却不让人测：它能开机吗？它合身吗？它在压力下会不会坏？我脑子里的画面就像汽车工厂。在软件里，你可以跑测试、可以预览、可以看日志，还有你展示的那些截图。

**Greg**：最后，一旦通过质检，它就出厂了。但总还有一些后续工作：合并、部署 PR、写发布说明；如果没通过质检，你还要把反馈送回产品团队，然后重跑一遍循环。
