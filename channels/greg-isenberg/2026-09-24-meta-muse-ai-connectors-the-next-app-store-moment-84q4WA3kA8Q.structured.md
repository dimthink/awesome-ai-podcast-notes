## 一、类比 App Store：为什么说这是 AI 的"App Store 时刻"？

回顾 2008 年苹果开放 App Store 时发生了什么。苹果造出了手机，而外部开发者现在可以为手机用户构建有用的东西，并通过商店销售。开发者可以做一个照片编辑应用并收费——苹果提供软件分发和收款渠道，开发者则可以专注于做出人们想用的产品。这是双赢：苹果获得了更好的应用商店，开发者赚到了钱。

到 2010 年 6 月，也就是商店开业不到两年的时候，苹果已经通过付费应用和应用内购买向开发者支付了 **10 亿美元**。一个围绕手机的全新市场就此形成，外部企业从中赚了不少钱。

这正是我对这则新闻公告感兴趣的原因：**Meta 在构建助手，而其他企业可以提供服务，帮助它完成客户的请求。** 这个市场能有多大，取决于用户是否真的会用 Muse 来完成这些任务。但对开发者来说，窗口已经打开了。

当然，我知道评论区会有人说——"谁知道这是不是一个大应用？"的确，没人能百分百确定。但截至录制时，Muse 是 App Store 排名第一的应用。

当我把 App Store 的类比套用到"AI 的 App Store"上时，还有一个有趣的新变化：**你的服务可以在一个更大的请求进行到中途时变得有用。** 让我解释这是什么意思。

假设有人在组织一个小型活动。他们需要场地，然后中途意识到还需要租一些设备。这时候，一家提供设备租赁的公司就可能变得关键——即便"租设备"并不是对话的起点。作为一个创始人、一个试图构建东西的人，我会密切关注这样的时刻：**当某个人正在努力完成某件事，而其中有一个步骤需要接入一家真正能交付的商业服务，同时钱正在发生转移。**

## 二、Meta 的平台现状：目录、审核与推荐

Meta 的平台现在有了提交流程和一个已批准连接器的目录。目前里面已经有一些大公司，而且我认为很快就会有大量中小型公司加入。**编辑们也可以推荐（feature）这些连接器**——这给了我们一个真正可以探索的东西。

我记得早年我发布应用时，有一次被推荐了，从那之后我每天获得约 **40,000 次下载**，而且全部是免费的。对于 Muse AI 连接器，我们还需要了解的是：人们如何找到这些服务，以及他们多久会使用一次。但如果目录本身就能带来大量客户，我也不会感到意外。这正是"早入场"的价值所在——你可以比同类别中的其他人更快学习。

所以，我会利用这段时间去理解客户的真实请求，让我的服务更好地满足它。然后，谁知道呢，也许你就被推荐了。

不过，在接近节目结尾时，我们也会谈到一系列**其他获取使用量（或者说"下载量"）的技巧**——那些不依赖于 Meta 推荐的获客方法。

## 三、Muse 连接器到底如何运作？

假设我告诉 Muse："我需要一间播客录音室，周二下午用 2 小时，预算 200 美元。"它需要先确定我在哪个城市、我要做哪种录音，然后需要一个能回答"是否有合适房间"的服务。

**API（应用程序接口）的核心，就是一种软件向另一种软件请求东西的方式。** 你可以把它想象成录音室的"服务窗口"：你发出一个具体请求（比如查询周二是否有空位），得到具体的答复。连接器让 Muse 可以使用这扇"窗口"。

具体来说，录音室的系统可能会返回一间可用的房间，价格是 160 美元，包含我需要的设备。Muse 向我展示这个报价；我一确认，服务就能完成预订并发回一个确认信息。

这是一个设想的工作流程，但它展示了连接器要达成的目标。当然，录音室仍然需要保持日历准确——总得有人确保设备正常。而且，如果客户需要进入大楼的帮助，商家也需要有办法处理。**很酷的一点是，智能代理让"请求服务"变得更简单了；但服务的质量本身仍然必须过硬。**

### 真实案例：Duffel 的旅行集成

你可以在旅行领域看到一个真实的版本。有一家公司叫 **Duffel**，他们表示其 Muse 集成能让用户搜索航班和管理预订。Duffel 还提到，其业务在其网页端和移动端应用上已经突破了 **10 亿美元的年交易额**。现在，他们也在押注 Muse AI 连接器这条新渠道。

顺带说一句，这 10 亿美元是"通过该平台完成的预订交易额"，而不是 Duffel 的收入——但这个例子很好地说明：**一家已经提供有价值服务的公司，正在通过一个新界面变得触手可及。**

> 💡 如果你以前写过软件，我建议你先看看你的客户已经能通过你的 API 做哪些事情——**你可能已经拥有一个藏在现有产品里的有用连接器。**

## 四、四个 Muse 连接器创业方向

如果你想创办一家 Muse 连接器公司，该从哪里着手？这里有四个我觉得相当不错的方向，逐一分析。

### 方向一：为商业供应商做潜在客户开发（Lead Gen for Business Suppliers）

举例来说，假设你在迈阿密经营一家亚麻布服务公司，为餐厅供应干净的桌布和餐巾。你可以让 Muse 去问："附近有哪些餐厅正在筹备开业，可能需要我们的服务？"而你的连接器会接入一个你自建的、用于追踪这些新开餐厅的系统，返回相关的餐厅信息，并附上：每个餐厅预计开业时间的来源，以及公开的商业联系方式（如果可用的话）。

当然，客户能清楚看到为什么每家餐厅值得接触。

**我的建议：**
- 从一个城市、甚至一个供应商开始；
- 可以使用你有权访问的信息源（比如本地商业公告）；
- 在把餐厅加入列表前，核实细节——计划中的开业可能会延期，有人可能在你还显示第一家店的时候又宣布开第二家店；
- **保持信息的时效性，将是你销售的核心价值之一。**

通用联系方式搜索早就存在（我相信你见过 Apollo 这类工具），但你的机会在于**对一个特定市场掌握及时有效的信息**。一家正在筹备开业的餐厅，给了亚麻布公司一个具体的理由去开启对话——当然，对方是否需要供应商，仍需进一步确认。

假如我能给一家亚麻布公司展示几个经过验证的机会，并询问他们是否愿意为每周、每两周或每三周更新的线索付费——然后你可以收取订阅费。这只是一个假设的例子：**100 个客户每人每月支付 99 美元，在你扣除任何成本之前，就是每月 9,900 美元的经常性收入（MRR）。** 所以，为商业供应商做潜在客户开发，完全能创造一门不错的小生意。我选择"本地"作为例子，是因为它足够细分。

### 方向二：家电维修派单（Home Repair Dispatch）

用户告诉 Muse："我的洗碗机坏了，找个人来修这个型号的 Samsung，并且明天能来。"你的服务会去查询入驻的维修公司，返回**能处理该特定品牌/型号、且确认有空档**的那些公司——他们确实能上门修好。客户选择一家服务商，同意分享工作详情，你的服务就把请求转过去；如果支持在线预订，也可以直接完成预约。

**商业模式**：你可以向维修公司收取一笔约定费用，比如 **100 美元一个合格线索或一个确认的预订**。

**为什么值得做**：Thumbtack 这样的大公司已经验证了一个事实——**人们是愿意为销售线索付费的**。但你的服务必须提供维修公司真正想要的请求。

**我的建议**：从一种维修类型开始，从一个城市或一个镇开始。你要深入了解服务商，以及他们真正能处理什么。当一个人站在厨房里面对坏掉的家电时，"明天有空"是一个极有价值的信息。

还有一点很重要：**房主可能只是偶尔需要你，但维修公司需要的是持续的客流——他们每天都需要客户。** 所以，我会同时关注本地市场的整体需求，以及单个用户回访的频率。

### 方向三：本地板式网球（Padel）比赛与场地查找器

这个想法更有趣。如果你了解我，就知道我喜欢球拍运动；而我住的地方，板式网球（Padel）正变得越来越流行。

用户打开 Muse 说："帮我找一场今晚附近的板式网球比赛，水平和我差不多。"你的服务会去查看入驻俱乐部和球场的空位，显示合适的比赛和价格。球员确认预订；如果他们已经有球伴，也可以直接订场地，把预订信息分享给朋友。

**关于社交性**：顺带一提，我预计在未来 6 到 12 个月，Muse 会变得越来越社交化——毕竟我们说的是 Meta，他们对社交的理解无人能及。

**我的建议**：
- 从一个城市开始；
- 参考现有的公司（比如叫 Playtomic 的平台，提供场地和比赛预订），寻找有用的空白点——比如那些玩家目前必须自己单独查询的本地俱乐部；
- 当然，你需要俱乐部允许你访问他们的空位信息并处理预订，有些愿意、有些不愿意，但你可以从中赚取约定的预订佣金。

**为什么有需求**：**一个有空位的俱乐部，手里有他们想卖的东西；而一个每周打几次球的人，有理由持续使用能帮他们约到比赛的服务。**

### 方向四：家庭晚餐规划 + 杂货购买整合

一位家长说："帮我把接下来三天的晚餐搞定。每顿最多 20 分钟烹饪时间。我们已经有米和西兰花了。"你的服务会：
1. 根据你为这类家庭测试过的食谱生成计划；
2. 调整食材分量；
3. 把缺失的食材转化为一份购物清单；
4. 接入 **Instacart 的开发者工具**，创建一个用户可以直接打开、查看商品并完成结账的"可购清单"。

这就给了你一个实用的起点，把食材真正送到用户家里。

**一个旁注**：也许像 Instacart 这样的公司，最终会直接收购这类连接器——如果这个生态做大了，未来几年可能会出现一波收购潮。

**如何验证**：我会和那些想每周使用的家庭进行订阅测试。关键在于：**餐食必须真正对他们有效。** 如果孩子们喜欢这些晚餐、份量也合适、用户有理由在下次买菜时继续用你的界面——那我就会想了解他们实际做了什么菜，用这些反馈来改进下一周的规划。

### 四个想法的优先排序

在这四个想法中，**如果是预算很有限，我会首先研究潜在客户开发（方向一）**。因为你可以先做出一个有用的样本，在写大量软件之前就拿给潜在客户看——这正是我喜欢这类生意的原因。

如果你已经认识一批本地服务商，家居维修（方向二）可能值得深入了解。

总体而言，我给了你几种不同类型的创意：有更偏消费端的，有更偏企业端的。**我的猜测是：消费端的想法做起来最有趣**——而且因为 Meta 本身就是消费应用公司，这类使用场景会更多。但我认为企业级用例同样会创造大量收入。

## 五、分发策略：如何让用户发现你的连接器？

这自然会引出一个问题——"太好了，我有一个连接器了。可人们怎么知道它？怎么知道我的业务？"

进入目录当然能带来大量曝光。但**一个不知名的服务在普通对话中是否会被推荐，我们还需要证据**。所以，我会围绕"我已有渠道触达的客户"来制定初始计划。

### 策略一：与拥有受众的现有创作者合作

以家庭晚餐服务为例，你可以找一位为家长分享素食食谱的创作者。你帮他们向观众演示：如何把几顿餐变成一个杂货订单。创作者给他们的受众提供经过测试的设置说明，你们再约定如何为被引入的客户付费。

观众看到了一个他们想完成的任务，也明白了为什么要连接这项服务。**我会先选一个相关性强的创作者，看看有多少人完成了第一个任务。** 说实话，受众规模对我来说不如"受众是否真的需要你卖的东西"重要。

### 策略二：产品驱动的病毒式分享（Product-Led Growth）

以板式网球服务为例：一个人预订了场地，会把包含时间和地点信息的页面分享给其他三位球员。**这本质上是在产品层面实现病毒式传播——这个概念也叫产品驱动增长。**

关键在于：**你如何让一个人愿意分享你的产品？**

在上述板式网球服务的设想中，那些球员在注册之前，就已经从你的产品中获得了有用的东西。如果你给他们一个方便的方式安排下一场比赛，你就有了一条通往下一次预订的路径。

所以，你可以优先选择那些**把分享机制内建在业务流程中**的多玩家型创意——这会极大地帮助推动增长。我们在移动互联网时代已经见证过：很多带有社交功能的应用变得非常流行。**在智能代理时代，同样的事情也会发生。**

什么算是这样的例子？发给某人的报价单、被传阅的活动邀请函——**让结果对接收方也有用，然后其中一些人就可能成为你的客户。** 这就是希望所在。我会先去衡量这个"增长循环"是否成立，再决定是否投入。但当你需要在两三个有前途的想法之间做选择时，这是非常实际的筛选标准。

### 策略三：通过现有的关联市场进行分发

**Ticketmaster** 表示，符合条件的活动现在可以通过其连接器出现，而活动组织者无需做额外的集成工作。这意味着，组织者可以在继续经营自身活动业务的同时，通过 Ticketmaster 的体验触达新的用户。

这让我好奇的是：**每项连接服务的"供给"究竟从哪里来？** 如果你所在的行业已经有一个现成的市场平台，去研究企业如何参与其中、哪些信息能帮助客户准确地选择他们——这就是进入这个市场最实际的方式。对其他一些人来说，因为已经有了客户或能引荐他们的合作伙伴，自建连接器更合理。

**尽早做出这个决定很重要。** 你要能够指向一个具体的人或渠道来带来第一批客户——哪怕你同时也在期待 Meta 目录成为有意义的需求来源。

### 策略四：Meta 目录推荐位（但不建议押注）

第四条路线，就是获得 Meta 目录中的推荐位。但坦白说，**你不能把宝押在这上面。** 我当年获得 App Store 首次推荐时，那件事基本上有点随机——我醒来后突然发现排行榜垂直上去了。我猜很多人会在 Meta 目录上经历同样的体验：你在赌门洛帕克（Menlo Park）的某个产品营销经理说一句"这是个好应用"。

## 六、如何构建第一个版本？

如果你对构建连接器感兴趣，我会怎么动手做第一版？

**第一步：先写下客户应该能完成的一件事。** 这听起来很基本，但确实是最重要的起点。以板式网球为例，我会写："显示明天晚上我附近可用的球场，附上每个的价格。"

**第二步：交给编码代理。** 把这个需求简报交给 **Claude Code 或 Codex** 之类的编码代理，同时给它你要对接的系统的文档。然后，用普通、日常的语言描述客户请求。如果你是在构建一个全新的服务，在梳理流程阶段，可以先从**标注清晰的示例库存数据**开始。

**第三步：分阶段构建。** 先让它构建"可用性查询"和"报价"功能——结果必须显示完整价格以及该价格的**有效时长**。预订操作要等这些基础功能正常工作后再做。

**第四步：注意托管和权限。** 你构建的是一个供其他软件使用的小型服务，需要托管在 Muse 可以访问的地方。它还需要一种方式验证当前用户是谁，确保人们只能访问他们**有权访问**的信息和操作——否则会很糟糕。

**第五步：让编码代理解释每一个部分。** 你可以让 Claude Code 或 Codex 在构建每一部分时同步向你解释，我强烈建议这么做。（我会在本期节目的配套资源中附上一个起步需求简报，方便你根据自己的创意调整。）

> 🤯 顺便说一句，**你能直接用 Codex 或 Claude Code 创建这些东西，简直是不可思议的。** 在 App Store 时代，想做一款高质量的移动应用，你可能需要一两百万美元、一个 10 人团队。而现在，任何正在观看或收听这个节目的人都能做到。

### 自定义连接器：两种推进路径

在推进过程中，有两条路径——我在做研究时发现这部分有些人会混淆。

**路径 A：利用"自定义连接器"选项。** Meta 文档描述了一个自定义连接器选项：你可以让自己个人的 Muse 使用 API 信息连接到一个服务。这给了你一条**在申请公开上架之前尝试受支持集成的路径**。但你仍然必须测试你自己的服务，任何凭证都应通过安全设置流程来配置。

**路径 B：通过 Meta 审核。** 顺便说一句，Meta 必须批准你才能成为连接器——这也是一个待解决的问题：**他们每天、每月、每周到底批准多少个？**

我看到了 Stack Tree 的创始人发帖分享的第一手提交给 Meta 审核的表格体验。表格中包含：
- 接入方式的选择：提供 API 或现有的 MCP 服务器（MCP 是 **Model Context Protocol** 的缩写，是一种让工具对 AI 应用可用的标准方式，如果你一直听本频道，应该很熟悉）；
- 产品信息；
- 实际使用示例；
- 文档和支持详情。

因为该计划太新了，你准备提交时一定要查看最新版本的表格。

### 提交审核前必须做的事

在我提交连接器之前，**我会确保服务能够妥善处理那些"刁钻请求"**——否则很可能被拒绝。具体来说，我会测试：

1. 请求一个**已被预订的时间**；
2. 尝试使用一个**已过期的报价**；
3. 检查**重复请求**是否不会真的创建另一次预订；
4. 尝试用户接下来很可能提出的操作，比如**把场地预订改到另一天**。

这就是你发现自己的服务到底能处理多少真实工作的时候。虽然编码代理（如 Claude Code 和 Codex）可以消除大量构建摩擦，**你仍然需要亲自检查结果，真正理解这个服务在做什么**，然后再让客户使用——否则，抱歉，我觉得你大概率会被拒绝。

## 七、本周就可以开始的行动建议

如果你对连接器和 Muse 感兴趣，并且看到这里在想"我该从哪里开始"——如果我是从本周开始，我会这样做：

1. **选定一类你能实际对话的客户；**
2. 询问他们**反复要处理的任务**。我想听他们讲：上一次是什么时候发生的？他们当时是怎么搞定的？在哪个环节让他们等待了？花了多少钱？
3. 这段对话通常会给你一个比盯着空白编辑器凭空发明一个 AI 业务更有用的起点。

（你也可以直接去 ideabrowser.com，那里有很多创业点子，注册完全免费，每天还会推送一个免费的点子，帮你活跃创意思维。）

接下来，我要做的才真正让这次 Muse 发布值得关注：

- 选择任务中的**一个小部分**；
- 看它能否通过连接器实现。

**Meta 已经为商业参与人们请求助手完成的事情，开辟了又一条新路径。** 我们可以开始探索：人们到底想要哪些服务，以及他们愿意为什么付钱。

## 八、结语：两个悬而未决的问题

目前还有两个悬而未决的问题：

**第一**，你认为 Muse 会拥有多少用户——1 亿、2 亿、5 亿，还是 10 亿？

**第二**，有多少 Muse AI 连接器会被批准进入这个"应用商店"？它会像 YC（Y Combinator）那样只有 0.1% 的录取率，还是会像苹果 App Store 那样——**只要质量够高、能为人们带来价值，大多数都能上架**？

我一直在想那个关于"明晚有空球场的板式网球俱乐部"的想法——有一群想打球的人，和一个很乐意填上那个空位的俱乐部。**帮助双方完成那次预订，就是一个商业问题。**

对我来说，我会从类似这样的小切口开始，看看能学到什么。

这是一个不可思议的构建和发布时代。把你的点子发出去、全力以赴。我为你加油。
