# 为什么 Agents 偏爱 Supabase —— 对话 Paul Copplestone 与 Ant Wilson

**频道/来源：** Latent Space

## 引言：主持人与 Supabase 的渊源及本集看点

大家好，又见面了。希望你们喜欢我们做的这些小开场。这样做让我有机会和大家聊聊为什么我们做这些节目，以及在采访中应该关注什么，这样你们能从音频采访中获得更多。我们还会添加一些弹出式叠加说明，让画面更有趣，解释一些行业新人可能不懂的内容，因为采访中我没时间逐一解释所有东西。

我最近参加了 Supabase Selects，这是 Supabase 公司的年度大会。有很多内容值得分享。我想先说明一下，我和这家公司关系非常密切。六年前我作为天使投资人参与了他们的种子轮，那是我的第一笔天使投资。他们做得非常好，过去六年估值从 0 增长到 100 亿美元。它是一家全远程的开源公司，规模非常庞大，而且它们实际上正在成为托管 Postgres 的标准。所以我想拆解一下他们成功的原因。我也想看看他们为什么在我的 AEO 排名中表现如此出色，因为这并非理所当然。很多公司都在争夺为 Agent 构建数据库的定义权。

他们也是我们在 2023 年举办的首届 AI Engineer 活动的第一家赞助商，现在他们将是我们 Latent Space 的第一家赞助商。我们现在开放赞助，我觉得应该和熟悉、信任、并能很好地向听众解释的公司与个人合作。

我想覆盖的主要内容，他们在 YouTube 上有完整的回顾，制作精良。但他们的核心是三大主题：**构建（Build）、运营（Operate）和扩展（Scale）**。我觉得这些公告正是我期待在一家公司大会主题演讲中看到的东西。

**构建**基本是关于如何改善 Postgres 在编码 Agent 中的体验和设置。两个让我印象深刻的点：第一，不用 Docker 就能启动 Supabase——这样我启动基础进程与数据库交互所需的负载越小越好，未来当然可以扩展到完整虚拟机。第二，**基于数据库的计算**，你在数据库旁边运行计算。我认为把它们放在一起非常容易，这一点真的被严重低估了，可能还没有充分展现其潜力。你的应用有一个来自 Supabase 库的 MCP 服务器当然很好，但**声明式 schema** 才是极其重要的，对吧？你希望声明式 schema，而不是标准的 SQL 范式——先建立 schema，然后不停地 migrate。这也是我们在播客中讨论过的：你希望一切都以 git 作为源代码真相，这样你的 Agent 可以爬取它，从那里开始设置、分叉等等。这看起来很简单，但 Postgres 最初并不是为此设计的，你必须把事件机制改装到一个 40 年历史的数据库上。我确实认为 Supabase 现在的势头是在做最后一公里，或者说 Postgres 开发的真正前沿，让 Agent 能更好地使用它们。美妙之处在于它并不只是关于 Agent，我们一直都需要它，人类也从中受益。我很喜欢这点，我不喜欢只为了让 Agent 开心才做事。

第二部分是**运营**，主要是提供更多上下文，无论是更多日志、更多检查、更多连接、为 SQL 生成 Markdown 文件（这超酷），还是知识和技能。他们每年都会发布一些有趣的管道工作，从 Stripe 到其他各种集成。我认为随着你在 AI 工程领域越走越远，通用的 ETL 问题会越来越多地成为数据工程栈的一部分，但现在 Supabase 有了第一方解决方案。你也可以混合使用两者，但有时候把所有东西放在一起很方便。

最后一部分可能是最复杂的，也是与规模相关的。这就是为什么 Supabase 把品牌标语从“prototype to petabyte”改为……（原文提到更改品牌），实际上他们在追逐越来越大的规模，因为客户在增长。因此他们宣布 **Multigress 的完整 v1**，这是他们对 Postgres 的 Vitess 移植版本，与 Vitess 的创建者一起完成，这在数据库界是件大事。如果你不知道 Vitess 是什么，你真的落伍了——你现在正在 YouTube 上观看，而 YouTube 就运行在 Vitess 上。还有 Ore DB 等等，有很多内容。你可以看到我和两位创始人的关系。我认为这是他们两人第一次一起接受采访，我也提到了这一点，并尝试展示你们之间的化学反应，让你们了解讨论和运营一家价值 100 亿美元的数据库公司是什么感觉。请享受。

### 重磅公告：Compute、Ore DB、Multigress 与收购 Terso

**Paul/Ant：** 好，有几个头条。首先从计算开始。我们有一个产品叫 **Edge Functions**，由 Dino 驱动，基本上有 2C 的限制。我们发现，社区长期以来想要运行更长时间的工作负载，比如分块和嵌入。所以明天我们会宣布——到节目发布时已经宣布了——**Supabase Compute**，你可以运行任何东西。它是长时运行的、无服务器的，与数据库在同一个私有网络中，位于同一位置，延迟非常低。你可以直接从 Compute 运行 Postgres 连接，里面可以运行任何东西，不再局限于 Dino。你可以使用 Rust 或 Python，可以在里面运行 Agent。基本上就是一个完整的计算实例。

**主持人：** 类似 Lambda 函数，但属于容器类型，可以运行完整容器？

**Paul/Ant：** 对。然后我们在数据库领域有三个创新。第一个是我们去年谈过的 **Ore DB**（也写作 OrioleDB），过去一年我们对其进行了严格打磨，确保它坚如磐石，为 Postgres 生态系统做好准备。三个创新分别是**性能、向上扩展和向外扩展**。Ore DB 关注性能，它是当前 Postgres 堆存储引擎的直接替代，运行速度快约 1.5 到 2 倍，无需更改任何其他内容，完全兼容。它完全消除了对 vacuum 等后台任务的需求，因此对数据库也非常高效。今年我们所有的工作是将其通过 PG regress 与 Postgres 的完全兼容性测试、Antithesis 测试、TPCC 夜间基准测试和 JSON 测试，确保它基本上永远不会丢失数据。明天我们以完整 Beta 版发布，并采用 Apache 2 许可，专利也包含在内。我们实际收购了该技术，继续开发，支付了专利费用，现在免费赠送。

**主持人：** 你刚才顺带提到我仍然难以释怀的是，你测试了每个操作符，并说每个操作符在某些情况下都会丢数据。

**Paul/Ant：** 这是第二个，关于扩展，也就是 **Multigress**。Multigress 是第二个重磅公告。我们考察了 Postgres 生态系统，研究了所有操作符。对于不熟悉的人，操作符是当你运行 Postgres 时从单节点开始，但几乎任何数据库都要运行多个节点，需要故障转移、管理备份，通常用操作符来运行整个集群。Postgres 生态中有不少操作符，我们发现在特定条件下，每一个都可能丢失数据。因此我们决定用 Multigress 从零开始重写整个操作符结构。Multigress 最初的目标是为 Postgres 社区提供分片，结果变成了一个完整的操作系统。我们再次进行了极其严格的测试，完成了 1000 次连续故障转移，没有丢失任何数据，并以各种方式敲打它，看是否会丢数据。我们现在对其稳定性非常有信心，明天也发布它。它完全开源，平台上将邀请制提供，运行严肃工作负载的客户可以联系我们，我们帮助他们扩展。

**主持人：** 这是 Multigress 完全并行于 Vitess 的完成版吗？还是还有未完成的部分？

**Paul/Ant：** 实际上是的，这很有趣。Sugu 最初为 MySQL 生态创建了 Vitess，特别是为了分片。实际上他加入后说，首要目标是因为我们一直在追赶兼容性，以前使用 Vitess 时，迁移到分片后总得修改一些查询。他说这次只想专注于兼容性优先。因此我们的设计方式，这次从零重写，就是为了确保当我们发布分片时，你实际上不需要为数据库做任何更改，继续运行相同的查询，Multigress 就能处理，代码零修改。

**主持人：** 这是了不起的愿景，而且你们能在两年内做到。

**Paul/Ant：** 是一年。我们还没有发布分片，但我已经看到了早期原型和设计，应该会在明年年初，取决于平台的一些进展。我们有很多事情要做，但我们对进展非常有信心，也很满意。

**主持人：** 是的，我认为这是全面统治 Postgres 的最后一块拼图。

**Paul/Ant：** 对，对于那些不知道的人，去查一下 Vitess，它支撑着 YouTube、GitHub、一切。

**主持人：** 如果工作负载从 MySQL 转移，你需要这个到 Postgres，然后 Supabase 就能赢。

**Paul/Ant：** 希望不只是 Supabase 客户能用，它是完全开源的社区项目。任何运行大规模 Postgres 的人都应该能使用 Multigress。

**主持人：** 我相信每个联盟、每家在某种程度上参与 Postgres 的公司都在为此做贡献，因为我们都想要这个。

**Paul/Ant：** 是的，我们有一套完整的设计合作伙伴计划，正在与 Booz Allen、Postman、Perplexity 等合作。很多客户加入，很多人需要它，他们在运行大规模 Postgres，需要帮助扩展。

**主持人：** 第三个是大消息，向外扩展。目前我们平台每月大约启动 500 万个数据库。我们知道的未来方向，需要每月启动数十亿。向外扩展是完全不同的挑战。所以我们决定考虑新的架构，在代理数据库领域，做代理最好的领先数据库提供商是 Terso。因此明天（节目发布时已宣布）我们宣布收购 Terso，为代理数据库提供动力。

**主持人：** 这太不可思议了。他们主要是基于 SQLite，但这并不重要，关键在于架构——我想不出词来描述，基本上就是广播？这就是向外扩展，他们扩展 SQLite 的想法是单个写入者和多个读取者。

**Paul/Ant：** SQLite 本身只有单写入者，是一种文件格式，通常不是为多写入者设计的。

**主持人：** 他们称之为 MVCC？

**Paul/Ant：** 对，他们构建了 Terso 架构，为 SQLite 构建了 MVCC，可以多写入者。

**主持人：** SQLite 许可证奇怪，他们必须分叉。

**Paul/Ant：** 他们一开始用 libSQL，然后做了另一个很酷的架构。这个架构几周前在 S3 上被广泛讨论。数据库领域的一些创新实际上来自对象存储的进展。对象存储增加了很多新功能，使你能够像使用数据库一样使用它。对象存储本身有 11 个 9 的数据持久性，虽然这不算可靠性。

**主持人：** 对，非可靠性，但它提供了集群数据库通常所需的东西，就像底层集群。

**Paul/Ant：** 因此你可以开始做一些很酷的事情，现在有不少流行数据库或数据用例直接构建在对象存储之上。它有一些局限，在我们的世界观里，可能适合较小用例。在事务方面，因为事务数据库需要大量读写，因此在大规模场景下你可能不想用它，这就是我们有 Multigress 的原因。但对于我们看到的要达到数十亿数据库的需求，我们需要的是文件格式，SQLite 特别有趣，它占主导地位。真正引起我们兴趣的是我看到 Globber 发布的博客，介绍了他们的重写方式，基本上让我们有了一条路径，可以获得与他们文件格式的 Postgres 兼容性。因此我们收购他们，并保留 Terso 品牌，Terso 专注于 SQLite，然后我们将在 Supabase 上引入新的更小实例类型，称为 **Supabase Spark**，它与我们所有库兼容，你可以为任何想法、任何原型使用一个数据库，当它起飞时，就升级到完整的 Postgres 数据库，一直到 Multigress。

**主持人：** 我知道你们已经为此工作了一段时间。这就是梦想，对吧？

**Paul/Ant：** 是的，向上扩展和向下扩展一直是我们想方设法解决的事情。当一些创新出现时，我们意识到我们可以做到。

**主持人：** 你们每月 500 万个数据库，轨迹到每月数十亿，其中一个秘密是这些数据库实际上很小，对吧？它们是空置的应用程序。你对此有什么见解？

**Paul/Ant：** 直到它们获得关注。这就是问题所在——一旦你登上 Hacker News 首页，你需要知道能走得更远。所以整个想法是确保后端之间平滑迁移，例如零停机迁移是必须的，因为现在有很多非技术建设者创建整个公司，比如客户 Magic School，创始人原本是老师，他看到教学中低效之处可以自动化。现在有创业公司没有技术合伙人或 CTO，这不再是孤立事件，每个人都是建设者。过去 18 个月增长疯狂，但仍感觉早期，存在更大的市场，包括公司内部人员、想创业的人，意味着更多数据库。如果给每个人专用 Postgres 集群，世界上物理计算机很快会用完，这正是正在发生的。

**主持人：** 恭喜。另外我发现 Globber 也是个迷因大咖。

**Paul/Ant：** 是啊，这是其中之一。

**主持人：** 他很棒，对于那些不知道的人，这些橡胶基迷因背后的人就是他，低调的杀手。

**Paul/Ant：** 还有 Will Glober 也是，非常厉害。

**主持人：** 不知道你们是否交流什么好笑？

**Paul/Ant：** 我们肯定会给他 Supabase 推特账号权限，我需要帮助。

**主持人：** 等等，推特还是你自己管吗？

**Paul/Ant：** 我们现在有一个小团队，一些青少年帮忙，每周做一次迷因工作坊。这很难招人，因为需要懂技术，并理解开发者觉得什么好笑，才能做这种营销。

**主持人：** 实际上你也是低调的迷因领主。我觉得不如你好笑，你真的很好笑。有一个海鸥的图，你站在上面……是海龟站在 Postgres 上面？还是海鸥骑着飞翔的海鸥？等等。这些都是深奥的 Supabase 历史，但曾经有段时间这些东西太好了，人们想模仿你但做不到，这就是你的护城河——迷因。

**Paul/Ant：** 是的，有些大公司试图在他们的推特上发迷因，我不点名，但是非常大的组织。这真的很难，像我说的，很难招人。

**主持人：** 有人写了一篇 4 万字的文章，分析你们的迷因策略。

**Paul/Ant：** 实际上有人在很早的时候研究了我们的推特策略，并发布在 Hacker News 上。有趣的是，他们记录策略的方式还没写入我们自己的文件。所以后来我们招新的营销人员时，就把这篇别人写的策略给他们看。

**主持人：** 当然 Hacker News 讨厌它，然后他们评论，Ant 还截图评论发到我们推特上。

**Paul/Ant：** “你的恨意只会激励我。”

**主持人：** 这是什么？有趣的文章。好吧，我评论了。我们很多增长要感谢 Hacker News。早期我几乎就住在那里。

**主持人：** 我们应该谈谈这个，你需要和 Dang 做什么魔鬼交易？

**Paul/Ant：** 我们多次被 Dang 责备，比如一周内发布太多东西。他合理地担心 Hacker News 和 YC 的关联，所以如果有什么事，他会想把我们推出去，让人们知道这不是为了 YC 客户，网站是独立的。他一直帮助确保我们不抹黑 YC News 的名声。

**主持人：** 现在你们不需要他们了，但 Dang 确实有很高的可信度。但你们 launch week 策略确实，我记得有一个 launch week 四五个发布都是 Hacker News 第一或首页。

**Paul/Ant：** 我因此被狠狠批评了，因为我自豪地发了推，后来被批评，因为看起来像 YC 公司霸占首页，有偏见。

**主持人：** 我是炫耀了事实，给大家一个忠告，永远不要截取你在 Hacker News 首页的截图发 Twitter，因为看起来像炫耀，确实也是炫耀，批评得对。

**Paul/Ant：** 这些现在都算老黄历了。但对于不了解 Supabase 历史的人，这些是必须了解的故事。最有意思的是，那篇置顶帖是别人发布的，我们还没准备好，我们不认为自己是 Firebase 替代品。

**主持人：** 是的，我们原有的标语是“实时 Postgres”。因为我在上一家公司不得不从 Firebase 迁移到 Postgres，但我需要实时功能，于是我在 Postgres 之上构建了实时引擎。我们想这就是杀手锏，有开源吸引力。但“实时 Postgres”没人关心。没人关心。所以我们改成“开源 Firebase 替代品”，因为那是我迁移的原因。大约 12 小时后那篇文章就出现了。

**Paul/Ant：** 现在仍然是历史置顶帖。当时我们运行在 Digital Ocean 上，每个新数据库使用两个 droplet，两个 5 美元/月的 droplet，一个用于数据库，一个用于 API，因为我们想升级 API。当时只有少量测试用户，突然之间，我们从 8 个用户增长到 800 个。然后我们烧光了大约 1 万美元的 Digital Ocean 信用，几乎在 48 小时内。然后我们进入了 YC，AWS 说：“如果你们迁移过来，我们给你们 15 万美元的信用额度。”所以我们第一周在 YC 就是迁移 800 个数据库到另一个云。如果你迁移过一个数据库，就知道有多痛苦，迁移 800 个绝不是你想用来度过 YC 第一周的方式。

**主持人：** 等等，你还记得吗？我们本可以留在 Digital Ocean，因为当你进入 YC 时他们有一个很大的信用计划，我们问能否给我们这些信用，因为我们正在爆发式增长，他们说不行，你已经使用了 1 万美元的信用计划，我们不能给你另外 30 万美元的。所以我们只能迁移到 AWS。这是 Digital Ocean 错失的最大机会，看我们现在 AWS 的账单。

**Paul/Ant：** 那段时间每个人都担心会发生什么，所以他们不想过度扩张，这很公平。但人们在新冠期间做了很多不理性的决定。

**主持人：** 我本来想说你们现在可能比 Digital Ocean 更值钱，但不知何故 Digital Ocean 也涨势惊人。看这个，因为计算机在过去一年翻了三倍。哇，真酷，他们现在市值 160 亿美元？

**Paul/Ant：** 是的。CPU 短缺。

**主持人：** 你们如何应对？我们经常面临跑道限制，我们多次与 AWS 会面。

**Paul/Ant：** 我们必须非常紧密地规划，我们付更多钱，与他们合作。实际上明天我们还将宣布引入新的投资伙伴 Capital G。Capital G 可以访问 Alphabet 生态系统。这对我们双方都有好处。我们不得不考虑多云策略。

**主持人：** 我们需要 GCP。

**主持人：** 太好了。提到 Lovable、Bolt，Lovable 将有自己的数据库功能，每个人都会试图侵入对方的地盘，这在大局中很正常。哪个更具粘性？CPO 更可能粘住 Lovable 还是 Supabase？

**Paul/Ant：** 好的。

**主持人：** 这是数据库领域的圣杯之一，传统上你需要 OLTP 和 OLAP 数据库，两者永远不该相遇，但有时你希望不必复制任何东西。你们关注这些吗？Supabase 未来有这方面的故事吗？

**主持人：** 是 MotherDuck 还是数据湖？什么是 DuckDB？

**Paul/Ant：** DuckDB 基本上就像分析领域的 SQLite，列式存储。它可以直接从对象存储读取，这是它的典型宣传点，它也可以从 Postgres 数据库读取。开源伟大技术，还有 DuckDB Labs 最近被 AWS 收购，他们是一个基金会，围绕开源建立委员会。我实际上认为 DuckDB 有点像分析生态中的 Postgres，他们试图让它不属于任何人，能做很多事情，非常多才多艺。

**主持人：** 就像是荷兰的一位教授。

**Paul/Ant：** 对，他们生活工作在荷兰，很酷。我们在仓库方面的兴趣不是让 Postgres 成为分析数据库，而是专注于使用合适的技术做合适的工作。我不知道 HTAP 是否可行，很多人试图斩杀这条龙，对象存储可能是解决方案，但我们一般认为，在 OLTP 方面一旦达到一定规模，就需要分片。NVMe 磁盘空间有限，如果你需要跨两台服务器拆分事务，最终要从对象存储读取，会拖慢数据库。所以我们认为分片是扩展到 PB 级的最佳方式，分析应该区别对待。这并不意味着你不应该把数据直接存储在对象存储上并从不同路线读取，但试图把两者硬凑在一起没有太大意义。

**主持人：** 向上扩展。除此之外，公司未来一年的 P0 目标是什么？你们如何指导方向？

**Paul/Ant：** P0 基本上就是赢得战略实验室、赢得模型，并继续我们的 PLG 推进，在企业方面赢得新工作。我们开始公司时认为 PLG 的天花板是 1 亿美元，也许能到 2 亿，然后就需要不同的动作。但因为 AI，这个天花板被抬高了，我们不知道抬高到了哪里：是 10 亿、20 亿，还是可以一直持续。但我们仍然想做其他事情。所以我们去年决定必须两者兼顾，小的和大的都做。也许我们有点贪婪。

### 声明式 Schema、代码优先与开发未来

**主持人：** 你们有什么开放问题？如果你有一个水晶球，哪些答案会改变你们的押注？

**Paul/Ant：** **开发将如何进行，人们将开发什么**。这两个问题我思考很多。今年我们重点从仪表盘公司起步，拥有最好的 DX，然后很多人说无头模式，我们一开始就有 API 驱动，这是成功的原因之一。今年我们的大重点是转向代码优先，变得原生。基本上当你在本地启动 Supabase 实例时，你会得到一个 Supabase 文件夹，它代表你的数据库，包含所有函数等。

**主持人：** 这现在存在吗？

**Paul/Ant：** 如果你使用我们的 CLI，现在已经存在。它是一个虚拟文件系统，就像基础设施即代码。

**主持人：** 好。

**Paul/Ant：** 实际上明天我们宣布的是，我们完成了声明式 schema 的最后修改。这一项非常具有挑战性，覆盖了所有 Postgres。现在你可以拥有 Postgres 数据库形态的完整文件表示，以声明方式放在文件夹中。这对 Agent 非常重要，因为通常使用 Postgres 的方式是，每次更改时添加一个迁移文件，就像历史日志。这很好，是行业标准。但想象一下让 Agent 处理一千个文件，问它“这个表的形态是什么？”它必须猜测。或者你必须在本地启动数据库、运行迁移然后内省数据库，但太慢了。所以我们想将 Supabase 文件夹中的 schema 文件夹变成数据库的完全声明状态。我们捕捉了表、策略、数据库注释等所有内容。因此我们发布一个新库 **PG Delta**，你可以用于任何 Postgres 数据库。我们有 Supabase 的机制。这是 Agent 的重要一步，我们知道 Agent 主要对代码进行操作，它们不想访问任何外部东西，它们必须在文件系统上非常快速地迭代。今天人们使用 CLI，并对这些工具感到满意。我怀疑我们正在迈向这样的状态：我现在尝试在手机上做开发，就可以很舒适地完成。当然我知道幕后发生了什么，我告诉它从基础设施角度必须做什么。但我们正在接近一种状态，你可以想象你不需要是工程师，你有个想法，对你的手机或你的个人 Agent 说“我想构建 X”，一秒钟后你就有一个可用的应用，可以自己迭代。

**主持人：** 作为有几十年经验的软件工程师，你对软件应该如何构建有强烈意见，比如持续集成、持续交付等，我发现自己把意见强加给 Agent，但现在越来越不需要。我担心的是它们会不会都收敛到一种构建软件的方式？

**Paul/Ant：** 是的，模式坍缩。好的是你们都会使用 Supabase（笑）。但软件行业的美好之处在于那些著名的圣战，什么才是正确的方法。我们会失去这些吗？

**主持人：** 你希望思想多样，最佳想法能胜出，但模型会让你变得懒惰，没人费心看细节。

**Paul/Ant：** 我认为这是一个合理的恐惧，而且超出你的控制。低品味、我们称之为休闲应用构建者会收敛到模型的均值，也就是你们。但高技能、有辨别力的人会一如既往地真正关心细节。这会最终滤下去。

**主持人：** 但高技能的人还会继续被训练出来吗？

**Paul/Ant：** 我认为人们有足够的热情。普通大学可能完蛋了，你可能不需要上大学，可以自学并找到工作。但总是有顶尖的一批人在推动很多进展，他们总会找到满足自己好奇心的方式，比如那些花一年时间去 Recurse Center 研究酷编程问题的人，即使他们可以在行业里赚钱。

### 开源未来与 Rust 重写

**主持人：** 你们为社区和开源做了这么多。未来大型商业开源会怎样？一方面有很多低质量内容，另一方面你们的依赖现在变得可选，你可以随意 vibe code。

**Paul/Ant：** 我认为用 Rust 重写是一个有效机制。团队里有人来跟我说：“我正在用 Rust 重写一切。”我问：“你要重写到什么程度？你要重写 Postgres 吗？Postgres 不是用 Rust 写的，但到那个程度你就不关心了。”所以重写是分层的，你不想把真正的创新代币花在重写一切上。最终几乎所有工具都会坍缩到 Rust，如果它成为最终编写方式，因为它更快、更正确。这可能会发生在大多数开源工具上。但迭代完成后，一切都运行在这个高效语言上，你就不会每次重写所有东西。会有少数赢家。经典例子是 Postgres，它用 Haskell 编写，非常不寻常，很难维护。现在能用 Rust 重写吗？可能可以。如果发生这种情况，会有一个 Rust 分支的 Postgres 成为那个类别的赢家。

**主持人：** 但你们还没做，而且你们很多东西是 Elixir。

**Paul/Ant：** 对，基础设施侧 Elixir 很有趣，因为 BEAM。然后你会想当你操作时合适的机制是什么。但现在改变范式很容易，只要你通过所有测试。

**主持人：** Malta（Vercel 的）有一条推文留在我脑海中，他拨出一些钱重写所有 C/C++ 级别依赖到 Rust，因为我们知道它更好、更安全、更正确。这是开源的一次性升级。

**Paul/Ant：** 我喜欢这个想法。我认为它不会发生，因为人们喜欢自己动手。但如果作为一个想法，我们公司会 100% 支持。
