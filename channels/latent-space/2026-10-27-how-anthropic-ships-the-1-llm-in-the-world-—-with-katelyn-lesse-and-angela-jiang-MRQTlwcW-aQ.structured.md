# Anthropic 如何打造全球最强 LLM：IPO 背景下的效率、平台与模型发布策略

## 开场：Anthropic IPO 与效率故事

今天我们尝试一种新的模式。随着 Anthropic 正式提交 S-1 申请文件，我们将启动针对其 IPO 的系列报道。预计 IPO 将在两周内进行，估值约 2 万亿美元。Anthropic 是史上增长最快的公司之一，据报道其累计融资超过 1000 亿美元，但累计烧钱不到 100 亿美元。因此，其中有很多值得深入探讨的效率故事。我们想重点关注的是：**Anthropic 如何在同时推出全球最强模型的同时，以极高的效率运营，并构建起一门令人难以置信的生意。**

我过去曾担任金融分析师，因此从 S-1 文件中摘取了一些我认为能为本期播客提供背景的陈述。我们想尝试一种新的形式，因为我觉得有些观众希望看到我们直接对着镜头交流，而不是像过去四年那样只与嘉宾对话。

### 人力资源效率的惊人跃升

首先我要强调，**Anthropic 从人均产出的角度看是一家效率极高的公司**。这或许并不意外，因为它本身就是一家人工智能公司，显然在很好地利用 AI。但我认为，它在过去一年中作为一家公司所发生的巨大变化，尚未被外界充分理解。

目前其过去 12 个月的人均营收已达到 **660 万美元**，而一年前仅为 140 万美元。这意味着人均营收增长了近五倍。这对任何企业主和工程师来说都值得深入探讨，因为提高人均营收不仅能提升盈利能力，还能增加你可以支付给员工的薪酬。

### 算力效率与盈利能力的历史性转折

这一增长同样反映在每美元算力所对应的营收大幅提升上。值得关注的是，在 2025 年第二季度，Anthropic 基本上每收入 1 美元就要亏损约 0.5 美元；而现在，每 1 美元成本能带来 **2 美元收入**。过去这一年对 Anthropic 的执行力来说是极其关键的，而它确实做到了。我们将尽可能深入剖析这一变化，并从播客的外部视角讲述这个故事。

这一系列增长带来的一个直接结果是：**Anthropic 刚刚报告了其首个实现盈利的季度**。这里说的不是调整后利润（即剔除各种成本之后的利润），而是按照公认会计原则（GAAP）计算的利润，利润率达到了 **19%**。这非常了不起，与一年前相比完全是天翻地覆的变化——一年前，它每获得 1 美元营收就要亏损 129%。

## 两个飞轮：驱动 Anthropic 效率的底层逻辑

我认为解释这种非凡效率的主要因素可以归结为：**Claude 喜欢循环、Boris 喜欢循环、Dario 也喜欢循环**。Anthropic 内部有两个循环在运转。

**第一个是改进循环。** 其基本逻辑是：

- 你拥有 Claude
- Claude 带来更好的模型
- 更好的模型解锁更多用例
- 更多用例产生更多反馈
- 反馈又反过来改进 Claude

**第二个是投资循环。** 其逻辑是：

- 采用范围的扩大带来营收增长
- 更高的增长带来更多投资
- 更多投资带来更强的能力
- 更强的能力带来更好的 Claude

这两个循环相互交织，形成一个无限循环，持续推动效率的提升（按照 Anthropic 的说法，这种循环将一直运行到时间的尽头）。

## Claude 平台：从模型实验室到平台级公司

今天我们将重点聚焦于 **Claude 平台**，因为它是 Anthropic S-1 中所说的"Claude 扩散"的三个核心要素之一。他们将其定义为**一个全面的代理式开发环境**，为客户提供直接访问原始构建模块的能力，使他们能够在自己的产品和工作流中构建、部署和扩展利用 Claude 能力的应用。

本期播客讨论中反复出现的一个概念是**"自用"（dogfooding）**——Claude 本身就是用与你可用的同一个 Claude 平台构建的。

另一个有趣的数据是：在 S-1 中披露，**超过 50% 年收入在 10 万美元以上的客户（按滚动计算）都在使用 Claude 平台**。这表明 Anthropic 不仅在从模型实验室演进，也在向超大规模服务商和云平台的角色转变。这或许已经包含在"Claude 平台"这个名字本身的含义里——这个平台正在从理论走向实际落地。

我还想强调之前多次提到的观点：**Claude Code、Claude Cowork 都使用与 Claude 平台相同的底层原语。** 这非常值得关注。

最终，Anthropic 似乎在将其 IPO 叙事定位为：**从聊天机器人到副驾驶（copilot），再到虚拟协作者（virtual collaborator）的演进**。他们使用"虚拟协作者"这个说法来替代"智能体"（agents），也许这样听起来更友好。但这些概念本质上与你对智能体的期待高度一致：

- 长时间自主运行的工作能力
- 判断力
- 自我纠错与迭代能力
- 工具调用能力

关键在于，它们**拥有目标并与人并肩工作**，而不是仅仅在一个应用或任务中作为替代工具。

本期播客录制于 **Opus 5.5 发布之时**。可以说，在我们与之交流的几乎所有高水准评测者中，**Opus 5.5 是目前世界上最好的模型**。Anthropic 甚至还在坐等 **Fable 5.5**，大概率将在未来两周内发布。我没有内部消息，但结合 IPO 的时机来看，这是非常合理的推测。让我们期待这一发布，并深入了解他们是如何构建 Opus 5.5 的。

## Opus 5.5 发布：嘉宾登场

播客录制于 Opus 5.5 发布次日，**Katelyn Lesse 和 Angela Jiang** 来到演播室。

> **恭喜你们发布了目前世界上排名第一的模型。**

Angela 回应说："这取决于你问谁。"

主持人接着问两位嘉宾的个人体会："你们有自己的官方博客文章，定价下调也很酷。当你们发布这样一个新模型时，从中得到的最大收获是什么？"

### 写作质量的改进与定价策略

Katelyn 表示："我们对这次发布非常自豪。团队为完成这个模型投入了大量不同的工作。我认为我们确实听到了关于 Opus 5 写作风格有些绕来绕去的反馈，所以我们真的努力去清理了这一点。我很高兴看到这似乎引起了大家的共鸣。内部试用模型时我们也有同样的感受，所以能得到外界的验证真的很好。"

关于定价调整，她补充说："关于定价下调，其中有很多内容。我认为越来越多的人在关注**每一美元所获得的智能水平**，因此确保我们在'每一美元'这部分做对非常重要。"

### 防止模型蒸馏的新措施

Katelyn 还提到一些博客文章中没有充分讨论的工作："我们在使我们的 API 更难被蒸馏方面做了大量工作。我们做出了一些改变，让这一点更加具体化。这些工作涉及如何做前缀锁定推理，或者如何在不同类型的模型之间重放思维 token 等。"

"我们在这些方面投入了大量精力，以确保我们能够调整那些非常合理的用例——比如你可能在压缩策略中需要这样做——与那些实际上来自恶意行为者的用例之间的平衡。在这些方面，我们花了很多功夫去拿捏分寸。"

### 关于"窃取推理痕迹"论文

这涉及一篇关于从专有模型中窃取推理痕迹的论文。Angela 表示他们非常感激研究人员做了负责任的披露。

Katelyn 进一步解释："我不认为这篇论文本身引起了多大恐慌，因为这是我们早就知道存在的一个缺口。"

她澄清了两个独立事件的区别："一方面是中方的模型蒸馏问题，另一方面是这个被高调发表的具体技术。"

她继续说："我们很早就知道，**思维链提取是蒸馏模型最有效的方法之一**。实际上，关于如何跨轮次保留思维块，并使其成为必要要求，我们早就开始探索了。一直以来我们都面临一个非常艰难的权衡：**用户体验的代价与防止蒸馏的保护之间如何平衡。**"

### 为什么防止蒸馏如此重要

Katelyn 解释了 Anthropic 的根本关切："我们不想让蒸馏发生的原因是，**Anthropic 存在的全部意义在于让 AI 安全地为世界创造积极结果**。我们在产出的 token 上运行了大量安全分类器，以确保它们的安全性。如果有人蒸馏了我们的模型，并在没有这些安全分类器的情况下运行它们，就有可能在世界上产生负面结果。这是我们不希望看到的。"

"因此，我们一直在思考如何防止思维链提取，以及如何在不过度损害用户体验的前提下保留思维块。"

### 如何在用户体验与防护之间取得平衡

Katelyn 详细解释了团队在平衡用户体验与防护方面的考量。他们将用户体验的影响分为两个层次：

1. **第一层：需要进行集成变更，虽然烦人但仍能完成原本能完成的所有工作。**
2. **第二层：实际上无法完成原本能完成的工作。** 这是他们极力避免的情况。

他们最近几个模型的落地方式是：采取一些渐进式变更，强制跨轮次保留思维块，现在进一步扩展到跨账户场景。他们与许多开源 harness 维护者主动联系，确保他们在升级过程中有良好的体验。同时，他们也照顾到了大客户的需求。

Katelyn 举例说："有些客户有压缩策略，如果强制保留思维块，这些策略就会失效。因此我们在 API 中提供了一个新的压缩功能，替代他们之前的手动操作，同时与思维保留机制兼容。这体现了我们在走这条钢丝——我们没有粗暴地一刀切地强制要求'必须用这种精确方式保留思维块'，因为那样会破坏很多人的现有系统。我们花时间与客户和开源 harness 维护者合作，为他们提供升级所需的条件。"

### 蒸馏防护的实际效果

关于蒸馏防护的效果，Angela 表示："我们确实看到，在我们能够测量的范围内，蒸馏的难度显著增加了。这要归功于我们的研究人员，他们非常负责任地进行了披露，因此我们能够及时关闭这个漏洞。他们还公开发表了研究结果，在推特上引起了相当多的传播。但我们已经看到，在我们能够测量的领域中，这确实降低了我们不希望看到的负面影响。"

Angela 强调了一个重要的观点："我在推特上看到很多人把蒸馏看作一个商业化问题，说什么'如果你能蒸馏一个模型，你就可以低成本运行它'之类的。虽然技术上确实如此，但这并不是我们真正在意的。**我们从安全角度远比从商业角度更加关注这个问题。** 实际上，如果有人从我们这里蒸馏，他们也得向我们付费。所以在商业上我们照样赚钱，不是那种性质的冲击。我们更关心的是确保 Claude 是好的，Claude 的衍生品如果最终走向负面结果，那将是不幸的。"

## 产品与工程的团队协作

主持人提到："你们两位经常一起公开露面，你是产品负责人，你是工程负责人。这两者之间是如何协作的？以模型发布为例。"

### 产品与工程的职责划分

**Katelyn（产品负责人）** 解释说："在模型发布方面，我们的团队非常紧密地合作。我这边更多关注的是：在推出具有正确智能门槛的产品与成本保护之间需要做出的权衡。我们更新的现金成本等指标反映了我们的意图——我们希望鼓励你做出实际上对所有人都有益的集成变更，并把节省下来的成本传递给你。"

"此外，还有如何平衡安全方面的因素，确保这是一个人们能够充分利用的优秀模型。这些围绕发布模型的质量和外围组件的决策更多属于产品层面。而在集成体验方面，很多工作直接来自工程团队。"

**Angela（工程负责人）** 补充说："我们有很多工程师实际上具有很深的产品思维，我们非常喜欢这一点。同样，我们也有很多产品经理更加技术化。我们想要这种跨学科的混合型人才，因为他们能够从不同角度分析问题，找出最佳方案。"

"但我倾向于更多从商业影响的角度考虑，而工程师则会更加关注集成体验。他们几乎更多地从用户体验的角度出发，当然这里的用户体验更多是关于 API 和开发者工具的。"

### 产品与工程角色的融合

Angela 提到有趣的一点："我和 Katelyn 一起工作很长时间了，之前在 Stripe 就是同事，后来各自去了不同的实验室。一个有趣的现象是：**Katelyn 经常被误认为是产品经理，而我经常被误认为是工程人员**，尽管这些并不是我们的实际职位。我认为这种搭配有助于做出跨两边一致的决策。"

当被问到"随着软件工程问题被解决，产品和工程领导这两个角色是否会合并"时，Angela 表示："我倾向于这么认为。如果大家仍然是分开的，那说明我们还没到那一步。"

Katelyn 补充说："我不确定我会用'软件工程被解决'这么强烈的表述。我的看法是，**野心会不断升级**。我们团队目前花时间的地方，除了安全发布模型所必需的所有工作（这是最重要的部分），另一半精力都放在了**规模化**上。"

### 从 Python 单体到多区域架构

Katelyn 回顾了加入 Anthropic 一年多以来的变化："我刚加入时，我们只有 messages API，是一个 Python 单体，运行在单个 GCP 区域。一切都很正常，当时我的家人和朋友都不知道 Claude 是什么。现在的情况完全不同了。"

"关于 API 上需要支持的流量增长，数据非常惊人。**CPU 变得非常紧张**，这对我们来说是个有趣的挑战。我们在如何扩展这些系统方面做了大量工作，这需要分布式系统专业知识，以及模型所具备的某些语言和框架知识。但在大规模运行和演进系统方面，我们远未达到'Claude 你自己搞定吧'的地步。仍然有大量工作需要人类来做，而且我认为这种状态还会持续一段时间。"

## 安全与模型发布流程

主持人问："当 Fable 首次发布时，经历了回滚和改变模型发布方式的过程。这在大多数前沿模型中都出现过。现在的安全测试情况是怎样的？你们如何决定一个新模型（比如 Opus 5.5 或新的 Fable）的发布？"

### 离线安全与数据保留政策

Katelyn 解释说："这首先要从关于安全防护的政策决策开始，包括离线安全和在线安全两个层面。"

"最近有很多关于数据保留政策的讨论，以及我们为了安全发布模型而采取的措施。原因是：你可能会遇到很多账户分布在一个庞大的网络中，有人选择创建多个账户以各种方式使用模型。当 token 在系统中流动时，我们无法实时捕捉到是否存在恶意行为或蒸馏。因此，我们需要制定数据保留政策，以便能够进行自动审查和人工审查，确保模型的使用是正当的。"

"**每个模型的发布都需要单独做出政策决策。** 例如，昨天发布的 Opus 5.5 就没有 Fable 那样的数据保留要求。但这是我们每次发布模型都必须做出的决定。如果需要有这些政策，我们就必须开展工作以确保这些政策得到执行。"

### 验证项目与授权系统

Katelyn 还提到了其他安全措施："我们还有网络验证项目，以及新推出的生命科学验证项目。这些项目意味着模型使用的在线安全防护机制有所不同。确保这些项目就位是每次发布模型工作的一部分。"

"这些都是我们在发布模型时现在必须考虑的事情，而这些在以前是根本不需要考虑的。现在大部分工作都集中在：如何防止蒸馏、在线防护、离线防护、各种政策。"

她举了一个具体的系统构建例子："我们构建了一个系统，用于确保使用某个模型或参与某些验证项目的授权能够贯穿整个系统。我们有一个非常强大的系统来管理授权，确保只有被授权的人能够以被授权的方式使用模型。"

### 能力增长带来的安全挑战

Angela 补充说："这随着能力的提升而不断升级。当我们的能力越来越先进，并在特定领域出现突破时，我们就需要额外关注这些领域。"

"很多评估都来自对特定能力的考察——这些能力可能是进攻主导的，也可能是防御主导的，需要采取不同的策略。当我们把这些考量贯穿到最终发布模型时，会有一些我们不太确定人们会如何使用的组件。"

"有些用途比较明显，比如编程——太好了，去创造优秀的产品，去发布更多东西。但其他领域如生物和网络安全，可能是双重用途的，可能产生负面效果。当然，你完全可能是合法的网络安全研究人员，在寻找漏洞，是好的行为者。生物领域也是如此，你可能在研究。所以这些项目（比如验证项目）的目的是为双重用途提供访问渠道。你需要明确你的使用场景，但我们确实希望让社区能够利用这些能力，看看他们能做出什么惊人的成果。"

### 为什么过度思考安全是必要的

主持人评论道："人们忘记了 Fable 曾被回滚，还有各种蒸馏攻击。人们会说'Fable 上没有零数据保留，太疯狂了'。但你必须记住——它曾经被收回过。有蒸馏攻击。在发布的同时这样做是好事。"

Katelyn 回应说："很多工作是在系统中构建适当的框架。我之前谈到过我们在整个系统中构建的授权和信任授予机制。"

主持人提到："平台工程中很常见的情况是，你遇到一次事故，然后为该事故过度准备，结果事故再也没有发生。"

Katelyn 认同并补充了具体的例子："确实如此。当时在各种事件发生后，我们有一个工作项目是建立一个系统，使其能够通过一个按钮就对所有人回滚。这很有趣，因为我们并不确定是否有必要做这项工作，因为我们希望类似事件永远不再发生。但在这个案例中，这实际上是把我们本来就想在整个系统中建立的原语累积起来，帮助我们管理验证项目和模型访问权限。我们把这些原语放在每个用户的模型访问之下，这样万一需要时，我们就有适当的控制措施。"

### 组合式思维与产品决策

Angela 进一步阐述了这种思维方式的转变："这样的决策实际上已经持续性地改变了我们制定路线图的方式。在传统的产品管理中，你可以假设某些事情会按特定顺序发生，你做出的决策更加具体。但 Fable 的部署这类事情，我想我们中没有人会预料到政府部门会那样使用它。显然这个概率是非零的。"

"因此，从产品管理的角度来看，这已经变得非常**概率化**。我们会问：这值得我们优先处理吗？它再次发生的可能性有多大？当我们审视这些问题时，我们实际上对未来走向的确定性非常低。所以我们实际上需要去做对冲，构建一个**投资组合式的选择**。"

"所以我们经常会采取对冲策略：我们认为这种事可能不会再发生，但万一发生了，我们希望能有对冲手段或能力来很好地处理。因此我们会优先构建这些东西。而且我们越来越发现，采用这种产品开发策略，大多数时候我们最终都会用上那个功能。"

### 验证项目的技术基础

Angela 详细解释了验证项目背后的技术架构：

"这个访问项目是一个很好的例子。我们专门为了能够向客户提供这类项目而开发了它。如果你想要双重用途——比如你拿一个模型比如 Opus，想要使用其高级网络能力进行研究或防御性用途，你可以申请这个项目。如果获批，我们实际上会**降低你的模型版本的安全护栏**，让你能够利用这些网络能力来完成你的用例。"

"这需要按用例来理解，需要确定特定用户，因为你不会对所有人开放。设计这个项目时，我们面临一个问题：应该做到多通用？还是应该过于专注于这个特定的验证门户和特定模型能力的授权？"

"我们倾向于更通用的设计，因为我们想：也许我们可以用它来做其他事情。结果证明，它后来在管理模型访问权限、处理可信访问项目、管理模型部署等方面都非常有用。"

"从普通产品管理的角度看，我通常会认为过于通用化可能不太合理，应该专注于实际的用例。但在这里，因为我们选择了更通用的方法，我们发现自己越来越频繁地使用这个解决方案，而且它带来的回报也在不断递增。"

### 信任授权（Trust Grants）系统

主持人问到信任授权与普通授权的区别。

Katelyn 解释说："其实没有太大区别。它就是授权的一种形式。有非常普通的授权——比如你向 API 发出请求，底层会访问一些数据，我们需要确保你访问的是你自己的数据。而信任授权则是我们建立了一个数据模型，非常清晰：**'信任授权'意味着你已经被授予访问某个特定模型或某个特定项目的权限。**"

"我们发现自己时时刻刻都在用到这个机制。另一个好例子是当我们首次推出 Fable 5.1 的思维保留功能时，我们给了一些客户过渡期，让他们有时间进行集成变更。要追踪谁是需要额外时间的现有客户，我们就创建了一个信任授权。然后我们可以在请求的热路径上运行一个服务，检查你是否拥有相应授权。"

"这其实与普通授权没有本质区别，但我们只是建立了一个特定于我们系统的机制，能够在需要的地方插入这些检查。"

## 一款模型的发布流程

主持人询问模型发布的完整流程。

### 从评估到客户反馈

Angela 详细描述了整个流程：

"除了安全方面（这部分更复杂）之外，现在发布模型已经变成了一套相当成熟的机制。流程大致如下：

- 我们做出模型
- 进行大量安全测试
- 评估我们需要达到的水平
- 做出必要的权衡和决策
- 进行测试
- 我们会切出多个版本的模型
- 进行评估
- 进行大量的内部自用测试
- 我们内部大量使用 Claude 来工作，因此能够看到早期信号
- 这帮助我们判断哪些变体更好
- 当我们对某些变体充满信心时
- 我们会为客户切出一个版本
- 有时会通过我们的第一方产品（如 Claude Code 或 Cowork）
- 其他时候会通过 API 客户
- 我们会与这些客户进行早期试用项目
- 他们需要对 harness 进行调整
- 我们与很多客户合作过，比如 Cognition、Harser 等"

Angela 还提到："反馈中有些是基于'感觉'的，我们也喜欢听这些。还有些是直接的评估结果：它在你在乎的事情上表现如何？我们把所有这些综合起来，当所有方面都让我们满意时，就发布模型。"

### 模型反馈的非结构化特性

主持人评论："模型反馈的状态感觉仍然非常非结构化。基本上就是一个公司之间的 Slack 频道，有人说'嘿，这事看起来不对劲'，然后其他人说'好的我来修'之类的。给我一个 ID 或其他什么。"

Katelyn 回应说："这确实是像 LLM 这样的非确定性产品的特质。参与我们早期试用项目的客户都是那些拥有非常完善的评估体系的客户。我认为很多对话确实是比较感性的、即兴的，部分原因是我们处于竞争状态——我们希望尽可能缩短从切出测试模型到向所有人开放的时间窗口。"

"我们倾向于选择的客户是那些我们知道他们会运行完整的评估套件，并能够尽快给我们反馈的人。当然还有感性反馈。当然，未来肯定有系统化的改进空间。但你会感到惊讶的是，世界上有很多代理式产品竟然没有好的评估体系来帮助测试这些模型。"

### 客户反馈中最有价值的部分

主持人问："什么样的反馈有帮助？是回归问题吗？我们发现这里有回归，注意到那里有好的属性？"

Angela 回答说："好的反馈总是非常令人振奋。我们往往并不感到意外，但我们希望在某些假设上得到验证。**说实话，最有用的反馈是负面反馈。** 比如'在这件事上表现不好，在那件事上也不行'。我们喜欢这种反馈，然后就会想'好，我们怎么修？'"

她举例说明了模型行为调整的难点："有些反馈真的很难处理，因为并不是每个人都希望 Claude 在任何一个维度上都落在完全相同的位置。一个好的例子是**惰性与主动性之间的平衡**。有时人们说'赶紧完成我的任务，别偷懒，做得更好'。另一些时候人们说'我们本来只是在探索和规划，结果你跑去写了一堆代码，或者采取了一大堆我还没准备好的行动'。"

"要在这个问题上做到完全正确几乎是不可能的，因为不同的人实际上想要不同的东西。但我们确实有过这样的情况：切出一个早期版本，发现惰性太强，于是把它放回'烤箱'再训练一下，把那种行为纠正掉。这类问题如果我们只是在内部自用测试，可能不会发现。把它放到 API 环境中让所有客户运行并告诉我们哪里需要改变，这一点非常重要。"

### 个性化与评估的挑战

主持人提出了一个核心问题："如果我站在你们的位置，模型产品管理中最难的事情之一可能是**对齐与个性化的平衡**。你想为所有消费者设定默认的人格和行为，但同时又想能够非常快速地响应某个用户的 Claude MD 指示——比如'请比默认更主动一些'。"

"以 Frontier Code 为例，模型曲线看起来奇怪的原因是它惩罚过多的活动或过多的文件操作。这是有设计目的的。但我可以轻松地在我的 Claude MD 里说'别那样做'，然后它就不会那样做。所以，我的基准测试是否不公平地惩罚了 Claude Opus 5.5，因为我的基准测试没有包含这种主观的个性化元素？你们如何处理个性化？"

Angela 坦承："我们在这方面的处理并不完美。这真的很难，非常难，而且各种因素在相互竞争。"

"A 提到'Claude 宪法'，但那是老东西了。宪法对于某些方面有帮助，但在如何根据不同的指令和偏好进行个性化方面，我们很难做好。"

"我们通常尝试通过提供更多参数来解决这个问题，让我们能够针对不同的客户群进行调整。如果我们无法控制你的客户群（比如你是 API 客户），我们会给你提供建议，然后你自己进行调整。"

"现在有一些参数可以调节，比如**努力程度**（level of effort）——你应该投入多少努力，模型的大小等。但这离我们真正需要的那种个性化水平还很远。"

"目前我们很多解决方案是**在收集到的所有反馈中尝试体现相互矛盾的品味**，然后在这些事情上做出判断。但我知道随着客户和用户规模的扩大，这不是可扩展的做法。我们需要开发让 Claude 接收个人化信号的方式。但就目前而言，我们确实只是在很多事情上做出判断，这相当困难。"

### 默认努力程度的调整

主持人提到："默认的努力推理设置改变了，现在是中等。这是那些可能影响普通客户的事情之一，因为大多数客户不会使用这个开关。"

Katelyn 确认说："这是 Claude Code 的设置，他们默认设为了中等。"

Angela 补充说明："这是一个很好的参数例子，我们用它对不同的子群体进行轻度定制。默认设置会根据你是免费客户还是专业客户、Claude Code 还是 Cowork、企业版还是 API 客户等因素进行调整。你当然随时可以调整它，但这是我们提供的一种轻度定制方式。"

"我们犹豫的一点是：我们不想让人们觉得无法控制自己的 Claude 定制。我们更倾向于提供温和的默认设置，同时给用户调整的选项。这目前还算有效，但我预计未来我们会在这方面做得更好。"

### 参数管理的复杂性

Katelyn 进一步阐述了参数复杂性的挑战：

"每次发布模型时，有一个重要问题是：Claude 在某些方面变得更擅长了，有时我们应该把这些能力作为 API 参数暴露出来让用户控制。但随着时间推移，我们积累了各种参数——effort、budgets 等等——用户怎么可能弄明白对于任何给定任务应该设置什么组合呢？"

"这是我们和客户一起探索的事情。我们在弄明白哪些参数应该被弃用，哪些应该有更好的默认值，哪些应该是 1 到 100 的刻度还是低中高的刻度。我们实际上训练了 Claude 来理解一系列选项，但是否我们应该暴露所有数百万种选项组合？这样用户反而会无所适从。"

"这实际上是 **Claude Managed Agents**（CMA）价值主张的一部分——你仍然可以通过 API 编程访问 Claude，但你获得了一个开箱即用的 harness。每次发布模型时，我们都会做大量工作来弄明白新参数是什么、破坏性变更在哪里、以及如何从 Claude 中获得最佳表现。对于使用 CMA 的人来说，这些工作你就不用操心了。"

### Claude Managed Agents 简介

主持人指出很多人对 CMA 还不太了解，请 Katelyn 做个简要介绍。

Katelyn 解释说："简单地说，我们目前有两套 API 体系：

- **Messages API**：本质上是原始 token 访问。
- **Claude Managed Agents（CMA）**：一套 API 套件，让你能够定义一个智能体、与它开始会话。

它本质上是一个更高层次的抽象，让你跳过搭建基础设施和 harness 的大量工作。对于想要编程方式运行智能体的人来说，这是一种更开箱即用的集成方式。"

### CMA 与 Claude Code 的基础设施共享

主持人问 CMA 是否与 Claude Code 共享基础设施。

Katelyn 回答："有很大程度上的共享。作为平台团队，我们运营 API，同时也运营所有的基础产品服务和产品基础设施。一个很好的例子是：我们团队运营的沙箱集群同时支撑 CMA 和 Claude Code 等产品。但在实际的 harness 层，这两个产品的需求有所不同，因此它们并不共享同一个 harness。但它们共享大量支撑执行和 API 的基础设施。"

主持人评论："人们应该更多地使用 CMA。基本上在你们发布之后，每个人都做了模仿版本。俗话说，模仿是最真诚的奉承。"

### 记忆与 Dreaming 的进展

主持人询问："既然提到这个话题，我们简单说说上半年 Anthropic 在记忆方面的工作。它是不是停滞了？现在还在继续吗？"

Katelyn 回应说："记忆和 Dreaming 仍然是我们工作的重要部分。我们发布 CMA 时，它是为一个特定目的而设计的：**一个平台，让那些不想亲自做所有事情的人可以放手，让我们的团队来确保你从 Claude 中获得最佳效果。** 我们在持续对这些进行评估，确保 harness 是强大的。"

"但我要说的是，正如我们之前讨论的，随着模型发布在安全方面变得越来越困难，我们团队的大部分精力已经从'开发有趣的功能来优化智能体'转向了'如何将安全带入所有这些工作中'。因为最重要的事情是让模型的能力上线，并且安全地上线。"

"所以，与今年早些时候相比，我们在 skills、Dreaming、memory 这些方面确实放缓了节奏。"她补充说："我们并不是什么都没做。我们依然很重视 skills。但相比其他方面的工作，这些方面的进展确实放缓了。"

### Dreaming 的技术架构

Angela 详细解释了 Dreaming 的底层机制：

"Dreaming 本质上是构建在 CMA 之上的多智能体系统。**Dreaming 的运作方式是：我们启动另一个 managed agent，让它可以检查之前的 managed agent，然后向它写入记忆。** 所以它是'managed agents 一层套一层'。"

"这是有意为之的设计，因为我们设想你可以将许多模块化组件组合起来，构建出有趣的东西。Dreaming 只是其中一个例子。"

"我们一直在思考：其实还有很多其他策略可以做。比如：

- **Best-of-N** 作为多智能体策略
- **验证者智能体**（verifier agent）专注于目标或结果
- 还有很多其他可能

我们见过人们做过一些非常疯狂的东西——比如有一个 harness 在所有任务之间共享疯狂的记忆，并启动大量并行智能体。我们看到后就觉得：其实我们应该让你们能够这样做，就像我们构建 Dreaming 那样，让 managed agents 一层套一层。"

"我们很快就会有一个更新，更新底层原语，将其暴露给用户，允许他们构建 harness 策略——或者你想怎么称呼都行——**多智能体策略**。我们会给你们模板，比如'这是我们开始构建 Dreaming 的方式，也许你作为开发者想在此基础上做一些更新，从中找到更多的价值。'"

"这其实是很好的框架：与其说我们在放缓这些工作，不如说我们已经搭好了基础原语，可以让人们直接使用这些原语，同时赋予他们工具来构建更酷的多智能体策略。而我们团队的大量精力则转向确保模型安全地在此系统中获得访问权限。"

## 评估（Evals）的最佳实践

主持人请 Angela 分享关于评估的建议和最佳实践。

Angela 说："评估有很多不同的类型，对吧？不同的评估适用于不同的场景。有静态的确定性评估，也有 LLM 作为裁判的评估，还有各种不同的策略。但我首先要说的是：**根据我们从大多数人那里观察到的情况，你需要的评估可能比你想象的还要多。**"

"不存在一套完美的评估集能给你所有答案。我们发现人们最终需要相对庞大的评估套件。你可以让你的智能体与你合作，随着时间推移不断演进你的评估套件。"

"不要在这里投资不足，这可能是我们见过的人们犯的最大错误。"

Katelyn 补充说："我的建议是从简单开始。有些人看到所有选项后会有些疯狂，他们想'哇这太疯狂了，让我试试这个试试那个，哪个最好？'但当他们在做这些事情的时候，他们实际拥有的评估数量是零。所以不如从简单的东西开始，它会有所帮助。"

### 将工程视为研究

主持人分享了他们的经验："对于 Fable 和 Astroclass 这类模型，我们把工程当作研究来做。当你把工程当作研究来做时，你自然会做更多的评估、更多的标注、更多的运行扩展——你是在构建 harness 或产品，但你的方法像做研究一样。"

"你要预先定义你的目标，尝试将其形式化为评估，然后识别为什么失败。有时你的评估本身是错的，有时你的环境是错的，有时才是模型的问题。实际上，这正在成为 AI 工程的本质。"

Katelyn 完全同意："我们会在 CMA 中继续发布更多功能，帮助人们更容易地做这类事情。你会从我们这里获得帮助你为 managed agents 创建评估的产品。这感觉就像与 Claude 一起工作。"

"Claude 实际上非常擅长创建评估。人们看到 JSONL 文件时往往会大脑一片空白。但一个漂亮的评估界面，你可以左右对比打分，就像人类标注员所做的那样，你可以自己做，把 Fable 放上去，它就能生成评估结果。而且它还会写注释——它输出所有评分，然后 Claude 可以直接消费这些结果，并在此基础上改进自己。人们只是不知道可以提示模型生成评估。"

主持人评论："我喜欢这种说法。这非常鼓舞人心，因为这让你能够非常系统地更新和编辑这个系统。随着新模型的改进和变化，你可以真正审视你的系统在哪里，它会持续演进，优化每一个部分。"

## 工作负载的演变：从编码到前沿科学

Angela 分享了她观察到的客户工作负载变化：

"我们讨论了大量关于安全和模型发布的话题，但这一切最终是为了帮助人们驱动工作负载。我们看到工作负载正在发生很大变化。"

"在某些工作负载中，智能似乎越来越达到饱和状态，这是一个新情况。但仍然有很多任务类别远未饱和——实际上比人们可能预想的要多。这些任务正越来越多地走向一个方向：**通过运行极长时间自主的智能体任务来获得超额收益。** 这些任务在历史上你无法用暴力破解，但现在有了更多智能在背后，也许你可以了。"

"这类工作负载对我们来说非常迷人。我们看到很多价值来源于此，既有企业从中获得价值，也有新公司和初创企业希望在此基础上构建智能体原生产品。"

"如果你看今天的任务类别，很多显然是编码类的，还有很多企业创新加速类的东西。但它们往往呈现出**自动化一个非常明确且具体流程**的形态。在某些领域，这真的开始奏效了，这很棒。在某些领域仍然不行。所以还有很大的空间去演进和推动这些模型的前沿。"

"然后还有一类全新的工作负载，比如我们之前讨论过的生物和网络安全。这是一组非常复杂的硬工程或硬科学问题。这些工作负载越来越多地出现在我们面前，作为一个真正有趣的空间，可以为客户创造价值。"

## 如何在团队内对抗"Slop"

主持人询问："你们如何在团队里对抗'AI 低质量内容'（slop）？"

### 文档中的 Slop 问题

Katelyn 分享了她团队内部的讨论：

"我们在这方面有过很多有趣的内部辩论。我们和任何人一样。如果你想生产一份文档或代码供他人使用，你当然应该使用 Claude 来帮助你。但如果你让 Claude 完全生成一个东西，自己却没有花时间真正阅读并确保它是高质量的，那你就是在给消费者增加额外负担——他们需要花大量时间去解析它。这简直是疯狂的、完全不公平的。"

"所以我们向团队强调：你不能那样做。如果你在产出东西，用 Claude 没问题，但你必须确保它是高质量的。**你作为人类仍然对质量负责。**"

"但有意思的是，因为一些'Claude 痕迹'（比如文档中的 M 破折号），人们的头脑会触发'我在读 Claude 写的东西而不是人写的东西'的信号，然后感到厌烦，因为他们想读的是达到人类质量标准的东西。"

"所以我们试图在团队内设定的标准是：**使用 Claude 来帮助你，但不使用它才是愚蠢的**——这个极其强大的智能体可以加速你的工作和生活。但它必须达到一定质量标准。对于消费者和读者来说，如果真的是低质量内容，就退回去，说'不行，我不在这上面浪费时间'。同时，也不要对小的 Claude 痕迹过于挑剔。我们需要找到正确的平衡。"

### 代码中的 Slop 问题

Angela 补充了工程方面的看法：

"在工程方面情况类似。我认为我们已经到了一个不错的阶段：人类在系统设计方面发挥很大作用，而**实现通常由 Claude 完成**。对于很多代码，你只需要快速审查一下就可以继续。你不一定需要有人逐行深度审查每行代码，因为你更关心的是整体计划和设计是否良好，而不是具体的实现是否完美。"

"我们显然依赖大量验证来确保交付的东西是高质量的。所以如今关于'代码质量低'的讨论已经减少了很多。这部分是因为 Claude 本身变得更好了，但另一部分是因为我们建立了适当的验证机制来维持高标准。"

### 产品管理中的 Slop 问题

主持人提到产品管理中也存在类似问题："你可以一天就发布很多功能。但我们应该更有意识地使用模型能力，而不是简单地向生产环境发布 10 倍多的功能。应该花更多时间理解用户、尝试实验。你很容易不断发布随机的东西，但你应该真正思考你在做什么。"

Katelyn 认同地说："我经常对这个问题感到愤慨：**软件和产品的规划与发布流程中仍然有很多基础工作，不应该因为智能体加速了某些环节而被跳过。** 但很多人开始产生一种'懒惰'——觉得'我不需要再思考流程中的某个部分了，因为智能体在帮我做'。但这些仍然是流程中极其基础的部分，你应该把时间和精力花在上面。"

"这就像创始人和创作者面临的情况：实验和探索的成本现在变得如此之低，以至于我应该做更多的实验。但实际上应该**用一个你从一开始就非常明确的目标来驱动这些实验。** 这很难，因为你手里有一个能做一切事情的玩具，你会忍不住到处尝试。"

## Angela 的推文角

主持人说接下来是"Angela 推文角"，会让 Angela 感到不舒服。

### 最喜欢的推文

Angela 表示她其实没有最喜欢的推文。"不过我喜欢那条：**'半心半意地做某件事是昂贵的做事方式，因为实际上你并没有在做。'** 这和我们今天的话题非常相关。"

### 这条推文的思维背景

Angela 分享了她写这些推文的经历："这已经是很久以前的事了。我经历过一段时期，阅读量非常大。我发现自己对当时做的事情感到非常无聊，觉得自己没有在智力上受到挑战。所以我进行了一段'读书狂欢'——**一年里读了大约 200 本书。**"

"我当时只是对一切都很好奇，想读所有东西。我怀念在学校时那种智力上的'肌肉训练'——面对一个新话题，你必须去学习它，这很艰难，并不是特别有趣，但你确实在挑战自己。工作几年后，我觉得自己停止了这种训练。工作本身很有趣，也有挑战性，但缺少那种智识层面的挑战。"

"所以我进行了这段阅读狂欢。我有一趟非常长的通勤，那是一趟地狱般的火车，所以阅读是很好的时间利用。从那段经历中出来，我思考了很多。当时我发推文并不是为了涨粉。我几乎没有粉丝，那些推文是写给我自己的。"

"我给自己设定的个人测试是：**如何用尽可能少的词来压缩我脑中的想法。** 后来人们开始喜欢这些推文，我就继续写下去。再后来工作太忙了，就停止了。"

主持人说："很高兴看到你的分享。"

### 书籍推荐

Angela 说："我最喜欢的仍然是 **Nassim Taleb 的《黑天鹅》**。这对我来说是一本改变人生的哲学之书，它给了我一种看待世界的完全不同的方式。"

"Fable 事件发生时，我想到的就是黑天鹅——一件你原本不知道可能发生的事情。一旦它发生了，它就永久地改变了你对事物运作方式的认知框架。黑天鹅这个概念如此简单，但他做得非常好的一点是真正击中了要害，并清晰地阐述了这是世界许多领域的共同属性。我非常喜欢那本书，那可能是我最喜欢的。"

主持人补充："如果你觉得那本无聊，可以读 Taleb 的另一本《随机漫步的傻瓜》。你读过《反脆弱》吗？"

主持人又问 Katelyn 是否有类似推荐。Katelyn 表示需要想一想。

### Slack 工作方式

主持人问起他们在 Slack 上的工作方式。

Katelyn 说她在 Slack 上非常"强迫症"："我对邮件和 Slack 都要做到 inbox zero。邮件比 Slack 容易一些。我会非常激进地管理哪些频道是我真正在参与的，哪些是静音的。我总是在确保自己掌握需要掌握的信息。"

"但这就像一份全职工作。有些日子我觉得：我可以取消所有会议，不写任何文档，什么都不做，只坐在那里在 Slack 上待一整天，然后会感觉像做了一整天的工作。这太疯狂了。"

"我会收到很多反馈说我很难在 Slack 上找到。所以现在经常发生的事情是，有人会发消息给 Katelyn 说'你能让 Angela 回复一下吗？'"

## 招聘与开发者关系（DevRel）

### DevRel 团队的建设

主持人转向 Katelyn 询问招聘和开发者关系团队的情况。

Katelyn 说："当 Lance 加入我们团队时，这确实帮了大忙。让我们的 DevRel 团队建立起来。"

"我刚加入 Anthropic 时，我们的团队非常小。我们负责平台、API 业务以及所有产品基础设施。我们的 DevRel 职能在 Anthropic 内部非常新，当时并不一定在产品与工程组织内。"

"我们后来在平台部门和 Claude Code 部门分别设立了 DevRel 团队，部分原因在于这两个是非常不同的开发者生态系统——一个是 API 业务，一个是智能体编程。"

"我当时要负责 DevRel，虽然之前在 Stripe 有接触过，但从未直接负责过。我说'我不知道自己在做什么'，然后 Lance 给了我这三个支柱的概念——**产品、内容、社区**。现在我可以随时脱口而出，人们会觉得'哇你真的懂 DevRel'，但我其实是'偷来的'。"

### 平台 DevRel 的独特挑战

Katelyn 详细说："我现在没有平台 DevRel 团队的管理者，这是我正在招聘的职位之一。我们的 DevRel 个人贡献者直接向我汇报，部分原因是这确实是一个极其困难的问题。"

"平台业务面临的一个特殊挑战是：**在我们的公众叙事中，平台业务可能被夹在研究、政策工作和应用（如 Claude Code、Cowork）之间而变得不易被看见。** 当我们想到 Anthropic 时，大家通常首先想到的是研究和政策，而不是我们实际上在运营一个巨大的开发者平台业务。"

"所以我们的 DevRel 团队的一个大目标是：不仅要处理传统的产品反馈收集等工作，还要**找到我们自己的声音、品牌和叙事，确定我们在社区中的角色**。"

### 思想引领者与"大师建造者"模式

Katelyn 提到她对团队风格的想法："Lance 非常技术化，他的 DevRel 方式更像是教学——他写关于记忆、成本管理的文章，深入构建评估，产出大量高质量技术内容。我很喜欢这种方式——我们的 DevRel 团队可以成为这个新兴、困难且不断演进领域中的**思想引领者**。"

"他们是教育者、思想引领者、事物的解释者。"

主持人分享了他喜欢的另一个模式："我喜欢一个叫**'大师建造者'（Master Builder）**的概念。我会用平台去构建东西，展示什么是可能的，然后你会觉得'我没想到这在 Claude 平台上可能实现'。这个概念来源于乐高。乐高是怎么卖乐高积木的？他们有大师建造者，用乐高积木建造东西，然后你看着就想'我也想这样做'。"

Katelyn 回应："这很棒。我们团队的另一位成员 CJ 也做了很多这类工作——写 cookbook、发布示例、在 X 上积极与社区互动。"

### 从 Cookbook 到 API Skill 的演进

主持人提到："当 LLM API 在 2023 年刚刚推出时，cookbook 非常重要。现在呢？没那么重要了。"

Katelyn 承认了这一变化："有趣的是，现在的情况不再是'复制粘贴代码然后使用'。但我认为 cookbook 仍然能向人们展示可能性——什么是用例，以及如何实现它。"

"我们之前有一个工程师写了 computer use 的 cookbook，那个东西复杂性极高，至今还在'困扰'他。那个时代你需要处理所有截屏和各种 Messages API 之间的复杂交互。"

"现在，我们有了 **Claude API skill**——它非常擅长帮你（无论是在 Claude Code 中还是其他编程智能体中）构建高质量的集成。现在很少有人会去翻那个巨大的 cookbook 了，更多人会加载这个技能，在编程智能体中操作。"

"有趣的是，Claude API skill 是我们的 DevRel 团队负责的，是 Lance 构建的。这确实是 DevRel 最高杠杆的形式——**将所有最佳实践蒸馏到智能体中使用的东西中。**"

### DevRel 的未来：前台与后台分离

主持人分享了他对 DevRel 未来发展的看法：

"我有时想告诉人们'你其实不需要 DevRel'。更好的是，让工程师和领导者成为公众面孔。Boris 刚出现时就是这样的：'嗨我是 Boris，Claude Code 的创造者'，他同时做着日常工作，同时也扮演着这个角色。"

"一个幸福的团队的最明显标志是所有人都快乐地工作，公开表达认同，没有人离职。"

Katelyn 承认："Cloudflare 团队就是个很好的例子。他们所有人都很棒。"

主持人进一步阐述了他对"前台与后台分离"的想法：

"我称之为 **DevRel 的前台与后台解绑**。典型做这份工作的人从开始到结束做所有事情，相对自主。但你可以建立一个后台团队，让你的产品负责人和工程负责人真正走上聚光灯下，只需要一个简单的约定：你坐下来和我聊 30 到 60 分钟，我们做一次头脑风暴，然后你就回去工作了。我们会帮你代笔。"

"那个负责制作、写作的人员团队为其他人提供服务。我认为这就是这类工作的未来。因为人们不想听 DevRel 的人说话，他们想听 **N** 说话。"

"Lydia 也是通过 Boris 才被大家认识的。但从功能上讲，他就是在做这件事。人们想听产品背后的人说话，而不是听一个付费发言人。当然这是一份工作，总得有人做。但合理地讲，你不能指望做工程的人同时也擅长对外表达。所以你应该雇一个专门做这件事的人。专业化是一种技能。"

主持人总结他的比喻："就像每个人都需要招聘，但你有一个人力资源部门。人力资源部门帮助你更好地招聘。"

## 结语与行动号召

### 用 Opus 5.5 可以尝试什么

主持人询问嘉宾，对想要尝试 Opus 5.5 的人来说，有什么建议。

Katelyn 说："Opus 5.5 非常具有成本效益。它没那么啰嗦了，所有我们提到的事情——感觉非常好。昨天对我们来说是很有趣的一天，我收到了一大堆朋友和前同事的短信，说'这个模型太棒了，谢谢你们'。我的一个前老板给我发消息说'Opus 5.5 刚刚在一次事故处理中救了我们的命'。这就是'我们回来了'的感觉。"

"所以，如果你之前因为成本和 token 效率而犹豫是否要尝试某些事情，现在是时候重新审视这些问题了。与那些成本效益较低的模型相比，我认为你会用 Opus 5.5 取得更大的进展。"

"我建议你尝试一些**多智能体设置**的东西。你会发现它非常擅长这个。"

### 多智能体架构的最佳实践

Angela 分享了关于多智能体系统的具体建议：

"这方面的表现很好。一般来说，你希望有一个主导智能体，然后把任务拆分成很多不同的部分。只要你有一个可以并行化的任务，并且它们在统一的上下文下共享信息，你就会获得很多收益。"

"当然，这取决于你正在解决的问题。但越来越多地，这是我们处理很多事情的更优方式。尤其是当每个子智能体（或者你想怎么称呼这些子负责人）是**异步的且不相互阻塞**时。"

"这是你在架构上需要关注的两点：

1. **共享状态**——确保它们可以并行处理
2. **子智能体不互相阻塞**

除此之外，放手让它跑，看看 Claude 为你设计出什么。我认为越来越多的架构会朝这个方向发展。Claude 会变得越来越聪明，它将学会如何自我拆分、自我克隆，并调整自己以适应合理的架构。"

"你只需要确保两件事：它有共享状态，并且不会阻塞它的子智能体。只要包含这两个原则，我认为人们就应该去实验，去尝试一些真正疯狂的东西。我不会惊讶于看到一些非常有趣的成果——也许有些问题人们觉得非常难缠、非常烦人，但像这样的方法可能实际上能一次性解决。"

主持人总结："很好，大家去构建吧。"
