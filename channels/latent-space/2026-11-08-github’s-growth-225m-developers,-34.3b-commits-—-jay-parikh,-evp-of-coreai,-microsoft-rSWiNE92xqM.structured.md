# GitHub 的规模与进化：2.25 亿开发者、343 亿次提交与 AI 编码代理的新时代——对话微软 CoreAI EVP Jay Parikh

## 导语：GitHub 的规模与变革

GitHub 位于我们所有开发工作的核心，并且越来越成为智能体与人类协作的核心。很多人因为宕机对 GitHub 有诸多批评，但它也是今年首个在可靠性方面达到 09s 的服务。不过，人们并不知道 GitHub 正试图以何等极端的规模演进自身，以适应人类和智能体的需求。

今天接受采访的是 **Jay Parikh**，微软 **CoreAI（核心 AI）执行副总裁（EVP）**。事实上，他或多或少是包括 GitHub 在内的许多核心 AI 服务的领导者。我们之前采访过 GitHub 首席运营官 **Kyle Dagel**。在 GitHub Universe 大会上，他们发布了许多新更新，涵盖基础设施层、模型层、应用层等，其中包括 **Copilot**——这款最初的编程助手大约五六年前发布。

一些统计数据令人难以置信：GitHub 上约 **40% 的拉取请求（Pull Request）由智能体创建**；智能体总量在 6 个月内增长了 6 倍。因此，GitHub 的构成已经发生了很大变化。即便如此，人类对 GitHub 的采用也在持续增长，目前已经达到 **2.25 亿开发者**——我还记得当初 8000 万开发者对他们来说就已经是件大事。而且，基本上全年每一秒就有一名开发者加入，这极其庞大、令人震惊。与此同时，他们还在尝试迁移到 Azure。这一切演进需要大量领导力。

幸运的是，Jay 在这个领域资历深厚：他不仅曾担任 Facebook 工程负责人，还担任过 **Lacework** 首席执行官，以及 **Ning** 和 **Akamai（阿卡迈）** 的工程副总裁——他就像是汇集了基础设施、安全乃至社交媒体领域的“复仇者联盟”。别忘了，GitHub 其实是一个开发者社交网络，大家共同维护着这个我们所有人都依赖的服务。这段旅程并非一帆风顺，但说到宕机和停机，我们谁又能独善其身？确实有很多人试图取代 GitHub，但 GitHub 永远是 GitHub。帮助理解我们所有人协作、发布开源成果、发现安全问题所依赖的核心平台的演进，符合我们所有人的利益。

我们目前正在筹备 **AIE code**，这是今年最后一场 AI 工程师会议，也是唯一一场完全专注于旧金山编码智能体的会议。为了准备这场会议，我觉得发布这次采访会很好，帮助大家从心理上为这一年编码领域发生的规模、雄心和变化做好准备，并预览明年。因此，我当然要问 Jay：GitHub 在 2027 年会是什么样子？希望你坚持到最后，看到他的预测。

## 对话：从 GitHub Universe 到未来的编码平台

### 头条数字与平台增长

**主持人**：我们正在你的主题演讲之后录制。感觉如何？恭喜又一次成功的 Universe。

**Jay Parikh**：是的，今天有很多内容要讲，很多好东西。

**主持人**：确实有很多好东西。实际上，有些内容你在台上甚至没时间讲。

**Jay Parikh**：没错，没错。比如安全方面的内容，还有接下来今明两天的各个工作坊，可以深入探讨并动手操作。

**主持人**：不过，让我们为播客听众重申头条数字。我不得不去查一年有多少秒，因为你说今年每秒都有一名开发者加入，那就是 3150 万。非常令人印象深刻。GitHub 总人数是 2.2 亿？

**Jay Parikh**：是 2.25 亿。

**主持人**：那都是谁在加入呢？嗯，每秒都有一个。你展示的那些图表真的很令人印象深刻，我认为这正是人们没看到的。他们只期待 GitHub 永远正常工作。

**Jay Parikh**：是的，你刚才已经提到。平台上现在有 **2.25 亿开发者**，覆盖世界上每一个国家。在去年的 **Octiverse 报告**中，每秒就有一名新开发者加入平台，而且这是连续第二年这样。此外，在 Octiverse 报告中，我们还谈到了几个主要统计数据：代码推送有 **179 亿次**，提交有 **343 亿次**，拉取请求有 **13 亿个**。开源社区继续比去年构建和分享更多，增长了 2.5 倍。我们平台上的开源社区或项目贡献达到 **21.5 亿次**。

**主持人**：对于开发者和工程师来说，这就像数据库写入、文件写入和元数据编写。绝对是一个代码社交网络。你曾从事社交网络方面的工作，管理这个社交网络是什么感觉？

### 从开发者社交网络到“人人构建”

**Jay Parikh**：你知道，这显然是一群非常不同的最终用户或平台使用者。但考虑到 AI 当前的发展，我认为存在一个非常大的机会：这个社区现在可以涵盖更多人。历史上，GitHub 可能只属于软件工程师、产品经理或设计师。但现在，你不必是一名熟练的软件工程师也能使用 GitHub。编码智能体可以为你做很多事情，而你可以分享一个想法。我前几天和另一位记者聊天，他正在试验一些东西，然后决定创建一个仓库，并想与人们分享这个仓库并获得反馈。我认为这是世界采用和学习 AI 共同构建事物的另一种方式。这就是我今天在主题演讲中说的：这个社区最了不起的一点是，你不必独自构建——我们都在这里共同构建。

### 智能体与“拉取请求的终结”？

**主持人**：我觉得你们得到的一个非常重要的背书来自 **Pete Steinberger（OpenClaw）**，他可能是你们排名前 0.001% 的用户，真的在把 GitHub 推向极限。我认为他有趣的推动之一，也许是“拉取请求的终结”。不知道你们是否考虑过这一点，以及它如何随着智能体而改变。

**Jay Parikh**：是的，当然。我认为你们——Peter 和团队——合作得非常愉快，他们不断推动我们变得更好、更好、更好，这正是我们欢迎的，因为技术发展非常迅速，我们希望不断迭代、不断构建。随着新范式的出现、新工作方式的兴起，我们会不断演进、适应和改变平台。如果其中某个概念不再有用，或者人们不希望它成为必需，那它可以被配置。但请记住，在 2.25 亿开发者、大型企业、小型团队、学生等之间，我们确实必须提供一个包含许多概念的平台，然后你应该能够按自己想要的方式将这些概念组装起来。我有一些仓库是我自己摆弄和玩耍的，我不做 PR。对我来说，我只是不断抛出想法，不断构建、构建、构建，我不想处理 issue 或 PR 之类的东西。所以，平台应该允许并提供这些功能，我们会不断适应。

### 重新定义仓库与代码

**主持人**：是的，很有趣。还有一个概念：也许代码只是可执行软件之上的抽象。你在主题演讲中突出展示的一个仓库，来自我的一位演讲者 **Matt PCO**。那只是一个 markdown 文件夹。但这确实让我想到，GitHub 有整个语言细分功能，比如这个仓库是 76% Rust，但现在也许不再重要了。那么，什么是仓库？什么是代码？我们在存储什么？因为你需要的不仅仅是可执行文件。

**Jay Parikh**：是的，我认为仍然有很多代码存在。你想想所有用 Java 和 .NET 编写的、正在运行关键业务的大规模企业代码。它们都在进行安全修复、现代化、优化、修复错误的过程中。所以请记住，它涵盖了许多不同类型的内容和文本，其中一些已经有几十年历史，而另一些在我们交谈时正被生成到生产环境中。因此，工具必须灵活，而且今天有很多选择。我们也关心并相信开发者需要选择。我是一名开发者，对某些事情很挑剔，我想要某些东西，因为从某些方面说，这是我的个性，或者是我通过使用的工具表达的一种手艺。

### Copilot Harness 与 Fusion：编排多模型

**主持人**：是的，没错。还有几件事我想谈谈。**Fusion** 非常重要。对我来说，它就像是一种对“harness”的元抽象。**Copilot** 是第一个 harness，到现在已经三年、四年，也许四年了。

**Jay Parikh**：四年左右。

**主持人**：但 harness 最根本的核心工作是最大化利用模型能力，其中很重要的一个部分是模型路由。你能多谈谈为什么在这方面建立领导力如此重要吗？

**Jay Parikh**：好的，这里有几点。第一，我们已经讨论过，并且今天发布了更多关于 **Copilot harness** 的信息。这个 harness 我们已经开发了一段时间。我们相信 SDK 部分很重要，这样你可以拿这个 SDK 去构建其他应用。我自己这样做过，很多人也这样做过。这个 harness 本身支持许多不同的东西，但其关键原则之一是多模型，你可以决定在哪里接入这个 harness。它也支持并持续改进，以适应 **MCP（模型上下文协议）**、编码所需的其他工具，以及不断出现的新模型。harness 到位之后，你需要一些智能来将一个任务、一个提示或某个最终将成为完整软件工作单元的事项分解，并在一定程度上减轻你作为工程师的认知负担。所有这些模型在价格、性能等方面各不相同，我们可以说：“嘿，我们可以为你优化，用更低的成本更快地获得最佳质量。”我们会继续迭代，还有很多想法，会不断改进。我把它看作 harness 和 Fusion 相互消长，因为你解决的正是开发者面临的那个工作：对所有工具的编排。但你也希望有 Fusion 来帮你决定使用哪个模型，因为今天选择实在太多了。

**主持人**：是的，我认为模型选择非常重要。显然我曾在播客上请过 Satia 来谈微软在这方面的信息。我真的很喜欢你们正在做的另一件事：基本上是 Copilot 覆盖每一个界面。你们有很棒的移动应用、桌面应用，你们都展示了。我的问题是：你们是否觉得需要在那里创新，还是说它基本上就是微软品牌版本，别人也有？你是否必须在 UI 上创新，还是只要在模型层做好就行了？

### 跨界面 Copilot 与智能累积

**Jay Parikh**：我认为两者都需要。今天我在很多方面谈到的是：每一层都在演进。这包括深层、底层的基础设施、存储、计算、网络、安全等；然后是平台层，我们谈到了 Git、Actions、AI Gateway 以及当今支持 Git 的许多其他服务；接着还有工作流，以及不同的界面。所以我认为让这一切都变得优秀很重要，这在很多方面是一条“铺好的路”。对我们来说，这关乎栈中每一层的创新与演进。还有一点：当你使用我们的界面时，比如 GitHub Copilot 应用、VS Code 或 .com，现在它们都通过同一个 harness 连接在一起。这非常强大，因为你可以手机上发起某个任务，然后可以在桌面或笔记本电脑上继续；或者你有另一个想法，把它输入手机，它会继续运行。但重要的是，所有这些上下文都伴随着你——在你的仓库、issue、PR、安全发现中。而且无论你使用什么模型，所有这些上下文、记忆、偏好，以及我今天早上谈到的智能引擎，都会在一个地方为你累积。今天，如果你使用不同工具，从一家提供商用这个工具，然后又换到另一家，它们不会把智能累积在一起。我们想尝试解决的就是：你应该能够完成越来越多的工作，而且会更便宜、更好、更快，因为你利用了我们平台和工具的力量，但你仍然可以大幅定制：使用不同模型、Fusion，以及其他工具。

### 安全与 AI 生成代码的质量门槛

**主持人**：太棒了。我想把安全内容留到接近结尾再谈。你们有巨大的责任，我认为最近随着 PHP 事件，这显然是头等大事。你想让人们了解 GitHub 在做什么？

**Jay Parikh**：是的，这里有很多工作在进行，我们还有很多工作要做。几件事。首先，从产品或功能角度，我们谈到了若干内容。比如我们现在有 **Code Review Max**，它应该能帮助发现更高严重性、更隐蔽的代码错误等。由于生成了如此多的代码，确保质量不下降非常重要，Copilot 代码审查等功能可以帮助维持质量标准。第二，是我们在安全和 **GitHub Advanced Security（GitHub 高级安全）** 方面所做的一切，现在已经加入了 AI 扫描技术。在主旨演讲演示中，Damian 不小心推送了一个密钥，但系统阻止了它进入仓库。我们还有更多：深度扫描可以寻找不只是表面漏洞，我们会持续推出大量功能。今天有多个深度工作坊，可以将更复杂的 AI 扫描嵌入到你的工作流和软件交付方式中。此外，微软安全团队与 GitHub 安全团队之间进行了大量合作，一方面是加固平台，另一方面是与开源维护者合作，做了很多工作来限制 **npm（Node 包管理器）** 等包管理器的暴露面，比如设置时间延迟、下架已被攻陷的仓库。每天都有大量持续改进，与社区、开源项目、维护者共同推进。整个微软都在投入资源加固安全，这对每个人都是头等大事。

### 开源供应链：加固而非围堵

**主持人**：太棒了。有一件事我一直在思考，关于安全与开源之间的关系。GitHub 以及我们的开源供应链建立在“代码昂贵”的前提上，但现在代码可能变便宜了。也许安全审查其实也便宜了，实际上保护系统的最佳方式是 vendor 一切，或者重写一切——因为现在很便宜，不再依赖开源。有这种观点：“我的依赖里有 2000 个大家都在用的核心软件，它们都是脆弱攻击面。也许我应该把它们减少到 20 个。”我不知道你们是否有观点，或者这太激进了。

**Jay Parikh**：我不认为太激进，因为这确实是我们会被问到的问题。但我也不认为那是万能药。因为，如果我正在使用 2000 个开源项目，我要去掉其中 1980 个，只用 20 个，那么剩下那 1980 个我现在必须自己维护。所以你必须选择把资金、人员和精力放在哪里。我还认为开源中有太多重要且有价值的事情正在发生，我不认为这会停止。如果有的话，开源对商业、构建者和创作者的价值只会从这里增加。因此，让我们解决真正的问题：让开源中的东西更安全，而不是让每个人都转向某种围墙花园式的方法。

### 预测：Azure 迁移、智能体管理与成本治理

**主持人**：好的，作为结束问题。我最近习惯问别人预测。到明年这个时候，我们会从 GitHub 看到什么？

**Jay Parikh**：你会看到几件事。第一，我们将继续今天谈到的路径，也就是如何不断演进栈的每一层。这个主题已经伴随我们一段时间，但我认为今天我们终于把它整合成一个从最底层基础设施一直到最顶层的叙事。到 Azure 的迁移会在明年完成吗？计划是明年，那是我们的目标。你们今天看到了扩展图表，非常疯狂。所以我们必须继续演进、快速行动，在栈的每一层做出阶跃式改进。我们会继续分享这些，因为这些都是非常有趣且困难的工程挑战，值得与社区分享。第二，人们正在改变工作方式，也就是我们如何构建软件、部署软件并优化。今天的方式我猜一年后会大不相同。到时候会是什么样子？是管理数千个智能体，还是几十或几百个？我不知道。所以我们必须继续用正确的原语来构建平台，这样你就可以按照自己的想法组合这些原语。我们会持续演进。基础设施规模方面的内容将是我们持续的主题。这些平台服务在不断演进，你可以把这些构建块按需组合。我会说另一件会更受关注的事：一是安全，我们已经谈过；二是“pops”，也就是如何管理我在 token 上的所有支出。这是当今非常热门的话题。你们展示了成本控制功能，这实际上是很多实验室不会做的，因为他们希望你想花多少就花多少。我们有很多其他功能，把组织支出分解为：这里是我们告知你支出的所有事项，这里是我们指导你如何优化支出的建议，比如你在这个用例中使用某个模型，也许应该换成另一个模型。我们会继续在产品中提供建议。对于财富 500 强公司，他们尤其需要治理，希望能设置限制，所以我们必须提供相应的控制和治理。作为公司领导者，我不介意你把我的钱花在 token 上，只要让我看到花得值。这就是我们如何帮助你和许多人形成闭环：嘿，我这周花了 1000 美元在 token 上。如果你能说“嘿，我创造了 25000 美元收入”，那可能你会觉得不错。

**主持人**：我认为提收入有点过了，因为我作为程序员不负责收入，但至少我发布了功能。我认为能够谈论它如何转化为某种 **ROI（投资回报率）** 会更好，也许不是收入，而是成本节省、参与度提升、留存改善或 **CSAT（客户满意度）** 提高。这些都是可衡量的，作为产品和工程团队，你应该与这些结果指标挂钩。

**Jay Parikh**：是的。

## 尾声：一个用 Copilot 制作的 Game Boy 徽章

**主持人**：太棒了。期待继续保持关系。恭喜又一次成功的 Universe。

**主持人**：好的，非常感谢。

**Jay Parikh**：谢谢。很高兴见到你。

**主持人**：是的，谢谢。
