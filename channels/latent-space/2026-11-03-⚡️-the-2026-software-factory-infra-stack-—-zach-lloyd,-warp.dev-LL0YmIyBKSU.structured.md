## 软件工厂的定义与常见误解

>> 你们落地页上的 H1 标题写的是“**云软件工厂的开放基础设施**”。也许你比我花更多时间向人们解释什么是工厂——那人们认为软件工厂是什么？他们实际上需要什么？
>> 当我和公司或开发者交流时，世界上大多数人都在试图构建某种**内部软件工厂**或一组软件工厂。我认为这意味着，或者我先定义一下它对我的意义：它是一个**云端的智能体系统**，在这个系统中，你定义了各种智能体在为你的团队或产品构建软件时所扮演的角色，并且系统中存在一定程度的**自主性**。也就是说，智能体可以自己完成一些事情。对我来说，这个系统应该是**高度可度量、高度闭环**的，随着时间推移，你作为一个团队可以对其进行调优、测量、基准测试，并最终获得信心——当人们转向这种智能体开发方式时，他们是在以最具可扩展性和最高效的方式进行。

>> 人们找到你时，通常带着什么样可能存在的**常见误解**？例如他们会说：“好吧，如果我买了什么什么，我就能在另一端得到一台神奇的赚钱机器”？
>> 是的。当人们找到我们、试图构建他们自己的软件工厂时，他们常常会把不同的自动化拼接在一起。有时候人们把软件工厂仅仅理解为“我们大量使用智能体来交付软件，并称之为我们的内部软件工厂”。而我们努力让它变得更具体，会说：不，不，不，你实际上应该把软件工厂当成一个**非常具体的东西**。你应该用**代码定义你的工厂**。你应该确保工厂拥有所有的工作流、技能、MCP（模型上下文协议），一切的一切都像一个具体的事物，你应该能在某个时间点运行它并衡量它的表现。

因为人们对这些工厂有各种随机的想法。所以对于 Warp 工厂——也就是我们的平台——我们会说：不，它其实是一个真实存在的东西。你可以编排它、测量它。你**每个产品表面使用一个工厂**。我们试图把它从“一堆任意自动化和交互式智能体的模糊集合”中拉出来，变成一个真正的事物。

## Warp 软件工厂平台：工作流、角色与数据闭环

理解软件工厂的方式——或者我们的理解方式——你在这里看到的是 Warp 软件工厂平台。**一个工厂作用于某个产品表面**。想象你正在构建你的移动应用，或者你在构建你的服务器应用等等。工厂本身作用于一组代码库，并拥有一组它需要的技能、一组 MCP，然后它还有一个与之关联的工作流。这个工作流大致上与你团队可能已经在做的、对该代码库进行更改的流程相匹配。所以可能会有一个**分诊**步骤、一个**规格制定**步骤、**实现**步骤。重要的是有一种定义好的工作流，而且该工作流本身是用代码定义的。所以对我们来说，基本上有一个 YAML 文件，里面写着：“好的，这些是你可以使用的所有代码库，这些是所有的 MCP，所有已接入的集成。” 这样你就在某个地方定义了整个东西。

使用工厂的方式，实际上有两类角色。一种是**构建产品的人**——他们在做产品工程，他们通过工厂交付功能。对这些人来说，他们使用工厂的方式是通过他们已有的工具。他们可以在 Slack 中向工厂派发工作，可以使用任务跟踪器如 Linear 或 Jira，可以通过 GitHub 与工厂交互，可以通过 API 或 MCP 调用它。这里的比喻是：你正在把一个**工作项放入工厂**。当它进入工厂时，就会启动一个预定义的工作流，而该工作流是用代码定义的。到这里还清楚吗？
>> 我喜欢“用代码定义事物”这一点。
>> 是的。好，你已经用代码设置好了整件事，一旦就位——这个比喻仍然是：某人在 Slack 中启动一个任务，或者在 Linear 中，或者通过自动化（比如出现了一个服务器错误）——一切都通过**一个系统**进行，这是关键。一旦它运转起来，你基本上就能获得随之而来的大量好处。

其中一个重要好处是：无论这些智能体在哪里运行，你都能看到一个**实时视图**——这是我们 Warp 内部团队如何运用我们自己的工厂——你会获得每个人在任何拥有工厂的产品上使用编码智能体所做事情的全量追踪。这很酷，不仅仅是因为“哦，我想看看人们在做什么，我想看看 Sofic 在做什么”，而是它开始**集中化所有智能体对话、智能体工件以及团队中编码智能体所做的所有工作**。

所以当我谈论**闭环系统**时，这些智能体对话、这些智能体追踪，就是这个系统如何改进的关键方面。举个例子，只看其中一个智能体追踪：Sofic 正在处理我们的移动应用。Sofic 是在 Slack 中做这件事的，所以我可以在 Slack 中打开查看。但关键在于，实际生成它的东西拥有**完整的对话记录**，拥有所有**计算机使用截图**——这些截图来自构建这个东西的过程。你可以看到编排智能体各个不同部分所做的事情的完整记录。

你拥有的不只是这一条，而是**每一条**。在今天你的团队中，当我和公司交流时，大多数人并没有这样的东西，因为他们的工程师大多是在自己的终端里单独使用 Cloud Code 或者 Codex 应用之类的，处于各自本地的设置中。但他们希望进入一个拥有这种**集中化**的世界。

当你有了这种集中化，你基本上就可以获得关于你的智能体编码在公司内部运行情况的所有有趣数据。你可以从不同维度来思考这些数据。比如，你可以把这些数据看成是：“在运用编码智能体的世界里，我们团队的产出是什么？” 这就是传统的 **DORA 指标**，比如某件事要多久才能发布？还有你的**自动化程度**如何？所以我们有一个指标，大致是：对于每一个被合并的 PR，人类需要干预多少次？你的吞吐量是多少？还包括**成本指标**。我们一直在使用这个指标，当和公司交流时，成本这件事非常重要，你希望能够通过正确的模型、正确的技能来调优你的工厂，从而随着时间推移**降低每个 PR 的成本**。你希望能够按人员切分成本，按自动化、按在 SDLC（软件开发生命周期）中哪个环节花钱来切分。

最后一个很棒的事情是：一旦你有了这种闭环系统运转起来，你实际上可以**深入查看你的编码智能体在不同维度上的表现**。你可以把这看作**在线评估**，或者我们称之为**评分器**。这些评分器可以从非常通用的角度，比如你的智能体是否过于啰嗦？是否高效？代码质量好不好？——这方面我们还有工作要做。

>> 这些是由我作为用户来定义，还是你们作为平台提供？
>> 两者都有。我们提供一套开箱即用的、我们认为普遍有用的评分器。但是，当我们与公司合作时，他们可能会有自己特定的智能体失败模式想要追踪。比如他们可能会说：“智能体是不是在做某种特定类型的、会破坏我们构建的改动？” 他们可能会想要一些非常符合其工作流的东西。所以，这些也都是用代码定义的，完全可定制。

当你设置其中一个评分器时，实际上背后发生的事情是：有一组运行记录——我所说的“运行记录”是指已经存储的历史智能体对话——然后有一个智能体会去**回溯性地评分**。这里有一个很好的例子，它在评分的对象是**冗余测试**。这是使用编码智能体时常见的失败模式。有时候它们会写一堆你并不需要的测试。它们在摸索如何实现某个东西的过程中写了这些测试，然后把它们留在了代码里。这会膨胀你的代码库，浪费 token。

假设你想检查这种情况，你基本上创建这样一个评估。再多展示一点评估是什么样子的：把它想象成 **LLM 作为裁判**。你选择一个裁判模型，然后你会看到：它们在哪里运行？用于评判的提示词是什么？还有一个**采样率**，因为你可能不想运行所有这些智能体——你必须当心它们的成本。

当你设置好这些之后，把它想象成：你拥有所有这些聪明的智能体，它们正在审视整个团队，观察你们所有编码会话的进展。它们会说：“好吧，有时候有些智能体写了太多测试。” 对不对？于是你得到了这份记录和这份理解，知道应该把改进重点放在哪里，以提升团队使用编码智能体的方式。到目前为止都清楚吗？因为我还想展示几件其他事情，好让“你能用它做什么”更具体一些。
>> 总体很好。我有点想知道，这是否基本上就是 Warp 的不同层次？比如你展示的是 **CTO 级别**的视角，对吧？你是在经营公司，有一群编码员的预算。

## 从“感觉”走向“测量”：工厂工程的核心原则

还有几件我想强调的事情，不是要把这完全变成 Warp 工厂的宣传，但对于任何试图构建内部工厂的人来说——不管是不是基于 Warp 工厂——一般原则是：**你要达到一个状态，一切都被存储、一切可观测、一切可度量**，因为那时你才能真正开始运用工程严谨性来改进编码智能体。

你可能经常在 Twitter 上看到：每个人都在发推说“你应该试试这个新模型，或者你应该用这个新的 harness，哪个更好？是 Pi 还是 Claude Code，还是 Cursor 什么的？” 我们对此的看法是，世界真正需要的是——**走出靠感觉来理解这些编码智能体的领域，进入真正测量的世界**。

我们认为这是公司会想要走的方向。他们会想要部署一个像 Warp 工厂这样的系统——不管他们真的使用 Warp 工厂还是自己搭建——来收集所有这些信息，然后提供所有这些方式来查看编码智能体的表现。

我猜有一件事我有点想当然，但它也是系统的一部分：你可以围绕它创建各种不同的自动化。比如，我想象人们会在 Slack 中工作，但人们也会设置不同的**基于触发器的**方式把工作投入工厂。一旦你有了我之前展示的那种评分视图，你还可以设置**另一种智能体循环**——如今一切都是循环——让那些智能体去审视你的评分中的失败，寻找进展不佳的地方，并尝试为你的系统提出改进建议。

一个非常简单的例子，我们称之为**自改进**：我们的自改进智能体在观察我们的**分诊步骤**表现如何。它们会说：“好的，我们有 54 个这种特定形式的失败案例，如果我们的分诊器能够生成一个子智能体来做调查，结果会更好。” 它们能够做的是——如果你愿意，可以去看它为什么会这么认为——但很酷的是，因为你的整个工厂是用代码定义的，而这些是编码智能体，它们本质上可以对**工厂定义**发起一个 pull request，尝试改进工厂本身。所以这是一个**完整的、内置于系统的学习循环**，试图真正实现自我优化。

我们目前还没有做到，但接下来我们想做的是：对于任何像这样的建议性更改，你可以**回放运行记录**，确保它确实会改善结果。一旦你有了正确的原语，工程化这些事物的可能性会变得非常酷。

我再展示最后一件事，然后我们也许可以更广泛地聊聊整体方法。另一件我认为公司应该追求、而且我们内部也觉得非常有用的能力，是**基准测试**。

在工厂语境下，基准测试本质上意味着：你可以拿任何正在你系统中运行的编码智能体，把它添加到一个基准测试套装中。这意味着你可能会**策划一组编码智能体运行记录**，比如与做前端编码相关的一组任务。一旦有了这个，你就有能力针对一个**不同配置的矩阵**，重放那些相同的任务。

我是个大信徒，不仅允许你改变模型，还允许你改变 harness。在 Warp 中，我们有自己的 harness，但我们实际上会让你针对 Cloud Code、Codex 或 Pi 进行基准测试。你可以选择模型，当你做这样的事情时，最终得到的结果看起来非常像 **SweetBench 或 CriminalBench** 的已发布结果，但使用的是**你自己公司的真实运行记录**。例如，我们在这里查看的是某组任务的**成本与正确性权衡**。你会希望处于左上角——最低成本、最高正确性。这些模型现在稍微有点旧了，因为世界变化太快，但基本思想是：我们可以看到，在这个任务集上，GPT-5.6 是 95% 正确，但平均花费 6 美元；而 GLM-535 是 93% 正确，花费 2 美元。

然后，很酷的事情是：你可以把这些信息输入到**模型路由策略**或**harness 路由策略**中——说实话，这个策略是专门为你们自己的工作流和代码库定义的。所以，如果我必须再次拉远视角，我认为真正酷且强大的一点是：**你正在走出猜测的领域，进入我们所说的“工厂工程”**。你采取的是真正的工程思维：我们有了编码智能体这个令人惊叹的新原始事物，我如何知道作为一个团队、一家公司，我们实际上在正确地部署它们？

所以，我们正在为各家公司构建这些基础设施和工具来做这件事。这种方法确实引起了许多公司的强烈共鸣，他们一直在尝试构建自己的版本。以上是当我说“工厂”时我所指的一个快速导览。我可以先停一下。

## 工厂工程堆栈：六个关键层次

>> 我确实认为，所谓的“权力之举”就是**把思想领导力做到极致，以至于每个人最终都在尝试构建 Warp，即使他们不使用 Warp**。是的。你的落地页上有一些我很喜欢的内容，在你的演讲中也提到过几次。我同样很喜欢的一点是：**任意表面**，对吧？它必须真的是任意表面。必须**工厂即代码**。你必须拥有**评估循环**。那么整体是什么？有人称之为 ADLC 吗？我不知道你是否用这个词。看起来你还在用 SDLC。所有这些。
>> 我会这样思考。再说一次，不管是不是 Warp——如果是我，显然 Warp 是我们全力专注的，我们有一个很棒的平台。但总体而言，如果你试图在这个领域构建一些东西，我会这样考虑：

**A，我会把它看作一个堆栈。** 作为基础设施，在堆栈底部，我认为非常基础且重要的是**用代码声明式地定义你的工厂**。同样，这里的类比是 **Terraform**。你获得的好处相同，但实际上更多。用代码定义所获得的好处是：你得到一个**版本化视图**，可以看到你的——无论叫 SDLC、IDLC、PDLC 还是什么 DLC——你得到了那个的版本视图。然后你有能力创建它的分支并进行测试；如果你做了更改，你可以回滚。所有关于源代码管理的显而易见的好处都很好。然后你还有一个极其酷的额外好处：**因为它在代码中，编码智能体可以对其提出改进建议**。所以对我来说，这是自改进软件工厂设置的基础：**声明式地定义你的工厂**。

堆栈中的下一步，当你考虑架构时，是**有一个地方来收集智能体产生的所有信息**。因为你想做的是检查那些信息、寻找失败模式，或者用不同的变量重放那些相同的过去任务，以便从测量角度真正优化你的系统。这就是那种心态。你需要数据来做这件事。你需要**智能体对话**，你需要**智能体工件**，你需要所有工具交互的记录，才能得到一个结果。

我的意思是：你可能会有一个从 Slack 开始、然后延续到 Linear、再延续到 GitHub 的工厂对话，还有一条代码评审评论，整个交互最终产生一段合并的代码。实际上，它甚至可能最终被发布，然后出现服务器崩溃。你希望能够**追溯性地**回去——很可能用一个智能体，但你也可以作为人来做——并诊断“这件事本来可以怎样做得更好？其中的失败是什么？”

**最后，你需要某种编排器。** 有时候人们把编排器说成好像它就是整个平台。我认为它只是其中的一个部分。我所说的编排器是指：你需要某个系统，它会接受工厂定义代码，然后真正沿着不同阶段推进工作，调用正确的模型、加载正确的技能等等。你需要能触发正确自动化的东西。
