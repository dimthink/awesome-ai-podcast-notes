## 开篇引入

如果你只用一句话概括 2025 年的 OpenAI Dev Day，那可能是：**AI 不再只是陪你聊天、帮你写代码，它开始拥有自己的电脑，学会像一个真实员工那样操作软件了。**

但这场由 Latent Space 在 Dev Day 当天录制的特别播客，远不止是一次新闻盘点。节目邀请到了两位直接负责这些产品的一线负责人——Ari Weinstein 领导计算机使用代理（Computer Use Agents）的产品与工程团队，Nikunj Handa 则领导 API 团队。他们不是站在台上念 Keynote 的宣讲者，而是真正动手写代码、被内部模型「指挥」着去订外卖、用智能体帮自己调试智能体的人。

于是，这场对话里既有冷静的架构分析——Decisions API 与计算机使用模型到底是不是同一个模型？WebSockets 为什么是这一切的地基？也有充满了烟火气的个人故事——花两小时手动配置一顿健康餐，然后看着计算机使用代理 15 分钟搞定。更有坦诚的行业判断：计算机使用目前已经比「平均人类」更快，下一个目标是超越「专家用户」；而 OpenAI 内部「被 Jev 卷到」之后，仅用四星期就把一个想法变成了即将发布的产品。

这篇文章将带你完整走一遍这场对谈。你会看到 OpenAI 当前代理技术栈的全貌——从拥有独立 Linux 电脑的 Dots 智能体，到决策 API（Decisions API）的架构真相，再到「应用快照」（App Shot）为什么不是截图。你也会看到两位产品负责人如何思考信任、安全、延迟、缓存与压缩，以及他们眼中计算机使用代理未来两年将要抵达的彼岸。

# 第一部分：计算机使用代理的全面觉醒

## 一场信息量爆炸的发布 `[开场 - 前 10 分钟]`

**核心观点**

OpenAI Dev Day 的公告并非零散的功能更新，而是围绕「计算机使用」这一核心能力构建的一整套相互咬合的产品矩阵——Dots 提供了全新的智能体形态，GPT-6.1 带来了成本与速度的双重跃迁，Agents API 则把最前沿的能力交到了每个开发者手中。

**深度阐述**

节目一开始，主持人就请 Ari 对当天的公告做一个快速梳理。Ari 刚从主题演讲现场走出来，语气里还带着兴奋：「今天超级激动人心，我们刚结束 Keynote，太燃了。」他提到的第一件事是 **Dots**——这个全新的个人助理产品，内置了令人兴奋的计算机使用功能。第二个是新一代模型——字幕中记为 **GPD 6.1 Soul**（考虑到转录误差，下文统称 GPT-6.1），Ari 特别强调这个模型「在成本与速度上的优势非常突出，尤其适合计算机使用任务」。他给出了一个惊人的数字：相比 Astra 模型，它的成本降到五分之一；如果只看计算机使用场景，成本甚至只有七分之一。他笑着承认：「抱歉，今天发布的东西太多了，我还在努力梳理。」

第三个公告是 **Agents API 正式加入计算机使用能力**。Ari 指出，这意味着开发者现在可以使用与 Codex、ChatGPT 内部完全相同的计算机使用实现——不是某个简化版，而是同一套技术。这在他眼中是历史性的一步：过去，前沿能力是产品的护城河；现在，OpenAI 选择把它变成开发者手中的积木。

随后他又补充了两个精彩的演示：**App Shot**——你可以把当前电脑上正在做的事情的完整上下文，一键带入 Codex 或 ChatGPT；以及 **Mac 上的原生计算机使用**——Roman 在演示中让系统自动给他的应用截图，与此同时他本人还能在电脑上做其他事情。Ari 特别强调了这个细节：计算机使用代理在操作你的应用程序时，你不再是「被占用」的状态，而是可以并行地做自己的事。

另一个主持人迫不及待补充的公告是 **Decisions API**。作为第一个在 Keynote 之外追问「这些产品是不是同一个模型」的采访者，主持人直接抛出了这个很多人心中的疑问：计算机使用和 Decisions API 背后的模型，是同一个模型蒸馏出来的不同版本，还是彼此独立的？

Ari 的回答廓清了一个关键的认知误区。Decisions API 确实拥有全新的能力——它支持**并行推理**、不进行显式推理（no reasoning）、是一个比计算机使用所用模型**更小的模型**。这些特征让它极快，但也让它「在长周期、复杂的任务上稍微逊色」。Ari 坦诚地表示，如何把「快而浅」的决策模型和「慢而深」的推理模型结合起来，仍然是一个开放的研究问题。但他对新 API 的潜力充满期待：「我真的很兴奋想看看大家会用它做出什么。」

**个人感受**

Ari 作为产品负责人的思维方式在这段开场中展露无遗。他关心的不是「我们发布了多少功能」，而是「开发者拿到这些能力之后能做什么」。他在提到 Agents API 时特意强调「开发者可以构建在和 Codex 与 ChatGPT 相同的能力之上」，那种「我们终于把压箱底的东西拿出来了」的释然感，隔着屏幕都能感受到。

**延伸思考**

这一系列发布其实揭示了一个产业趋势：**计算机使用正从「模型能力」演变为「平台基础设施」**。当 OpenAI 把同一个计算机使用实现既用于自己的产品、又开放给第三方开发者时，它事实上在定义一个标准——就像 AWS 定义了云计算的基础服务一样。接下来值得观察的是，第三方开发者基于同一套 API 构建的应用，是否会反向推动 OpenAI 进一步开放 harness 的定制能力。

**精华收获**

- 计算机使用的「成本拐点」已经到来：GPT-6.1 将计算机使用场景的成本压低到前辈模型的七分之一。
- Agents API 不是「简化版」计算机使用，而是与 Codex、ChatGPT 同款的生产级实现。
- Decisions API 和计算机使用模型是两套不同的技术路线：前者追求极致速度，后者追求长程任务能力。

## 两个 Dots 的故事：每个智能体都拥有自己的 Linux 电脑 `[第 1-3 段对话]`

**核心观点**

Dots 最本质的创新不在于「更聪明的模型」，而在于它改变了智能体的生存环境——每个 Dot 都拥有一个独立的云端 Linux 虚拟机，可以像人一样运行完整的桌面应用和浏览器，这意味着理论上它能够操作世界上任何为人类设计的软件。

**深度阐述**

主持人在提到 Dots 时用了一个非常精准的词：「attached personal computers」——每个 Dot 都挂载了一台个人电脑。这带来的直接后果是：**Dots 的持久性远超以往任何产品形态**。主持人自己透露，他已经开始把大量客户服务任务交给 Dot，比如「这个搞错了、我不想登录、不想认证，你直接去把它修好」。

Ari 进一步解释了 Dots 的架构特性。他说，Dots 是很酷的产品，关键在于「每一个 Dot 都能访问自己在云端的 Linux 虚拟计算机。这和其他产品都不一样——过去，我们要么给智能体一个云端的浏览器，要么让它访问你自己的电脑；但这一次，智能体拥有了一整台完整的 Linux 电脑。」这意味着它可以运行完整的桌面应用程序，也可以用浏览器，两者都不耽误。

这背后的哲学，Ari 讲得很透彻：「计算机使用之所以如此令人兴奋，是因为它让智能体可以做任何你能做的事。世界上所有的软件都是为人类设计的，而现在智能体可以使用同样的软件，你可以把任务委托给它。」他建议听众从自己的痛点出发：「想想你花时间做什么，然后想想怎么把这些事情委托给智能体。」

主持人随即抛出一连串真实场景——订机票、购物，「甚至玩个游戏也行」。Ari 点头赞同，并分享了一个他个人的故事。他最近订阅了一个健康餐配送服务，因为想吃得健康一些。这个服务的好处是定制粒度极高——「我可以指定要多少克鸡肉、多少克米饭」。但问题是，每次下单太复杂了，他需要花整整两个小时。后来他试着让计算机使用代理来做这件事，结果**15 分钟就完成了**。他特别提到，这是在 GPT-6.1 上完成的，「它比我快 8 倍，帮我省下了两个小时。」

主持人则从自己的创作者视角补充了一个很实用的场景：用计算机使用代理自动化 YouTube 运营——因为 YouTube 很多东西不开放 API，AB 测试功能、社区帖子等等都必须在浏览器里手动操作。「他们恨开发者，什么都不给 API。」主持人打趣道。Ari 笑着说：「这句话我已经从我们的开发者体验团队那里听到过了。他们确实用了很多 YouTube。」这算是官方认证了这条「野路子」的可行性。

**个人感受**

Ari 讲 meal prep 订餐故事时的语气特别有大厂产品负责人亲自「吃狗粮」的味道。不是那种「我们在实验室里验证了效率提升 800%」的抽象叙事，而是「我真的省下了两个小时，这让我觉得 AI 终于开始为我省时间了」。他选择这个案例本身也很有意思——不是炫技级的复杂任务，而是一个极度琐碎、但真实消耗注意力的日常任务。这恰恰是计算机使用真正进入日常生活的标志。

**延伸思考**

Dots 拥有独立 Linux 虚拟电脑这一设计，在架构上打开了一个全新的可能性空间。过去，云端浏览器智能体的能力被浏览器边界锁死；如今，完整的操作系统意味着智能体可以安装软件、修改配置文件、运行本地脚本、与桌面应用深度交互。这与「沙箱中的网页代理」有着本质不同——它更接近「远程实习生」。与此同时，「每个智能体一台电脑」也意味着成本结构、并发策略和安全边界的全新设计，这些都是后续值得深入探讨的工程问题。

**精华收获**

- Dots 与以往智能体产品的本质区别是「拥有自己的 Linux 电脑」，而非「拥有一个浏览器或借用你的电脑」。
- 「任何你能在电脑上做的事，都可以交给 Dot」——这是计算机使用能力最简洁、也最震撼的表述。
- 判断计算机使用代理是否真正有用的标准很简单：它能否在真实生活里帮你省下「两小时」。

## 面对质疑：计算机使用在两年里几乎没有进步？

**核心观点**

针对外界「计算机使用两年未取得进展」的批评，Ari 给出了一个简洁而有力的回应：那是几个月前的判断，现在的情况已经 180 度不同了。这种转变来自模型、harness、接口多样性三者的合力进化。

**深度阐述**

主持人把话题引向一个略带火药味的方向：「我们的朋友——另一个顶级 AI 播客的主持人——以说出『计算机使用在过去两年没有进步』而闻名。我觉得你是世界上最有资格回应这个观点的人之一。」Ari 笑了笑，没有回避：「他们几个月前说过这句话，我希望他们现在有了不同的看法，因为计算机使用已经是 180 度的不同了。」主持人不依不饶：「他可是个很难被打动的人。」Ari 只是简单地说了句「好吧」。

接着，主持人请 Ari 回顾他的职业主线：从 Apple 的快捷指令（Shortcuts），到创业公司 Sky，再到 OpenAI——这条路径中贯穿的线索是什么？是什么驱动他一直在做计算机自动化？当年有哪些事做不到？Ari 的回答带着一种真诚的自我剖析：「我一直对自动化充满热情，因为你可以节省生命中的时间，把精力投入到比精细操作电脑更重要的事情上。」他还提到，当年在 Apple 的工作方式几乎像是在「从外部撬开 Apple」，直到 Apple 说「好吧，我们直接雇你进来做吧」。回顾 Sky 时期，他说：「我们在那里也做过计算机使用，但当时的模型能力差太多了。」

关键的转变发生在最近一年。Ari 总结了三个层面的飞跃。

**第一，模型从「会开始」进化到「会调试」。** 过去，模型能可靠地启动一项任务，但遇到问题就卡住了；现在的模型「非常擅长调试、非常擅长重试、反思什么有效什么无效」。这看似只是一个能力列表中的一项，但恰恰是它把计算机使用从「demo 里的玩具」变成了「日常可用的工具」。

**第二，计算机使用的方式发生了质变。** 「如果你在 Codex 里展开工具调用的日志，你会看到它不再是一次一个动作地执行，而是真的在写 JavaScript 代码，然后让计算机执行这段代码，一次完成多个动作。」换句话说，模型不再「看着屏幕手动点」，而是「写脚本批量做」。

**第三，接口的多样性。** Ari 提到，模型现在会综合使用截图、无障碍接口（accessibility tree）、Playwright 等多种机制，根据不同任务选择不同工具。这种多模态、多接口的融合，大幅减少了早期的笨拙操作（比如不停滚动页面、截图、再滚动）。

主持人紧接着追问了一个 Benchmark 层面的问题——Tijall 在 Keynote 中提到了 7 倍的速度提升和多项基准测试的进步，你们内部到底怎么衡量计算机使用能力？Ari 的回答非常务实：「我们有很多不同的衡量方式，在不同的 harness 配置和组合上测试。」他坦承这很复杂，因为生产环境的产品有额外的安全检查，不同任务需要不同的配置。但无论怎么测，「收获都是一致的」，而且这些进步「有时来自 harness，有时来自模型」。他特别兴奋地提到，GPT-6.1 在计算机使用上的性价比提升幅度超过了它在一般基准上的成本下降幅度——模型越「专精」，成本优势越被放大。

**个人感受**

这是整场对话中 Ari 最「工程师」的一段。他没有用「我们取得了巨大的突破」这种模糊措辞，而是拆解成模型、harness、接口三个层面，逐一分析。尤其是「模型现在会写 JavaScript 来一次性执行多个动作」这一点，信息量极大——它意味着计算机使用早已不是「模拟人类点按钮」，而是「用机器的方式重新操作软件」，只是**结果**等价于人类操作。这种「形不同而神同」的路线，可能才是速度能远超人类的核心原因。

**延伸思考**

「模型会写代码来操作电脑」这件事，对「计算机使用」这个概念本身构成了挑战。当一个智能体不再用鼠标在 DoorDash 上滚动页面，而是直接调 JavaScript 修改页面状态时，它还算「像人类一样使用电脑」吗？这引出一个更根本的问题：**我们到底需要智能体「像人」，还是只需要它达成「人想要的结果」？** 如果答案是后者，那么计算机使用的终极形态可能不是「更好的 GUI 操作员」，而是「能够自由选择操作方式的通用软件操纵者」——这条路通往的也许是远超人类的效率。

**精华收获**

- 「会调试」是计算机使用从演示走向生产的分水岭。
- 当前计算机使用代理的一大杀手锏是：直接编写 JavaScript 代码来执行批量操作，而非逐步模拟点击。
- 模型能力与 harness 能力在同时进化，OpenAI 内部对此有系统化的测量手段。

## App Shot：不是截图，而是「无障屏幕」 `[中段对话]`

**核心观点**

App Shot 容易被人误解为「把你的屏幕截个图丢给 AI」，但它的真实机制是提取应用的无障碍表示（accessibility tree）与元数据，把完整、结构化的上下文交给语言模型。它为人类发明的无障碍技术，正在成为 AI 使用电脑的「眼睛」。

**深度阐述**

主持人提醒听众：「很多人在用 Codex 时看到 App Shot 的视觉效果，以为只是把一张截图扔进了对话框，然后疑惑『为什么我要发一张截图？』」Ari 详细解释了这背后的工程含量。

「如果你给模型看一张网页截图，截图里不会包含超链接指向哪里。如果你截日历的图，事件标题可能是截断的。但当你用 App Shot，它会把完整的上下文都交给语言模型——每一个按钮、每一段文本、每一个链接——所有这些都被以一种对模型友好的方式提取出来。」

打开 App Shot 的具体操作是：在 Codex 里双击 Command 键，它会把当前应用的上下文抓取进来。如果你点开附件、再点右上角的一个小按钮，就能看到原始文本和原始的无障碍表示（accessibility representation）。Ari 笑着说：「我们花了很多功夫把所有东西导出来，同时还要做到 token 高效。这有点像一门艺术。」

最动人的一个洞察出现在这里。Ari 指出，这项技术最初是**为有障碍的人类发明的**——视力受损的人使用屏幕阅读器，依靠的就是这些无障碍接口。而现在，「同样的技术对语言模型使用电脑也极其有用」。他用了两个连续的「really」来强调：「这对他们（人类）真的很有帮助，现在对 LLM 也真的很有帮助。能够从事这项工作真的很有趣。」

主持人不禁补了一句：「所以这其实是把人类无障碍技术复用到 AI 上，真的很有意思。」还顺势透露，他已经邀请 Jason Louu 在 AI Engineer 大会上开一个关于 App Shot 的完整工作坊。

**个人感受**

Ari 在讲 App Shot 时，语气里有一种「技术宅的快乐」。他特意提到「你可以像我一样 nerd 到极点，点开那个小按钮看原始的 accessibility tree」——这不是一个产品经理向记者堆砌技术名词，而是一个真的会拆开玩具看看内部齿轮的人。他反复强调「token 高效」和「导出完整上下文」之间的平衡是一种艺术，这句话值得细品：**模型能"看"到什么程度，不仅取决于模型本身，更取决于我们为它准备的信息表示是否足够精良。**

**延伸思考**

App Shot 揭示了一个反直觉的趋势：**AI 使用电脑的方式，正在经历一场「从像素到结构」的回归。** 早期计算机视觉驱动的代理依赖截图，后来演变为依赖 DOM 结构、无障碍树——结构化的信息远比像素更容易被模型「理解」。这可能也是通往「超级人类速度」的重要一步：一个依赖像素「看」屏幕的代理，本质上被人类的视觉带宽锁死；而一个直接读取结构化表示的代理，天生就能以机器的速度获取信息。当然，这也带来了一个现实问题：如果某个软件没有良好的无障碍接口，App Shot 的效果就会打折——这或许是未来计算机使用代理要突破的边界。

**精华收获**

- App Shot ≠ 截图：它提取的是完整、结构化、token 高效的应用上下文。
- 无障碍技术是人类为「有障碍的人」发明的，如今成为 AI 的「眼睛」——这是功能复用与跨界融合的经典案例。
- 选择「结构」而非「像素」，是计算机使用走向高速的关键路径之一。

## 当前瓶颈与终极远方：从「快过普通人」到「快过专家」 `[后半段]`

**核心观点**

OpenAI 内部已经观察到：计算机使用代理在大多数任务上比「平均人类」更快。下一个里程碑是让它比「专家级人类用户」更快、更流畅地操作软件。Ari 认为，一旦实现这一点，产品形态和用户习惯都会发生根本性变化。

**深度阐述**

Ari 对这个前景的描述带着一种压抑不住的兴奋：「过去的几个月里，团队达成的成就真的很疯狂——在大多数情况下，计算机使用执行任务已经比普通人类更快了。而下一个前沿，是让它在性能上真正达到超人水平——像我们这样的专家级用户一样快，甚至更快地使用软件。」

他随即解释了为什么这件事会如此重要：「当它真的发生时，我们可以突然构建出提供实时体验的产品。」注意，他说的不是「更快地完成后台任务」，而是「实时体验」。这意味着用户与智能体的协作方式将从「你提交一个任务，它在那里跑几分钟」变成「它就在你身边同步操作，你们像同事一样并肩工作」。Ari 还点出了一个更深层的变化：「降低使用计算机使用的激活能（activation energy），会让我们开始默认把某些事情交给智能体，而不是像现在这样习惯性地自己动手。」这不仅能节省大量时间，更将重塑人与软件的日常关系。

但通往这个未来的路上，有许多「小 paper cuts（纸割伤）」。Ari 一针见血地指出了当前最隐蔽的瓶颈：「随着计算机使用变得更快，我们越来越被『操作本身的速度』卡住。」他举了一个再真实不过的例子：「在我们的基准测试中，自动化 DoorDash 任务有相当多的时间其实是在等 DoorDash 网站自己加载完成。」

主持人对这个问题很有共鸣：「对，你写了一个 wait，然后执行那个 wait。」Ari 进一步展开：「你需要在它加载完成的那一刻立即触发语言模型生成下一个动作，而这本身是一门统计学。」他提到，理想情况下，这种等待应该是事件驱动的——Web 导航有 load 事件可以监听，但很多场景并非如此，「比如与客服聊天，回复可能要 30 秒，也可能要 3 分钟，你根本无法预判」。

主持人听后忍不住分享了自己的「实战经验」：「我用 Codex 跟客服聊过很多次，它确实很厉害，但我不知道对方是否意识到自己在跟机器人说话——因为我总是用完整的句子、正确的标点、提供完整的参考号……显然太完美了，不像真人。」他的解决方案是：「我会在 prompt 里写——别假装你是机器人，你要做一个很烦的、三言两语的真人。然后我还会让它等回复的时候开子代理去研究更好的方案。」Ari 听得津津有味：“这真棒，我现在有一半的对话对方也是机器人——所以现在是两个机器人在对话。”

Ari 自己也感慨，信任的建立正在飞速推进：「三四年前，我们还害怕把 LLM 接入互联网和设备。现在我让它配置 DNS，让它支付我的账单——几万美元的东西我直接丢过去，yolo 一下，最坏能怎样？」这句话既是玩笑，也折射了技术成熟的速度。

**个人感受**

这是整场对话里 Aric 内心世界泄露最多的片段。他谈到「激活能」这个物理/化学隐喻时，其实是在说一种习惯的惯性——人类使用软件的方式正在被 AI 悄然重写。你可能不会为了节省 10 分钟去设置一个自动化流程，但如果这个流程「几乎不需要启动成本」，你就会毫不犹豫地使用——届时，「你的操作方式」本身会被重新定义。「支付几万美元的账单直接交给代理」这件事，从安全角度或许会受到质疑，但它确实反映了这位一线负责人对自家技术的真实信任程度。这种「敢用」本身，可能比任何 Benchmark 都更有说服力。

**延伸思考**

「等网站加载」成为瓶颈，这个场景极有象征意义。它意味着 AI 的能力天花板正在从「智能」转移到「世界」。当模型已经足够聪明、足够快，现实的网络延迟、服务端响应、第三方系统的不确定性就成了新的限制因素。这预示着一轮新的工程竞赛：如何让智能体在不确定的等待中仍然高效工作（比如并行做其他事、提前预判结果），以及如何让智能体与 web 的交互从「轮询式」进化为「事件驱动」。这场比赛的结果，将直接影响「实时智能体体验」能否真正落地。

**精华收获**

- 里程碑判断：计算机使用已快过「平均人类」，下一目标是快过「专家用户」。
- 实时体验与低激活能，将导致用户从「手动操作」迁移到「默认委托」。
- 新的瓶颈不是模型智能，而是「等待网页加载」之类的现实世界延迟。

## 给开发者的建议：使用官方 harness 是一种「分布内」优势 `[API 讨论前段]`

**核心观点**

当开发者拿到 API 后，最重要的建议是：尽量使用 OpenAI 提供的官方 harness，因为模型是在官方 harness 上训练出来的——使用「分布内」的工具本身就是一种速度、成本与准确性的优势。同时，安全与信任的建立需要产品设计来共同完成。

**深度阐述**

Ari 首先表达了开发者版的兴奋：「终于把计算机使用放进 Agents API 了。这对开发者意义重大，因为很多应用需要与第三方网站和服务打交道，而计算机使用有它的普适性——它可以和任何东西协作。」在他看来，开发者现在等于「站在 OpenAI 内部团队的肩上」。

他随后给了一个非常务实的建议：如果你考虑自己搭建 harness，请先想清楚一个问题——「我们是在我们的 harness 上训练模型的。所以使用那个与模型分布一致的 harness，确实存在速度、成本和准确性方面的优势。」这里 Ari 用了「in distribution」这个机器学习术语，意思非常明确：模型训练时「见惯了」官方 harness 的输出格式和运行方式，因此换到第三方 harness 时，模型的性能很可能会打折扣。

接下来他谈到了安全与信任。他坦承：「我们所有人都还在适应和信任这项技术的过程中，也许我们中的一些人走得比大多数人更远一些。」因此，他呼吁开发者履行责任：「我们必须在产品中构建可靠性、正确的安全检查、在执行支付等重大操作前征得用户同意，并且尽量让代理只访问执行任务所需的网站和应用。」

**个人感受**

Ari 谈到「我们都在这个过程之中」时，少了一贯的速度感，多了一种罕见的谦逊。他并不掩饰这项技术还有安全与信任的沟壑，但又不像许多谨慎的发言人那样以风险为由画地为牢。他给出的答卷是：用产品机制来弥合信任缺口，而不是用禁止来回避。

**延伸思考**

「Model is trained on our harness」这个细节被很多人忽略，但它对第三方开发者至关重要。如果你构建了自己的浏览器操作框架，却发现模型的成功率骤降，并不是模型变笨了——而是它离开了「舒适区」。这提醒我们，未来的竞争焦点不仅是模型本身，还包括「与模型训练分布一致的工具链」。OpenAI 开放官方 harness 这一举动，客观上也在把第三方开发者「锁定」在自己的技术栈里。这种「模型 + 工具链」的联合体，可能比单独售卖模型 API 更深刻地定义了平台护城河。

**精华收获**

- 用官方 harness 开发是「分布内」操作，有实打实的性能红利。
- 安全与信任不该只靠模型自律，而要通过产品机制（确认、限制访问范围、安全设置）来构建。
- 代理只应访问完成任务所必需的网站与应用——这是权限最小化原则在 AI 时代的新形态。

# 第二部分：API 平台的底层革命

## 异步、中途转向与 WebSockets：API 正在从「问答」变成「协作」 `[Nikunj 出场]`

**核心观点**

在模型层之外，API 层的「执行模型」也在经历根本变化。异步函数调用让模型不再被工具执行阻塞；中途转向（mid-turn steering）让人可以在模型推理过程中注入指令；而这一切都由 WebSockets 支撑，把一个「请求-响应」式的 API 变成了一个「双向实时通信」的 API。

**深度阐述**

Nikunj Handa 在 OpenAI API 团队做了三年，自我介绍十分简洁：「我负责 API 团队的产品工作，主要就是和 post-training 团队、研究团队紧密配合，搞清楚每个新模型有什么新能力，然后把这些能力暴露给 API。」

谈到 GPT-6 系列的新能力，他首先提到的是**异步函数调用（async function calling）**。「Codex、Dots 里那些你能看到的现象——工具调用要花很长时间——你不需要停下来等待工具运行完。你可以发起一个工具调用，然后继续运行、继续推理，之后再回来检查结果。」这里他点出了一个容易被忽视的 API 范式转换：过去，函数调用是阻塞式的，模型等工具，工具完事再轮到自己生成下一个 token；现在，整个过程是流水线式的，**推理与工具执行并行**。

然后是**中途转向（mid-turn steering）**。它的直观含义是：你可以在模型推理中途插入消息。「当你的工具调用完成时，你可以把新的指令塞进去。」主持人立刻指出，这其实也依赖模型本身的训练——模型必须被训练成能够在推理过程中接受新信息。Nikunj 表示认同：「我们在应用里其实早就有这种交互方式了——你在模型思考时可以跟它说话，它得到的转向指令的质量变得越来越好。」

而这一切的底层，是**WebSockets**。Nikunj 透露，WebSockets 是几个月前开放的，它打开了与模型之间的双向通信通道。「不是 GPT Live 那种消费级实时 API，而是 GPT-6 的 API 可以通过 WebSocket 做所有异步工具调用、异步推理、中途注入消息。这是一个很有趣的 API。」主持人调侃道：「这就是为什么我们是工程类播客——因为我们连 WebSockets 都要聊。「Nikunj 笑着补了一句：这一点对 UltraFast 特别重要——因为高速流式输出意味着每一次往返的额外开销都必须被压到最小。

**个人感受**

Nikunj 讲异步函数调用时用的那个「kick off a tool call, keep running, keep reasoning, then check back in」的描述，非常生动地刻画了下一代代理的「工作方式」——不是「机器人串行地做一件事」，而是「像人类一样同时推进多条线程，随时根据最新反馈调整动作」。这种执行模型的改变，要比单纯模型智商提升更根本地影响未来应用的形态。

**延伸思考**

把「中途转向」和「异步工具调用」放在一起看，你会发现 API 的隐喻已经从「打电话」变成了「开一个永不结束的会议室」。模型不是一次性回答你的问题，而是始终在线、随时接收新指令、同时执行多个任务。这种「持续在场」的交互模型，对上下文管理、状态管理、缓存策略都提出了全新要求——这也解释了为什么后半段对话中 Nikunj 花了大量时间讨论缓存与压缩。API 的战争，正在从「谁能生成更好的文本」转向「谁能维持更长的低延迟对话」。

**精华收获**

- 异步函数调用实现了「模型一边推理、工具一边执行」的并行流水线。
- 中途转向（mid-turn steering）是在模型思考过程中插入指令的能力，它正在越来越好用。
- WebSockets 是一切异步与双向交互的物理基础，也是超低延迟体验的前提。

## UltraFast：在 Astra 上榨干每一毫秒 `[API 讨论中段]`

**核心观点**

UltraFast 是「前沿智能首次以极限速度运行」的产物。Nikunj 把这归功于推理团队的持续挖潜：先用数月时间把成本打下来（Luna 降价 80% 的幕后功臣），再转向把速度推到极限。而 WebSockets 是支撑这一体验的关键技术。

**深度阐述**

Nikunj 谈到 UltraFast 项目时，语气里有藏不住的兴奋：「这个项目太让人兴奋了。最有趣的部分，是看推理团队用 Astra 模型『烹饪』。」他描绘了一幅生动的内部图景：「他们不停地开着 CEX（代码执行）代理，试图榨出更多性能。」

他透露了一个重要的时间线：「至少有两三个月，大量工作集中在效率和降成本上——Luna 的价格能降 80%，很大程度上是他们的推理优化换来的；然后他们开始转向另一个目标：怎么让模型跑得尽可能快。」于是 UltraFast 诞生了。「在 Astra 这样的模型上跑到这个速度，真的很不可思议。」

主持人提到，GPT-5.3 Codex Spark 是 WebSockets 的首次应用场景——Nikunj 笑着说「不敢相信我们给模型起了这个名字」，但 WebSockets 的价值在那一刻已经显现：「工具调用需要它，它大幅度减少了工具往返的额外开销。」他还提到一个有意思的细节：主持人说自己的 Spark 用量「几乎从没消耗过」，Nikunj 笑道：「它还在那儿，如果你想要的话……我觉得它应该已经下架了。」这句话引来一阵笑声，「这段位的老模型正在一个个退役」。

被问到「UltraFast 是否与 Cerebras 有关」时（字幕中明确提到「5.3 Spark 是明确归功于 Cerebras 的」，而 UltraFast 至今没有官方确认，但外界一直在猜），Nikunj 没有直接确认或否认，只说「已有自己的硅片」。主持人也笑着把话题引开。

**个人感受**

Nikunj 身上有种典型平台团队领导者的气质：把光环留给别人。他一直强调「这是推理团队的功劳」「他们太厉害了」，而不是「我领导了这个项目」。但另一方面，他对「前沿智能以极限速度运行」这个表述感到由衷的自豪。UltraFast 不止是一个技术 demo，它第一次让「最强的智能」和「最快的响应」同时出现在一个产品里——这两者过去一直被看作是鱼与熊掌。

**延伸思考**

「UltraFast」这类产品的意义，可能被很多人低估。大多数人以为速度只是「体验更好」，但它真正打开的是**新的交互模式**：当响应时间足够短，智能体就能被嵌入到人类的实时决策环中——比如在客服对话中实时生成建议、在驾驶中处理突发指令、在直播中即时回应。这已经超出了「工具」的范畴，更像是一种实时的「认知外骨骼」。

**精华收获**

- UltraFast 实现了「前沿智能 × 极限速度」的组合，而其技术底座是 WebSockets 与极致的推理优化。
- Luna 降价 80% 的背后是推理团队数月如一日的「榨性能」。
- 当延迟降到极限，全新的实时交互产品才会成为可能。

## 被 Jev 点燃：四星期从「黑客想法」到「即将发布」 `[中后段对话]`

**核心观点**

OpenAI 的 Decisions API 直接受到 Jev 的启发。内部团队在短短四周内从「一起黑客松式的原型」走到「即将发布的产品」，这背后是 OpenAI 强大的黑客文化和「看到有趣的东西就忍不住动手改」的传统。

**深度阐述**

主持人提到，他们是最早做 Jev 深度解读的播客之一，还在 AI Engineer 大会上邀请了 Jev 团队的人来做分享。他问 Nikunj：你们看到 Jev 之后的速度有多快？

Nikunj 先向 Jev 团队致意：「首先，向 Dogo 和 Jev 团队致敬，他们真的启发了市场中的整个领域。Jev 一出来，大家都疯了。我们的用户在问，我们的内部团队也说，‘我们需要一个快得多的分类系统’。」

有趣的是，主持人说到的「Jev」其实也是市场里全新的模型，虽然大厂没有公开名字，但它是一个「极快、结构化输出、便宜的模型」，其 API 设计也非常简单。Nikunj 承认，OpenAI 内部确实被「卷入」了：「好几个人都被 Jev 给 nerd-sniped（被感兴趣的技术问题吸引而分心），他们开始琢磨：我们能不能也做到？我们不会训练一个新模型，但是……」

这里 Ari 插了一句关键的话：「大约四周前，这根本不在我们的路线图上。」Nikunj 接道：「完全不在。这就是 Jev 激发的灵感。而且我认为你们是第一个真正采纳并复刻这个思路的前沿实验室。」Ari 说：「是啊，OpenAI 有一种特别强的黑客文化，大家会因为某个东西兴奋起来。于是，一位来自推理团队的哥们儿，和一位来自基础设施团队的牛人，看到这个方向后说：‘太牛了，我们要 hack 一下。’他们搭了个原型，跑通了，然后我们就在延迟优化上不断 hill climbing（爬山式优化），一直想把它做得尽可能快。我们想在未来几天就发布——只要达到延迟目标，立马推出。」

主持人敏锐地捕捉到一种张力：「有趣的是，你们一方面有强烈的黑客文化，另一方面——就像 Sam 说的——你们又是 99% 最可靠的 API 之一，拥有可能是全行业最大的使用量。人们应该怎么理解 Decisions API？很多人听说了 Jev，听到了炒作，但还没真正用过。你们是在把它变成主流产品。」

Nikunj 给出了一套理性的定位：「我觉得最主要的用例是超快的分类。所有计算机使用的 demo 都很棒。但它当然有局限——让 Astra 写一段 JavaScript 来控制电脑，和让 Luna 一次只选择一个动作，不是一回事。我认为它的智能水平不可能完全一样，但对某些计算机使用任务来说，这个速度也许已经够用了。」

他还分享了一个内部很酷的原型：「有人把 Decisions API 和 GPT Live 串了起来。GPT Live 是一个双向实时 API，基于前端模型 + 后端模型的架构——GPT Live 本身就是极快的、善于委派的‘说话者’，而像 Astra 这样的重模型在背后做推理。但在 GPT Live 中，工具调用一直感觉特别拖沓。而现在，GPT Live 控制电脑的 demo 让人觉得流畅自然了很多。我真的很期待看到大家用 Live + Luna + Decisions API 能做出什么。」

**个人感受**

这段对话里最动人的词是「nerd-sniped」。它精准描绘了 OpenAI 内部的文化：一个让所有工程师都忍不住放下手头工作去尝试的技术想法，能在极短时间内从一个原型长成产品。但 Nikunj 也没有把「黑客文化」浪漫化——他马上提醒听众，平台团队的另一面是保持稳定可靠。这两种文化在同一个组织里并存，正是 OpenAI 独特的节奏：**既能快速试错，又能把成熟的东西做成企业级产品。**

**延伸思考**

「四周从想法到发布」这种速度，放在传统企业软件领域几乎不可想象。它说明了两件事。第一，**模型能力已经足够弹性**——当你不需要训练新模型，只需要在现有权重上优化推理栈、做一个「快路径」，产品的落地周期就被压缩到了周级别。第二，**竞争压力正在驱动这种速度**——Jev 的出现让市场上的每个参与者都意识到，「快」本身可以是产品。这也让「快速跟随」成为大模型时代的一种关键战略能力。

**精华收获**

- Decisions API 并不是 OpenAI 预谋已久的产品，而是「被 Jev 卷出来的」——四周内从想法到即将发布。
- OpenAI 内部的黑客文化与平台可靠性追求并存：原型可以乱来，上线则必须有 SLA。
- 「速度」也可以是核心竞争力：当一个任务足够快，它就有资格进入实时交互场景。

## Decisions API 的真相：Luna 的权重，极致的推理栈 `[最后一段]`

**核心观点**

Decisions API 并没有训练一个新模型，它建立在现有 Luna 权重之上，通过结构化输出约束、推理栈优化和批处理并行，把「极快的决策」变成了一个 API 产品。它与 Jev 在架构上可能殊途同归，但 OpenAI 的打法更依赖现有权重的挖掘。

**深度阐述**

主持人提出了一个非常尖锐的问题，他认为这对理解整个市场至关重要：「很多人都在做 Jev clone，过去两周我看到了至少 100 个克隆。我觉得有必要帮大家理清——什么是决策模型？它不只是延迟低，不只是结构化输出。因为如果我直接用 Luna（价格相同），关掉推理，加上结构化输出，我是不是就得到了一个 Jev？不是，对吧？关键是：这里有一个置信度（confidence）的问题。」

Nikunj 给了非常坦诚的回应：「我们并没有为这个训练一个新模型，完全是基于现有的 Luna 权重。在此基础上你做的事情是：第一，约束——结构化输出是一个大头；第二，真正去优化推理栈，让它能在 token 生成上非常快；第三，因为可以一次处理多个问题，你在批处理中并行运行它们；此外还有各种各样的推理技术。」他特意强调，这是一个「经典的迭代式部署」——「把它丢出去，看看大家怎么用，然后我们需要做更多的模型改进。」

主持人补充了两点关键差异：「你们还有 vision，他们没有，对吧？这对我们来说是 Luna 自带的优势。」Nikunj 说：「对，是免费的午餐。」

接下来，主持人探讨了更深层的架构问题。「大家不知道 Jev 的确切架构，但有两个主流猜测：一个是融合模型（fusion model）而不是自回归模型；另一个是某种机械可解释性（mechanistic interpretability）——通过分析激活值、直接输出权重。这两种做法都有研究 demo。Gemini 分享了 Gemini Diffusion，也有人从中间层提取表征。但这些都只是猜测。」他问：「你们追求的目标是什么？因为 API 本身谁都能复制，难的是速度、准确率，以及校准（calibration）等额外特性。」

Nikunj 承认：「校准确实是我们可能需要通过未来模型版本来 hill climb 的领域。」但他显然对整场「追赶赛」感到兴奋：「这个领域被激活了，大家会做出超酷的东西，而且所有人都会互相学习。」

**个人感受**

主持人这段追问堪称教科书级的「产品解剖」。他区分了三层：API 接口（谁都能抄）、推理速度（工程深水区）、校准与置信度（模型能力的试金石）。Nikunj 的回应也很诚实：目前只是基于 Luna 的推理栈优化，「未来模型改进」这几个字已经暗示了此路尚长。这种「先发一个能用的、再慢慢变好」的迭代逻辑，与 OpenAI 一贯的发布策略一脉相承。

**延伸思考**

「决策模型」是否真的需要一套全新的架构，这个问题仍然没有定论。Jev 可能用了某种非自回归的路径，OpenAI 则选择在自回归模型上「压榨速度」。这两种路线之争，很像当年「专用芯片 vs. 通用芯片」的竞争——专用路线在特定任务上更快，但通用路线拥有更多的生态和更强的可扩展性。从长远看，也许两种路线会各自演化出擅长的应用场景。

**精华收获**

- Decisions API 当前的实现基础是「Luna 权重 + 结构化输出约束 + 推理栈优化 + 批处理并行」。
- “做一个 Jev clone”的难点不在于复制 API，而在于达到同样的速度、准确率和校准水平。
- 计算机视觉能力（vision）是 OpenAI 决策模型比纯文本决策模型多出来的一张牌。

## 平台战略：缓存、压缩与「AI 云」的隐喻 `[结尾部分]`

**核心观点**

在平台层面，OpenAI 正同时推进两条主线：一是持续优化响应速度（包括缓存与压缩），二是摸索如何把「智能体」变成更高层的平台原语。Nikunj 将之比喻为「构建 AI 云」——EC2、S3 的 AI 原生版本正在被一个个创造出来。

**深度阐述**

主持人问 Nikunj 想从开发者那里得到什么样的反馈。Nikunj 直言，最希望得到反馈的是两个最新产品——Agents API 和 Decisions API。而在 Responses API 这个「平台基石」上，他正在聚焦两件事。

第一是延迟。「我们正在重写整个 Responses API 的技术栈，从 token 生成首字延迟（TFDT）和 token 间延迟（TBDT）的角度让它尽可能快。」第二是缓存。他特别谈到「个人代理」这个场景——一条永远不会结束的对话线程，是缓存的天然受益者。「我们现在提供 30 分钟内的缓存命中保证。实际上，我们刚刚为一个大客户上线了更长的缓存窗口——12 小时的缓存保证。即使你的线程放下三四个小时再回来，仍然能命中缓存。」主持人敏锐地问：「这个公开 API 有了吗？」Nikunj 说：「还没有，还在预览阶段，我们会尽快让所有人都能用上。」他进一步解释：你可以「多花一点钱」购买缓存保证，换来的是「更长的缓存命中」。对开发者来说，「非常值得做缓存感知的应用设计，并且使用我们的缓存诊断工具来看哪里缓存掉了」。

第二件大事是压缩。主持人提醒了一个硬约束：「你仍然会撞上一百万 token 的上下文窗口，这个短期内不会变，所以你需要好的压缩方案。」Nikunj 给出了清晰的路线图：OpenAI 有自有的压缩技术（Comp），并在 Agents API 中内建了它。在 Responses API 中，有「服务端压缩」（server-side compaction）——设置一个 token 阈值，达到后自动压缩；也有「/compact」——程序员风格的完整手动控制。Nikunj 还透露：「新的压缩技术也在开发中，有些已经实现了，你会看到 Codex harness 里有一些基于文件的系统，我们正在试验。」

最后，主持人请 Nikunj 聊聊平台未来的方向。Nikunj 说，他之前在 Stripe 工作，「在 Stripe，游戏的核心是在支付基础之上构建更高层的原语与产品。我一直在好奇，在 AI 里这件事应该怎么做。我们尝试过 Assistants API，但不是特别合适。现在我们推出了 Agents API，它提供了 Codex harness——但应该提供多少灵活性？这是开放问题。我们该不该做记忆库（memory vaults）这类更上层的 API 对象，把存储等概念抽象掉？这是我非常好奇的领域。」

主持人总结道：「我总是用这个类比：你们在构建 AI 云——Sam 一年前说过。你们几乎是在重复 AWS 的过程：这是 EC2，这是 S3……只是你们在做 AI 原生版本。预热的缓存，就是为了你预知会到来的请求而准备的。」Nikunj 认同：「没错，而且很酷的是这一切都开放给了开发者，它打开了许多新的构建方式。」

**个人感受**

结尾这段对话最珍贵的地方，是两位产品负责人罕见地展现了「不确定中的探索」。Nikunj 说「什么样的灵活性是对的，这是开放问题」「我们该不该提供记忆库这类高层对象」，这些问题没有标准答案。与许多闭门造车的平台团队不同，他把「让开发者告诉我们路线图」当作一种真实的策略，而不仅仅是客套。这种态度本身，就是平台型产品最健康的生存方式。

**延伸思考**

「AI 云」的隐喻非常精准。缓存预热、缓存保证、云端压缩、专属线程环境——这些概念在 AWS 时代都有对应物，只是 AI 时代的「资源单位」不再是虚拟机和对象存储，而是「上下文」和「推理」。当上下文成为像存储一样被精细管理的资源，平台层的竞争焦点便从「模型的智商」转移到了「智能体的运营效率」。这可能是大多数开发者尚未意识到的大趋势。

**精华收获**

- 缓存正在成为代理平台的关键能力：30 分钟命中保证已是默认，12 小时缓存窗口已出现。
- 压缩是 100 万 token 上下文时代绕不开的工程问题：
  - 自动化（服务端压缩）与手动（/compact）两种模式并存。
- OpenAI 的平台方向是在代理之上构建更高层原语（如记忆库、存储抽象），但具体形态仍在探索中。

# 结语：当智能体真正拥有「自己的电脑」

这场对谈最令人震撼的时刻，不是某个 Benchmark 数字，而是两个一线负责人在不经意间透露的日常：Ari 用计算机使用代理订健康餐，15 分钟干完了自己两小时的活；Nikunj 聊到「我们正在用 WebSockets 重写一切」，语气平常得像在说今天午饭吃了什么；Ari 说「我让它帮我付几万美元的账单，yolo 一下」——这些细节拼凑起来，勾勒出一个已经发生的现实：

**计算机使用代理不再只是「能跑通 Demo」的演示品，它已经开始接管真实世界里的真实任务——以比人类更快的速度，并且带着一种令人艳羡的从容。**

但两位负责人也展现出了难得的清醒。他们知道模型的智能已不再是唯一的瓶颈，真正卡住速度的是 DoorDash 网页加载的时间、是客服回复的不确定性、是现实世界本身的延迟。他们也知道，当智能体拥有了完整的 Linux 电脑、能够无障碍地读取屏幕背后的结构信息、能够并行地推进多个工具调用，「智能体体验」的设计法则将被彻底改写——而这场改写才刚刚开始。

也许，这正是 OpenAI Dev Day 最值得被记住的时刻：**Agent 不再睡在「云端浏览器」里，它第一次拥有了自己的电脑；而人类，第一次可以把「操作电脑」这件事，真正地、大规模地委托出去。**

未来两年，当计算机使用真的做到「比专业用户更快」，我们也许会回望这一天，把它视为人机关系史上一个安静的拐点。
