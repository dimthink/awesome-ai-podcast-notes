# OpenAI 新代理技术栈全解析：计算机使用、决策 API、UltraFast 与 Dots — Ari Weinstein 与 Nikunj Handa 深度访谈

> 本期节目中，OpenAI 计算机使用代理产品与工程团队负责人 Ari Weinstein，以及 API 团队产品负责人 Nikunj Handa，共同做客 Latent Space，针对 OpenAI DevDay 发布的一系列新产品进行了深入解读。讨论涵盖了新一代计算机使用能力的进展、Dots 个人助理产品的特性、全新决策 API（Decisions API）的设计思路、UltraFast 推理速度的实现，以及开发者如何构建下一代 AI 代理应用。

## 开场：DevDay 重磅公告回顾

**主持人**：今天我们非常激动地邀请到了两位嘉宾。今天是 OpenAI DevDay 特别节目，我们邀请了领导计算机使用代理产品与工程团队的 Ari。在深入探讨计算机使用之前，你能先快速回顾一下今天发布的主要内容吗？

**Ari**：当然，今天是非常令人兴奋的一天。我们刚刚结束了主题演讲，现场效果非常棒。今天发布了多项与计算机使用相关的重大公告。首先，我们推出了 **Dots**，这是一款全新的个人助理产品，具备非常出色的计算机使用功能。其次，我们发布了 **GPT-6.1 Soul**，这是一款非常出色的新模型，我认为它特别适合计算机使用场景，因为在成本和速度上具有显著优势。我们公布的数据显示，它的成本是 Astra 的五分之一，如果专门看计算机使用场景，成本更是只有七分之一，这确实非常了不起。此外，**Agent API** 现在也集成了计算机使用能力，这意味着开发者可以在 Codex 和 ChatGPT 的基础上，构建同样强大的计算机使用应用。我们还演示了一些现有的计算机使用功能，比如 **App Shot**——你可以快速捕捉电脑上正在处理的内容并带入 Codex 或 ChatGPT。以及 Mac 上的**原生计算机使用功能**，Roman 展示了它如何自动截取应用截图，同时你还可以在计算机使用功能运行应用时，去做其他事情。总之，这是一场非常令人兴奋的主题演讲。

**主持人**：还有别忘了 **Decisions API**（决策 API）。

## 深度解析：各产品背后的模型关系

**主持人**：首先想问一下，这些不同的产品是否都基于同一个模型？或者是将同一个数据集蒸馏到不同的模型中？具体来说，计算机使用功能和决策 API 是一回事，还是各自独立的？

**Ari**：决策 API 真正酷的一点在于，它具备一系列新的能力。它支持并行推理，由于没有推理（reasoning）过程，它是一个比我们用于计算机使用的模型更小的模型。这些特性让它变得非常快，但也意味着它在处理长周期、复杂的任务时，能力会稍弱一些。我认为，如何将这些不同的方法结合起来，仍然是一个开放的研究领域。但我非常期待看到大家用决策 API 构建出什么样的应用。

## Dots：带独立云计算机的个人助理

**主持人**：一个有趣的亮点是，Dots 现在拥有了专属的个人计算机（personal computers）。这似乎意味着它们具有更强的持久性。你自己使用 Dots 已经有一段时间了，人们应该如何拓展它的应用边界？应该瞄准什么目标？应该尝试些什么？就我个人而言，我现在主要把它用在客户服务上，比如“这个出错了，我不想登录，我不想认证，帮我找到并修复它”。我们该如何推动它走得更远？大家应该尝试些什么？

**Ari**：Dots 是一个非常酷的产品，因为**每个 Dot 在云端都有一台属于自己的 Linux 虚拟计算机**。这与我们的其他产品不同。传统上，我们的产品要么是在云端有一个浏览器访问权限，要么是可以访问你自己的电脑。但现在，你在云端拥有了整台 Linux 计算机，可以运行完整的桌面应用程序，同时也可以使用网页浏览器。计算机使用功能之所以如此强大和令人兴奋，是因为它让代理能够做到任何人类能做的事情。世界上所有的软件都是为人类设计的，而现在代理也能使用这些软件了，你可以把任务委托给代理。所以，任何你会在电脑上做的事情，都可以让 Dot 来完成。

**主持人**：确实，我觉得特别有用的场景会因最终用户的不同而有所差异，取决于他们生活中什么是有价值的。但我会建议从思考“你平时在哪些事情上花了时间”开始，然后考虑如何把这些任务委托给代理。

**主持人**：是的，比如订机票、购物，甚至玩游戏之类的。

**Ari**：完全同意。就我而言，最近我做了一件事——我订阅了一个备餐服务，因为我想吃得健康一些。我真的很喜欢这个备餐服务，因为它允许我以很高的精细度定制餐食。我可以指定“我要多少克鸡肉，多少克米饭”。但这个操作太复杂了，我花了两个小时才完成一次下单。后来我发现可以让计算机使用功能帮我来做，结果它 **15 分钟**就搞定了。这样一来，我实际上节省了两个小时。它不仅比我快 8 倍，还在 GPT-6.1 Soul 上为我节省了两个小时。我觉得这类任务才是真正强大而有价值的。

**主持人**：作为一个内容创作者，我可以告诉你，我最重要的用例无疑是自动化 YouTube 运营。因为 YouTube 很多功能不通过 API 开放，你只能把它放到虚拟机里运行。比如他们的 AB 测试功能，或者发布社区帖子，这些都无法通过 API 实现——因为他们不喜欢开发者。总之……

**Ari**：我从我们的开发者体验团队那里也听说过类似的情况（笑）。他们确实经常用计算机使用来操作 YouTube。这真的很棒。

## 计算机使用的历史性进步：180 度大转变

**主持人**：接下来我想聊一个稍微尖锐一点的话题。我们有位做 AI 播客的朋友，以说过“计算机使用在过去两年没有任何进步”而闻名。

**Ari**：是的，我觉得这是一个非常有趣的说法。你是世界上最有资格谈论这个问题的人之一。事情到底是如何进展的？

**Ari**：他们是在几个月前说的，我希望他们现在有不同的看法了，因为**计算机使用已经发生了 180 度的巨大变化**。

**主持人**：他可不是那么容易被打动的人（笑）。

**Ari**：确实不容易。

**主持人**：你几乎整个职业生涯都在从事某种计算机自动化的工作——从 Apple 的 Shortcuts，到 Sky，再到加入 OpenAI。你能梳理一下你的主线吗？是什么驱动力让你一直走在这条路上？当时有哪些事情是无法实现的？你经历过的关键里程碑是什么？另外作为补充问题：从上周到今天的 Codex 计算机使用功能，最大的变化是什么？是模型？是 Dots？还是 harness（驱动框架）？

**Ari**：关于这条主线，我可以说，我一直对自动化和帮助人们自动化任务充满热情。因为自动化能够帮你节省生活中的时间，让你专注于比精细操作电脑更重要的事情。这就是我们当初做那些产品的原因。我之前在 Apple，后来创办了 Sky 公司，最终加入了 OpenAI，这真的很令人兴奋。

回头看在 Sky 的经历很有意思，当时我们也在做计算机使用相关的工作，但那时模型的能力要弱得多。而现在，仅仅在过去一年里，模型在计算机使用方面的能力已经变得极其出色。我认为我看到的最大变化是：过去模型能够可靠地启动任务，但遇到问题就会卡住；现在它们非常擅长**调试**，非常擅长**重试、反思什么有效什么无效**。此外，计算机使用这个领域本身也向前推进了。我们现在使用了更多的技术。

比如，计算机使用功能现在经常**编写代码**。如果你在 Codex 中展开工具调用，你会看到它不仅仅是一次执行一个操作，而是会编写 JavaScript 代码并执行，一次完成多个操作，这是一项巨大的速度提升和能力跃升。我们还使用了更多的无障碍（accessibility）多模态接口。模型可能会使用截图，也可能会使用无障碍接口，还可能会使用 Playwright。它会根据当前任务选择不同的机制。此外，模型的加速也令人惊叹。

至于今天有什么不同——我们一直在持续改进 harness。所以我认为**单日之间的差异，可能不如过去一两个月的变化那么显著**。但可以肯定的是，Dots 中的计算机使用功能以及我们发布的新模型，都是非常令人兴奋的进展。

## 如何衡量计算机使用的进步？不仅仅是速度提升

**主持人**：Tijall 在演讲中提到，计算机使用速度有 7 倍的提升，在一些基准测试上也有更好的表现。你们内部是如何衡量它的？计算机使用是那种会随时间持续改进的事情——是 harness 的改进？模型的提升？还是后训练（post-training）的进步？你们内部是如何评估它的好坏，新模型又带来了哪些具体变化？

**Ari**：我们实际上有**多种不同的衡量方式**。其中一些是在 harness 的不同排列和配置上进行的测试。这有点复杂，因为我们的生产产品会有更多的安全检查，而且这些检查会根据任务需求以不同方式配置。所以我们有很多种测量方法，但无论我们如何衡量，都观察到了相当一致的收益。这些收益有时来自 harness，有时来自模型。让我特别兴奋的一个结果是，**GPT-6.1 在计算机使用方面的成本效益比其基准成本改进更为显著**，与 Astra 相比，这真的非常酷。

## 关键突破时刻：多模态接口与整页感知

**主持人**：是的，直播中有一个我很喜欢的画面，就是你们在持续改进 Pareto 前沿曲线。你们也谈到了如何把模型和 harness 结合在一起来推进。你能分享一些“顿悟时刻”的例子吗？无论是模型推动 harness，还是 harness 推动模型？

**Ari**：我不想重复，但**引入更多模态**确实非常有力。一个更具体的例子是：过去我们看到很多计算机使用产品需要花大量时间滚动页面。它会截图，尝试做点什么，发现“哦，我需要滚动到下一页结果”，然后截图、再尝试、再滚动。但通过**无障碍接口**、**直接访问 DOM**，以及其他类似手段，现在语言模型可以一次性看到**整个页面或整个应用程序**，它可以编写代码一次性执行多个步骤。这些可能是最大的“顿悟时刻”。相比之下，还有很多小的改进点没那么激动人心，但实际上我们发现，很多速度提升正是通过逐个修复这些小问题、深入反思来达成的。

**主持人**：这需要大量的硬核工程。App Shot 本身就是一个典型的例子，对吧？我觉得很多人不太理解它的特别之处。在 Codex 中截取快照时，虽然展示的是一个好看的视觉图，但他们可能没有意识到，你实际上能驱动每一个按钮，并且每个文本元素都是以最优化的表示方式呈现的。

**Ari**：完全正确（笑）。如果你真的很极客的话，这还挺有趣的。你可以进入 Codex，双击两个 Command 键启动 App Shot，抓取你正在使用的任何应用的内容，将其带入 Codex 或 ChatGPT。然后如果你点击附件，再点击右上角那个小小的按钮，你就能看到原始文本——也就是原始的无障碍表示。我们在**完整导出所有信息**方面做了大量工作，同时也让它在**token 效率**上很友好。这确实有艺术性。有趣的是，这项最初为人类发明的技术——那些有无障碍需求、需要使用屏幕阅读器的人——不仅对人类使用电脑非常有帮助，对语言模型使用电脑也同样有帮助。能参与这项工作真的很有趣。

**主持人**：给听众一些背景：很多人不理解 App Shot，甚至不知道它有这个功能。就是当你双击 Command 时，它会拉进来一个看起来像截图的东西。人们会疑惑“为什么我只是打开了一张截图就丢进来了？”但实际上，它拉取的是**所有的元数据、所有的代码、所有的一切**。

**Ari**：没错。如果你截取了一个带链接的网页，截图不会包含链接指向哪里；如果你截取日历，事件标题可能被截断了。但当你使用 App Shot 时，它给语言模型提供了关于一切的**完整上下文**，这样就让它能做更多的事情。

**主持人**：是的。想了解更多详情的朋友，我邀请了 Jason Louu 在 AI Engineer 大会上做了一场完整的专题工作坊。

**Ari**：他做得非常棒。

## 计算机使用的未来：从超越普通人到超越专家

**主持人**：我还有一个关于计算机使用代理的更宏观的问题。从你说的“截图、滚动、再截图”的过去，到今天的自动化能力，你们已经走了很远。那么现在的瓶颈是什么？是模型？是 harness？你觉得两年后会是什么样？你是否看到它会连续运行几个小时？我们要如何达到那个目标？你对计算机使用的未来有什么预测？

**Ari**：我认为最疯狂的是，团队在过去几个月里达成的成就是：**现在计算机使用在完成任务方面的速度，在大多数情况下可能已经超过了普通人**。我认为下一个前沿是让计算机使用真正达到**超人类**的表现——在使用软件的速度上，至少和专业级计算机用户（比如我们自己）一样快，甚至更快。当这一切发生时，将产生深远的连锁反应和巨大的兴奋感，因为我们突然能够构建提供**更实时体验**的产品。此外，降低计算机使用的准入门槛（或者说“激活能量”）也会让我们开始默认把某些事情交给代理去做——那些我们过去习惯手动完成的事情。这同样令人兴奋，因为这会为我们节省大量时间。

目前，还有很多不同的小问题（paper cuts）和瓶颈横亘在这条道路上。在模型侧、推理侧、harness 侧、表示层面，都有需要改进的地方。我们发现，随着计算机使用变得更快，我们越来越受限于执行操作本身的速度。举个例子，在我们的计算机使用任务基准测试中，**相当大一部分时间实际上是在等待 DoorDash 网站本身加载完成**。

**主持人**：没错，然后你只能写一个等待，然后执行这个等待。

**Ari**：完全正确。而且你其实非常希望尽可能减少延迟——当页面终于加载完成到你触发语言模型执行下一步动作之间的间隔。这本身就是一门统计科学。

**主持人**：也许在可能的情况下，用事件驱动的方式来做？

**Ari**：是的，在可能的情况下，你确实希望它采用事件驱动。JavaScript 有网页导航的加载事件，但还有其他类型的事件实际上无法真正做到事件驱动，所以这里有很多复杂性。

**主持人**：我想到的一个场景是和客户服务的在线聊天——回复可能需要 30 秒，也可能需要 3 分钟。

**Ari**：哦对，我用 Codex 跟无数客服机器人打过交道。这体验很棒，但我也好奇对面是否知道他们正在和一个机器人对话。因为我的回复都是完整的句子，标点规范，还提供完整的参考编号。这显然好得过头了。不过我不在乎（笑），我只要能解决问题就行。

**主持人**：我会在提示里告诉它：“不要装成机器人，要做一个非常恼火的人类，用简短的一句话回复，给他施压。”我还会让它说：“在等待回复的时候，用子代理去研究更好的方法，弄清楚我们还需要什么。”就像是一个微妙的“人类干预”。

**Ari**：太棒了。我甚至觉得有一半时间，对面也是个机器人。所以现在是**机器人跟机器人在对话**（笑）。

**主持人**：那确实很有趣。

**Ari**：我还想说一点：我们今天正处于计算机使用的一个里程碑。三四年前，我们还害怕把语言模型连接到互联网和我们的设备上。而现在，我在让它帮我配置 DNS、帮我付账单——成千上万美元的开支我都直接交给它，用计算机使用功能“梭哈”（YOLO）一把，最坏能怎样呢？（笑）所以，这真的是一个很好的时代。

## Agent API 实践：给开发者的建议与安全提示

**主持人**：现在你显然也在亲身体验自己的产品。既然你们已经通过 API 发布了这些能力，对于即将亲身体验这一切的开发者，有什么坑或建议想告诉他们？

**Ari**：首先，我真的很兴奋我们把计算机使用带进了 Agent API。这对开发者来说意义重大，因为很多开发者构建的应用程序需要与第三方网站和服务进行交互，而**计算机使用具有这种通用性**——它可以与任何东西一起工作。现在，开发者可以直接使用我们内部正在使用的同一套计算机使用实现。

如果你想构建自己的计算机使用 harness，这里面有很大的工程空间，但这很难，而且我们是在自己的计算机使用 harness 上训练模型的。因此，**使用与模型分布一致的 harness 会带来一定优势**——在速度、成本和准确性上可能都有好处。所以我认为能在这个基础上构建对大家来说非常棒。

另外，正如你刚才提到的，我们所有人其实都还在适应这项技术、建立信任的过程中——有些人可能比世界上大多数人走得更前面。因此，我们有责任通过以下方式逐步建立信任：确保我们构建的东西是可靠的，建立正确的安全检查机制，在执行付款等重大操作之前征得用户同意，并且根据应用场景，确保代理只访问它完成任务真正需要的网站或应用。这些是需要重点考虑的方面。但总之，我非常鼓励大家尝试新的 Agent API，在上面构建各种酷炫的东西，也非常期待听到大家的反馈。

## 自动化测试：完善软件开发全生命周期

**主持人**：你有没有观察到它如何影响开发工作流程的变化？Dots 的一个重要特点是，你可以看到它出现在 Slack 中，人们通过语音来构建。Roman 展示的例子是“修改这个应用，过程中给我发截图”。你有没有看到人们在采用计算机使用进行编码工作流方面的变化？有什么可以借鉴的建议？

## 性能优先：缓存策略与压缩技术

**主持人**：有没有一个你希望人们特别关注并在使用后反馈给你的点？也许你刚刚发布了这些功能，现在正面临一个分叉路口，希望开发者帮你做决定？

**Nikunj**：Agent API 和决策 API 是我们最新的产品，我们非常希望获得关于它们**任何形式的反馈**，以便决定下一步方向。在 Responses API（我们的“主力”API）方面，我们现在非常关注**性能**，而性能主要体现在两个方向。首先是**延迟**——我们一直在重写整个 Responses API 技术栈，从 TDF（首 token 延迟）和 DBD（token 间延迟）的角度把它做到最快。这依然是我们关注的核心。第二个方向是**缓存**，特别是在这些“个人代理”场景下——基本上就是一条永不结束的持续对话线程。我们一直在努力提升缓存能力。我们目前提供 **30 分钟内缓存命中保证**。实际上，我们刚刚为某个用户上线了一个长得多的缓存窗口——**12 小时缓存保证**，这样你就可以在更长时间内获得缓存命中。

**主持人**：这个有公开 API 吗？

**Nikunj**：还没有，目前是预览版，我们会尽快推广给所有人。基本上就是多付一点缓存费用，但我们保证在更长的时间内缓存可读。所以即使你的线程比如“Codex 线程”——你做了某件事，然后过三四个小时再回来，你仍然能享受到缓存性能。

**主持人**：在新模型的加持下，成本也大幅降下来了，对吧？

**Nikunj**：是的，我们的缓存读取成本也在持续下降。

**主持人**：对于开发者来说，他们应该去实现节点化，因为这会便宜很多。

**Nikunj**：是的。我建议开发者构建应用时要有**“缓存意识”**，并使用我们的提示诊断工具或缓存诊断工具来确定哪些地方的缓存失效了。缓存这部分非常重要。另外，我还想提一下**缓存预热（pre-warming）**——现在 API 已经支持了。如果你知道自己即将处理某个提示词，你可以直接预先把缓存填好——现在就支付缓存写入费用，让它准备好，接下来 30 分钟内随时可以使用。

**主持人**：而且我可以生成这个线程的许多实例。

**Nikunj**：完全正确，你可以一直往下走。所以，我非常期待收到关于这类底层性能问题的反馈，以便我们继续让 Responses API 成为基于大语言模型构建应用的最高性能和最可靠的方式。对于新发布的产品，我就是在寻找任何形式的反馈。

**主持人**：总之就是去用，然后把结果告诉我们，为你们定路线图（笑）。

**Nikunj**：（笑）是的，告诉我们，帮我们制定路线图吧。

**主持人**：对我来说，缓存这部分非常棒，显然是刚需。但归根结底，你仍然会撞上一百万 token 的上下文限制——在可预见的未来这可能不会改变。你仍然需要好的**压缩**。这方面有什么最佳实践吗？

**Nikunj**：是的，完全正确。首先，OpenAI 有自己的专有压缩方法——**compaction（压缩）**，它已经集成在 Agent API 中了。

**主持人**：你们替我们做了决定，对吧？（笑）

**Nikunj**：是的，在 Agent API 中，压缩被直接构建在 harness 中。如果你使用 Responses API，有两种方式：一种叫做**服务端压缩（server-side compaction）**——你告诉 Responses API，如果达到某个 token 阈值，就自动压缩，减少上下文的使用。另一种是 **/compact 命令**——如果你想要完全控制，可以随时手动压缩，按你自己的逻辑来决定什么时候触发。

**主持人**：这不是……（笑）

**Nikunj**：但它的确是一种手动覆盖方式。

**主持人**：是的，这确实是手动模式。

**Nikunj**：很多大型编码代理喜欢手动压缩。比如你看 Codex 的开源实现——在开源的 Codex harness 代码中，你可以看到他们用 `/compact` 来做这件事。另外，我们还在开发一些**新的压缩技术**。有些你可能已经能在 Codex harness 中看到了——它们已经在那里实现，还有一些基于文件（file-based）的系统正在实验当中。总之，压缩方向上还有很多很酷的东西在推进。

## 平台未来：AI 原生云中的高层级抽象
