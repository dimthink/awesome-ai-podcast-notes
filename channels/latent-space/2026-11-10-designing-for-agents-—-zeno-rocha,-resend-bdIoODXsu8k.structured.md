# 从开源项目到基础设施：Zeno Rocha 与 Resend 的电子邮件平台重塑之路

## 开场：从独立开发者到基础设施创业者

Zeno Rocha，Resend 的创始人，过去以 VS Code 主题 **Dracula** 而闻名。他开玩笑说，自己当时“只是一个独立开发者”，但实际上在 2022 年他是 GitHub 上最活跃的 20 位开发者之一，在开源领域非常活跃。

如今，人们仍然更多地知道 Dracula 而不是 Resend。Zeno 表示这种认知正在慢慢改变，但他对于如何介绍自己并不太在意，更多聚焦于近期的职业生涯。

## 为什么选择电子邮件？

Zeno 原本是一名前端工程师，专注于 JavaScript 和 HTML5，对基础设施和邮件系统一无所知。他使用过 Mailgun、Mailchimp、SendGrid 等工具，但总觉得这个市场虽然庞大、竞争激烈，却没有人真正关心开发者体验。其他玩家可能关心营销人员或产品经理，但开发者被忽视了。于是他开始思考：“如果存在一个‘电子邮件领域的 Stripe’，它会是什么样子？”带着这个前提，他开始构建 Resend。他坦言，如果早知道电子邮件有多难，他可能就不会创办这家公司了。

## Resend 的规模与客户

Resend 目前为 **430 万用户**提供支持（截至采访当天早晨）。客户包括华纳兄弟、HBO 等大型企业，以及大量独立开发者和小团队。付费客户数已突破 **12 万**，公司年经常性收入（ARR）达到 **1000 万美元**。Zeno 表示，他更愿意生活在这样的现实中——公司营收 1000 万美元，但女儿还愿意和他一起玩、与他亲近——而不是营收 1 亿美元却失去了与家人的联系。

## 从零开始构建电子邮件服务

当被问及如何构建一个批量发送电子邮件的服务时，Zeno 解释说，电子邮件与普通应用不同，不能简单地通过增加 GPU 或水平扩展来解决问题。**投递到收件箱**（尤其是高发送量时）必须遵守游戏规则。Gmail、Outlook、Yahoo Mail 的行为各不相同。这个行业非常传统，依赖大量联系人和人际关系。

Zeno 承认，他们最初对这个世界一无所知，但这种“极端天真”反而是最大的优势。因为没有先入为主的观念，他们敢于挑战传统做法。例如，其他平台要求用户先填写表格、说明发送量、用途，然后等待人工审核，两天后可能被拒绝。Resend 选择完全移除这些摩擦，将风险转移到自己身上。当然，经营三年后，他理解了为什么其他公司会这样做——欺诈、钓鱼和滥用问题非常多。Resend 内部建立了各种疯狂的系统来应对这些问题。

### 发送架构的艺术与科学

当发送 10 万封邮件给 Gmail 时，如果一次性全部发送，Gmail 会进行节流。邮箱提供商希望看到渐进式的发送模式，并根据初始打开、存档、删除或忽略的比例来决定如何处理后续邮件。明智的做法是：**将最活跃的收件人放在发送队列的前面**，然后分批发送，并在不同提供商之间进行间隔。现在，Resend 甚至购买不同的 IP 块，查看 IP 块的历史记录，将用户分配到不同的 IP 池，并随时间平衡这些池。这是一个复杂的架构游戏。

自动化程度很高，但对于新客户，Resend 会限制发送速度以保护发件人。邮箱提供商希望看到持续增长的发送图，而不是一次性大发送后长时间静默。滥用者通常一次性发送大量邮件，然后不再发送。因此，发送者需要**做与滥用者完全相反的事情**。

## 反滥用与信任哲学

Zeno 举了一个例子：最近有一个日本团伙购买了约 **2 万个域名**，这些域名分散在不同的顶级域名（TLD）和不同的域名注册商中。Resend 会检查多个因素：域名是否刚刚注册（新域名声誉差）、网站是否返回 200 状态码、是否使用了仿冒域名进行冷外联等。这些行为看起来就像钓鱼。因此，Resend 反向工程钓鱼攻击的模式，构建了一个做完全相反事情的平台。

### 默认信任与快速干预

Zeno 用一个比喻来说明 Resend 的理念：出生在一个你必须先在监狱里待 18 年证明自己是好公民后才能自由的社会，这不是他想要的。他想要的社会是：出生时自由，犯错时受到轻微的惩罚，或严重错误时受到严厉惩罚。所以 Resend 默认信任用户，但一旦发现问题（通过退信率、投诉率、邮箱提供商的反馈），他们会非常快速地封锁用户，然后进行沟通。大多数情况只是误用而非滥用，需要区分。

## 扩展客户支持

支持经历了多个版本。最初只有 Zeno 自己，后来他随便雇了一个人，但发现需要能主动防止工单产生的人。V2 版本的新员工有领域知识，但仍然没有做预防性工作。他们制定了一项政策：**只能用链接回复工单**——必须先写知识库文章或文档，然后再回复。这花费更多时间，但帮助建立了知识库。

当用户达到 100 万时，他们意识到不能靠不断增加人力来解决问题，必须重新思考整个支持体系。Resend 希望保留免费层，因为 Zeno 自己作为工程师时就依赖免费产品。现在问题集中在 **DNS 设置**上——许多新用户（例如来自 Lovable、Bolt、v0 的用户）不知道如何设置 CNAME、A 记录、TXT 记录。Zeno 提到一个鲜为人知的协议 **Domain Connect**，它类似于“域名的 OAuth”，通过点击按钮而无需输入任何内容即可完成 DNS 配置。GoDaddy 对此收费很高，协议维护者也难以联系，但 Resend 已经推动了 Cloudflare、Vercel 等加入。

## 从 React Email 到平台

React Email 是 Resend 的开源引流渠道。Zeno 在构建 Resend 时做了大量用户研究，发现编写邮件模板非常痛苦：HTML 表格、内联 CSS、Outlook 特殊语法等。React Email 本质上是一个编译器，让开发者用 React/JSX 编写模板，然后编译为兼容所有邮件客户端的 HTML。它不包含 JavaScript 交互，只是模板化，但通过 Tailwind 和 TypeScript 提供了类型安全和验证。Zeno 有意在 React Email 文档中加入了如何在 SendGrid、Mailchimp、Mailgun 上使用的内容，以“给予、给予、再索取”的策略（他开玩笑说这是 Gary Vee 的策略）吸引用户，最终将他们引导到 Resend。

## 行业内幕与竞争对手

### Mailgun

Zeno 提到早期与 Mailgun 创始人 Ev 的对话。Ev 告诉他，Mailgun 研发的 90% 都用于打击滥用者，这是一个糟糕的生意。这促使 Resend 将自动化反滥用作为核心。

### SendGrid / Twilio

SendGrid 一直是 Zeno 的最爱，也是行业巨头。Zeno 曾经觉得“我们怎么可能打败 SendGrid？这简直不可能。”但今年早些时候，Resend 的 SDK 在 npm 下载量上超越了 SendGrid，现在已经是其两倍多。尽管邮件发送量仍不如 SendGrid，但开发者采用率是一个重要指标。

Zeno 敬佩 Twilio 早期在开发者关系上的创新（“Ask your developer”），但现在他看到 Twilio 的广告变成了“客户 AI”等，觉得他们忽视了当初让他们成功的开发者社区。他认为 Twilio 收购 SendGrid 后可能过于分散，而 Resend 则始终聚焦。

### AWS SES

Zeno 指出，SES 看起来便宜（例如每月 5000 美元发送数百万封邮件），但隐藏成本很高：需要 SNS 获取事件，需要 CloudWatch 日志，需要 SQS 队列，需要自己构建 webhook 等。使用 SES 会让你的基础设施足迹迅速膨胀。Resend 最初构建在 SES 之上，专注于开发者体验层；但现在他们正在**向底层金属迁移**，构建自己的基础设施，以获得更好的吞吐量和投递率。

## 深入底层：构建自己的基础设施

Resend 正在推进一个大型项目，即自主研发底层发送基础设施。其中最大的难点之一是**IP 块**的管理——自己购买和管理 IP 池，进行流量控制，并与邮箱提供商建立关系。拥有底层基础设施后，Resend 可以暴露更多可观测性数据，让开发者看到邮件是否真正送达、是否进入垃圾邮件或促销标签等。

Zeno 提到 Resend 一直使用 Node.js 和 TypeScript，但最近在发送路径上改用了 **Go**，以提升性能。他也提到了使用 Rust 的可能性——虽然自己不熟悉 Rust，但认为现在语言不是障碍，可以选择最适合的语言。

## AI 与代理时代

### MCP（模型上下文协议）的爆发

Zeno 观察到，许多人曾认为 MCP 已死，但 Resend 的 MCP 调用量呈指数增长：每月至少翻倍，到 8 月达到 120 万次。他们的第一个 MCP 是由 A16Z 的 Yoko 构建的开源本地版本，后来 Resend 将其纳入正式维护。为了做好远程 MCP，他们需要重新构建权限模型和 **OAuth**，这是一个完整的旅程。

Zeno 认为，**官方 MCP** 很重要。作为消费者，他现在会根据是否有官方 MCP 来决定是否使用某个产品。例如，他放弃了 Plausible 而选择 PostHog，因为 PostHog 有官方 MCP；他使用 Strava 也是因为其官方 MCP。如果一个 MCP 不是官方维护的（即使由 Sentry 团队构建），他也不会完全信任。

### 好的 MCP 的特征

Zeno 提到，工具数量不再是问题（Resend 的 MCP 从不到 20 个工具扩展到 80 多个），关注点转向**数据量**和长尾覆盖。要做到 100% 覆盖仪表盘功能非常困难，包括使用、计费、团队邀请、账户配置和删除等。Zeno 认为 Next.js 的一个错误是让开发者容易将数据绑定到页面，从而不暴露公共 API，这不利于构建完全无头的后端。

### LLMs.txt 与 AI 可见性

Resend 对文档和网站做了大量优化：增加 FAQ、LLMs.txt 文件、每个页面的 `.md` 版本。Zeno 举了一个例子：AI 曾经错误地认为 Resend 的定价“非常模糊”，于是他专门为定价页创建了 markdown 版本，包含完整的定价信息，之后 AI 的答案就正确了。他承认这需要维护两个版本，但这是正确的做法。

## 多渠道与未来方向

Zeno 提到他们正在探索 **入站邮件** 领域，计划推出允许用户编程创建多个收件箱并供代理访问的 API。这将提供读取、标记未读、标签等 API，与 Missive、Help Scout、Front 等产品类似，但完全 API 驱动。

他还提到了对 **短信、WhatsApp、Slack** 等渠道的思考。WhatsApp 通过 Meta 的商业消息会收费；短信利润率更低；电话他不太感兴趣。他关心的是**与受众建立联系**，而不是特定渠道。

## 职业申请与产品哲学

Zeno 甚至在 Resend 的招聘页面上做了创新：求职者可以通过 **CLI、API 或 MCP** 申请职位。他特别关注那些通过 CLI 申请的人，因为愿意走额外步骤的人通常更有热情。这体现了他的产品哲学：**优化所有边缘用户**，包括在巴西长大时使用糟糕电脑和差网络的自己。因此，Resend 提供免费层和所有主流语言的 SDK（包括 .NET、Java、Rust 等），并且所有 SDK 都是人工生成的，而不是用 Stainless、Fern 等工具自动生成，因为他希望每个语言都有最佳体验。

## 邮件投递率与域名策略

Zeno 强调，如果没有投递率，企业就无从谈起。现在邮件声誉更多地与**域名**相关，而不是 IP。他建议使用不同的子域名来区分交易邮件和营销邮件，例如 `transactions.resend.com`、`marketing.resend.com`，甚至个人使用 `confidential.resend.com`。他警告不要购买与主域名相似的域名，因为这看起来像钓鱼。例如，如果 Coca-Cola 拥有 `coca-cola.com`，再购买 `coca-cola.net` 可能看起来可疑。但 `.com` 域名通常仍然值得投资。

## 结论

采访结束时，采访者表达了对 Zeno Rocha 的敬意，称赞他选择了正确的领域、执行出色，并且兼顾了家庭。Zeno 也再次感谢了这次交流。
