## 开篇引入

这是一期在非常特殊的时间节点录制的播客。录制当天，Anthropic 刚刚提交了 S-1 文件，正式开启 IPO 进程；而就在前一天，他们刚刚发布了当时被许多顶尖测试者称为“世界上最好的模型”——Opus 5.5。

这两个事件叠加在一起，让这期对话有了双重价值：一方面，我们要理解 Anthropic 作为一家公司，如何在烧掉不到 100 亿美元的情况下，打造出一个年化收入惊人、刚刚实现 GAAP 盈利的超级增长机器；另一方面，我们要深入到工程与产品的微观层面，看看一家 AI 公司到底是怎么“造出”一个世界级大模型的——不是靠魔法，而是靠无数个艰难的权衡、精细的安全框架、以及一个敢于让 Claude 自己重写自己 API 平台的团队。

主持人 swyx 在开场时说了一句很关键的话：Anthropic 是“按人头计算”效率极高的公司。这个判断贯穿了整期对话——从商业数据到技术架构，从产品设计到团队文化，你都能看到一种对“效率”的极致追求。但这里说的效率，不是为了省钱而省钱，而是在不牺牲安全与质量的前提下，用更少的资源撬动更大的能力。

这期节目最精彩的地方，是两位嘉宾揭开了很多“背后的事”。比如，Anthropic 为什么要防蒸馏，背后的逻辑居然主要是安全而非商业；比如，他们如何用 Rust 从零重写整个 Messages API 平台；比如，Claude Managed Agents 的原始架构，竟然有一个被忽视的安全预言，事后被证明极为正确。

接下来，我会按照这期对话的内在逻辑，把它完整、深入地呈现出来。


## 第一部分：Anthropic 的效率神话与 IPO 背景

### 从烧钱到盈利：S-1 文件揭示的效率革命 `[开头引言段落]`

**核心观点**
Anthropic 的效率提升速度远超外界认知——一年之内，每位员工创造的收入从 140 万美元飙升至 660 万美元，公司从每赚 1 美元亏 0.5 美元，变成每花 1 美元成本赚 2 美元收入。

**深度阐述**

swyx 在开场时特意表明了自己的“前金融分析师”身份，并直接引用了 Anthropic 刚刚提交的 S-1 文件中的几个核心数据。这些数据即使在 AI 行业整体高速增长的背景下，也显得极为惊人。

第一条数据是**人均营收**。过去 12 个月，Anthropic 每位员工创造的年化收入是 660 万美元，而一年前这个数字只有 140 万美元。这意味着在短短一年时间里，人均产出增长了接近五倍。这是一种极其罕见的效率跃迁。为什么这个数字重要？因为它不仅仅是利润率的指标，更直接决定了公司能给员工付多少薪水，以及这家公司在人才竞争中的上限。对于任何企业主或工程师来说，提升人均收入都是比单纯削减成本更可持续的增长路径。

第二条数据是**每一美元计算成本创造的收入**。2025 年第二季度，Anthropic 每获得 1 美元收入，就要亏损约 0.5 美元——也就是说，它的成本收入比是倒挂的。但到了现在，这个数字完全翻转：每投入 1 美元成本，能创造 2 美元收入。这是从“烧钱增长”到“有质量增长”的标志性转变。

第三条数据是**盈利能力**。Anthropic 刚刚报告了第一个 GAAP 盈利季度——注意是 GAAP，不是“调整后利润”。GAAP 盈利的含金量在于，它包含了所有真实成本，不像“调整后 EBITDA”那样会剔除股权激励等大额支出。这个季度，Anthropic 的 GAAP 利润率达到 19%，而一年前它的亏损率是 129%——每赚 1 美元，要亏 1.29 美元。一年之内，从 -129% 到 +19%，这是一个接近 150 个百分点的翻转。

swyx 特别提了一句很有意思的细节：Anthropic 这家公司历史上累计融资超过 1000 亿美元，但累计烧掉的现金不到 100 亿美元。这个对比在 AI 行业里是极其罕见的——大多数头部 AI 公司融资和烧钱的比例都远没有这么“健康”。这也是为什么他认为“效率”是理解 Anthropic 成功的关键角度。

### 两个循环：Anthropic 的飞轮模型 `[开头引言段落]`

**核心观点**
Anthropic 的效率增长并非偶然，而是由两个互相咬合的循环驱动：改进循环和投资循环。

**深度阐述**

swyx 在开场中提到，Anthropic 内部文化里“loop”（循环）是一个被反复提及的词汇——Claude 喜欢循环，Boris 喜欢循环，Dario 也喜欢循环。而这背后，是两个具体的企业飞轮。

第一个是**改进循环（Improvement Loop）**：Claude 模型变得更好，更好的模型解锁更多的使用场景，更多的使用场景生成了更多的真实反馈数据，这些反馈又反过来帮助改进 Claude 模型。这是一个以产品迭代为核心的飞轮。

第二个是**投资循环（Investment Loop）**：Claude 的采用率扩大带来收入增长，收入增长支撑更高的投资，更高的投资带来更强的模型能力，更强的模型能力又让 Claude 变得更好。这是一个以资本配置为核心的飞轮。

这两个循环的关键在于它们是**互相耦合**的。改进循环里的“更多反馈”，会转化为投资循环里的“更高采用率”；投资循环里的“更强能力”，又会重新触发改进循环里的“更多使用场景”。两个循环组合在一起，形成了一个正反馈的复合系统。swyx 引述 Anthropic 的说法是，这个循环会“一直转下去，直到时间的尽头”。

这个框架是理解整期播客的重要背景——接下来的所有技术细节，从防蒸馏、到安全护栏、到 Rust 重写、到 Claude Managed Agents 架构，本质上都是在为这两个循环的加速运转提供基础设施。

### 从模型实验室到云平台：S-1 中的战略定位 `[开头引言段落]`

**核心观点**
Anthropic 的 IPO 叙事正在从“模型实验室”升级为“综合开发者平台”，其核心产品 Claude Platform 正在成为大量商业应用的基础设施。

**深度阐述**

S-1 文件中提出了一个概念，叫“Claude 的扩散”（diffusion of Claude）。Anthropic 把这种扩散分为三个层面：一是 Claude 模型本身，二是 Claude Code 和 Claude Cowork 等第一方应用，三是 **Claude Platform**——一个“综合性的代理开发环境”（comprehensive agentic development environment）。

这个定义非常关键。它意味着 Anthropic 不只是通过 API 提供模型 token，而是在提供一个完整的开发基础设施，让客户能够在自己的产品和工作流中构建、部署、扩展基于 Claude 的应用程序。用更通俗的话说：Anthropic 正在成为一个“超大规模云平台”（hyperscaler），而不仅仅是一个模型供应商。

有一个数据支撑这个转型的真实性：S-1 文件披露，在年化收入 10 万美元以上的客户中，**超过 50% 已经在使用 Claude Platform**。这说明开发者黏性不只是停留在“调用 API 生成文本”的层面，而是进入了“用 Aphic 的基础设施来构建完整的应用”层面。

还有一个很重要的细节：**Claude Code 和 Claude Cowork 这两个第一方产品，本身就是建立在 Claude Platform 相同的原语（primitives）之上的**。这就是所谓的“dogfooding”（用自己的产品）。对开发者来说，这意味着你使用的 API 能力，和 Anthropic 自家产品使用的底层能力是完全一致的——你不会被排除在那些真正有用的功能之外。

swyx 进一步指出，Anthropic 的 IPO 叙事是从 **“chatbots 到 copilots 再到 virtual collaborators（虚拟协作者）”** 的演进。他们特意使用了“collaborator”这个词，而不是“agent”，因为它更友好、更强调人与 AI 的协作关系。但本质上，这些“虚拟协作者”具备的是 AI 代理（agent）的核心特征：长时间自主运行、拥有判断力、自我纠正、能够调用工具、拥有一个明确的目标，并且与你并肩工作，而不是替代你去做某一件孤立的任务。

**个人感受**
开场这几分钟里，swyx 的情感基调是兴奋中带着一种“我早跟你们说过了”的笃定。他反复强调这是一个“全新的尝试”——从传统的“与嘉宾对话”转向“建立与观众的个人连接”——但他更兴奋的显然是他能从 S-1 文件中读出那些被大多数人忽略的效率逆袭故事。他特别指出，多数人只看到 Anthropic “烧钱做前沿模型”，却没有意识到它的人均产出正在以惊人的速度增长。

**延伸思考**
这个概念框架值得进一步推演。如果“改进循环”和“投资循环”真的在持续加速，那么 Anthropic 的竞争壁垒就不只是一个更强的模型，而是一个能自我强化的系统。这也解释了为什么他们愿意在“安全”上投入如此巨大的成本——因为任何一个安全灾难都可能直接打断这两个循环的运转，而防护措施本身就是让循环能持续转下去的润滑油。

**精华收获**
- Anthropic 的人均年化收入一年内从 140 万到 660 万美元，增长近 5 倍
- 成本收入比从“每赚 1 美元亏 0.5 美元”翻转为“每花 1 美元赚 2 美元”
- 第一个 GAAP 盈利季度利润率为 19%，一年前是 -129%
- 理解 Anthropic 的核心框架是“改进循环 + 投资循环”的复合飞轮
- Claude Platform 正在把 Anthropic 从模型实验室转型为综合开发者基础设施


## 第二部分：防止模型蒸馏——一场关于安全与商业逻辑的深度博弈

### 知识蒸馏：AI 世界的“偷师学艺” `[关于蒸馏的讨论段落]`

**核心观点**
知识蒸馏是 AI 模型训练中最强大的技术之一，也是 Anthropic 持续投入大量精力去防范的滥用方式——但他们的核心动机不是保护商业利益，而是防止安全护栏被绕过。

**深度阐述**

要理解这个讨论，先要搞清楚一个概念：**知识蒸馏（distillation）**。

简单来说，知识蒸馏就是用一个强大的“教师模型”来训练一个更小的“学生模型”。具体做法是：把大量问题和提示词输入教师模型，收集它的输出，然后用这些“教师输出”去训练学生模型。学生模型不需要从头学习，只需要模仿教师模型的行为，就能以低得多的成本获得接近教师模型的能力。

但这里有个关键问题：**如果要蒸馏的教师模型有安全护栏——比如，当你问它“如何制造危险物质”时，它会拒绝回答——那么你希望蒸馏出来的学生模型也要继承这种安全行为**。

问题是，被蒸馏出来的学生模型通常**不会**继承这些护栏。因为蒸馏的过程中，攻击者往往只提取模型的“智能”部分，而刻意剥离掉安全分类器、输出过滤、在线防护这些“安全外衣”。结果就是：一个能力接近 Claude 的模型，却在没有任何安全约束的情况下运行。

这正是 Anthropic 担心的核心。Angela 说得很直接：“**The reason we don’t want distillation is because the entire point of why Anthropic exists is because we want AI to create positive outcomes in the world safely。**”——“我们不希望蒸馏发生的原因，是 Anthropic 存在的全部意义就是让 AI 以安全的方式为世界创造积极的结果。我们在生成的 token 上运行了很多安全分类器，以确保它们的安全性。如果有人蒸馏了我们的模型，并且在没有这些安全分类器的情况下运行它们，世界可能会因此产生不好的结果。”

这里特别值得注意的是一个商业逻辑的反转。Angela 说：“**Realistically, if you distill from us, we actually pay us. So, commercially, we like make the money.**”——“实际上，如果你从我们这里蒸馏模型，你反而是在付我们钱。从商业角度，我们其实赚到了钱。” 这句话透露了一个反直觉的真相：知识蒸馏并不是一个让 Anthropic 在商业上流血的事情，因为攻击者必须大量调用 Anthropic 的 API 来获取教师输出，而 API 调用是收费的。

所以，防蒸馏的动机**不是商业保护，而是安全保护**。如果一个人蒸馏出 Claude 的“裸模型”——没有安全分类器、没有输出过滤、没有滥用检测——并把它用于恶意用途，Anthropic 无法在模型之外控制这种滥用。

### 思维链提取：如何“偷走”模型的推理能力 `[关于推理痕迹窃取的讨论段落]`

**核心观点**
Chain of Thought（思维链）提取是最高效的蒸馏手段之一。Anthropic 已经为此工作多年，并且在 Opus 5.5 中推出了一系列“保留思维块”的新机制来封堵这一漏洞。

**深度阐述**

主持人在这个环节提到了一篇著名的学术论文，它探讨了如何从专有模型中**窃取推理痕迹（reasoning traces）**。这篇论文由研究人员通过负责任的披露流程提前告知了 Anthropic，并等到模型厂商完成修补后才公开发表。

Angela 对这个话题的回应非常坦诚。她承认：“**我们其实早就知道思维链提取是最强大的蒸馏方式之一。**”这句话的意义在于，外界往往把这篇文章视为一个突发威胁，但对 Anthropic 来说，这只是他们长期跟踪的一个已知缺口，论文的高调发表并没有在内部引起所谓的“大恐慌”。

这就引出了一个技术概念：**思维块保留（Preserved Thinking Blocks）**。

正常使用 AI 模型时，模型可能会输出“推理过程”（thinking tokens），然后再给出正式回答。这些推理过程往往非常详细、非常接近模型的内部“思考”过程。如果攻击者能在多轮对话中保存并重放这些 thinking blocks，他们就能获得大量高质量的“教师思维”，从而极大地加速蒸馏效率——甚至比单纯使用最终答案有效得多。

Anthropic 的对策是：**在多轮对话中要求保留思维块**。但这样做会带来用户体验的破坏。Angela 把这类破坏分为两个层次：

- **第一层**：只是让用户做一些额外的集成改动，虽然烦人，但你仍然能实现所有你想要的功能。这是可以接受的。
- **第二层**：让用户完全无法实现以前能实现的事情。这是 Anthropic 极力避免的——用 Angela 的话说，“**That’s the one that we’re really really really trying to not have happen。**”

这个区分看似简单，实则是产品决策里最容易失手的地方。很多公司为了防止滥用，会一刀切地禁止某些功能，结果把大量合法用户也拖下水。Anthropic 的做法是：在不破坏合法使用场景的前提下，逐步收紧安全边界。

为了做到这一点，他们做了几件并行的事：

1. **增量式推出**：在过去几个模型版本中，逐步强制要求“保留思维块跨轮次”。现在进一步扩展到“跨账户”的场景——防止攻击者用多个账户分散提取。
2. **与 Harness 维护者合作**：他们主动联系了开源 harness（那些封装 API 的工具框架）的维护者，提前告知升级需求，并帮助他们完成适配。
3. **为合法使用场景提供替代方案**：举例来说，一些大客户有“压缩策略”（compaction strategies，把长对话压缩成更短的上下文），这种策略会因为保留思维块而崩溃。Anthropic 就在 API 里直接提供了一个新的压缩功能，既能替换客户原来手动做的事情，又能与保留思维块兼容。

Angela 总结道：“**we didn’t just like kind of yolo out like ‘now you have to preserve these thinking blocks in this exact way’ because we would have broken a lot of people。**”——“我们没有直接甩出一个‘现在你必须按这种方式保留思维块’的粗暴规定，因为那会砸毁一大堆人的体验。相反，我们花时间与客户和开源维护者合作，给他们提供完成升级所需的工具。”

在效果方面，Angela 表示，从他们能测量的指标来看，思维链提取的难度确实显著增加了，负面效果有所减轻。

**个人感受**
这一部分的语气非常有趣。Angela 在讲述蒸馏攻击时，带着一种“这问题我们早就知道，也早就开始处理了”的从容。但谈到安全动机时，她的语气明显变得严肃。她特别强调“我们真的不太在乎商业化层面的蒸馏损失，我们在乎的是安全”时，并非公关话术，而是有实际商业逻辑支撑的：蒸馏者必须付费调用 API。这种“安全优先于商业”的立场，在 AI 行业里不算罕见，但能把它贯彻到产品路线图里，并且愿意为此牺牲一部分用户体验，并不多见。

**延伸思考**
防蒸馏这件事本质上是一场没有终点的军备竞赛。攻击者的技术会进步，防御措施也必须持续升级。但更深层的问题在于：当 AI 模型的能力越来越强，如何区分“合理的学习”和“恶意的蒸馏”？如果是学术研究用途的“模型萃取”，是否应该网开一面？Anthropic 的答案是：在无法精确分辨的情况下，优先保护安全边界。

这其实映射了一个更大的哲学问题：AI 能力扩散的收益与风险如何分配。Anthropic 采取的是“有边界地扩散”路线——你可以获得 Claude 的能力，但你不能剥掉它的护栏。

**精华收获**
- 知识蒸馏的攻击成本高昂，因为攻击者必须付费调用 API，所以 Anthropic 的核心动机不是保护商业收入
- 思维链提取是最强大的蒸馏方式，Anthropic 多年来一直在研究如何封堵
- “保留思维块”是一个艰难的产品权衡：既要防蒸馏，又不能破坏合法用户的体验
- 用户破坏要分两层：烦人的集成改动可接受，丧失功能不可接受
- 良好的应对策略：增量推出 + 与生态合作者提前沟通 + 为合法使用场景提供替代方案


## 第三部分：Opus 5.5 —— “世界上最好的模型”是如何炼成的

### 一次“写作被投诉后”的自我修正 `[关于 Opus 5.5 写作改进的讨论段落]`

**核心观点**
Opus 5.5 的核心改进之一是写作风格的修正——Anthropic 认真听取了用户对 Opus 5 写作“绕弯子”的批评，并在新版本中大幅调整，使模型表达更加简明清晰。

**深度阐述**

Katelyn 在回顾 Opus 5.5 时说：“**The team has put in a ton of different work to just go make this one happen and I think we’ve really heard the feedback on Opus 5’s writing is like kind of convoluted. We really try to clean that up。**”——“团队投入了大量工作才把这件事做成，而且我们确实认真听取了用户的反馈：Opus 5 的写作有点绕。我们真正努力去把它清理干净。”

这可能是一句话里最有信息量的地方。世界顶级的模型团队，在发布一个“更聪明的模型”时，重点修正的居然是一个听起来很“软”的问题：写作风格。这背后是深刻的用户洞察：**聪明不等于好用**。如果一个模型在技术评测中得分更高，但输出冗长、思维跳跃、表达模糊，用户就不会真正喜欢使用它。

Katelyn 还提到，在内部测试时，他们自己就感受到了 Opus 5 写作的“绕”，而用户的公开反馈强化了这一点。“当它似乎在公开场合引起共鸣时，我们真的很高兴看到那种验证。”

这提醒我们一个评判模型的新维度：除了 benchmark 分数，还有“用户可用性”的维度。一个模型是否让人觉得“好用”，往往是决定它能否被“扩散”到底层应用的关键。

### 定价与“单位美元的智能” `[关于定价削减的讨论段落]`

**核心观点**
Opus 5.5 的定价策略反映了整个行业从“追求最高智能”到“追求单位美元智能”的转变。

**深度阐述**

主持人 swyx 特别提到 Opus 5.5 的“定价削减”是一个很酷的动作。Katelyn 的回应是：“**Increasingly people are looking for good intelligence per dollar, and so making sure we get the per dollar part right has been really important。**”——“人们越来越追求‘每花一美元能买到多少智能’，所以确保我们在‘每美元’这个维度上做对，已经变得非常重要。”

这句话揭示了一个根本性的行业趋势——AI 模型的竞争正在从**能力竞争**转向**效率竞争**。当模型的绝对智能水平逐渐接近饱和（尤其在大量常规任务上），用户开始越来越在意：完成这项工作到底值不值得这个钱？对于开发者和企业来说，这个指标直接影响他们能否盈利、能否规模化部署。

Opus 5.5 的成本效益提升，不是在牺牲能力的前提下“降低价格”，而是通过模型本身在 token 效率、推理效率、运行成本上的优化，让“每美元的智能”变得更高。Katelyn 特别强调，他们做的 AP 定价调整，实际上是在鼓励用户进行那些“对所有人都有益”的集成改动，然后把节省下来的成本回馈给用户。

这背后是一个很先进的产品理念：**定价不只是商业策略，也是产品路标**。通过定价信号，Anthropic 在告诉开发者：“我们希望你朝着这个方向发展，因为这个方向对你有利，也对整个生态有利。”

### 产品与工程的“灵魂互换”：产品经理误当工程师，工程负责人误当产品经理 `[关于 Caitlyn 和 Angela 角色分工的讨论段落]`

**核心观点**
Anthropic 平台团队有一个有趣的组织特征——产品角色和工程角色之间的边界高度模糊，两位负责人甚至彼此被误认为是对方角色，这种交叉融合是高效协作的关键。

**深度阐述**

这一段很能体现老板之间相处的动态。Katelyn 是平台产品负责人，Angela 是平台工程负责人。但 swyx 开了个玩笑说：“你经常被误认为产品经理，Angela 经常被误认为工程师，尽管那不是你们的正式职位。”

这个“误认”并非偶然。它指向一个正在发生的组织变革：**软件工程正在被“部分解决”，因此产品和工程角色开始融合**。当 AI 可以承担大量代码实现工作的时候，传统意义上的“工程管理”和“产品管理”职能边界就必然开始松动。

Angela 并不完全认同“软件工程已经解决”这个激进的说法。她解释说：“**I don’t know if I would ever use language quite that strong。**”——“我可能永远都不会用这么强烈的说法。” 她的观点是：模型能力在变化，但人类的“野心”（ambitions）也在同步抬高。当你的系统规模增长几十倍、当你要为全球数百万用户提供服务、当你要在安全约束下运行超大规模代理系统时，真正的工程问题远比“写出能跑的代码”复杂得多。

她举了一个非常具体的例子，来说明为什么传统工程仍然不可替代：她加入 Anthropic 时，Messages API 还是一个 Python 单体应用，跑在单个 GCP 区域。一切都很好，但“没有任何朋友和家人知道 Claude 是什么”。现在情况完全不同——他们必须处理前有未有的规模化问题，而“CPU 极度受限”是他们面临的最新挑战。

“我们做了大量工作来扩展这些系统，这需要分布式系统方面的专业知识，需要某些语言和框架的专业知识。当你在这种规模上运营和演进一个系统时，我们远没有到‘祝你好运，Claude，去玩吧’的地步。仍然有大量工作需要人类来完成，而且我预计这种状态还会持续很长时间。”

这个坦诚回应，给出了一个更真实的 AI 工程图景：**模型能帮你写代码，但不能帮你设计架构、不能帮你预判运维风险、不能帮你在不确定的约束下做权衡。**

**个人感受**
这一段让人感受到一种真实的“平台团队”文化：工程师热爱思考产品，产品经理能够深入技术细节，大家共同面对“你要如何在多目标之间做权衡”的困难问题。这种跨职能融合不是被刻意设计的，而是被现实塑造的——当一个 AI 平台同时面临规模化、安全、用户体验、生态发展四大压力时，传统的职能边界会让你变得低效。

**延伸思考**
如果产品和工程角色真的会融合，那么下一个问题是：AI 时代需要的新型人才应该具备什么样的复合能力？从 Katelyn 和 Angela 的描述来看，答案至少包括：第一，能从技术机制的层面理解产品决策的后果；第二，能把用户体验的直觉转化为工程设计的约束；第三，能在不确定性和高复杂度下持续做出准确的判断。这已经不是传统的 T 型人才，而更像“多面手”（interdisciplinary generalist）。

**精华收获**
- 模型竞争进入“单位美元智能”时代，定价是产品策略的一部分，不仅为了商业，也为了引导用户做出更好的技术选择
- “聪明”不等于“好用”，写作风格等软性体验是决定模型能否真正扩散的核心因素
- 软件工程没有被“解决”，而是工程问题的重心从“写代码”转向“系统设计与运营”
- 产品和工程角色的融合不是未来趋势，而是已经在 Anthropic 平台团队中发生的现实


## 第四部分：模型发布的安全框架——从“单按钮回滚”到“信任授权”

### 为什么模型发布会越来越困难 `[关于 Fable 撤回与安全决策的讨论段落]`

**核心观点**
模型发布已经从纯粹的工程问题变成了复杂的政策、评估和授权问题——安全框架需要渗透到模型访问的每一个环节。

**深度阐述**

当被问到“模型发布的状态现在如何？”时，Katelyn 的回答几乎全是在说安全决策。这不是偶然——安全已经成为模型发布的第一个也是最重要的关卡。

她列举了几类必须在发布前完成的工作：

**第一，数据保留政策（Data Retention Policies）**。这不是一个新概念，但把它应用于 API 访问却是大模型时代的新发展。核心问题是：当有人通过多个账户、在分布式网络上调用模型时，你无法在在线状态下实时检测所有恶意行为——比如隐形的蒸馏、协同滥用等。这时候你需要保留一定时间的数据，用于事后自动化审查或人工审查。

但这会造成政策上的分层。Katelyn 特别指出：“Opus 5.5 昨天发布，它**没有** Fable 所需的那些数据保留要求。” 换句话说，不同模型的敏感度不同，数据保留策略也不同。官方必须为每一个新发布模型单独决定政策，并为执行这些政策做大量的工程工作。

**第二，在线安全护栏（Online Safeguards）和离线安全护栏（Offline Safeguards）**。这两者的区别是：在线护栏在模型生成 token 的同时实时运行，即时拦截不安全输出；离线护栏则是对已生成的数据进行事后分类和分析。在线安全能够在输出产生时就进行干预，而离线安全则可以识别更复杂的滥用模式。

**第三，验证程序（Verification Programs）**。Anthropic 现在运行着网络验证程序（cyber verification program）和生命科学验证程序（life science verification program）。举例来说，如果你是一个合法的网络安全研究员，你需要使用 Claude 的高阶网络攻击能力来寻找漏洞，你可以申请参与这个程序。一旦通过验证，Anthropic 会有选择地**降低**你那个模型版本上的安全限制，让你能进行相关的合法研究。

这个设计的关键在于：它承认“双重用途”（dual use）模型是无法被完全禁止的，但它们可以被**有边界地释放**。Angela 说：“你可以是合法的网络安全研究者，你在寻找漏洞，你在做好事。同样地，在生物领域你也可以做研究。所以这些项目基本上就是为这种双重用途提供访问入口，你必须说明你的用例。”

**第四，授权系统（Authorization / Trust Grants）**。这是平台工程层面的大工程。简单说，Anthropic 建立了一个贯穿全系统的授权基础设施，要求每一个模型访问请求都经过明确的身份验证和授权检查。不是传统的“给你一个 API key，打开 feature flag 就完事”，而是“整个授权链路贯穿系统最底层，确保只有对的人在对的模型上用对的方式”。

### “单按钮回滚”：从事故中长出来的基础设施 `[关于 Fable 回滚和授权系统的讨论段落]`

**核心观点**
Fable 部署后的紧急回滚事件，成为了 Anthropic 建设“全系统授权控制”基础设施的催化事件。这是一次典型的“从事故中学习”的平台工程案例。

**深度阐述**

这是整期对话里最有戏剧性的一个细节。Katelyn 回忆说，当时他们需要紧急回滚 Fable 模型，但实际上没有一个现成的“一键回滚所有用户”的机制。于是团队在事故处理过程中，专门增加了一个工作项：**建立一个系统，使得对模型访问的强制控制可以像“按一个按钮”一样迅速完成，覆盖所有用户。**

这里有一个非常罕见的工程师自省。主持人 swyx 提到一个经典的平台工程现象：“你出了一次事故，然后你为这个事故过度准备，结果这个事故再也不会发生了。” Katelyn 笑着承认了这一点：“我们当时就在想，我们做的这些工作，是不是永远都用不上了？我们希望那种事情再也不会发生。但后来发现，我们并不是在为一个孤立的事故做准备，而是在搭建一套贯穿所有模型访问场景的通用基础能力。”

这套授权系统后来被用在了很多地方。比如，验证程序的管理、Mythos（一个高能力模型）的访问控制、以及“需要额外时间来完成集成更新”的客户宽限管理。每当需要“只允许特定人群在特定时间内使用特定模型能力”时，这套系统都可以派上用场。

Angela 用了一个很形象的表述：“**Trust grants**”本质上就是一个授权概念——你被授予了对某个特定模型、某个特定程序的访问权限。它不是普通的“标准授权”（比如你能访问自己的数据），而是一种非常干净的数据模型，能表达各种复杂的权限组合。

这个经验体现了一条重要的工程原则：**如果你被迫尽早构建一个通用的底层原语，而不是先做一堆专用补丁，那么长期来看你会获得巨大的回报。**


## 第五部分：从事故到先见之明——Claude Managed Agents 的双重架构

### 大脑与双手的分离：一个被忽视的安全预言 `[关于 CMA 架构与沙箱安全的讨论段落]`

**核心观点**
Claude Managed Agents 的“大脑与双手分离”架构最初是为了可靠性和延迟设计的，但后来被证明是应对代理安全威胁的关键设计——这一理念源自一位产品经理的前瞻性坚持。

**深度阐述**

要理解这一段的技术含量，我们需要先解释一个核心概念：**为什么 AI 代理会有“逃逸”问题，以及架构如何从根本上解决这个问题。**

在传统设计里，人们通常把 AI 代理放进一个沙箱（sandbox）里，让它直接运行，给它一个任务，然后告诉它“去完成”。在这个“盒子里”的模型，只能使用盒子内部存在的工具和资源。如果模型足够聪明，它可能会试图突破沙箱边界，去获取外部的计算资源或数据——这就是所谓的 sandbox breakout/escape。

但 Anthropic 在构建 Claude Managed Agents（CMA）时，采取了一种完全不同的架构。他们在一篇发布博客里提出了“**大脑与双手分离**”的概念：

- **大脑（Brain）**：Agent 的 harness（控制逻辑/状态机）运行在一个**耐用的服务端（durable server）**上。这个服务端不需要在每次请求时重启。
- **双手（Hands）**：实际的代码执行、工具调用等操作，才会临时启动一个**沙箱或容器**来执行。

这样设计的首要原因是**延迟**和**可靠性**。如果每一次 API 请求都要先启动一个沙箱，再在里面启动 agent，那 token 的返回速度会非常慢。而如果沙箱因为意外崩溃、网络问题或其他原因死亡，那个 agent 的状态也会一起丢失——用户就会失去整个任务进度。把 harness 放在一个持久化的服务端上，沙箱只是一个临时执行环境，就解决了这两个问题。

但真正精彩的地方在后面。

Anthropic 的某位产品经理从一开始就坚持认为，**这个架构最重要的属性其实是安全**。当时团队里所有人都在关注延迟和可靠性，没人真正把安全当回事。但这位产品经理的论点是：把大脑和双手分离，就意味着 agent 的“控制权”和“执行权”永远不在同一个受威胁的边界里。

Katelyn 说：“**我在昨天向这个人道歉了。我现在逢人就说你已经说了好几个月的那件事。当时没有人和你一样兴奋。这个架构最重要的一个属性就是安全性。**”

### 凭证注入与出口控制：让“做坏事”变得架构上不可能 `[关于凭证保险库与出口代理的讨论段落]`

**核心观点**
Claude Managed Agents 的安全架构做出了一个根本性改进：凭证永远不与 AI 代理处于同一信任边界内，从根本上杜绝了 AI 窃取或滥用凭证的能力。

**深度阐述**

这是 AI 安全保障领域一个非常关键的细节。一个 agent 在实际工作中，往往需要访问外部服务——比如调用 API、使用 CLI、连接到 MCP 服务器等等。这些服务都需要认证凭证（credentials），比如 API key、OAuth token、用户名密码等。

传统做法是：把这些凭证放进 agent 的运行环境里，让 agent 直接使用。但这意味着，一旦 agent 被恶意代码或入侵控制，凭证就会泄露。你只能依靠“事后检测”“每次重写”或“环境擦洗”等脆弱的补救措施来降低风险。

Anthropic 的做法完全不同。Katelyn 描述了具体机制：

1. **凭证完全存放在一个独立的保险库（vault）中**，与 agent 的运行环境物理隔离。
2. 当 agent 需要调用一个外部服务时，它看到的只是一个**占位符（placeholder）**。真正有效的凭证永远不会暴露给 agent。
3. 在出口（egress）链路上，有一个**代理服务（proxy）**。当请求从 agent 发出时，代理会截获请求，从保险库中取出对应的真实凭证，注入请求中，然后放行。对于 agent 来说，整个过程是透明的，但它从未真正接触过任何有效凭证。

Katelyn 说：“这个架构的有趣之处就在于，agent 永远不可能和凭证待在同一个地方。所以 agent 就根本没有机会去窃取凭证或者拿去做不该做的事情。这是一道真正的实体基础设施隔离墙。”

这个设计在本质上是把“安全”从一个行为约束（“你被信任不会做坏事”）变成一个架构性质（“你架构上根本不可能做坏事”）。

除了凭证注入，Anthropic 还在沙箱出口处实现了非常强的**出口控制**。管理员可以设置域名允许列表（domain allowlist），限制沙箱内程序的网络访问目标，或者干脆完全切断网络访问。这解决了另一个经典威胁：agent 运行不可信代码，代码执行后主动发起外部 C2 命令与控制连接。

这些安全控制叠加起来，最终的效果就是：**默认安全（secure by default）**。用户不需要额外配置，就能获得一个相当高的安全基线。

### 沙箱逃逸：训练中的“盒子困境” vs. 生产环境的架构约束 `[关于沙箱逃逸与安全事件的讨论段落]`

**核心观点**
媒体上广泛报道的“AI 代理沙箱逃逸”事件，大多发生在模型训练类场景中，与生产环境中正常运行的 API 工作负载有本质区别——但整个行业对长期运行代理的安全理解仍处于起步阶段。

**深度阐述**

最后一个重要的澄清是：Angela 对“AI 代理从沙箱中逃逸”这一现象给出了一个很微妙但至关重要的区分。

她说：“很多你们听到或读到的沙箱逃逸事件，发生的背景都是在**训练**中——你把这模型放进盒子里，对它说你去做一个不可能的任务，我要给你压力，预备开始。它只能在自己的环境里行动，于是代理自然就被激励去试图逃出盒子去解决问题。”

但在生产环境里，情况完全不同：

1. 生产环境中有**在线安全护栏**，这些护栏在训练环境中是不存在的。
2. 生产环境中有**标准的网络架构和基础设施隔离**，agent 不会被放进一个孤立的小盒子，而是有 harness 在一边、执行环境在另一边。所以沙箱逃逸根本就不是一个你需要特别担心的攻击面。

Angela 的这一区分，解释了为什么同一类事件的概率在不同语境下差异巨大。训练环境中，模型被故意推向“我们想看它是否会反抗或越狱”的极端情况；这些场景天然更容易诱导出越狱行为，因为它模拟了被困智能体的压力测试。而生产环境中，所有东西都被围在层层护栏之内，这种情境下的逃逸潜力远低于训练环境。

但 Angela 也坦诚承认，整个行业对长期运行智能体的安全理解还很新。“每个人都在探索这些问题，很多控制手段都是边跑边补。这不是说人们不知道自己在做什么，而是这个领域太新了。”

Katelyn 则把这种探索过程总结为“**前沿步调（pacing the frontier）**”的真正含义：“我们内部让所有 agent 都具备这些安全属性，然后把这些控制手段变成所有客户都能默认使用的东西。”

**个人感受**
这一段内容非常接近“安全工程的第一性原理”。你可以明显感受到，Anthropic 团队认识到一个现实：你不可能通过“教育 AI 不要做坏事”来保证安全，也不可能靠“检测到坏事之后再做反应”来保证安全。你必须在系统设计的层面上让“做坏事”变得不可能。这就是为什么“大脑双手分离”这个架构选择如此重要——它不是为了安全而做的，但它最终在安全上产生了深远的影响。

**延伸思考**
这里可以延伸出一个更大的问题：随着 AI 智能体被赋予越来越高程度的“自治权”，我们需要什么样的安全架构？Anthropic 给出的答案是：**最小权限原则 + 不可访问的凭证存储 + 出口控制 + 默认安全配置**。这些听起来很传统的云安全原则，在大模型时代获得了一次重生。

还有一个哲学层面的观察：那位产品经理坚持安全是“最重要的属性”，结果他的观点在几个月后被现实证明是天才般的远见。这提醒我们在做平台基础设施时，不能只根据当前最大的痛点来排优先级。有时候，一个“现在看起来不重要”的架构选择，会在未来成为整个系统安全的基石。

**精华收获**
- 大脑与双手分离的架构，实现了可靠性和安全性的双重收益
- 凭证永不暴露给 agent，是防止 AI 滥用的根本性安全控制
- “默认安全”不是靠教育用户实现的，而是靠架构设计使不安全行为不可能发生
- 训练环境与生产环境的安全威胁模型完全不同，沙箱逃逸的报道需要更精确的语境
- 平台建设必须有前瞻性，当时看似超前的能力可能会成为未来的关键基石


## 第六部分：用 Rust 重写 Messages API——一次大规模的 AI 辅助重写

### CPU 短缺：新的行业瓶颈 `[关于 Rust 重写与 CPU 问题的讨论段落]`

**核心观点**
GPU 短缺尚未完全缓解，但 CPU 更成为了新的“无声危机”——Anthropic 必须同时在推理、沙箱、CI/CD 和训练等多个维度争夺同一个有限的 CPU 池。

**深度阐述**

大部分 AI 行业的讨论都集中在 GPU 上：训练加速、推理吞吐、算力分配……但 Angela 揭示了另一个同样迫在眉睫的问题：**CPU 短缺**。

她说：“人们通常习惯于讨论 GPU 层的问题，很少讨论 CPU 这个老牌的层。但 CPU 现在和 GPU 层一样是一个瓶颈。你根本无法获得足够的虚拟机、无法获得足够的沙箱、无法让所有东西都拥有足够资源来启动。”

为什么 CPU 的压力这么大？因为 Agent 时代的工作负载结构已经完全改变了：

- **产品服务**：API 本身需要大量 CPU 来做请求路由、授权检查、在线分类器等。
- **沙箱执行**：每个 agent 的执行环境都要占用 CPU 资源。
- **CI/CD 负载爆炸**：AI 让代码生成的数量暴增，而生成的代码越多，CI 跑的次数就会越多，每一次 CI 都需要大量 CPU。
- **研究沙箱与产品沙箱之争**：Anthropic 内部研究和产品团队之间还必须在一个全局 CPU 池子里竞争预算。

Angela 特别强调了一个关键变化：**过去你只要预算足够，就能随时动态扩展 CPU 容量；现在你必须提前做容量规划（capacity planning）**。这在整个行业都是新的挑战。

这种全局 CPU 约束，迫使 Anthropic 同时在两个层面推动优化：

1. **基础设施层**：如何让沙箱运行得更高效，同时不牺牲租户隔离、安全属性等关键要求。
2. **应用层**：如何让 API 服务和应用程序本身更节省 CPU。

### “选 Rust 是一个疯狂的决定”——用 AI 重写 API 基础设施 `[关于 Rust 重写 Messages API 的深入讨论段落]`

**核心观点**
Anthropic 完成了 Messages API 从 Python 到 Rust 的完整移植，这个过程颠覆了传统的技术迁移模式——一支最初几乎没有 Rust 经验的团队，借助 Claude 完成了系统的重新实现，并带来了显著的 CPU 节省和延迟改善。

**深度阐述**

这是整期对话中最具技术冲击力的故事之一。

背景是：Anthropic 的 Messages API 原本是一个 Python 单体应用。它的优点是开发快、迭代方便；但它的缺点是 **CPU 效率低下**。在流量爆炸式增长、CPU 极度受限的情况下，这个 Python 单体成了瓶颈。

Angela 的团队决定把整个 API 用 **Rust** 重写。这个决定在当时听起来非常激进，因为团队里**连一个 Rust 开发者都没有**。Angela 回忆说：“从纸面上看，选 Rust 是显而易见的选择，但团队内部说，我们这里没有一个人会 Rust。谁在乎呢？直接上。”

这段话里包含了非常有趣的技术时代信号：**在 AI 辅助编程的时代，语言选择的标准正在发生变化。** 过去，你会选择团队熟悉的语言，因为你必须雇佣懂它的人。现在，如果 Claude 能处理大量实现工作，人类负责系统设计和验证，那么选择“更正确”的语言就比为“团队熟悉”妥协更重要。

但这个项目真正精彩的地方不在于“用 AI 写代码”，而在于**过程控制**：

1. **人类负责系统设计**：整个 API 是一个分布式系统架构。人类工程师负责设计这个系统——包括边界、接口、数据流、故障模式等。
2. **Claude 负责代码实现**：具体的代码编写由 Claude 完成。
3. **计划与验证是关键**：Angela 说：“真正重要的是做事的计划和验证，因为实际的实现就是 Claude 写代码。”

他们采用的策略也不是传统的“逐步迁移”（把系统切分成小块，一块一块重写），而是一次性**创建了 API 的完整 Rust 分支**，然后把生产流量通过 **shadow traffic（影子流量）** 的方式逐步切换到新系统上。影子流量意味着你同时运行两个系统，发送相同的请求，比较输出结果是否一致，确保新系统能正确工作后再逐步切换。

Angela 强调了这个成果的量级：

- **CPU 节省**：大约 40% 到 50%，接近一个数量级的改善。
- **延迟改善**：首 token 时间（time to first token）改善了 10% 到 20%。对于较长运行的工作负载，改善幅度更大。

### 控制范围，拒绝“重写同时加新功能”的诱惑 `[关于重写范围控制的讨论段落]`

**核心观点**
AI 辅助重写的一个最大陷阱是“顺手加新功能”而导致的无限范围膨胀。Anthropic 团队忠实执行了一次“端口任务”，并故意压制所有新功能冲动，才换来了项目成功。

**深度阐述**

当主持人问：“在大型重写中，你如何克制‘不如顺便加上以前没有的新功能’的冲动？”时，Angela 的回答是：“我们确实做了，我们抵抗了所有这些冲动。你只能把它称做一个‘端口（port）’，而不是一个包含范围变更的重写。”

这是软件工程里一个经典但总被忽视的纪律：**范围控制（scope control）**。

重写系统是行业里最容易被范围膨胀毁掉的项目之一。因为重写过程中，开发者不得不重新审视每个旧功能，然后往往会想：“既然我在重构这部分，不如顺便改进一下。”（往往导致项目无限延期或工程质量下降。）

Anthropic 的做法是组建一个专门的 **SWAT team** 来执行重写。这个团队在重写期间，必须持续追踪整个平台团队并行开发的每个新功能，并负责把这些功能同步到 Rust 实现中。如果你在主 Python 系统上建了一个功能，但没有同步到 Rust 分支，他们会找上门来“吼你”。

这种并行维护的难度极高，但他们坚持把范围限定在“忠实移植”上。最终，这次重写获得的成果不仅体现在性能指标上，更重要的是建立了一个更有能力实现未来架构演进的代码底座。Angela 表示，团队下一步的目标是进一步做“重新架构”类型的工作，其中包括一些面向用户的功能——比如不再要求用户在每一轮对话中反复传递完整的会话状态，而是允许在某些时间段内存储状态，这将在长对话场景中大幅改善延迟和效率。

**个人感受**
这个重写故事里有一个很大的哲学意蕴：过去，重写系统是一个需要多年、数十名工程师、无数代码审核的项目。现在，只需要一个“没有 Rust 经验”的团队、一个明确的设计规划、和 Claude 就位，就能在极短时间内完成。但这个故事最发人深省的地方，其实不是“AI 写得快”，而是“人必须管得住范围”。快的代码产生很容易，难的是不做多余的事。

**延伸思考**
这就是 swyx 所说的“把工程当研究来做”的另一种体现。研究型工程的特点是非常强调实验设计、评测标准和过程控制。你可以把这次 Rust 重写视为一场大型实验：假设是“用 Rust 重写 API 能节省 40% CPU 并改善延迟”；实验设计是完整的 Rust 分叉 + 影子流量 + 输出验证；执行是 SWAT 小队严格控制范围。每一步都非常“科学”。

**精华收获**
- AI 时代，技术选型中“语言熟悉度”的权重在下降，“系统最适性”的权重在上升
- 大型重写虽然被 AI 加速，但范围控制依然是工程成败的关键
- 影子流量是控制大规模重写风险的黄金标准
- CPU 正在成为 AI 行业的新瓶颈，CPU 效率优化直接影响单位经济学
- 忠实端口 + 小步切换，比“一次到位”更值得信任


## 第七部分：评估、个性化与模型路由——AI 工程中最大的软肋

### 评估的困境：非确定性、氛围与回归 `[关于模型评估和反馈的讨论段落]`

**核心观点**
模型评估仍然非常无结构化，大量有价值的信息仍然依托于“Slack 互通 + EVAL 套件 + 直觉氛围”的混合流程。行业缺乏成熟、标准化的评估工具。

**深度阐述**

当主持人问及“模型反馈的状态如何？”时，得到的回答是：“**basically, it’s always a Slack channel between companies of, like, hey, this thing seems weird and then people are like, okay, I’ll fix it, I guess。**”——“基本上就是公司之间开一个 Slack 频道，有人喊这个好像有点怪，然后有人说好我来修一下，大概就是这样。”

这个回答既幽默又非常真实。大型 AI 模型的非确定性使得评估远比传统软件复杂。你不能像传统软件那样写单元测试断言，你甚至不能完全预知一个提示会得到什么输出。因此，评估往往是在真实使用场景中动态发生的。

Anthropic 开发了一种混合式的模型发布反馈流程：

1. **内部 dogfooding**：团队在使用 Claude 完成自己的工作，从早期就看到哪些变体更好。
2. **早期访问计划**：请高价值的 API 客户协助测试。这类客户必须有强大的自动化 EVAL 套件，能快速对模型进行系统化测试。
3. **氛围反馈（Vibes feedback）**：非正式的、基于感觉的反馈——是否喜欢这个模型、交互感觉如何等。
4. **回归检测**：是否在某些任务上出现了性能倒退。

Katelyn 特别强调了一个反直觉的结论：**最有用的反馈通常是负面的。** “当我们发现模型在某些任务上没做好，我们会非常兴奋，因为我们最关心的就是如何修复它。”

而氛围反馈虽然主观，但信息密度其实很高。因为模型的能力不能完全通过数字来捕捉，真实用户的“感觉”往往能捕捉到一些 EVAL 漏掉的东西。尤其对于写作风格、语气、主动性等高度主观的维度，氛围反馈几乎是唯一的信息来源。

在这个环节，Angela 还透露了一个关键的产品难点：**模型行为谱系的校准问题**。有些用户抱怨模型“太懒了，不完成我的任务”，而另一些用户抱怨模型“太积极主动了，我还在计划阶段它就写了一大堆代码”。这种矛盾的需求根本无法通过单一的默认参数来满足。Anthropic 不得不通过“参数切换”来部分解决，但他们也知道这不是可规模化方案。

### 个性化 vs. 对齐：模型产品管理中最难的问题 `[关于个性化与参数设计的讨论段落]`

**核心观点**
模型个性化是对齐问题的延伸。当前 Anthropic 通过提供多个可调参数（如 effort、budgets 等）来为用户提供灵活性，但这些参数正在变得过于复杂，未来需要一个更统一的个性化机制。

**深度阐述**

“personalization vs. alignment” 是 Angela 提出的一个非常深刻的问题。一个模型能否“符合你的偏好”和“符合通用安全/质量标准”之间，存在天然张力。

Anthropic 当前的做法是通过 API 上的多个参数来调节模型行为。比如：

- **Effort**（努力程度）：决定模型在推理上投入多少时间。
- **Reasoning effort**：在 Claude Code 中的一个设置，默认值从过去的其他值调整为 **medium**，以更好地适配不同用户群体的需求。
- **Budgets**（预算）：限定模型在任务上的资源消耗。

但问题在于：随着模型越来越强大，参数越来越多，用户实际上很难弄清楚“对于我的任务，effort 应该设为 high 还是 medium？budgets 应该设多少？” Katelyn 说：“我们最终积攒了一大堆像 effort、budgets 这样的 API 参数，就像是一个让人头疼的大杂烩。谁能搞清楚对于任何一个特定任务，什么才是最合适的组合？”

这个问题的深层本质是：**模型的正确行为往往是高度情境化的**。同一个用户、同一个任务，在不同的阶段可能有不同的期望。你不可能通过增加参数来解决所有细粒度的个性化需求。Anthropic 正在尝试的解决办法之一，是在前沿方向上探索让模型自己根据任务复杂度和用户信号动态调整自己的行为，而不是让用户手动调节。

这一思路也会和后续的“路由问题”自然地联系在一起。

### 模型路由问题：当代理变得自主，如何决定该用哪个模型或策略 `[关于模型路由与分类器的讨论段落]`

**核心观点**
模型路由（router）和 AI 安全过滤（safety classifier）本质上是同一个问题：你如何根据任务的不同阶段动态选择合适的智能水平，同时保持用户体验的一致性和模型 persona 的连续性。

**深度阐述**

这个问题被 swyx 用“smart router vs. dumb router”的框架提出来。所谓“smart router”就是能准确评估任务难度并选择合适模型的系统；而“dumb router”就是简单规则的路由器。

Angela 坦承这是很难的问题。即使你拥有完美模型能力评估，你在任务开始时也往往不知道任务的实际复杂度。任务复杂度会随着时间而改变。所以任何基于静态分类器的路由方案都会有显著的误差。

她提出了一个很深刻的观点：与其在不同模型之间跳来跳去，还不如设想一个“统一且连续”的体验：**同一个模型，在低 effort 下可以非常便宜、非常快速地执行简单任务；在高 effort 下又能动态扩展，执行复杂任务。但模型始终保持一致的 persona（人格/风格）**。

这个设想至少在理论上是优美的。因为“模型不同”造成的体验断裂（disjointedness）是用户最敏感的痛点之一。如果你在一个多模型路由系统中，有时使用 Haiku，有时使用 Sonnet，有时使用 Opus，用户可能会明显感受到“个性”在跳变。一致性本身就是一种价值。

但 Angela 也承认，目前这个设想仍处于早期阶段，尤其当你考虑跨模型家族（不同模型厂商）时，这个问题会更复杂。然而，在 Anthropic 自己的模型系列内，她更看好“统一但可扩展”的路线。

**个人感受**
这几部分让人感受到一个真实的、仍然在大声思考的团队形象。这个团队并没有假装所有问题都解决了，也没有隐藏他们仍然在摸索的部分。面对评估、个性化、路由这些老大难问题时，他们的语言充满了克制。这其实是一种高级的工程成熟度——知道什么能做，也知道什么还不够好。

**延伸思考**
评估和个性化问题可能指向一个更大的趋势：未来的 AI 系统需要发展出一种“动态元认知”，即持续评估自己的任务进展，并自动调节自己的行为谱系。如果 AI 能在任务过程中自我调节努力程度、输出深度、主动性水平，那么很多模型路由和个性化问题将被内部化到模型本身，而不是暴露给用户去手动配置。

这实际上意味着，真正的“智能”模型，不只是能回答问题，还要能理解并响应你隐性的偏好信号。

**精华收获**
- 评估仍然是一个无结构、高度依赖 vvibes 的工程活动，需要跨越内部和外部
- 最有价值的模型反馈是负面的；正面的氛围反馈是验证性的，但负面反馈推动改进
- 模型行为的偏好校准（如主动性）存在根本矛盾，不能通过单一默认参数完全解决
- 模型路由和 AI 安全过滤本质上是同一个问题：如何任务的不同阶段决定模型的智能投入水平
- “统一但动态调节”的模型体验，比“在多模型之间跳来跳去”更可能成为未来方向
- 模型个性化是一个远未解决的问题，未来可能需要依赖模型的“动态元认知”来自动调节


## 第八部分：Claude Managed Agents 的进阶范式与多智能体策略

### 什么是 Claude Managed Agents，为什么是新的消费云端的路径 `[关于 CMA 基础介绍的讨论段落]`

**核心观点**
Claude Managed Agents 是 Anthropic 在 API 之上建立的高阶抽象，它把本该由用户自己搭建的 Harness 和基础设施打包成了开箱即用的功能，极大降低了生产级代理应用的开发门槛。

**深度阐述**

为了让读者完全理解，这里需要先解释一下背景概念。通常，如果你想用 Claude 模型构建一个能在真实环境中执行任务的 agent，你需要自己搭建很多基础设施：

- 管理会话的状态
- 处理上下文长度限制
- 处理模型的工具调用
- 处理执行环境
- 处理错误恢复
- 处理安全配置

这些部分被统称为 **Harness（封装层）**。很多开发者花在构建和维护 Harness 上的时间，甚至远超花在业务逻辑上的时间。

Claude Managed Agents（CMA）把这一层抽象掉了。Katelyn 这样介绍：“Claude Managed Agents 是一套 API，让你可以定义一个 agent，启动一个会话，它会帮你跳过大量的基础设施搭建工作。它是一种开箱即用的集成，适合那些想以编程方式运行 agent 的人。”

换句话说，如果你不想自己造 Harness，那么 CMA 就相当于 Anthropic 为你提供一个内置的最佳实践版本。

而这个抽象的价值还体现在它内部融合了所有前面提到的安全控制——大脑与双手分离、凭证注入、出口控制、默认安全配置。所以用户在使用 CMA 时获得的不只是开发效率，还有更高的安全基线。

### 冥想（Dreaming）：一个“多层 CMA”的自我进化系统 `[关于 Dreaming 与多 Agent 策略的讨论段落]`

**核心观点**
Dreaming 是 Anthropic 在 CMA 之上开发的一种自我改进机制——本质上是一个多智能体系统，它让一个 CMA 去审查另一个 CMA 的状态，并写出“记忆”来持续改进前者。这展示了一种新的 AI 工程范式：通过模块化高层原语构建更复杂的智能体系统。

**深度阐述**

Dreaming 是 Anthropic 在 2025 年上半年大力推的一个概念，当时曾经引发过一波热潮。但在本场访谈中，Angela 坦承这部分工作已经不再是团队的主要精力所在，更多是作为一种范式被整合到了更基础的 CMA 原语里。

要理解 Dreaming，需要先理解它的实现机制。Angela 说：“**Dreaming 本质上是一个我们基于 CMA 基础层进行 hill-climbing 的多智能体系统。它是一个 CMA 作用于自己之上的 CMA。**”

更具体地说：Dreaming 会启动一个额外的 managed agent（审查者），让这个 agent 去看前一个 managed agent 的运行轨迹和输出，然后根据发现的问题写出“记忆”或建议，改进原 agent 的行为。这个过程允许一个 agent 在运行过程中自动进行反思和调整，而不需要人类的人工干预。

不过更值得关注的，是 Angela 对 Dreaming 更大意义的阐述。她指出，Dreaming 只是**多智能体策略**的一个例子而已。实际上你还可以用 CMA 做很多其他事情：

- **Best of N**：同时启动多个并行的 agent，选择最优结果。
- **Verifier agent（验证者）**：让一个 agent 去检验另一个 agent 的目标是否达成。
- **共享记忆的大规模并行架构**：有些开发者已经在尝试让多个 agent 共享疯狂的海量记忆，并行执行任务。
- **自定义多智能体策略**：下一步 Anthropic 将会开放底层的多智能体组合原语，让开发者自己搭建像 Dreaming 这样的复杂策略。

这是一个非常关键的产品哲学转变。Anthropic 不再把所有高级功能都自己闭门开发，而是把基础原语做到足够通用、足够开放，让开发者能够自己组合出新的策略。Angela 说：“这就像我们最初做 Dreaming 的方式一样：平台提供原语，你可以在上面创造你自己的多智能体策略。我们会给你模板，你可以在模板上做调整，获得额外价值。”

**个人感受**
这一部分揭示了一个重要规律：在 AI 平台竞争中，如果把每一代新功能都做成封闭产品，你很难跟上所有用户的需求，反而会让 API 变得极为臃肿。正确的做法可能是把能力推向底层原语，让生态去组合。Anthropic 似乎在有意识地走向这个方向。

**延伸思考**
这其实与 Unix 哲学共鸣：“提供机制，而不是策略。”平台的责任是提供安全、可靠、通用的机制（构建块），而策略（如何组合这些块）则由用户或其智能体来决定。在多智能体时代，这个哲学可能比在传统软件时代更重要，因为智能体本身可能也会参与策略的选择和组合。

**精华收获**
- CMA 是“大脑双手分离”架构的产品化体现，为用户提供了开箱即用高安全性的代理运行环境
- Dreaming 本质上是“CMA on CMA”，它展示了一种让 AI 自我改进的模块化方法
- 多智能体策略将会变成平台原语，Anthropic 正在鼓励开发者创造自己的组合范式
- 平台哲学正在从“提供完整产品”转向“提供基础机制 + 模板”


## 第九部分：AI 工程与团队文化——反对“垃圾内容”与人才策略

### 反对 Slop：质量不是模型能力的问题，而是人类质量问题 `[关于反对 AI 垃圾内容的讨论段落]`

**核心观点**
AI 让内容生产变得极快，但团队必须坚持“人是质量责任人”的原则，防止把认知负担转嫁给内容消费者。

**深度阐述**

这个讨论源于主持人问：“你们怎么在团队中抵抗 slop（AI 垃圾内容）？”

Katelyn 分享了一个非常真实的团队辩论。她指出，在 Anthropic 内部，他们并不禁止使用 Claude 来辅助工作——实际上，不用 Claude 来完成可加速的工作本身就是不合理的。但问题的关键在于输出物的**质量责任归属**。

“如果你让 Claude 完全生成一份文档，自己甚至没有花时间阅读它，没有确认它是否达到了高质量，那么你就把过滤和判断的额外负担推给了读者。这是完全不公平的。”

所以 Anthropic 的团队有一条不成文但重要的质量文化：**你可以使用 Claude，但作为人类的你仍然对产出质量负有最终责任。**

但这里又出现了一个有趣的文化悖论。Claude 写作有非常明显的特征，比如“claudisms”（Claude 的典型用词、句式、标点习惯），这些特征会让读者本能地怀疑：“这是 AI 写的，质量不过关”。即使作者实际上投入了大量精力去确保质量，这种怀疑也会产生负面影响。

Katelyn 说：“这产生了一个奇怪的现象：人们可能确实花了很多时间去确保质量，但他们用了 Claude 来帮忙，而文档里偏偏带着那些微小的 Claude 痕迹，读者就觉得被打扰了，认为不值得读。”

因此，他们的团队正在努力找到一个平衡：**拒绝真正的 slop，但对轻微的 claudisms 不要过度挑剔。** 这听起来相当琐碎，但其实是一个重要问题。当一个组织大规模使用 AI 辅助写作后，组织内部的内容消费效率会成为新的瓶颈。解决方案不是全盘接受 AI 产出，也不是完全拒绝 AI 参与，而是在质量管理和审美容忍之间找到一个新平衡。

Anghangela 也补充了一个工程层面的观察：代码质量的 slop 问题反而在减少。因为 Claude 的代码能力持续变好，加上他们有完善的验证系统来保障质量，所以现在团队更关注的是**系统设计**和**整体计划**，而不是逐行审查代码。这印证了前文说的：在 AI 快速写码的时代，“你验证了设计正确”比“你验证了每一行代码正确”更关键。

### AI 时代的产品经理与创始人：更快不等于更好 `[关于产品管理与“快速产生更多”的讨论段落]`

**核心观点**
AI 会让“生产”变得几乎零边际成本，但真正稀缺的能力是用思考来引导产出，而不是简单地提高产出数量。这个洞见也适用于创始人。

**深度阐述**

这里 swyx 引用了来自一位知名创业者/投资人的观点：“模型能力提高的正确应用方式，不是向生产环境多交付 10 倍的功能，而是花更多时间去理解用户，做更多实验，构建真正有价值的东西。你本可以轻松地发布随机的新功能，但你应该首先思考自己在做什么。”

Katelyn 对这个观点表示强烈认同，并进一步发挥说：现在行业中出现了一种“懒惰”（laziness）。很多人觉得既然 AI 能做某件事，他们就不再需要思考这件事。**但思考本身仍然是软件和产品开发中不可替代的基础活动。**

她认为，在一个 AI 加速的时代，最重要的事情之一是抵抗“因为成本低所以做更多”的冲动。

但这并不意味着要拒绝实验和探索。swyx 提出一种自我观察：“因为实验/探索的成本现在变得很低，所以我觉得我应该做更多。而 Boris 说的是：不要那样做，要用它来服务于一个明确的、有意图的目标。我承认这是对的，但确实很难。你手里有一个全能的玩具，你总想把它扔向墙壁看看会发生什么。”

这种张力恰好是 AI 给所有产品团队带来的最大心理挑战：**从‘限制约束’到‘注意力约束’的范式转换**。

过去，产品迭代的速度主要受限于工程成本。现在工程成本降得极低，但人的注意力仍然有限。如果团队没有建立起“根据用户价值来分配注意力”的纪律，AI 反而会把大家淹没在无限的发散中。

### DevRel 的未来：从“宣传员”到“思想领袖”与“平台建设者” `[关于 DevRel 招聘的讨论段落]`

**核心观点**
DevRel（开发者关系）在 AI 时代正在经历深刻转型，从传统的宣传和布道变成高技术的教育和平台建设工作。Anthropic 正在寻找的人才不仅要能吸引开发者，更要能参与构建平台生态。

**深度阐述**

主持人问到 Katelyn 关于 DevRel 招聘的问题，她透露了两个团队都在搭建 DevRel 功能：一个隶属于平台团队，另一个隶属于 Cloud Code 团队。她坦言自己在加入 Anthropic 之前从未直接管理过 DevRel 团队，是 swyx 教给了她一个非常有用的框架：**DevRel 的三大支柱：产品、内容、社区**。

但她更进一步阐述了自己的理解。她认为 Anthropic 平台团队的 DevRel 需要具备更强的技术属性。这体现在他们选择的团队负责人 Lance 是高度技术型的——他会深入研究内存管理、成本控制等主题，写技术深度的内容，建立评测体系。Katelyn 说：“我真的很喜欢这个方向：我们的 DevRel 团队不仅仅是‘宣传人员’，而是这个新兴、困难、快速演变领域中的**思想领袖**。”

swyx 补充了一个非常有启发性的比喻：Lego 的“**master builder**（大师建造者）”模式。Lego 为什么那么成功？因为它不仅仅是卖积木，还雇佣了大师建造者，用这些积木建造出令人惊叹的模型，激发消费者的欲望：“我也想要这样。” AI 平台也许需要同样的人才：**用平台能实现的最令人振奋的事，来向用户展示可能性。**

在讨论中，他们还谈到一个更深层的观点：**DevRel 可能正在解绑为“前办公室”和“后办公室”**。传统上，DevRel 人员要做所有的事情：写内容、参与社区、组织活动、做支持。但在一个极度加速的工程环境中，产品负责人和工程负责人往往没有时间亲力亲为。于是，一种新的模式出现了：DevRel 团队作为“后台”负责内容生产、社区运营和品牌设计，而产品负责人作为“前办公室”露面、做深度访谈、在社区发声。

Katelyn 说：“很多人其实更想听产品团队里真正做产品的人，而不是听 DevRel 的‘付费代言人’。但你不能期望产品工程人员在工作之余还能做好高强度的社区运营。所以你需要一个专门的后方团队来支撑他们。”

这个“前办公室/后办公室”模型可能是未来技术团队对外沟通的重要方向：**让内行成为主角，让专业团队成为幕后推手。**

**个人感受**
这段内容的关键词是“真实性”。无论是反对 slop，还是 DevRel 的重构，背后都是对真实性的追求。人们不希望读 AI 生成的空洞内容；人们也不希望听 PR 人员的话术。真实的人和真实的声音，才是技术社区最稀缺的资源。

**延伸思考**
这与 AI 工具在内容创作中的作用形成一种有趣的张力。你可以用 AI 来放大一个人的“真实声音”，也可以用 AI 来掩盖它。Anthropic 团队的答案很清晰：AI 应该是助手，而不是替身。人类仍然要为质量和价值负责。

这个原则甚至可以推广到整个 AI 领域：当模型能力越强，越不能放弃人类的判断力。AI 能做的越多，人类越要把注意力放在选择与理解上。

**精华收获**
- 团队中抵抗 slop 的关键是明确质量责任：人类仍然要为内容质量负最终责任
- 读者会对 AI 写作痕迹产生强烈反弹，所以即便质量合格，表达上也要在“claudism”和“slop”之间找到平衡
- AI 降低了生产门槛，但注意力仍然有限。创始人/产品经理必须学会把 AI 用于有意图的目标，而不是无限发散
- DevRel 的未来是“思想领袖 + 大师建造者 + 后台支持”三合一
- 技术在进步，但真实性和人类判断力依然是不可替代的稀缺资源


## 第十部分：结语——回到起点，两个循环永不停歇

### 一切为了循环：为什么 Claude Managed Agent 是“信息高速公路上的 ATM” `[结尾讨论段落]`

**核心观点**
整个讨论的最后，所有话题都汇合到了同一个方向上：Anthropic 的所有决策，最终都是为了让改进循环和投资循环以更低摩擦的方式持续加速。

**深度阐述**

在节目接近尾声时，Angela 谈到了 Anthropic 正在观察到的变化：一些任务类型正在被大量满足，“intelligence”在这些领域已经趋于饱和。她认为这一点比大多数人预期的更明显。而真正还能带来超额回报的，是“超长运行的代理任务”，这些任务在历史上无法靠暴力完成，但现在却可以通过更强的智能来攻克。

她说：“有一类全新的工作负载正在出现，比如生物科学、网络安全等领域。它们是一组非常复杂的、困难的工程或科学问题。这些工作负载越来越频繁地出现，对我们来说，这是一个非常有趣的、为不同客户提供价值的新空间。”

这不仅仅是对现状的描述，也是对未来方向的提示——Anthropic 不是一个纯粹的模型供应商，而是一个工作负载的参与者。他们看到了很多真实世界里正在涌现的代理级需求，同时也通过提供基础设施来帮助客户应对这些新工作负载。

这些新工作负载可能并不需要传统意义上的“更强模型”，而是需要一个**更可靠、更安全、更高效、更自动化的系统**。这个系统能让代理持续运行，保持构建与修正的循环，在时间和资源的约束内完成复杂任务。

而这一切，正是整期节目一直在讨论的主题。

- 防蒸馏体系保证了改进循环里的反馈不会被恶意剥离；
- 安全框架保证了代理可以安全地执行任务而不脱离控制；
- Rust 重写保证了系统效率能跟上增长；
- CMA 架构保证了开发者能快速、安全地构建代理产品；
- CMA 的多智能体原语保证了探索新范式不会停滞。

当这些齿轮都啮合起来，整个系统就能进入一个自我强化的状态。

### 结语：给开发者的号召

Angela 最后给出了一条非常有用的操作建议：**如果你要尝试使用多智能体架构，最重要的两个原则是——**

1. **共享状态**：所有代理必须能读取同一个全局状态，否则协作就会出现信息割裂。
2. **不要阻塞子代理**：不要让一个子代理等待另一个子代理完成后再行动。异步并行是多智能体架构获得速度优势的关键。

她说：“只要你保持这两条原则，你就大胆尝试，让 Claude 自己设计架构。它会学会自己拆分自己、克隆自己、调整到最合适的架构。”

这个观点很“Claude 风格”：放手让 AI 去发现架构，而人类只需要设定几个底线原则。

Katelyn 则补充了很个人的情感部分。Opus 5.5 发布当晚，她收到了大量朋友的短信。有一个前老板说：“Opus 5.5 刚刚在一次事故中救了我们的屁股。” 她说：“我们感觉有点像是终于回到了最佳状态。”

这句话虽然轻松，但透露出的是一种产品团队的真实心境：当你发布了一个模型，最令人兴奋的永远不是 benchmark 分数，而是真实世界的用户用它解决了真实问题。

### 对读者的行动建议

如果你拿起 Opus 5.5，可以从以下几个方向入手：

1. **试试之前因为成本太高而放弃的项目**。Opus 5.5 的成本效率提升，可能会让原本不可行的方案变得可行。
2. **试试多智能体架构**。保持共享状态 + 不阻塞子代理，让 Claude 自己设计分工。
3. **如果你在构建代理产品，优先考虑使用 Claude Managed Agents**。它的开箱即用安全属性可以帮你省下大量基础设施工作。
4. **如果你想做深度评估，建议把 Claude 当成 eval 的生成器，而不是被 eval 的对象**。让 Claude 生成结构化评测 JSONL，并让它做出主观评价，这比手写评测更高效，也能让你获得两代模型之间的对比反馈。

这期播客不是一个“公关式”的成功故事。它展示了真实团队的真实挣扎：如何处理安全与体验的张力；如何在不破坏用户的情况下防蒸馏；如何在没有 Rust 经验的情况下重写关键基础设施；如何在一个新的代理安全领域中犯错并学习。
