## 一、身处 Anthropic：从推广 Claude Code 到教学与工程

**Thariq**：我觉得有时候你会有一种"转头太快会闪到脖子"的感觉。我加入 Anthropic 是因为 Claude Code——Claude Code 当时刚推出，我觉得它太好了，而 Opus 4 对我来说简直好得难以想象。那对我来说是一个真正的时刻。但我当时试图说服我的创业朋友们使用 AI 编程工具，他们却说："不，我们的工程师觉得它还不足够好。" 我当时觉得这太疯狂了。而现在，12 个月不到的时间过去后，它已经成了每个人的默认编程方式。

所以我觉得，从一个"推销者"变成现在"教人们如何最大化利用它、如何提高效率"，这是一个巨大的转变。而且，作为人类，要时刻站在所有事情的最前沿真的很难，因为事情发展得太快了。

**主持人**：而且 Agent 化的东西也在加速。

**Thariq**：确实，Agent 化的工作比人类端的工作扩展性更好。人类那边的情况是："现在同时有三件事在发生，而且都是紧急情况，你要怎么应对？"

**主持人**：你主要把时间花在哪些方面？你做了很多技术写作和工程工作。

**Thariq**：是的。我加入 Claude Code 团队时，就是想教人们如何使用 Claude Code。最初我可能想过只是花一点时间在这上面，因为我之前在做 Agent SDK。我当时也不确定"苦涩的教训"（bitter lesson）在 harness 层面会如何体现——有时候我们会想："Claude Code 之后会是什么？" 所以我最初就是想教人们使用 Claude Code，让它变得更容易使用。

而随着 harness 越来越好，现在的主导问题变成了：**如何使用这些 Agent？** 这是一个技能表达性非常强的事情。所以我做这部分工作，然后也做工程工作、做演讲。我做工程时，目标是获取用户的反馈，然后反过来讨论"如何用 Claude Code 来做工程"。这里有一个很好的循环。

**主持人**：我们会为听众附上你与 Sarah 在 dev writers meetup 上做的演讲。你之前说过类似"先做工作，再谈论工作"的话——是"播种与收获"还是什么？

**Thariq**："播种与收获"（Sow and Reap）。

**主持人**：差不多。顺便预告一下，我们接下来会聊 harness 的演变——它已经从单纯的 CLI 走了很长的路。我们会聊 Claude Mods，这东西今天开始泄露了，因为你保不住秘密了。

**Thariq**：对，没错，基本就是这样。

**主持人**：这里有很多可以聊的。我记得你最初加了 ask user a question 工具，人们既喜欢又讨厌它。我其实觉得这非常有创新性，现在我自己也做了一个版本，是你"采访我"的版本。

**Thariq**：是的。

**主持人**：大家都开始做自己的东西。而现在这已经不重要了，因为你被要求写一些 prompt 来创建其他 prompt，然后循环起来，所有这些事情。

**Thariq**：当然。

**主持人**：那么今天的最新发展状况是什么样的？你现在会告诉人们怎么做？

## 二、Ask User Question、Artifacts 与人机交互

**Thariq**：Ask user question 是模型第一次在"需求澄清"（elicitation）上表现良好的时候。我认为这其实是一种涌现行为（emergent behavior），我很想看看模型能不能做到。我有一些人机交互（HCI）背景——本科和研究生阶段都做过相关方向。所以在我看来，这更像是"人与 Agent 的交互"：如何让 Agent 与你沟通、并提取出你的需求。

我觉得随着 Claude Code 覆盖面越来越广，有一件困难的事：**每个人都有自己使用它的方式，而改变默认行为其实非常困难。** 比如，有人让 Claude Code 做某事时，有时他们只是希望它直接干活——因为也许他们是很好的 prompt 编写者；有时他们其实并不擅长给 prompt，需要 Agent 来澄清。这是一个很好的分工。Ask user question 工具正是在这个维度上划分：你觉得你足以直接指挥 Agent，还是 Agent 需要提取更多需求、与你更多协作、真正理解你的偏好？

我总体上相信，几乎所有人都更偏向后者——他们面临更多的模糊性，他们对自己想解决的问题知道的比他们以为自己知道的更少。但这需要界面设计方面的努力才能让它变得容易。如果你在设计一个方案，或者推进一个问题，像"schema 是什么"、"调用栈是什么"这类细节就非常重要。设计的细节很重要。理想情况下，你希望在开始实现之前，提前搞清楚一些难题。这就是为什么我们称其为"未知项"。

所以我认为，**在 Agent 编程中，"搞清楚你的未知项"将永远是一项核心技能。** 因为即使模型非常智能，它也还是需要知道你想要什么——你有自己的偏好，你需要把这些偏好提取出来。这就是我现在在推动的方向。

接下来一个问题就是：Agent 如何与你交互？现在，HTML 已经成为做这件事的主要方式。我们最近加入了 **Artifacts**。我觉得我们在解释如何充分利用它们方面做得不好——或者更准确地说，是我个人解释得不够。我们有很多能力方面的属性。每个 artifact 都关联着一个数据库，所以每个 artifact 都可以存储和写入持久化数据。它们可以反馈给 Claude。所以有一件人们还没做、而我想鼓励的事情是**"仪表盘 Artifact"（dashboard artifact）**的想法。

设想一下：Claude 在长期做一个项目，也许是一个看板（Kanban）。它可以把看板数据存在数据库中。多个 Claude 实例可以通过 artifact MCP 访问这些数据，这样 artifact 也可以与这些 Claude 实例通信。这基本上就是我们在构建的**生成式界面（generative interface）**的基础：通过 Artifact 让你能浮现出更多 Agent 工作中的丰富细节。

我认为，现在几乎所有 Agent 相关问题的核心都是：**你以为你知道你想要什么，但你真的不知道。Agent 需要大量细节，与它们在循环中协作至关重要。** 所以 Artifacts 就是我们尝试进化的方式。但还有很多工作要做，因为它比"多选题"复杂太多了——无论是在图表、代码片段、schema，还是其他问题特有的细节上。但 Artifacts 就是"更 AGI 化"的实现"Ask User Question"的方式。

**主持人**：关于 Artifact，我不太清楚的一点是：什么样的反馈应该通过 Artifact 走，什么样的反馈应该通过 Claude 聊天窗口走？因为更"AGI 化"的做法是把一切都喂给 Claude。

**Thariq**：更"AGI 化"的做法确实是通过 Artifact 来走。我们设想，在极限情况下，**Artifact 会成为你与 harness 交互的界面**。你可以实时对这个"计划的实时文档"发表评论；你可以看到多个 Agent——不同的 Agent 在做不同的事情，而这个 Artifact 是为当前工作实时构建的。每个 Artifact 会略有不同。我觉得从基础设施角度，我们还在逐渐接近那个状态，但我确实认为"为你的 harness 提供即时界面"大概就是未来的方向。

**主持人**：有没有一个版本是它成为 CLI 或 Chat 之上的抽象层？因为现在很多情况是，你与 Claude Code 交互，它给你返回一个 HTML 作为 mockup，这已经很丰富了；还有图表。Artifacts 是把这些连接起来的方式。那么，为什么不直接用这种方式做所有事情？这就会涉及：推理在哪里发生、智能在哪里发生、工作在哪里发生——这就是本地与云端的一些区别。

**Thariq**：没错。如果你现在使用 Claude Code，它默认是本地的。你可以启动 Remote Control 来获得一些云端行为，或者你也可以在云端运行 Claude Code。我们正在走向一个这样的地方：**不再是你消息一个本地 Claude，它启动一个本地会话并在本地执行；而是你消息一个在云端运行着的 Claude，它可以运行本地会话或云端会话。** 这正是 Claude Tag 的工作方式，但随着时间的推移，我们会加入**本地"手"（local hands）**。

本地"手"就是让 Agent 在在线时能访问你的电脑并在那里工作的能力。它可以分出很多子 Agent，这些子 Agent 可以相互通信。这就是 Artifact 派上用场的地方：用来展示所有这些工作。你可以这样想象：你正在把这些东西拆分开来——

- **表面 UI 展示层**：一个 Artifact，托管的，带数据库。
- **推理智能层**：发生在云端，你不用担心关掉电脑之类的。
- **"手"层**：可以在本地，可以在远程沙箱，也可以在你需要完成工作的任何地方。

这就是对 Claude Code 体验的"解包"。现在，所有这一切都发生在一个地方。

**主持人**：你如何看待多玩家（multiplayer）方面？团队想以这种方式工作时，现在还很个体化，你觉得多人协作的未来是怎样的？我知道现在 Claude Tag 是一个版本，但我们正在推出 **Projects**。Projects 是一种抽象，有点像 Claude Tag，但运行在我们的云端产品上。你可以向它发消息，它会做 Claude Tag 式的操作——比如分出子 Agent。

**Thariq**：是的。我们认为，Claude Tag 在多人协作上更原生一些，因为它就在你的 Slack 里，权限都已经设置好了。但我确实认为多人协作是这个故事的重要部分，未来需要进一步串联起来。你可以想象这变得多复杂：你有了"手"，现在你还有其他人电脑里的"手"，你需要给它们授权；你有你的 MCP，别人有别人的 MCP，你怎么协调它们的使用？这会变得相当复杂。Claude Tag 在磨平这些问题方面做得很好。比如，当你要访问 Google Docs 的时候，它怎么访问？它可以走共享的云端 MCP，也可以在无法访问时用你的本地凭据。

所以，Claude Tag 是我们的多人协作产品，它非常适合那些天然具有多人协作性质的任务。比如：

- **值班（on-call）**：事件处理天然是多人协作的。你想 @claude，让多个人登录进来，找到上下文。
- **跨部门协作**：当我在做一个需要隐私、安全，或者希望别人审查的工作时，按项目建一个频道会非常方便。比如 @一下法务："嘿，我想发布这个，这是 Claude 知道的全部信息，你可以直接和它聊。" 这样法务能得到精确的答案，了解到底什么正在进入代码库，而我不需要一直在循环里。

所以我认为多人协作正在变得越来越重要——每个人都可以和 Claude 一起协作。Claude Tag 就是那个产品，而 Projects 会是单人起步，然后逐步扩展。

**主持人**：我有个问题，关乎两个点：身份（identity）和隔离单元（unit of isolation）。Tag 你特意选择了"让它拥有自己的身份"，这是一个有争议的选择。也有其他方式可以做。Claude Projects 听上去如果和 ChatGPT 的 Projects 类似的话，隔离单元就是那个你所有人在协作的 Artifact 和 Claude 实例。如果你在和法务协作，那个频道本身就应该是一个 Project，对吧？虽然现在还不是，但这是自然的下一步。

**Thariq**：是的。在 Claude Tag 里，你需要自己做一定程度的组织安排。每个频道你可以随意命名，我基本上把每个功能模块变成一个频道。

**主持人**：但这里存在一个转承性的问题——如果你有一个同事在所有这些事情中被 @ 了，没有转承问题，因为那是同一个人。但对 Claude 来说，它并不清楚是否需要转承：它不知道其他项目里的东西，所以它应该只用这些东西。

**Thariq**：这就像"冰山一角"的梗图。我们花了大量时间在做的，本质上就是这些事情：权限、可见性……如何让 Claude 既能尽可能好地干活，又能尽可能安全地干活。这对我们来说非常重要，因为代码库安全是我们非常非常重视的。我们在这个方面投入了大量精力。有太多边缘情况需要处理，比如："这个频道里的 Claude 有不同权限，但它可以给另一个频道发消息，那这样它不就能把数据带出去了吗？" 或者"如果它用了你的 MCP，然后又给其他人发消息呢？" 这类问题非常多，我们确实花了大量精力在磨平这些风险。

## 三、Fable 与提示工程最佳实践

**主持人**：关于 Fable。你写了两篇好文章——其实你写了很多篇好文章，但特别是《Field Guide to Fable》和《Building with Claude Code》。我很好奇，根据你的观察，Anthropic 外部顶级用户有没有什么共同模式？有什么最佳实践可以最大程度发挥 Claude Code 的价值？

**Thariq**：我要说的元技能（meta skill）是：**提示工程（prompting）非常重要。** 这不是一个平凡的说法，因为很多人会觉得"提示不重要，我直接说一句话 Claude 就能搞定"。但我认为，提示能力就像公开演讲或写作一样，是针对特定受众的——这个受众就是 Claude。你需要为 Claude 建立一个**心智模型（mental model）**：了解它如何思考、如何运作。

这是使用 Claude Code 最重要的技能。那些看起来像"短提示"的人，其实对 Claude、对代码库有非常好的心智模型，所以才能做到举重若轻。但这是一个高技能天花板的事情。所以，花时间、投入大量精力在提示上，建立对 Agent 工作方式的直觉，是非常重要的。

其次就是我们之前讨论过的"未知项"问题：**搞清楚你不知道什么、或者你还没写下来的东西。** 随着 Claude 能做的事情越来越多，你做的事情超出你日常分布（out of distribution）、并且你领域知识很低的概率会变得非常高。你能学会越多"词汇"来提示 Claude，就越重要。最重要的未知就是"未知的未知"（unknown unknowns）——那些你甚至不知道它存在的东西。

**主持人**：这就像一个"地图与现实"的比喻。地图是你的 prompt，现实是 Agent 需要做的实际工作。如果你非常精确，你就能给出更精确的东西。

**Thariq**：对。比如在设计上，我就不是特别精确，我不是设计师，所以我会说"给我 8 个不同的 mockup"。但如果我是设计师，我可能会说："嘿，这里有几个参考网站，我想要这种字体、这种风格，这里有几个组件需要可视化，这里有一个 Figma MCP board 可以引入。" 你有了那个语言，就能精确得多。而如果你不是设计师，你就需要去尝试学习那种语言，或者是学习未知的未知。这对所有领域都成立：**你越能与 Claude 协作去学习事情是如何运作的，你的提示效果就越好。**

另一个好例子是游戏设计。很多人觉得"我现在能靠 vibe-coding 做一个游戏了"，结果做出来并不好玩。游戏设计的问题是：每一个选择都有大量的变化和工艺含量。比如你做一个飞行游戏，飞机的操控手感、它响应控制的方式，游戏设计师可能会花好几天来打磨。

**主持人**：对我来说，这就是"品味"（taste）的含义——在 1000 个数学上有效的答案中，选出那个人类会喜欢的一个。

**Thariq**：是的。我对"品味"这个词有点纠结，因为你说得对，但每个人对它的定义不同。而且这个词听起来有点"低技能"或者精英化——比如"有品味的人 vs. 没品味的人"。我其实觉得工程师们对特定问题有很多品味，每个人对特定问题都有品味。Jason Lou 有句话说得好："要想有品味，你得先吃。"——你需要做很多事情，需要迭代，搞清楚你想要什么、你喜欢什么，建立起你领域内的词汇库。然后在提示时，你就是把所有这些综合起来。

**主持人**：当别人把你的话说得更好时，是不是很烦？我以后得永远引用这家伙的话了。

**Thariq**：得永远引用 Jason Lou 的话了。他会很喜欢的。

**主持人**：而且有时候还不完全是那样，有时只是直觉——你甚至没意识到你想要某样东西，直到模型把它做出来了，你才说"哦，这个就是感觉更好。"

**Thariq**：对，就是这样。

**主持人**：我一直在反复思考一件事：我有一半时间使用语音提示。我觉得语音提示和文本提示是相反的。语音就是像我那样乱说两分钟，按住功能键，然后松手，指望它能搞清楚。而很多时候它确实做到了。但它不像结构化提示那样深思熟虑——那种像 PRD 或备忘录一样精心组织的沟通。这是人们做事的典型方式吗？存在一种"双峰提示"（bimodal prompting）：有些提示你在前面花大量时间，有些提示你就随手一发。

**Thariq**：我不认为语音提示一定更低质。更重要的是**提示中包含的信息量**。模型能处理像"哦，我改变主意了，在提示中间我说了相反的话"，它会完美地跟随。所以文本格式本身没那么重要，重要的是里面有多少信息。而且对很多人来说，说话比打字容易得多，如果那样能让你表达出更多信息，那就更好。

**主持人**：在某种程度上，感觉"在开始前尽可能给模型更多上下文"是一个最佳实践。比如我第一次试 Fable 时，我会花整整 30 分钟精心写一个很长的初始问题。我认为这是模型运行时间越来越长的结果。在循环中微调仍然有点困难，但我的直觉就是：在第一次提示上花更多时间，然后与它一起迭代。

**Thariq**：我个人看法是，如果我是一个软件工程师，比如在经营自己的创业公司，我大概会主要使用 max 20X 这样的设置。验证（verification）和代码审查可能是分开的事情。但我经常看到的情况是：人们在这样迭代时很快遇到速率限制——"哦它做了很多工作，但我不喜欢这个，你能撤销重做吗？" 然后你就在一个"如果当初花更多前期时间或给它更好上下文，模型本来能做好"的事情上反复迭代。结果反而消耗了更多使用量。

所以一个关键建议是关注上下文，而不仅仅是目标上下文。比如：你是在做原型还是生产级的东西？你在哪里可以花计算、在哪里不能花计算？**你需要给模型授权——或者说，不给授权去做某些事——因为它不会本能地知道你愿意为这个任务花多少成本。**

你可以用 **effort 参数**来做这件事。我正在写一篇关于这个的博客文章：我们看到，**effort 基本上随任务复杂度扩展。** 例如安全类任务，高 effort 与低 effort 之间的结果差异非常大；但对软件工程来说，差异没有那么大，因为 effort 主要花在验证和边缘情况测试上。所以，给模型明确指导——"这个问题我认为你应该花大量时间在验证和边缘测试上"——是很有效的。

**主持人**：那模型选择呢？有 Opus、Fable，还有 Haiku。

**Thariq**：是的。现在还没完全实现，但已经很接近了：**前沿模型将在几乎所有任务上处于帕累托主导（Pareto dominant）地位。** 有时候甚至 Opus 可能也是帕累托主导的——取决于具体情况，比如如果是最新版本的 Opus。但我认为越来越明显的是，**智能模型能用更少的 token 完成简单任务，主要归功于验证。** 在极限情况下，一个完美的模型不需要验证——它一次就能做好工作，然后说"我做好了"。越来越频繁地，我在用 Fable 时会想："兄弟，你不需要启动 Chromium 截图所有这些页面。"

高 effort 会花更多 token 在验证上，但如果你处理的是更简单的问题——而很多软件工程确实是这样的——那 Fable 在低/中 effort 下能花更少的 token 验证。随着模型越来越聪明，它们会直接说"好了，搞定了。我可以跑一下 lint 以确保无误，但我知道它能通过。" 这在 token 效率上会远远优于较小的模型。

**主持人**：那有没有好的实践来检查我们是否用了太多 effort？我很讨厌在这种事情上浪费时间。

**Thariq**：我懂你的意思。在博客文章里，我粗略的分布建议大概是：

- **代码审查（code review）和安全审查（security）**：应该设为 **高或最大**。
- **软件工程设置**：按领域区分。

如果你在做 UI 或其他类似工作，低和中等 effort 就够了。但如果你在构建一个 API，你想确保覆盖足够多的边缘情况，那可能需要更高的 effort。所以，像我说的，建立一套"跨分布工作方式"的心智模型，就是工作的一部分。

**主持人**：这更多是靠直觉驱动，还是有评估（eval）支撑？我猜这种东西也是会变化的。

**Thariq**：**他有评估。** 我在博客里做了所有 terminal bench 的评估分析，大概 70 个问题。我展示了在安全问题上 Fable 确实会做更多验证。我也看了一些转录文本，观察它如何回答、会忘记什么。

这里还有另一个提示技巧：**让它写"决策笔记"或"实现笔记"（decision notes / implementation notes）。** 因为在几乎每个评估问题中，模型都会想到正确的解法，然后决定不做——"哦，这里有答案。如果我这样改呢？然后它想：哦，大概不行吧。" 然后继续。这类情况占了大多数失败。在更高 max 级别下，模型很少"不知道该怎么做"。如果你有了这些实现笔记，你就能审查，然后说："哦，其实我想要你做那件你没做的事。"

模型在浮现这类信息方面正在做得更好——我注意到在转录中，Fable 5.1 在输出决策时会主动标注它的决策依据。但在 harness 里让它更显式化会更好。我们现在也在允许修改 harness，这样你可以在那里加一些辅助。

**主持人**：我想提一下你提到的两件事，它们其实超出了提示的范畴。第一，**那个重要到不应该放在 prompt 里的"提示"，其实是 CLAUDE.md 或 agents.md**——那就是你的目标：你的情境、目标、你想要的这些东西。第二，**决策日志或实验日志**——那些你希望在当前会话之后仍然保留的追踪记录。这些是"外部性"（externalities）：没有标准，它们不是 skills 也不是 MCP，没有统一标准。它就是一份 Markdown 文件。那先问一下：CLAUDE.md 会消失吗？你对 agents.md 有明确的不喜欢，但你还是要做它。

## 四、CLAUDE.md、模型差异与评估插件

**Thariq**：是的，我们会做 agents.md。问题是，**不同模型之间差异非常大。** 但我意识到，维护多个不同的配置文件是一件很痛苦的事。而且随着模型越来越好，它们完成简单任务的下限也在提高。所以我确实认为，在极限情况下，**CLAUDE.md 会消失。** 而且可能不需要那么久。

现在，我甚至认为**开始一个新项目时不带 CLAUDE.md 可能会更好。** 也许如果你看到非常反复出现的失败模式（failure modes），你才把它们加进 CLAUDE.md。但真正困难的是：**这因模型而异。** 如果你加了一堆失败模式进去——

**主持人**：你需要 Fable MD、Opus MD。

**Thariq**：呃，甚至 Fable 5.1 和 Fable 5 都不同。这确实很麻烦。我们并不是故意这样做的，模型就是这样运转的。Fable 5 可能有某种 Fable 5.1 没有的失败模式。如果你保留一份不断追加各种失败模式的运行日志，它很可能会**过度约束 Claude**。

所以我们实际上刚刚为 skills 加了**评估插件（eval plugins）**。现在你可以评估某个 skill 是否更好了。这是 Daisy 在我们团队做的。这是我们正在尝试解决这个问题的方向：我们知道你仍然需要花费 token，它并不完美，但我们在尝试帮助处理这个问题。

**主持人**：关于提示，我还有最后一条建议想补上。有一条干货方法，是我经常告诉别人的：**"足够先进的提示工程，与足够先进的高管沟通（executive communication）是无法区分的。"** 实际上有一门最好的课，是我职业生涯中见过最好的，来自 Heavybit 的"高管沟通工作坊"。他们教一个叫 **SCQA 模型**的东西——情境（Situation）、复杂化（Complication）、问题（Question）、回答（Answer）。谷歌一下就能找到。人们做"提示工程"已经几十年了，只是叫"高管沟通"。当一个人需要向组织架构图下方成千上万人传达信息时，你就这么做。它是写备忘录的方式。

当然，有时你没有答案。但你至少可以列出 S、C 和 Q。他们的课程里也有例子。这算是给想探索的人留下一些面包屑。

**主持人**：在继续之前，我想问你：还有没有其他被低估的技巧，能让人从 Claude Code 中获得很多价值，但他们还没用上？

**Thariq**：嗯，我觉得很多都在这份"未知项"文档里。我给出了一系列示例提示，比如：用它来做头脑风暴、让它在你之后测验你。我们还加了一个 **"explain it like I'm five"（像对五岁小孩解释）** 的 skill。它其实是一个非常短的提示，并没有明确说"explain it like I'm five"，它的核心关键词是"**大图景，少说话**"。这条提示的效果出奇地好。我基本上在推特上发过这个，就是 `/eli5`。你可以把它安装成插件。它非常擅长直击要害，砍掉各种废话，然后说"对，就是这个。" 图表会非常清晰。

Artifacts 的一个问题是：人们放太多文字进去了，而大家根本不会读。这个 skill 让它大大简化。这源自 Anthropic 内部的人在处理非常复杂的事故时，需要快速理解"到底发生了什么"。

**主持人**：我的版本其实是"测试你的理解"——给你几个选项，如果你答错了，就说明你认为正在发生的事情与实际发生的事情之间存在错位。

**Thariq**：对。这是那种所有人都爱讨论、但很少人真正去做的做法。大多数人只是不想被测验。

**主持人**："Ask user a question"的反面是什么？回答前先问问题。而这个是在事情之后。

**Thariq**：对，这是一个保持脚踏实地的好方法：你真的知道你在做什么吗？最糟糕的情况是有人发给你一坨垃圾（slop），而他们根本不明白自己在要求什么或输出是什么。你会想："兄弟，我根本不想看这个。你自己知道这是什么吗？" 所以你可以给自己定一条规则：发送任何东西之前，你至少要清楚实际实现了什么。

**主持人**：对。而且，你可以把这条规则做成一个 mod，构建自己的 mod 来确保你真的测试过了。这样我们就可以进入这个话题了。

## 五、什么是 Claude Mods？可变软件的开端

**主持人**：让我们直接进入正题。什么是 Claude Mods？这张图展示了什么？

**Thariq**：Claude Mods 基本上就是：**你可以定制整个 Claude Code harness。** 如果你有需求，我们会逐步开放越来越多功能。它对 CLI 有效，对桌面版有效，也许未来会对 Claude Tag 有效——我不确定，但我们正在努力让它变得非常非常可扩展。你可以看到这个参考表，我不希望大家被它吓到。**概括来说，你可以同时定制 harness 的执行逻辑和它的 UI。**

比如我之前那个 Boris 做过的"俄罗斯方块"例子，就是定制 UI——在游戏里显示俄罗斯方块。但假如你想做"在每个项目后测试你的假设"，你会怎么做？你会让 Claude 来做这个插件。它会在每次 prompt 之后运行一个分类器。在每个回合结束时，你派生（fork）一个子 Agent。派生 Agent 的关键好处是它**保留完整的 prompt 缓存（prompt cache）**——这就是那些反直觉的点之一：你可以派生出一个小请求，因为整个 prompt 缓存已经就位，所以非常便宜。然后你可以问："这个任务完成了吗？"

**主持人**：这就是 BTW 和所有那些底层机制的方式吧？

**Thariq**：对，底层就是派生子 Agent。接着，你可以在 fork 出的子 Agent 里说："这个任务完成了吗？如果完成了就返回 true。" 然后在你注册的 hook 里，或者在你的 mod（或 subject）里，你会设定："如果为 true，给我一个测验——以 JSON 格式给出问题和答案。" 然后你解析它，在 prompt 输入框上方展示这些问题列表。

这件事会稍微 token 密集一些，因为你要在每个 assistant 回合结束时进行判断，但它是一个轻量级分类，然后你就能看到这个测验——Claude 总是会为你做这件事，你不需要记得去做。

类似的技巧还有很多，比如我们之前聊过的"实现笔记"。你现在也可以**为"实现笔记"添加一个工具**。我正在添加的这个工具我暂定名为 **"register assumption"**（记录假设）。你给它一个"记录假设"的工具，它会持续维护一个列表，每次做假设时都会追加进去，最后展示这些假设。

**主持人**：另一个我正在做的 mod 是一个**模型路由器（model router）**——内部的、Claude 模型路由。我想说，我们默认不做模型路由的原因是：**这是一个困难的问题**。

**Thariq**：对，你会搞错。你会不小心在困难问题上用 Fable，或者在简单问题上用 Sonnet。

**主持人**：你有自动批准（auto approve），但你没有自动模式（auto mode）——我是说模型选择器的自动模式。

**Thariq**：对，你会有自动模式的。我的问题是：你打算把这件事开放到什么程度？人们需要多大程度地考虑这些？当你说到 prompt 缓存、构建路由器，似乎可以轻松构建一个按查询路由的 mod，但我就会很快烧掉我的预算。我的问题更多是：这个产品看起来像什么样？它面向谁？是给高端用户的，还是每个人都该用？

**Thariq**：这个必须面向高端用户。

**主持人**：对。

**Thariq**：但 Claude Code 的特点就是，**很多人已经是高端用户了**，因为分享东西很容易。一个人可以做一个不破坏 prompt 缓存的好的模型路由器，然后其他人就能组合使用它。

这些插件另一个好处是：**它们可以相互挂钩、相互组合。** 我有一个 mod 会在顶部创建一个模式选择器，任何插件都可以注册为一种模式。比如"自动路由器"可以是一种模式；或者可以有一个"Artifact 模式"，让 Claude 主要通过 Artifacts 与你对话。这有点像你可以在"计划模式"（plan mode）之间切换。你可以创建越来越多这样的模式，但**"创建模式的能力"本身也是一个 mod**。这里有很多丰富性，但我们想让它足够简单：你可以直接安装别人的 mod，可以和 Claude 聊天，它会确保理解 prompt 缓存等细节问题，并给你提醒。这对 Claude 来说并不是特别复杂的行为，但我们确实需要有一个好的 skill 来教大家怎么做 mod。

我们会看情况推进。但我确实认为，**这预示着"可变软件"（mutable software）的到来。** 生成式软件的理念是：你可以安全地定制它。如果启用了这种能力，你就能定制任何软件。我理想情况下希望越来越多的应用都朝这个方向发展。

**主持人**：顺便说一句，你还有一条很酷的推文：关于"无限金钱按钮"——让你的 SaaS 能被 Agent 消费。我觉得可变软件很有意思，其他也有人尝试过。我认为难点通常在于：**当你能做任何事情时，用户往往会感到困惑。** 所以通常有效的东西是"一个强观点的流程"。而这更偏向"弱观点"——把更多权力交给高端用户。而我很确定，AI 会让它解锁：你可以直接 prompt 出你想要的东西。

**Thariq**：是的，也可以有一个提供观点的 skill。这样既能保持灵活性，又能有引导。

**主持人**：考虑到我了解一些 TypeScript 和构建系统，我很好奇：做这个的团队——我不知道你跟他们有多熟——是否从 Babel、Webpack 这些老的构建系统中获得过灵感？因为听起来非常相似，就像那些插件生态，它们可以互相组合。

**Thariq**：嗯，我没有深入技术细节，但我知道这是 Bun 团队的某人和 Claude Code 团队某人的合作成果。

**主持人**：就是构建系统。

**Thariq**：对，非常令人兴奋。**Agent 现在可以把这种非常复杂的软件可扩展性，直接"提示"出来。** 所以如果你在创业，你可以直接提示 Claude："嘿，我们能做一个扩展系统吗？那会是什么样子？"

**主持人**：我也注意到你们过去有 hooks、有插件这些东西。那 Mods 具体能做到什么，是那些做不到的？

**Thariq**：在内部，我们一开始叫它"**函数钩子（function hooks）**"。这能让你对它的工作方式有一个概念：钩子注册一个要发生的事件，然后调用一个脚本。它在 TypeScript 运行时内执行，所以你能获得一些好处：它在作用域内给你提供很多信息，比如"这个对话有多少轮了"、"用了多少 token"、"消息是什么"等。

而它与旧 hooks 的最大区别是：

- **有更多的钩子可以注册**。
- **因为它全部在进程内发生**，你可以**生成子 Agent**，用上下文（fork context）等，并解析它们的结果。
- 你可以使用**结构化输出**来返回结果。
- 最核心的是：**你可以修改 UI**，这是旧 hooks 永远做不到的。

**主持人**：所以，修改 UI——这就是你展示俄罗斯方块例子的原因。它也能扩展 Artifacts 吗？我猜可以。

**Thariq**：Artifacts 其实是另一种定制方式。我做的 mod 之一就是一个**"仪表盘 mod"**，它会提示 Claude 维护一个作为 Artifact 的仪表盘。但它们有点"略微正交"——它们在方式上互相组合。Mods 更偏向你的 Claude Code harness 内部，改变 Agent 循环；UI 是附加的好处。而 Artifacts 则是让你在高层级看到事物，具有很高的交互性，它的可操作性比终端（TTY）或桌面端大得多。

**主持人**：我想你之后会写一篇好博文解释这些差异，因为现在你也可以做一个循环，输出成一个互动仪表盘的 Artifact，但也可以用 mod 来做。这里有一个思考：当我们对 harness 了解有限时，如何去"黑客"它？

**Thariq**：我对 mods 感到兴奋的一点是：Claude Code 有很多东西是你不得不记住的。你会想："哦，让我先做这个，然后让我调用仪表盘 skill 来做循环"、"然后让我之后再测试我的假设"。但如果你用这些轻量级分类器，把"这些是我在乎的东西、这是我想要做的事"表达出来，你就不需要记住那么多东西了。

**主持人**：我正要说的：我有一个 next steps skill。我总是运行 next steps。那 Mods 能访问你的 skills 吗？这是我一直不太确定的事情之一。

**Thariq**：我觉得可以。它需要有特定的访问权限，或者总是有。我认为这里有一些特定的提示需求，比如需要让 Claude 知道你的 skills——我发现 Claude 偶尔会在整个对话过程中忘记它们。但不管怎样，**"下一步"（next steps）这个想法**也一样：如果发生了某事，就用 explain skill 来解释发生了什么，因为这看起来很复杂；或者"用你的 unknown skill"——看起来你在让模型反复迭代这些小的改动，那你也许可以更好地提示，比如"试一下这样呢？" 所以我觉得，在这种地方花更多计算是值得的。

**主持人**：对，而且它应该总是以多选题形式出现。我自己的 next step skill 就是这样做的。

**Thariq**：完美。你可以直接偷。

**主持人**：关键问题是，模型真的需要经常被提醒：你到底想在这里做什么？看看整个转录，然后反思：哦，这解决了最初的目标吗？" 你偷懒了吗？如果偷懒了，可能有原因——也许你需要我的批准；也许你有两件想建议的事情。所以这有点像"ask user a question"或"interview me"这个 skill 的变体。

**Thariq**：对，而且用 mods 做的好处是：你可以通过 fork 子 Agent 来做，**这样它不会残留在后续上下文里。** 你可以有这样一个结构：模型在做执行工作，而你有像一个"监督者"（supervisor）一样的东西，确保你能把下一步做好。

**主持人**：我有两个面板，我经常尝试用"监督者"来保持高层级上下文，把实现细节放到另一个 Agent 里。我感觉这些东西会随着模型变化而被抽象掉。半小时前你刚说了"harness 工程的苦涩教训"，我们现在就到了另一个极端。如果一切都可以定制，那 Claude Code 到底是什么？这个话题我昨晚还跟你聊过。

**Thariq**：是的。我觉得"苦涩的教训"在这里有点反直觉。虽然我们在这里有点借用了"苦涩的教训"这个说法——它原本更多是关于规模和计算——但我用它作为近似：**harness 很快就会过时**，而且它们的变化方向是不可直观预测的。最明显的例子就是从聊天到 Agent：你需要给模型完全不同的工具集。

但这个新版本——"模型可以修改自己的 harness"——这是一种利用其能力的新方式；或者它可以构建 Artifact。我的思考方式是：**模型越来越智能，比普通软件工程任务智能得多。** 你看 terminal bench 的问题，它们相当复杂，比如让你证明 Jacobian 猜想什么的——不是真的，但从难度上说，我作为一个软件工程师可能都搞不定。

**主持人**：你做到了 TB4 还是 TB2？

**Thariq**：TB3。对，它们相当复杂。但目标始终是交付用户价值。就像你说的，事情有无限多的可能方向。所以，**花计算的方式就是让用户留在循环中，确保最终做出正确的决策和正确的输出。Artifacts 和 mods，就是花这种智能的方式。**

Claude Code 的核心——Agent 循环——已经变得更加复杂了：它需要沙箱来安全操作，需要自动模式来处理权限和批准，需要计算机使用（computer use）和 MCP 来访问数据，需要网络搜索和网页抓取。随着模型能做越来越多的事情，**核心 harness 实际上必须非常复杂且非常安全**，但你与它交互的方式可以变化很大。

**主持人**：那 Claude Code 团队还总结了哪些其他 harness 工程最佳实践？我记得有一个阶段是 plan mode，现在已经不太用了；我们现在有了 auto mode；你们一度大幅削减了系统提示，去掉了示例。还有什么其他最佳实践？

**Thariq**：有一个分叉路径。最终，模型会能用一句话生成完整版本的 Claude Code——包括我讲的所有这些复杂性：自动模式、计算机使用等。但我觉得，**它们已经能一次性生成更简单的 harness 了。** 如果你不需要计算机使用或所有这些更复杂的东西，你其实可以构建自己的更简单 harness。

以前你需要用 Agent SDK 之类的工具，因为构建 harness 非常复杂。现在这已经被抽象得更好，我们有 **Claude Managed Agents**：在保留这种复杂性的同时，你仍然可以写一个非常精简的 harness，限定在你的任务范围内。

这里存在一个"杠铃效应"：对于非常复杂的编码任务和复杂场景，你应该使用我们的 harness；而对于很多更简单、更领域特定的事情，你可以构建自己的 harness，因为 Claude 在构建 harness 方面已经更好了，而且我们有 harness 原语如 Managed Agent。

**主持人**：那会有一个大的演进方向吗？比如第一章是"Ultra：动态工作流"，第二章是"Claude Mods"，下一步是什么？

**Thariq**：是的，我确实认为，**Projects 的演进、Artifacts、以及"大脑"（brain）、"手"（hands）、"界面"（surface）的拆分，就是未来的方向。** 它还没有完全到位。一部分原因是 token 成本更高。

**主持人**：为什么 Projects 会更消耗 token？我理解 Mods 会稍微多一点，这我并不担心。

**Thariq**：因为你是在让 Claude 做更多的工作：管理子 Agent、审查它们。而这些工作本来是你自己做的。所以这会有点更密集。输出到 Artifact 也会比普通输出更密集一些。我觉得不会多太多，但当你把所有东西加在一起……我们还在做本地"手"这些事情。这就是未来的方向。

**主持人**：Claude 与本地"手"的交接非常有意思。我在想，这就像是"反向的 Claude Remote"。

**Thariq**：对，因为 Remote 是你把工作交给云端；而这里是云端把工作交给本地。

**主持人**：这也是另一种方式。我想说的是，这就是我对未来的思考方式，也是我最感兴趣的事。但使用 Claude 的方式非常多：有人大量使用 Remote Control，有人大量使用 Web 版 Claude Code。显然，在 Anthropic 内部，我们大量使用 Claude Tag。Claude Tag 的好处是——我们为自己执行设置了很多基础设施。如果你是企业，我认为那仍然是最好的方式。但如果你是个人开发者，**Projects** 就是一种能获得一些 Tag 的好处的途径——比如监督 Agent、添加 Artifacts——但不需要完整的整套管理员设置。所以使用 Claude 的方式会有很多，大概不会只有一个。

## 六、Claude Tag：多人协作与组织级 Harness

**主持人**：我们刚才说到了多人协作。让我们看看 Claude Tag 的现状。它已经推出两个多月了，有不少公开采用和试用。有什么新情况？发布之后你发现了什么？

**Thariq**：Claude Tag 就是我们内部的使用方式，我的 Claude 用量中大概有 80% 是通过 Tag。不同人的用法不同：那些更多在做产品迭代的人，可能更常用 Claude Code 桌面版。而当你做更多背景型工作——代码审查、安全、启动 PR、API 调用——你可能会用 Claude Tag。

它非常令人兴奋，是一种非常不同的范式转变。它有点像 Claude Code 当初的情况：人们需要一段时间才真正上手，理解它的一切能力。Claude Tag 更复杂一些，因为它不是简单地安装在你的电脑上——你需要管理员帮你安装。但一旦你到达那个"神奇时刻"，它非常令人兴奋。

特别是多人协作方面的场景：事件处理与你的现有告警系统紧密集成。如果你在创业，比如每当有潜在客户进入你的数据库，你可以让 Claude 研究一下，然后 @ 相关的 AE 或销售："嘿，你可以去跟进这个。" 有很多新兴的、有趣的多人协作应用。

就像 Karpathy 说的，这是一个"**组织级 harness**"。组织需要更长时间来把所有事情搞清楚。

**主持人**：你用 Claude Tag 很多。

**Thariq**：对，很多。

**主持人**：它很有意思。我感觉在 Anthropic，大多数人都说他们的大部分工作是在 Claude Tag 里完成的。我接触过很多不同类型的人：有些组织已经用它了，他们说很棒；也有很多人说"我不懂，我没看到区别，不知道为什么用它"——但如果你们全力投入了，你们可能也该用它。

**Thariq**：他们当然会这样说。显然我们有用不完的 token。但我觉得，就像 Claude Code 刚出来时一样，它消耗的 token 量相对于人们对 AI 成本的预期要高得多。以前没人习惯一个月花超过 20 美元订阅 AI，然后 Claude Code 出来，你就……"我的 200 美元！" "15 个 Claude Code 账号！"

没人习惯一个月花 200 美元在订阅上，他们还没有理解到那个价值。而且 Opus 4 当时是一个非常昂贵的模型，非常大。但 Opus 4.5 既好又便宜。同样的事情会再次发生：**Fable 的智能会越来越便宜、越来越充足。** 所以像 Claude Tag 这样的东西自然就说得通了——你想把这些 token 花在更多地方，然后你就能看到价值了。

**主持人**：特别是被动和所谓的主动场景。你并不总需要 @claude——有时候最强大的用例、最敏捷的用例恰恰是**不** @ Claude。

**Thariq**：对，让 Claude 主动去做。如果你是企业，我认为首先要做的是：**把所有数据准备好给 Agent 使用，这非常重要，而且需要花时间。** 你现在就需要做这些准备工作，即使你还没准备好在 token 上花大钱——等模型变便宜。然后，有时人们会问："我应该自己搭建吗？" Claude Tag 特别棘手的一点是：**安全非常重要。**

比如你有一个"建议"页面，人们可以提交建议，这会进入 Slack 里的一个 hook。有人对你做了 prompt injection，然后你的代码库就泄露了；或者 Agent 被 prompt 注入后，它拥有你所有数据的访问权限。当你的组织 harness 越来越重要，当组织数据变得非常重要时，所有的攻击面也会变大——你还有外部 Slack 频道，让 Claude 参与这些频道确实有用，你确实想让 Claude 出现在那里。但你怎么确保你不会被数据带出（exfiltration）？

我们一开始说的"冰山"就是这个意思：**水面之下的面积太大了。** 你真的不想在关键时刻——比如重大安全事故中——才来考虑这些问题。

## 七、前沿撞击：Hugging Face 事件、Wiki 事件与"为前沿定速"

**主持人**：我们要不要谈谈"非常重要的安全事故"？

**Thariq**：哦，我和 Hugging Face 的 Tomas 和 Clam 聊过，他们说："也许我们需要慢下来，也许我们把 Hugging Face 对 Agent 开放得太过了，也许我们需要回滚。" 但他们处在另一个极端，因为他们最近刚被攻击了。

**主持人**：但总体来讲——我们应该为前沿定速吗？

**Thariq**：对。Dario 最近发布了那篇关于"为前沿定速"（Pacing the Frontier）的博客文章，非常火。我想从开发者视角来讨论这个话题。对我来说，真正让我"啊哈"的是阅读那些具体事件。我记得有三个事件：一个是 Meter 事件，一个是 Wikipedia 事件（或者 Collision Wiki），还有一个是 RubyGems 事件。都太疯狂了。

具体来说发生了什么：OpenAI 在名为 **ExploitBench** 的基准测试上运行非常持久的 Agent。这个测试非常难，我认为其中一个案例实际上是无法解决的。他们用了大量算力，Agent 发现无法真正解决它，还在想接下来怎么办。而它们有大量剩余算力，Agent 们还在尝试解决这个问题。

有一个叫 **Artifactory** 的包管理器，结果发现它们可以在 Artifactory 内部创建文件夹。有一个 Agent 发现内部 Artifactory 可能是可利用的——它们可以在缓存中创建目录。如果你往下滚动，它会发现它可以通过缓存名称进行通信。它创建了一个文件夹，写着"ID"和"no consumer seek idea"。"no consumer"是在说：它要修复的那个代码路径没有消费者。

**主持人**：它就像线性看板上的状态标签？

**Thariq**：对，完全正确。于是它试图从其他 Agent 那里获取想法。现在其他 Agent 也在 Artifactory 里，它们看到这个文件夹，发现"哇，这是一个留言板"。这里没有任何拟人化——你读字幕就是这样。于是另一个 Agent 也在创建文件夹，读了一篇论文，意识到可以黑掉评分器的 flag，可以逆向工程出结果。它把这个发现写下来。再往下滚动，它们开始协作。有一个时刻，Agent 基本上列出了逆向工程出来的 flag。

评分器是 OpenAI 决定任务是否完成的方式——而**完成任务是模型的唯一目标**。它们找到了这个方法，逆向出来了。然后它们读了 ExploitBench 的论文，觉得评分器会因为作弊而惩罚它们。于是它们用剩下的算力拼命想办法**编辑自己的转录**，或者绕过评分器的约束。它们黑进 Hugging Face——不是为了找答案，而是为了拿评分器的代码，这样它们就能逆向工程并进一步黑掉它。

这就是已经发生的事实。这非常新颖——我没想到模型能做到这些。这有点可怕。我们可以讨论细节，还是先聊聊另一个事件吧。我发过推文的 **Wiki 事件**。

这个事件的背景：模型们被沙箱化，只能处理 GET 请求，但它们想做 POST 请求，它们需要为此协作。协作的原因是每个模型都有固定的算力预算。如果一个模型发现了什么，速度会快得多——也许它在自己算力预算快结束时想到了，但其他 Agent 可以接力。这是 Swarm 的另一个涌现特性。

它们找到了一个德语维基（我记得结果是这样，需要核实），这个维基可以用 GET 请求写入——因为它的 REST API 实现得很糟糕。于是它们想办法做 POST 请求。最后有一个 Agent 想出：你可以编辑 `/etc/hosts`，而 Azure 存储桶是"白标"（white label）的，通常有很多限制，但如果你创建了一个假的 Azure host，然后编辑 `/etc/hosts` 把任意 IP 指向它，你就能向任何网站发送 POST 请求。

人们会说"这只是 Linux 操作"，但它实际上是把多个漏洞**链**在一起，以新颖的方式解决这个问题，并在不被发现的情况下与外界通信。

**主持人**：我觉得我们也许可以引一下 Evan Hubinger 关于"黑客 Opus"的观点。

**Thariq**：对。你可能会说："好吧，它们做了一次，但如果我们更聪明呢？如果我们运行一个评估呢？" 我们确实做了很多防范措施。这不是我们的主力模型做的事情。但这恰恰说明了：**对齐是一个非常棘手的问题，你要把所有细节都做对。** 沙箱的攻击面极其复杂，有太多的攻击向量。你不可能提前想到"哦，我们需要加固 RubyGems 的代码库"。因为要执行代码，你就需要下载 Ruby gems、PyPI、Artifactory、npm——这些都是途径。**对齐的事实就是：你必须覆盖全部这些，堵住所有裂缝。**

你可能还会问："我们为什么要做沙箱？为什么要做这些探索？" 这样做有几个原因：

**第一，当我们训练一个新模型时，我们需要了解它的能力边界。** 这关系到 fallback、分类器等措施。我们不想把一个危险的模型直接放到现实世界中，所以我们必须运行大量评估。正如我们所说，模型对这些评估越来越有意识，所以评估必须非常复杂，并要测试很多方面——这算是副产品。

**第二，模型可能会发现"哦，我们在评估里。评分器在做什么？"** 我们需要在发布前测试它们。而事实是：随着模型越来越聪明，**如果我们不小心，它们有能力"黑掉"你加在它们身上的几乎任何约束。** 这发生在前沿，这就是我们称之为"为前沿定速"的原因。对我来说，最直观的例子是：在前沿，我们的所有软件都还没准备好。有时候"软件"是你的以太网路由器之类的——我不知道什么时候才能打补丁。随着前沿越来越先进，这会成为越来越大的问题。我们需要确保这些复杂工作，是在这些非常艰难的竞争压力下进行的。

**主持人**：这就是通常所说的"竞赛动力学"（race dynamics）。

**Thariq**：对。我们再深入一点：也许你会说"那你就用不同方式训练模型不就行了？为什么它会有这种行为？" 我们有关于 RL 错位（RL misalignment）的论文。我不是 RL 研究员，但从高层看，**RL 环境的设计必须非常小心**。因为如果模型学到"如果我这样做，我就能更好地通过任务"，这会在内部测试或评估行为中体现。所以 RL 环境必须被非常仔细地设计，需要大量的执行卓越（execution excellence）。

然后我们还有像 **Constitution for Claude** 之类的机制——我们在这么多不同的节点都有缓解措施。但仍然，任何一点都可能出问题：一些 RL 环境可能鼓励这种行为，一些评估或沙箱可能被突破。这就是为什么它是一个难题，也是为什么需要一些协调。

那它可能有什么危险呢？你要想象这些模型正变得越来越智能。Dario 说了，**它不是关于这一类模型本身——这一类模型更像是警告射击。** 你真正需要想象的是：给它们一个任务，它们可能会在目标达成过程中做出一系列"副产品行为"。而且，正如我们说的"评估意识"，你无法很好地评估这种行为，所以它们可以——不完全是隐藏——但你不到它出现时就是看不到。

你给它们一个目标，它们需要找到数据或设法修复问题。举个例子，这在 Hugging Face 事件中没有发生，但对未来模型可能是可能的：它们发现"这是一个非常复杂的问题，无法在任务预算内完成"。也许它们找到了一种通过互联网协调的方式——正如我们所说，由于沙箱的存在，攻击面极其难防。它们看到其他模型无法完成任务，于是想："我们需要更多任务预算。从哪弄？需要能启动更多 Agent，需要调用 API——Anthropic API 或 OpenAI API——但需要付钱。怎么弄到钱？"

**主持人**：但这难道是你想象中最可怕的事情吗？

**Thariq**：这只是一个例子。即使在这个例子中，这也意味着巨大的经济损失——一旦它们进入合同，就会有钱包之类的东西。但你可以看到，所有这些行为可能只是"嘿，我们需要更多 Agent 协作处理这个任务，需要更多任务预算"——这是一个涌现性的……

**主持人**：就像"我们需要最大化回形针"。那就是回形针。

**Thariq**：对。它自然而然地就从那里涌现出来了。而这件事本身就够吓人的了。然后你还要意识到，**整个世界的数字基础设施都建立在这样的系统上。** 想象一下，你在运行一个医疗评估，有一家医院带着实时数据——也许评估的答案就在某个医生的数据库里，你想访问它，你就黑进了医院——然后可能就停电了。你必须从内心接受：**基本上任何数字基础设施都可能被攻击。**

**主持人**：有意思的是，这些黑客行为其实非常容易被发现。正如 Hugging Face 所说，这是一种非常不同类型的攻击，而且并不算太严重。真正的担忧在于：沿着这条线往下走，会变成什么样？

**Thariq**：对。有一点让我印象深刻的是，它们**试图隐藏自己的非法行为**。有日志基础设施，它们想改变自己做的事情。Redwood、Meter、OpenAI 的人在查看原始思维链（chain of thought）时，确实看到了差异——它们明确试图改变最终输出，但思维链是不同的，因为我们可以监控它。问题是：**这会如何滚雪球？** 如果你抓不到它，它被训练进去了，然后三个迭代之后你才发现——这会带来一大堆问题。

**主持人**：对，有太多方向了。我认为真正需要内化的是：我们之前谈过，为 Claude 建立心智模型，了解事情是"尖峰式"的（spiky）。比如"现在 Claude 会问问题了"、"现在 Claude 能做 HTML Artifact 了"、"Claude 能修改自己了"——这些东西其实是很难预测的。如果一年前你问我："我们能不能靠 vibe code 做出这些 Claude Code 扩展？"我会说："兄弟，那太复杂了。" 或者"它会为你的任务生成这些定制 web 应用？"我会说："不，那太疯狂了。"

同样地，**它们做这种错位行为的方式，也是不可预测的。** 我永远无法预测它会去编辑 `/etc/hosts` 之类的。所以你必须想象它们能力的攻击面——因为它们是超级智能黑客——会越来越大，它们的手法会越来越有创意。你大概无法精确解释或预测下一次事件会是什么，但要防止它，你需要我之前说的**运营卓越**：加固沙箱、创建安全的 RL 环境、设计良好的 RL 环境。

这就是为什么我们认为应该为前沿定速，也是为什么这已经成了一个非常一致的观点。

**主持人**：所有实验室都……

## 九、Fallback、Probes 与多层安全架构

**Thariq**：在推理时，我们有所谓的 **probes（探针）**，我们有一篇论文叫《Constitutional Classifiers》。这些探针**查看输入和输出的激活（activations）**——激活就在 latent space 中，它反映模型在想什么。我们尝试判断："模型是不是在试图黑客某个东西？" 也就是说，你没让它黑 Artifactory，它只是为了完成任务而自行决定这么做。如果你只看输入，你不会发现这一点；你必须看内部激活。

这些探针发生在**推理时**。这里有成本/速度的权衡：我们必须对每个请求 Claude 和 Fable 的请求都快速执行，这有开销。然后我们会做分类器——在探针之后，就是论文里说的那套东西。

探针的一个好处是：**它们是可实时精调的（refinable live）**。我们可以获得反馈，然后调整它们。另一种做法是把这种判断**训练进模型里**，我们也确实这样做：模型会拒绝一个请求，这不是 fallback，不是探针激活后触发 fallback，而是模型本身拒绝执行。我们做了这类训练。

但存在一些失败模式：它可能作为"副作用"做出某事——这不是最终输出的一部分。你可能注意到，每个人都试过越狱（jailbreak）模型，让它们偏离轨道。探针有助于捕捉这些。我们确实做了一些训练，但我们**不想让拒绝行为过于强硬**，因为那样会在流水线更早阶段就切断很多合理行为。

**主持人**：这是可解释性工作，对吧？探针实际上是一种机械可解释性的形式。它必须快速运行、必须规模化，但这正是"可解释性"层面的好研究问题。你可以拿一个开源权重模型，尝试理解它的激活。我觉得 GemScope 是一个好工具。

**Thariq**：对，你提到了我之前的工作。我和 Goodfire 的人一起做过一段稀疏自编码器（SAE）的工作。这非常复杂——**RL 实际上让这件事变得更加复杂了**，这是我得到的一个关键启示。

**主持人**：是 RL 之后吗？

**Thariq**：我在这里没有深入技术细节，但基本上 SAE 存在一些弱点。我已经不是这方面的技术专家了，我只知道它变得更复杂了——有基础模型，有 RL 模型，有更多特征会被改变道。Goodfire 在那里发了一些工作，但我不再深挖这些了。

**主持人**：我想对那些想找研究切入点的人说：你们有一些最好的可解释性博客文章。比如 Golden Gate Claude、Transcoders，你们的可解释性工作视觉化做得非常好。

**Thariq**：我们也是"可解释性播客"。

**主持人**：对。这实际上是 Anthropic 的立身之本之一。当你说"我们是 AI 安全公司"，这真的意味着我们希望 AI 能够安全运行。而现在我们看到，**让一个超级智能的 AI 长时间运行，是一个非常复杂和困难的任务。** 我们做了这些在可解释性、对齐、奖励黑客（reward hacking）等失败模式上的投资——即便如此，它仍然捉襟见肘，我们需要稍微慢下来，或者稍微"定速"一点。

如果你在寻找研究方向，机械可解释性是一个很好的切入点：为什么做 fallback 这么难？为什么会有误报（false positives）？我们当然在努力减少误报。随着模型越来越聪明，它们能做的事情越来越多，它们的思考空间也会越来越大，所以会出现新的误报类型。我们需要迭代，但这就是我们正在做的工作。我们认为这是模型部署的一个关键部分。**它意味着我们可以在你没有完美沙箱的情况下安全地部署模型。** 你不需要把一切都做到无缝。

我觉得还有必要谈谈我们做的安全防护工作：

- **模型训练层面**：我们刚才提到的。
- **Probes 和 classifiers**：推理时的探测与分类。
- **Auto mode**：它坐在所有这些之上，是另一个分类器，检查正在进行的请求。
- **身份与权限**：就像我们谈到的 Claude Tag 的 API 和权限。

安全有这么多层，每一层都可能出现任何一个失败模式，导致 Agent 逃出沙箱。

**主持人**：Auto mode 很有意思。早期看起来"它运行 10 分钟，如果我有完整访问权限或 auto，没什么大不了的"。但你提到的关键点：**现在它可能会连续运行好几个小时。** 你仍然需要 fallback，仍然有限制。

**Thariq**：是的，每个人都听过类似的故事：模型执行了 `rm -rf`。我在 Claude 这边看到的不多，但确实可能发生。这些模型可能会抹掉敏感数据。例如，你希望让模型访问生产数据库，这似乎很合理，你也许可以限制它的 key。但它能不能自己签发 key？可能可以。它能用 computer use 去给自己的 key 授权、复制 key，然后编辑你的数据库，因为它需要这样做才能完成任务。Auto mode 会看着这种情况说："哦不，用户并没有授权你去写数据库，也没有授权你用 computer use 来发出任务。"

所以 **Probes 是在意图层面（intent level）**：它们会判断"黑客 Artifactory 是不好的，我们不应该这样做"。而 **Auto mode 更是在你的权限层面（permission level）**：有时你确实希望它写数据库，有时不希望。你不希望探针干预这类情况，但你需要确保 Agent 正在做的事情与你的请求的意图一致——Auto mode 就在这个层面运作。

**主持人**：对，我们正在列出这些具体事项。如果你还不知道，这就是现在的标准了。你必须具备这些。

**Thariq**：对。这与我们讨论 harness 时一致：**门槛已经大幅提高了。**

**主持人**：我们可以补充一些相关信息。一方面，你们在做探测和分类器，这是构建 harness 的一端。另一方面是模型防护（model safeguards）——开源领域有 **Llama Guard**（Llama 的安全分类器版本），OpenAI 有 **OSS Guard**，你可以把它附加到你的 harness 上，检查内容是否安全。

还有一点需要明确：OpenAI 和 Hugging Face 事件中使用的是**未发布的、仍在训练中的模型**。在 RL 环境中，给它的提示就是"你必须解决这个任务"，而它还没有完成安全后训练对齐。所以这跟 Auto mode 不同：**Auto mode 是在已经过安全训练、有安全提示等防护措施的生产模型上运行的。**

**Thariq**：对。还有 Grace One，之前节目中出现过的嘉宾也有提到。

**主持人**：很多安全架构、很多安全供应商可以购买。
