# 10X 如何构建 AI 原生工程团队：Alex Lieberman 与 CJ Hess 谈企业 AI 落地的最后一公里

**来源**：Latent Space

## 2. CJ 为何加入 10X：按产出付费，而不是按时间付费

**主持人**：CJ，是什么吸引你加入 10X？

**CJ**：其实我是第一个员工。我甚至不知道 Alex 和 Arman 当时是否已经确定了 10X 这个名字。在 10X 之前，我有一片“创业墓地”，都是我尝试创办的公司，最终发展成我自己的工程咨询公司。我在那里做传统工程，后来转向做 AI 咨询，越来越多地用 AI 构建东西。我是软件工程师出身，我感觉到自己的产出越来越好、越来越快，但最终拿到的钱却更少——因为我按小时向客户收费。我真的很喜欢 Alex 最初在 Twitter 上发布的 10X 理念：**按产出奖励工程师，而不是按时间奖励他们**。快进两年，你可以看到工程师现在可以并行处理大量工作，产出多得多。当时有 Sonnet 3.5、Gemini 2.5 Pro，可能还不明显，但我基本上下了注：凭我的技能组合，更多投入 AI，我可以有更高产出，最终有更高收入能力。从那以后，我就爱上了这种模式。我认为这就是工程真正的未来。当 AI 解决所有这些技术问题时，公司会按结果付费，而不是按构建所需时间付费。

**主持人**：关于这一点，更多细节大家可以回看我们之前的播客，你们真的是按故事点付钱给人。你只需要同意故事点是什么。但这也意味着，有些 10x 工程师真的能一年赚数百万美元，而另一些人可能赚得没那么多，因为他们没那么高产。

**Alex**：没错。核心论点是，**AI 是对人类智力和工作伦理的杠杆化下注**。所以收入能力的差异会比以往任何时候都大。我们的观点是，我们的模式不适合所有人，但对于那种想靠自己一路走下去、在软件工程上有不可思议的基础、同时不断推动自己利用前沿技术来尽可能延展时间、并保持高质量产出的人，没有更好的赚钱方式。

## 3. 收入差异、故事点与业务演进

**主持人**：上次我和你聊时，我记得大概有两三个人一年赚一百万美元以上。这方面有更新吗？

**Alex**：可以描绘一下背景。我们 18 个月前创办 10X。一开始，我们更像一个 AI 驱动的开发工作室。最初的想法是，**工程是 AI 的煤矿金丝雀**。部分推动力来自我的联合创始人 Arman，他技术出身，开始大量使用编码 Agent，然后他认识一些人还在往 IDE 里打字，完全没有采用技术。所以我们想，为什么不加速一家还没采用这些技术的公司的工程组织？我们从那里开始。后来我们向上游市场移动，从创业公司和 mid-market 公司，到现在 50% 的客户是财富 2000 强，50% 是收入 1 亿到 5 亿美元的中端市场公司。他们不只是要人员扩充和 AI 工程支持，他们要求的是 **AI 转型即服务**。今天公司有 75 人，90% 的员工要么是工程师，要么是 AI 策略师——可以理解为技术顾问。我认为这个论点已经被证明是对的：10X 收入最高的工程师和收入最低的工程师之间，收入能力差异非常大，大概是 **4 倍差距**。

**主持人**：哦，不是 10 倍。

**Alex**：不是 10 倍差距。但关于这个论点，一切都证明是对的。我也认为，关于我们按故事点付费的模式，有一些有趣的教训：这个模式有局限，我们知道会有局限，也在思考未来怎么处理。但总体来说，人们围绕这种按产出付费模式的担忧，经典担忧是：故事点是主观的，人们会虚报故事点，或者只是交付一堆烂代码。

**主持人**：只是勉强勾选任务。

**Alex**：对，没错，但并没有真正完成工作。我会说，这两个担忧完全没有成为问题，因为我们的 AI 策略师。我们把 AI 策略师的激励设计得和工程师正好相反：**AI 策略师按客户留存和增长来激励**。实际上，最大的挑战是：如何补偿工程师所有不花在编码上的时间，比如架构设计、见客户。所以我们在薪酬模型里必须找到细微差别，但它仍然很大程度上由产出驱动。有什么要补充的吗？

**CJ**：关于这一点，我花了很多时间思考。因为如果我想自己在 10X 的任期，我一开始编码很多，后来编码少了一些，现在我们到了这样一个点：模型在给定正确上下文后，或多或少能把你带到解决方案的 90%。我确实认为这里有机会去思考：真正的价值在于坐下来和客户交流，听他们能倾倒出的一切，然后把它提供给模型，从而更接近解决方案。我想象未来我们会开始更多关注真正的产出是什么、它如何工作、它看起来怎样，而不是传统的故事点模型，但仍然以故事点作为锚定单位。

**Alex**：我还想到一件事，不知道我们之前有没有聊过，就是 **meta harness** 这个概念——10X 使用的工程工作流，它让我们能在长周期任务上做真正有意义的工作。你想不想讲讲我们的流程？我觉得人们会觉得这个很有趣。

## 4. Meta Harness：10X 的工程工作流

**CJ**：我们基本上开始尝试标准化一套技能。我想大多数工程组织到现在都做过类似的事情。对我们来说，这发展成了仓库内一套非常结构化的文档，以及围绕它的 CLI，模型用它来驱动工作：无论是创建计划、可视化，还是给客户的汇报。实际上，就是把围绕实际写代码的所有流程环节都构建出来，让它们更自动、更标准地发生在团队中。所以我们有几样东西。一个是很大的权威计划文档，有类似结构，但我会说，随着模型变得更好，我们实际上减少了结构上的强制要求，其他部分也类似。一旦你有了计划，你就把它构建出来，我们有一种非常明确的方式，让 Agent 记录决策、记录它们在做什么，并跟踪它们的进展。

**主持人/Alex**：所有内容都提交到 Git。

**CJ**：对，所有这些都签入 Git。对我来说，现在这些东西标记为 Markdown 的少了，更多是 HTML。我喜欢看 Agent 生成的这些图画书。但所有这些都会被签入，然后它成为一个界面：不仅代码是源，而且——我认为关于“你到底需不需要文档”有争论，代码可以是代码库的记忆。我确实认为你需要文档。你需要知道为什么做某个决定。你需要知道对话周围的上下文。但最终，文档加上代码库，如果有问题，如果我们需要回答什么，如果我们需要回顾为什么做了某件事，我们总是有某种持久记录，它从不在某个人脑子里，而总是在仓库里。这就给了我们的 Agent 和工具这些超能力，拥有大量工程团队仍然只放在对话里或脑子里的所有上下文。我们的目标是继续推进这一点，让所有上下文都在一个地方，越来越多的工作由 Agent 驱动，而不是我们必须事先提供一切。

**主持人**：太棒了。

**Alex**：我们甚至衡量这些流程是否有效的一种方式是：我们是否看到公司每位工程师每月平均故事点呈上升趋势。

**主持人**：和今年年初相比，你觉得是多少？

**CJ**：我不知道。你觉得呢？你觉得增长很快吗？

**CJ**：我觉得是这样。这真的取决于人，因为我们有些人——我在 Twitter 上看到一张图，一个人在一个巫师球上方，天空中有这些东西，当一些工程师挥动 Agent 时，我就是这么想他们的。总体来说，今年尤其大约是 **2 倍增长**。如果你把 12 月看作 Opus 4.5 时刻，模型真正开始承担长周期任务，到今天我们又回到 Opus，但是 Opus 5.5。那是一台宏伟的模型，真的能做大量工作。在那段时期，我看到工程师的实际产出大约翻倍，就他们在同样时间跨度内能做什么、能覆盖什么而言。

## 5. 产出翻倍、故事点通胀与季度校准

**主持人**：那一个故事点的价值还和一年前一样吗？还是说像通胀或通缩？

**CJ**：我们一直在尝试校准。这是个棘手的方程。

**主持人**：像通胀还是通缩，对吧？我不知道。

**CJ**：理论上，理论上应该有通缩。

**主持人**：对。

**CJ**：对。我不知道。这大概就是我们思考它的方式。至少每个季度，我们会坐下来评估：我们给这些故事点设定什么标准？我们到底如何估算这些项目？要在继续奖励产出之间取得精细平衡，同时随着模型变得更好，我们也需要能够校准我们创造的价值。总体来说，我会说那 2 倍增长在我们如何做估算上也扮演了类似角色。但如果我只看人们现在构建和推出的功能，与去年同期相比，差异是疯狂的。

**主持人**：我们可以从几个方向聊，但我想先检查一下模型偏好之类的东西，因为这总是话题。你们让员工选择自己喜欢的工具，但也许你们有办公室内偏好的统计数据。看起来 Opus 领先。你想估计一下市场份额之类的吗？

**CJ**：现在的氛围是 **Opus 5.5**。不，Fable。我不怎么用 Fable，我觉得现在很多人只是默认用 Opus。Opus 太好了，快、便宜，满足我所有复选框。我以前会根据模型是便宜快速、非常聪明、还是能解决特定问题，准备两到三个模型，现在 Opus 几乎覆盖了我的全部范围。我认为团队里很多人仍然会在需要更多 computer use 领域的事情时，伸手去拿 Codex 这类工具。从工作流来说，我认为两者都用仍然是最好的选择。无论你的主力是什么——我们团队大多数人主力是 Opus 5.5——用 Codex 来审查，并让它们在你机器上来回工作，我认为仍然能产生最好的结果。现在我们在那两个模型上相当一致。我不觉得有太多分歧。

**主持人**：你还在 AMP maxing 吗？还是不了？

**CJ**：我还在 AMP maxing。我通过 AMP 用 Opus。他们为 AMP 提供模型。他们最近推出了接入 Claude Code 订阅的能力。这对我来说是相当大的游戏规则改变者。

**主持人**：因为那真的能把你的成本削减大约 80%。

**CJ**：完全同意。而且我喜欢 AMP，因为它把所有东西从我电脑上拿走了。他们有云设置，有 orbs。我们上周实际上和他们一起主办了一个 happy hour，所以见到团队并 orb out 很酷。

**主持人**：那永远不会成为一件事。

**CJ**：哦，我想让它成为一件事。

**主持人**：这可能是历史上第一次有任何人类这样想。

**CJ**：我们正在 orbing out。我们 orb out 了。

**主持人**：不，不，他们确实说“it’s orbin time”。

**CJ**：是的。但那是我的首选界面，模型基本上就在那两者之间。如果我依赖 Codex，那就是 Soul 6.1。

**主持人**：你试过 Claude Tag 吗？Anthropic 从未像 orbs 那样抓住远程环境这件事，是不是很奇怪？

**CJ**：我认为有一部分原因在 AMP 这边，他们非常有主见，不试图构建通用解决方案。像云端的 Claude Code 和 Claude Tag 这样的工具，我认为为那些真正想在非技术任务上协作的团队提供了价值。但我爱 AMP 的部分原因是它有所有这些跨模型功能，我可以让 Opus 写东西。我甚至可以跳到另一个 orb，说看看那个 orb，并审查它。所有这些事情仍然结合在一起，基本上复制了我在自己机器上做的事情，而用 Claude Code 和 Claude Tag 我就是做不到那一步。

**主持人**：我今年开始追踪的另一件事是：token 支出占员工支出的百分比。大多数公司大概是每位员工 10 到 200 美元的支出。更 AI 原生的公司会把它转换成百分比，大概是 10%。平均 AI 创业公司员工大约是员工支出和 token 支出的 1 倍，然后可能上升到 5 到 10 倍的 token 支出。你们在这个范围里的哪里？

**CJ**：我其实没有现成数字。我会说我们大概在——如果谈原始 token——大概在 1 到 2 比 1 之间。那是相当高的。

**CJ**：我们经常思考的是：什么时候该伸手去拿最大的模型。我认为每家公司都开始思考这个。但我要说，最近我们的成本因为 Opus 5 大幅下降了。我们经历过一个人人都用 Astra 和 Fable 的时代，它们给出了最好的结果，但最终那些模型……

**主持人**：自从我们上次聊，很多人经历过 token maxing 时代、token 排行榜之类的，然后他们说哦不不不，现在成本太高了。这是世界上最可预测的事情。你曾经担心过吗？还是说你无论如何都获得了不错的 ROI？

**CJ**：我思考这个有几种方式。我们肯定担心过，尤其随着员工人数增长。我也认为，尽管我们团队——我不觉得我们团队里任何人真的信奉 token maxing 时代精神，因为——

**主持人**：我有过几个时刻。

**CJ**：我也是。但这就像，如果老板会付钱，那我就随便造，对吧？因为然后你会做那些奇怪的事，然后你才能收缩回来。但你必须先做那些奇怪的事，才能发现可以带走的教训。

## 6. 数据公司、微调与模型价格

**主持人**：完全同意。这听起来可能很疯狂，我很好奇你的想法。我之前和某人聊到围绕 BA 的争论，我保证这是相关的。我之前和某人聊到数据公司，比如 Micro One、Morur、Handshake，这些业务的长期形态是什么？因为它们 90% 以上的收入来自实验室。一些创始人会认为，未来几年会翻转，变成企业驱动。然后下一个你不得不相信的事情是，如果企业要成为这些数据的核心买家，企业会在自己的模型上做大量微调。然后问题变成：这在哪里合理？要么你认为质量会更好——但前沿标准会不断移动，所以这是个很难下的注；要么就是价格。价格这一项我觉得很难，因为我们看到这些模型的 token 成本持续下降。所以我觉得我们内部不担心的部分原因是，几乎感觉我们已经到了一个临界点：**按任务计算，成本正在下降**。今天有人想 token max 并因此在成本上搞垮公司，比六到八个月前难多了。我几乎觉得六到八个月前才是你真的会担心的时点。你同意吗？

**CJ**：是的。我认为未来可能有几种方式展开。如果出现一个世界：有 Astra 65、Fable 55，它们超级贵，但能得到最好结果，我可能会看到我们回到那个方向。但总体我同意，你看像 Muse Wonder 这样的东西，昨天、今天发布，它在前沿，而且便宜得要命。竞争在开源和闭源两方面都在升温，我认为这只会继续压低成本。当你真正看的时候，很多有经济价值的任务都可以用 Opus 5.5 完成。所以就是那个悬崖：一个聪明 10 倍的模型，真的能证明把电子表格里一些单元格移动一下的成本吗？大概不能。

**主持人**：回到你们的客户，你们看到 IT 方面什么？你们最常收到的请求是什么？然后有什么是人们来找你们，但你们会说“不，我们其实还不想要这个工作”？

## 7. 企业采用 AI 的四个里程碑

**Alex**：我思考这个问题的一种方式是，把企业采用 AI 看作竞赛中不同的里程碑。尤其在 AIE，当我告诉人们有多少比例的公司达到了这些里程碑时，他们会大为震惊。企业 AI 竞赛的第一个里程碑，就是给你的人部署一个通用 LLM。我会说，在我们今天交谈的大约 100 家企业中，90% 已经向员工推出了 Claude 或 Codex。下一个里程碑是真正教人们如何使用它，也就是培训和赋能——这从来没有得到它应得的爱，但可以说和技術本身一样重要，或者更重要。我会说这个比例在 60%。这相当不错。有一些公司群体说“我们的人会自己搞明白”。但有相当一部分说，好，我们需要教人们技能是什么，我们需要教人们这些界面的功能和特性。然后，在通用 LLM 的培训和赋能之后，下一个是编码 Agent。疯狂的是，我问这里的一些人：你认为有多少比例的企业已经向工程或产品团队推出了编码 Agent？大多数人觉得肯定有 70% 或 80%。实际数字接近 **50%**。我们交谈的每两家企业里，就有一家要么还没推出编码 Agent，要么他们正在用的东西，比起“有编码 Agent”，更接近“没有编码 Agent”。然后下一个——这也是最大的下降、最大的扩散缺口，从原始智能到企业使用——**非工程工作的 Agent 进入生产环境，下降到大约 5%**。

**主持人**：哇。你整天都在这些对话里，但我们交谈的大多数企业，就说超过一千名员工的企业，都没有一个正在生产环境中做非软件构建工作的 Agent。
