# 工业革命与文艺复兴：与 Thariq Shihipar 对谈 AI 时代的软件构建、反馈回路与人类角色

## 开场预告

我甚至并不真的觉得自己被智能所限制，也许更受限于野心，也许是一件更大的事。AI 既是工业革命也是文艺复兴，你知道吗？我们是否希望模型完全无监督地自我改进？我还不清楚这是否会是最好的选择。

（音乐）

## 主持人开场与本期导览

**主持人：** 大家好，我们又回来了。这次带来的是我们近期在 AI E Code 峰会上录制的一系列节目，并将在接下来一周左右陆续发布。今天我们请回了一位大家非常喜欢的嘉宾——Thariq Shihipar（原文中也出现了 Tarek Shebar 和 Darak Shapar 等不同转写，后文统一使用 Thariq Shihipar）。他此前在 Anthropic 工作，但今天他宣布将加入 OpenAI。我们将稍微深入探讨他的思考，以及他在构建智能体方面感到着迷的地方。他在 AI E Code 上做了闭幕演讲，反响非常好，我特别喜欢他提出的“革命与文艺复兴”的整体框架。今年最热门的流行语之一是“软件工厂”。有趣的是，AI E 的很多信息传达的是：我们可能过早地冲向了工厂；即使我们拥有了工厂，它也会释放出生产力提升的另一面——也就是文艺复兴。革命让软件变得更便宜、更可靠、更容易大规模生产，但也会产生大量“垃圾内容”；而文艺复兴则让构建个人化的东西变得负担得起，提升你的艺术水平，花时间在人类参与的循环中打磨它的感觉。因此，革命和文艺复兴可以发生在同一个项目中，这正是他在演讲中谈到的，我们在播客中还会更深入探讨。他传递的核心信息是：你希望重新获得反馈回路，对吧？我们花了大量时间把人类从智能体回路中移出，为了实现自主、黑暗工厂等目标。但他认为，为了拥有更多品味，你实际上应该把部分人类反馈回路放进去，以便轻松构建临时工具来尝试各种东西。一旦你试过了，你就会知道，因为人类真的试过了。我认为很多垃圾内容之所以产生，就是因为人类没有真正地进行“吃狗粮”式的充分测试。所以他展示了一个“/human”技巧。这也来源于很多直觉：他构建过一些技术上完美的东西，比如模型完成了一个完美的工作，一个完美平衡的游戏，一个漂亮的 Mac OS Dock 应用，但之后你并不使用它。为什么不用呢？因为你在构建过程中从未使用过它。这确实来自大量内省。我认为这也部分暗示了他接下来计划做什么。当他宣布转到 OpenAI 时，T-Bone 和 Andrew 都说基本上到了重新发明 Codex 的时候了。所以他的意思还有些开放。演讲中有几张幻灯片，我认为透露出一些想法。这只是我个人的观点，不代表他。但总体而言，我认为这是一次非常有趣的对话，很高兴今天与大家分享。最后提醒一下，本期节目由 Atlassian 的 Jira 赞助。你可以管理你的智能体集群并保留记录。每个部分、每个决策、每个 PR 都集中在一个地方可见。团队和智能体共享上下文。了解更多信息请访问 jira.dev。感谢 Atlassian 支持本播客。

### 开场与主题：过去一年的反思

**主持人：** 好的，我们现在请到了我们的好朋友、失业的《魔兽世界》职业玩家 Darak Shapar（即 Thariq Shihipar）。欢迎。

**嘉宾：** 谢谢邀请。（笑）

**主持人：** 你是我们的闭幕演讲嘉宾。没有压力，但要谈什么？

**嘉宾：** 我在谈过去一年我错在哪里。

**主持人：** 哦。

**嘉宾：** 我想有很多事我做对了。我觉得我是最早想到 Claude 能用代码制作视频的人之一，那大概是去年。同时我也是最早真正讨论 HTML 及其类似东西的人之一。

**主持人：** “HTML 的不合理有效性”。

**嘉宾：** 对，对。当你第一次跟我聊这个时，我想：这有点像最大化 token 的方式吧？但实际上，是的，它是丰富的输出。

**嘉宾：** 我认为，那些你看到模型做出一次聪明的事，然后觉得“哦，一年后它就能真正做到了”的时刻，有些现在就能看到，我们可以稍后讨论。但我一直擅长发现那些，不过在某些情况下我也错了。比如，我曾经非常认同“bash 就是一切”的观点，你明白吗？就是只需要命令行界面。

**主持人：** CLI 浪潮。

**嘉宾：** 对，对。一切都是，不再需要 MCP，只有 CLI。你甚至不需要工具，你只有 CLI。另外还有“React 就是一切”这种观点，认为 React 会成为终极语言，因为模型只会写 React。

**主持人：** 我没看到你写过这个，那是不对的。

**嘉宾：** 我没写过，但我想过。

**主持人：** 你想过。

**嘉宾：** 对。但我认为基本上你看到的是：模型变得越来越好，但也变得越来越宽泛。当它们能完成诸如用 React 做前端，并且处于能力边缘时，它们只能用一种方式。但当能力提升后，你现在可以让它使用计算机、使用 Figma，在 Figma 里画出前端，它也会做得一样好。因此，这让我很惊讶：它更像是按照我们的工作方式来工作，而不是模型需要的那种特定方式。我认为我错的地方正是我最感兴趣的地方。我错在以为模型只会以一种方式做事，并且像一种奇怪的异类，你懂吗？就像现在我们全都用 bash 写东西，或者用 XML 什么的。那是错的。实际上，模型变得更通用后，就能在你想要的任何格式下工作，包括在 Figma 里绘图。

**主持人：** 包括在 Figma 里绘图。好的。

**嘉宾：** 对，对。我觉得这种下游效应是你可以理解模型在做什么，你懂吗？你可以与它们协作。我不认为未来必须是“模型在循环中创造出不可维护的烂摊子”。

**主持人：** 你给听众的闭幕演讲的主要要点是什么？除了“一些预测错了”之外。

**嘉宾：** 我觉得要点是你可以更多地设计构建软件的体验。比如我现在正在构建我的游戏。

**主持人：** Avatar。

**嘉宾：** 呃，是的，我是说我们不想说任何……不侵犯版权的 Avatar。（笑）

**嘉宾：** 我们做了泛化处理。但我觉得提示的一个困难是，我实际上不知道游戏中会发生的一切，因为我描述一些东西后，模型会做出一些合理的假设。然后当我尝试玩游戏时，我会想：“等等，我都不知道这个角色在这种情况下会做这种事。”你懂吗？我发现这非常令人迷失，我不喜欢这种 vibe coding 的方式。但后来我想：等一下，我可以为自己解决这个问题。所以我没有直接那样做，而是编写了一种脚本语言，它是一个文件夹。像一个“人类文件夹”，我就叫它“/human”。然后那里有一种脚本语言，这个文件夹的 linting 规则非常不同。比如注释密度很高，没有单字符变量名，还有一堆东西来让它感觉像规范，比如行长有限制等。目标是让每个文件读起来像规格说明，但它们是真实的代码。这样我可以玩它、调整它、理解发生了什么。它不是一种附属产物，不是文档之类，而是真正的代码。这就是我喜欢的工作方式：让模型制作底层原语，然后我可以玩一下，比如“这个角色如果同时发射三个火球会怎样？”

### 工业革命与文艺复兴

**主持人：** 我觉得这很有趣。很多模型非常擅长给出默认结果，对吧？大多数生成的网站看起来都一样。你让它做一个游戏，它默认会加入“按住 Shift 可以加速”之类的。默认值很好，但这也是人们意识到你可以做更多事情的好方式，对吧？

**嘉宾：** 对，对。我认为起点是：软件，AI 既是工业革命也是文艺复兴，你知道吗？

**主持人：** 哦。

**嘉宾：** 工业革命让你想到效率、可靠性、标准质量水平。而文艺复兴让你想到每一点边际质量提升都很有用、很有价值，对吧？所以我们谈论很多关于软件工厂和工业化，也谈论文艺复兴。比如 Jason 的演讲等内容。但我对此非常感兴趣。我认为 2026 年是软件工厂和软件工业化的一年。而接下来一年将更多是软件的文艺复兴。

**主持人：** 我可以说一下吗？当你说文艺复兴，我想到意大利文艺复兴，那种艺术文艺复兴。但你把它描述为增量的质量改进。这听起来不太像文艺复兴。

**嘉宾：** 不，不。我是说，（笑）比如你有一个游戏，你会问：这个游戏的控制方案是什么？你可以接受 Claude 做的默认方案，也可以迭代，它会变得更好。人们会欣赏这种质量提升，这是一种将软件视为艺术或内容的方式。另一方面，你可以用它来创造全新语言、全新的编写软件体验、全新的原语等等。这些也会非常被重视。

**主持人：** 我喜欢你要传达的信息。一边是你可以用 Rust 重写任何东西，另一边你可以把东西推到额外的边际效用，无论多么小众，都可以添加小功能。

**嘉宾：** 对，对。人们会想要真正高质量的软件。

**主持人：** 你能在同一个项目中同时做到这两者吗？还是它们是 AI 的不同应用？

**嘉宾：** 我认为可以。比如我最终在游戏中会尝试：一旦引擎做好，我会用 WebAssembly 写引擎。所以引擎将在 WebAssembly 中运行，脚本语言将是更轻的一层，通过钩子接入。然后所有平衡调整可能会自动完成，你懂吗？我会得到游戏中不平衡的报告，通过自动化测试和实际游戏进行。也许 Claude 会提出一些建议，但我也会有自己的观点。我认为一个好的描述方式是：完美平衡的游戏很无聊。

**主持人：** 是的。

**嘉宾：** 我认为这是真的。

**主持人：** 什么？

**嘉宾：** 我认为这是真的。

**主持人：** 比如剪刀石头布就是一个完美平衡的游戏。

**嘉宾：** 你想要一些挑战，一些难度，你想继续玩下去。

**主持人：** 不不不，等等。但如果它不平衡，比如《英雄联盟》是不平衡的，有些角色被认为很弱。

**嘉宾：** 是的。

**主持人：** 你说你认为那很有意思？

**嘉宾：** 是的。你可以专精一个弱势角色并玩得出色。

**主持人：** 那太……

**嘉宾：** 没有角色会永远弱。

**主持人：** 你……

**嘉宾：** 他们会有……

**主持人：** 对，有某种……

**嘉宾：** 你想要高方差，对吧？弱但高方差。

**主持人：** 你想弄清楚游戏的元（meta）。

**嘉宾：** 对。

**主持人：** 有趣。

**嘉宾：** 必须存在真正的 alpha。

**主持人：** 弱势角色对这种用例更好。

**嘉宾：** 呃，你还没试过这个吧？你只是在考虑这是下一步。

**主持人：** 我还没告诉你，我已经告诉他我在做一个卡牌游戏。

**嘉宾：** 好的，酷。

**主持人：** 像桌游、卡牌游戏，叫“Frontier Lab”。

**嘉宾：** 好的。

**主持人：** 你扮演一个 Frontier Lab。

**嘉宾：** 当然。

**主持人：** 然后你拥有各种资源和技术树可以做研究。

**嘉宾：** 对。

**主持人：** 我原打算把它做成类似《文明》的游戏。你从建立文明开始，与其他文明竞争，有多种胜利条件。你可以获得经济胜利，赚最多的钱；科学胜利，达到 AGI；文化胜利，让普通人喜欢 AI，那是最难的。（笑）

**主持人：** 我忘了第四个。总之，我构建了整套东西，然后让 Claude 对它进行模拟。结果显示你总是想要经济胜利。所以我认为，从我的探索来看——我基本上运行了成千上万场模拟游戏——现在我想：好吧，这是不平衡的，你能修复它吗？它尝试修复，但做得非常糟糕。所以我认为这是一个评估：你是否理解在数千回合中运行的整体系统，并且能否调整游戏平衡，使得至少在某些情况下，通常失败的策略能获胜。

**嘉宾：** 我觉得这也是游戏设计问题。游戏设计中调整的方法之一是增加方差。比如 rogue-like 游戏就是一个很好的例子：在这场游戏中规则略有不同，比如军队生成速度翻倍，或者你……这不完全是难度等级，而是比如说，你有一个文明，每次升级时你会从牌组中获得三个随机选项。你选择什么会改变你文明偏好的结果。这样的游戏方差更大，可能有很多“破坏性”组合，如果选择正确的组合你的文明会非常 OP，但你不可能每局都这样做，这就让它有趣。

### 当前状态、决策模型与 RL 讨论

**主持人：** 你对当前的状况有什么看法？有什么想评论的？出现了这么多决策模型、基于权重的编程，什么让你忙碌和兴奋？

**嘉宾：** 好的，几点。首先，我不是“永久底层阶级”的信徒。我觉得公开模型很棒。我目前用的是 200 美元/月的计划，我还有 Codex 和 Claude 两个模型，它们各自擅长不同的事。我并不受 token 限制，一点也不受 token 限制。我甚至不觉得自己被智能所限，也许更受限于野心，也许如果我有一个更大的目标的话。但我确实受限于与模型的工作方式。这就是我为什么做了那个脚本语言的东西，因为我现在非常讨厌构建这个游戏的体验。尽管很酷，但我完全不知道发生了什么。我认为在这方向还有很多进步空间。我觉得与 AI 一起工作的体验可以变化很大。我认为，是的，成为聪明的通才，或者说，你不再需要知道领域特定的事情。比如我了解可解释性和 RL 的概念，但我不懂 PyTorch，不懂 CUDA，对神经网络架构了解也不多。但我可以尝试一些 RL 和可解释性实验，这很酷，因为我可以和模型对话。我认为 Astro 在这方面很擅长，比如：“嘿，我们能不能拿 Kuen，修改它，让它认为埃菲尔铁塔在罗马？”你知道会发生什么、下游变化是什么？这确实是个很好的时机去尝试新类型的事情。

**主持人：** 在你不具备深厚专业知识的领域更多地动手鼓捣？

**嘉宾：** 对，有点。我有一个 RL 想法，正在做，可能非常天真，但我也觉得：哇，我不认为有人以这种方式做 RL。所以我可以去尝试。它很可能是错的，但我认为让更多天真的人在某种能力水平上尝试事情对人是有好处的。

**主持人：** 酷。关于 RL，我思考的一件事是探索的目标函数、数据集，或者我们还想做什么。我认为除了 RLCD 之外，最后的大跳跃是什么？因为天知道那是什么。（笑）是不是 DKO？就是那个摆脱……直接偏好优化的 DPO？

**嘉宾：** Deep C one？Dr. DPO DPO？

**主持人：** 对，比如群体偏好也是一个好方法。但除此之外，很难说目标是什么、可能的空间是什么。我有一个建议，挺酷的：人们其实还没有真正做过“图灵测试 RL”，就是“这听起来像不像人类”和“你是否偏好这个输出”是两个不同的东西。

**嘉宾：** 嗯。

**主持人：** 对。

**嘉宾：** 是的，你是这个意思。

**主持人：** 然后是 RLVR，更多是可验证数学。但我觉得一切都在于选择正确的目标函数。

**嘉宾：** 是的。

**主持人：** 最新的是 RLCD，人们可以猜测它是什么，因为没有论文，所以你可以随便猜。（笑）

**嘉宾：** 对。

**主持人：** 你可以随便猜。（笑）

**嘉宾：** 是的。回到其他很酷的事情，我觉得决策模型非常酷。我认为目前的框架没有充分利用决策模型。通常当我开始一个新项目时，我会说：“请研究一下决策模型是什么，并在 Jev 或类似工具上写文档，这是我的 Jev API key”之类的。

**主持人：** 从模型蒸馏？对。

**嘉宾：** 不，不是蒸馏，我只是想让他们知道它可以使用这个类。

**主持人：** 这太新了，模型还无法自己使用，对吧？即使你明确告诉它，它可能也会做，但不知道具体怎么做。

**嘉宾：** 让它使用决策模型，它可能会说“什么是决策模型？”然后可能自己训练一个小分类器之类的。（笑）但我觉得在决策模型方面有很多很酷的 UX 和……

**主持人：** 你有没有用决策模型构建过什么例子？

**嘉宾：** 是的。

**主持人：** 或者，重新提示一下：是什么令人兴奋？是速度、延迟，还是别的？是置信度？全部？

**嘉宾：** 对。我认为一个例子是，假设你在为一个游戏编写 AI。一种方式是：从全部硬编码到全部推理。一方面你可以让 AI 完全硬编码，另一方面每个回合都是一个工具调用循环。你需要一个非常快的推理循环。决策模型介于两者之间。你可以预先写出 AI 的行为，但也可以在任何时刻评估游戏状态，然后说：“基于这个游戏状态，你想做什么？”当用户有很多不可预测的表达方式时尤其有趣。比如也许你可以输入，或者可做的事空间很大，难以用普通代码预测。我认为一个我现在会尝试的好例子是主要基于决策模型的支持机器人。因为支持机器人本质上就是一棵棵事情发生的树。它可以在需要时选择推理，从而兼顾两者优点。

**主持人：** 我认为问题在于你到底需要多少智能？

**嘉宾：** 是的。

**主持人：** 因为显然决策模型没有思考、没有推理，但你需要某种智能来理解你被问到什么，才能正确路由。

**嘉宾：** 对。

**主持人：** 这是我个人为 TypeSafe 的做法辩护的地方：他们不叫决策模型，而是叫“系统一模型”。这只是很细微的差别，但有时候你想要一个聪明的模型来做决策。
