## 开篇引入

在软件世界的集体意识中，GitHub 常常被视作一个“理所当然存在”的背景板——它就在那里，默默地承载着每一次 `git push`，每一次 Pull Request，每一次开源贡献。但很少有人真正意识到，这个平台正在经历一场比它过去十五年里任何一次转型都更深刻的蜕变。

当我们谈论 AI 编码代理、谈论 Copilot、谈论“软件开发的未来”时，有一个核心事实常常被忽略：**GitHub 本身，就是这场变革的主战场和实验室。** 它是一个拥有 2.25 亿开发者的社交网络，一个每秒都在吸纳新成员的全球性基础设施，一个正在同时进行“迁移到 Azure”“重构为 AI 原生平台”“应对代理驱动开发浪潮”三重转型的巨型系统。

Latent Space 的这次访谈，邀请到了微软 CoreAI 执行副总裁 Jay Parikh——一个在基础设施、安全和社交网络领域都留下过深刻足迹的工程领袖。他曾是 Facebook 的工程主管，曾担任 Lacework 的 CEO，也曾是 Ning 和 Akamai 的工程副总裁。现在，他站在 GitHub 的驾驶舱里，试图回答一个所有人都在追问的问题：**当软件开始由代理编写，代码的载体、协作的方式、安全的边界、成本的逻辑，全部要重新定义时，一个承载着全球开发者协作的平台，该如何进化？**

这不仅仅是一次关于产品更新的对话。它是一次关于“软件工程哲学正在发生怎样根本性转变”的深度审视。

## 详细内容

### 一个数字背后的平台巨变：每秒一个开发者意味着什么？

**核心观点**
GitHub 的开发者规模已经达到 2.25 亿人，并且连续第二年实现了“每秒新增一个开发者”的增长速度，这背后折射出的不仅是平台的吸引力，更是一个根本性的社区性质转变。

**深度阐述**
访谈的开场就抛出了一组令人眩晕的数字。Latent Space 的主持人提到，他在准备问题时特意去查了“一年有多少秒”，因为这个增长速度的表述方式太过震撼——**每秒都有一个新开发者加入 GitHub，这意味着一年新增 3150 万开发者。** [访谈开场]

Jay Parikh 确认并扩展了这组数据：**“2.25 亿开发者遍布全球每一个国家。”** 他补充道，去年的 Octoverse 报告中已经记录了“每秒新增一个开发者”这一事实，而今年是**连续第二年**保持这样的增长速度。 [访谈开场-规模数据]

但真正的冲击力来自另一组数据。Parikh 在 GitHub Universe 的主题演讲中公布了平台的年度运营数据：

- **179 亿次代码推送**
- **343 亿次提交**
- **13 亿个 Pull Request**
- 开源社区的贡献量比去年增长了 **2.5 倍**，达到了 **25 亿次贡献** [访谈开场-核心数据]

对于任何一位工程师来说，这些数字背后意味着什么？主持人给出了一个精准的解读：**“这是数据库写入、这是文件写入、这是元数据编译。”** 这些数字不是冰冷的统计，而是全球开发者每一天的实际工作流在基础设施层面产生的真实负载。 [访谈开场]

**视觉/结构信息描述**：Jay Parikh 在 GitHub Universe 主题演讲中展示了平台规模的增长图表。这些图表不仅展示了开发者数量的增长曲线，还呈现了代码推送、提交、Pull Request 和开源贡献等多个维度的指数级增长趋势。主持人对这些图表印象深刻，特别指出“人们期望 GitHub 永远正常工作，但他们看不到这些幕后数字”。

**个人感受**
主持人回忆了一个非常个人化的感慨：**“我记得当年 8000 万开发者对 GitHub 来说就已经是一件大事了。”** 这个对比突显了平台在短短几年内的惊人扩张。而 Jay Parikh 在描述这些数字时，语气中带着一种工程领导者特有的冷静和务实的自豪感。对他而言，这些数字不是营销素材，而是每一天都要面对的真实工程挑战——毕竟，你要为一个每秒钟都在增长、遍布全球每一个国家的平台，提供“永远在线”的基础设施保证。 [访谈开场]

**延伸思考**
每秒一个开发者的增长速度，在人类历史上没有任何一个社交平台或开发工具曾经达到过。Facebook 在其增长巅峰期的年增长率约为 2-3 亿用户，但那是一个面向所有人群的消费级产品。而 GitHub 是一个面向“构建者”的专业平台，它的增长意味着**全球软件开发能力的民主化进程正在加速**。当一个平台以这种速度扩张时，它的用户构成、使用模式、以及平台本身需要提供的抽象层级，都在发生质的改变。这不再是“专业工程师的代码托管平台”，而正在变成“每一个有想法的人都可以参与构建的地方”。这个转变的深层含义，在后续的对话中被反复触及。

**精华收获**
GitHub 的增长不是线性扩张，而是一种**结构性转变的信号**。当一个新的开发者每一秒都在加入，平台面对的就不再是“如何服务好专业开发者”的问题，而是“如何让不同技能水平、不同使用意图的人都能在这个平台上创造价值”的问题。

### 从代码社交网络到 AI 协作平台：GitHub 的用户边界正在消融

**核心观点**
GitHub 本质上是一个围绕代码构建的社交网络，而 AI 正在打破“只有专业软件工程师才能使用 GitHub”的边界，将这个平台开放给更广泛的人群。

**深度阐述**
主持人在访谈中提出了一个极具洞察力的观察：**“这是一个代码社交网络。你做过社交网络（Ning、Facebook），运作这个‘社交网络’是什么感觉？”** [关于社交网络的讨论]

Jay Parikh 对这个比喻给予了肯定，但也给出了一个关键性的修正。他承认自己的职业生涯中确实有明显的模式——Ning、Facebook，再到现在的 GitHub，都是某种形式的“社交网络”。但他指出，GitHub 的用户群体与传统的社交网络有着根本性的不同。然而，**AI 的出现正在模糊这条边界。**

Parikh 讲述了一个他在 GitHub Universe 期间遇到的真实故事：**“我那天在和另一位记者聊天，他正在试验一些东西，然后决定‘嘿，我想创建一个 repo（代码仓库），然后把这个 repo 分享给其他人，获得反馈’。”** [关于社交网络的讨论]

这位记者显然不是专业的软件工程师，但通过 AI 编码代理的帮助，他能够将自己的想法转化为一个可以分享的代码仓库。Parikh 认为，这是一种全新的世界与 AI 互动、共同构建的方式。他引用了自己在主题演讲中的一句话：**“这个社区最令人惊叹的事情之一，就是你不必独自构建。我们都在这里一起构建。”** [关于社交网络的讨论]

**视觉/结构信息描述**：访谈中 Parikh 描述了一个场景：非专业开发者通过 Copilot 的帮助创建代码仓库，然后将这个仓库分享给社区获取反馈。这个场景在他 GitHub Universe 的主题演讲中被作为典型案例展示，体现了平台用户画像的转变。主持人将这种模式与他本人在 Ning 和 Facebook 的经验进行了对比——那些平台降低了“社交分享”的门槛，而 GitHub 在 AI 的加持下，正在降低“建构造物”的门槛。

**个人感受**
Parikh 在讲述这个故事时流露出一种真实的兴奋感。作为一个在社交网络领域深耕多年的工程领袖，他显然在 GitHub 的转变中看到了某种历史的重复——但这一次，被民主化的不是“分享状态更新”的能力，而是**“将想法转化为可运行软件”的能力**。他的语气中带着一种“我们正处在某个重大转变的开端”的确信。 [关于社交网络的讨论]

**延伸思考**
这个观点引发了更深层的思考：社交网络的历史演进是由“内容生产的门槛降低”驱动的。从博客到微博，从长视频到短视频，每一次门槛降低都带来了用户基数的数量级跃升。GitHub 正在经历类似的转变——AI 编码代理将“能够创建代码仓库”的门槛从“需要数年编程训练”降低到“能够清晰表达一个想法”。如果这个逻辑成立，那么 GitHub 的用户增长曲线可能还远未触及天花板。

但这也带来了一个根本性的张力：当用户不再理解他们创建的内容时（因为代码是由 AI 生成的），平台的责任从“托管代码”扩展到了“托管可信任的构建结果”。这个张力，在后面对安全和成本的讨论中变得愈发清晰。

**精华收获**
GitHub 正在从“代码托管平台”进化为“想法实现平台”。AI 编码代理不仅改变了人们**如何**写代码，更改变了**谁**能写代码。这让 GitHub 的增长逻辑从“开发者数量的增长”升级为“所有想要构建的人的增长”。

### 拉取请求的终结？代理时代的工作流范式转变

**核心观点**
当 AI 代理成为编写代码的主要力量时，以 Pull Request 为核心的传统协作工作流可能不再是最优解。GitHub 的选择是提供灵活的平台原语，让用户自己决定如何使用。

**深度阐述**
这个话题由一位极有分量的 GitHub 超级用户引出。主持人提到了 **Peter Steinberger**，他是 OpenClaw 的开发者，被描述为 GitHub **“前 0.001% 的用户”**——一个真正把 GitHub 推向性能极限的人。Steinberger 最近提出的一个激进观点是：**“Pull Request 可能正在走向终结。”** [拉取请求终结的讨论]

这个观点的逻辑是：当代码主要由 AI 代理编写时，代理之间的协作不需要传统意义上的“人类审查”流程。PR 作为一种人类协作机制，其核心价值在于让人与人之间能够审查、讨论和决策代码变更。但如果两个代理之间交换代码，它们需要的是完全不同的接口和协议。

Jay Parikh 的回应体现了一种深刻的平台设计哲学。他首先表达了对 Peter 和其团队的高度赞赏：**“Peter 和团队非常棒，他们不断推动我们变得更好、更好、更好。这正是我们欢迎的，因为技术在飞速发展，我们想要持续迭代和构建。”** 然后他给出了一个关键立场：**“随着新范式的出现和新的工作方式崛起，我们将持续演进、适应和改变平台。如果某个概念不再有用，或者人们不希望它是必需的，那它可以变成可配置的。”** [拉取请求终结的讨论]

但 Parikh 同时提醒我们注意一个现实：**“记住,2.25 亿开发者中包括大型企业、小型团队、学生等各类人群。我们必须提供一个包含多种概念的平台，让用户能够按照自己的方式组装这些概念。”** 他随后以自己的工作方式为例：**“我有一些 repo 是我自己折腾着玩的，我根本不做 PR。对我来说，我就是不断地把想法扔进去，不断地构建、构建、构建，我不想处理 issues 或 PR 之类的东西。”** [拉取请求终结的讨论]

**视觉/结构信息描述**：这段讨论的核心是一个概念性的张力：GitHub 作为平台，必须在“提供足够多的结构化概念（PR、Issue、Review 等）”和“允许用户绕过这些结构自由工作”之间找到平衡。Parikh 用自己的个人工作流作为例子，展示了一个“低摩擦、高速度”的代理驱动开发模式——这种模式与传统企业级开发流程形成了鲜明对比。这种对比直接映射在 GitHub 的产品设计策略中：提供平台原语（primitives），让用户自由组装，而不是强制一套固定的工作流。

**个人感受**
Parikh 在描述自己的工作方式时，使用了一种非常个人化、甚至略带叛逆的语气——**“我不想处理 issues 或 PR”**。这位管理着全球最大开发者平台的工程领袖，自己却在用一种“反传统”的方式使用自己的产品。这种坦诚让他的平台哲学显得更加可信：他并不是在宣传一套“正确的工作流”，而是在构建一个能够容纳**所有**工作流的底层平台。 [拉取请求终结的讨论]

**延伸思考**
PR 的消亡与否，本质上是一个更宏大的问题的一个切面：**当“代码生成”从瓶颈变为商品，人类协作的瓶颈就转移到了“代码审查、决策和责任归属”上。** PR 作为一种机制，其核心功能未必会被消除，但其执行方式无疑正在被 AI 深度改造。如果代理可以自动生成高质量的代码审查意见，人类审查者的角色就从“逐行检查代码”转变为“理解意图、验证方向、做出决策”。

这也意味着，未来 GitHub 上可能出现**两种截然不同的工作流并行存在**：一种是传统的、围绕 PR 的、重治理的企业级流程；另一种是代理驱动的、低摩擦的、面向探索和原型的个人化流程。平台的价值不在于强制统一这两种模式，而在于让它们能够在同一个基础设施上共存。

**精华收获**
平台的原语化设计原则：**提供能力，不强制工作流。** 在一个快速演化的技术生态中，没有任何人知道未来的“正确工作流”是什么样的。唯一正确的策略是提供足够灵活的基础构建块，让社区自己去定义最佳实践。PR 不会“消失”，但它会从“默认选项”变为“可选项”。

### 什么是代码？什么是仓库？GitHub 的内容定义正在扩展

**核心观点**
AI 时代的“代码”不再仅仅是可执行的软件代码，而是扩展到了包括 Markdown 文档、配置文件、AI 代理的指令等多种内容形态。这迫使 GitHub 重新思考“仓库”的本质。

**深度阐述**
这个话题的切入点非常有意思。主持人提到，Jay Parikh 在主题演讲中展示了一个非常有代表性的仓库——来自 Matt Pocock（同样是 Latent Space 的演讲者）的项目。主持人指出：**“它就是一个 markdown 文件夹。只是 markdown。”** 但这引发了一个根本性的问题：如果仓库的内容大部分是文档而非代码，那么 **“这个 repo 是 76% Rust”** 这样的语言统计还有什么意义？**“什么是 repo？什么是代码？我们在存储什么？”** [什么是代码的讨论]

Parikh 的回应体现了一个平台领导者的全局视角。他首先承认这个变化的真实性，但同时提醒我们：**“仍然有大量代码存在。想想所有用 Java 和 .NET 编写的、正在运行关键业务系统的代码。这些代码需要安全修复、现代化改造、持续优化和调试。”** 他描述了一个横跨数十年的技术跨度：**“其中一些东西已经有几十年的历史了，而另一些东西可能正在我们说话的这一刻被部署到生产环境中。”** [什么是代码的讨论]

这个观察揭示了一个关键事实：GitHub 同时服务于**两个截然不同的世界**。一个世界是数十年积累的企业级 Java/.NET 代码库，它们运行着全球商业的基础设施，需要极其严谨的安全和治理流程；另一个世界是 AI 代理生成的新兴内容生态，其中“代码”的定义正在迅速模糊化——它可能是 Markdown 文档、可能是配置脚本、可能是写给 AI 代理的指令，甚至可能是数据文件。

Parikh 对此给出的结论是：**“工具必须具有灵活性，而且需要提供大量选择。我们关心并相信开发者需要选择。”** 他随后以自己为例，描述了一个非常个人化的开发者心态：**“我是一个开发者。我对某些事情很挑剔，我想要某些特定的东西，因为在某种程度上这是我的个性，或者说我通过使用的工具来表达一种工艺。”** [什么是代码的讨论]

**视觉/结构信息描述**：这段对话的核心视觉意象是 GitHub 平台上“语言统计”功能的失效——当一个仓库的主要内容从 Rust/Python/Java 等程序设计语言转变为 Markdown/YAML/JSON 等格式时，传统的“语言占比”统计就不再能够描述这个仓库的本质。这种转变在 GitHub Universe 的主题演讲中被具象化为 Matt Pocock 的 Markdown 文件夹项目。这个项目之所以引发关注，是因为它代表了一种全新的仓库类型：**“内容即代码”**——其中“代码”的价值不在于执行，而在于结构化和可分享的知识。

**个人感受**
Parikh 谈到“开发者需要选择”和“工匠精神”时，语气中带有一种来自资深工程师的真切共鸣。他不是在做一个产品决策的理性论证，而是在表达一种对开发者文化的深层尊重。作为一个在基础设施领域摸爬滚打数十年的工程师，他显然理解那种“我用自己的工具、自己的方式做事”的执念。这种理解让他对“什么算代码”“什么算仓库”的问题保持了一种开放的态度——**平台不应该替用户定义这些概念，平台应该适应并服务用户对这些概念的不断重新定义。** [什么是代码的讨论]

**延伸思考**
当“代码”的定义扩展到 Markdown、配置文件、甚至自然语言指令时，GitHub 的底层内容模型就面临一个根本性的挑战：传统代码的版本控制、依赖管理、安全扫描等工具，大多建立在对“代码是可执行指令”的假设之上。如果代码不再是可执行的（或者执行逻辑完全由 AI 代理来决定），那么**版本控制的语义、依赖的意义、安全的边界**都需要重新定义。

更深层次的思考是：如果 AI 代理生成的“代码”本质上是一种“意图的精确化表达”，那么 GitHub 的核心资产可能正在从**代码本身**转变为**代码背后的意图和上下文**。代码变成了可再生的中间产物，而真正有价值的是产生代码的思维过程、决策记录和团队知识。这可能是 GitHub 在 AI 时代面临的最根本的自我重塑。

**精华收获**
平台必须同时服务“旧世界”和“新世界”，不能偏废任何一方。旧的 Java/.NET 代码库仍然运行着全球经济，而新的 AI 生成内容正在重新定义“代码”的边界。真正的平台领导力，在于让这两种世界在同一个基础设施上优雅地共存，并且让用户自己去决定他们的工作流的本质。

### Copilot Harness 与 Fusion：多模型编排的核心引擎

**核心观点**
Copilot 不仅仅是一个编码助手，而是一个“harness”（驾驭系统/框架）——它负责在最底层利用多种模型的能力，而 Fusion 就是实现智能模型路由的关键组件。这代表了 AI 平台从“绑定单一模型”向“编排多模型”的根本转向。

**深度阐述**
主持人对这个话题的引入非常精准。他指出，Copilot 是**“第一个 harness”**——这是指它是第一个真正意义上的 AI 编码代理框架（至今已有约四年历史）。而 harness 最核心、最底层的功能之一，就是**模型路由**：决定哪个任务应该由哪个模型来处理。**“能否深入讲讲，为什么在模型路由领域建立领导地位对你们如此重要？”** [Fusion 与 Harness 的讨论]

Jay Parikh 的回应从架构层面展开了这个问题的全貌。他首先解释了 Copilot Harness 的核心组件：**“我们今天发布了很多关于 Copilot Harness 的信息。这个 harness 我们一直在开发。我们认为 SDK 部分非常重要——你可以使用这个 SDK 来构建其他应用程序。我自己就做过，很多人也做过。这个 harness 支持很多不同的能力，但其中最核心的原则之一就是多模型。”** [Fusion 与 Harness 的讨论]

这里的“多模型”不仅仅意味着“支持多个模型”，而是指一个系统应该能够**根据任务的具体需求，智能地选择最合适的模型**。Parikh 进一步解释了这一层的挑战：harness 需要处理 MCP（Model Context Protocol）等新标准、不同类型的编码工具、不同模型之间的差异，以及不断变化的模型生态。然后，在 harness 之上，需要一层**智能**来完成以下任务：**“接收一个任务、一个 prompt、一个最终会成为已完成软件工作的单元，然后将其分解，以一种方式卸下工程师的认知负担……”** [Fusion 与 Harness 的讨论]

这就是 **Fusion** 的角色。Parikh 描述了 Fusion 的核心价值：**“如果你有所有这些不同价格和性能的模型，我们可以帮你优化。我们可以给你最好的质量、最快的速度、以及更低的成本。”** 他将 Harness 和 Fusion 的关系描述为一种动态的“潮起潮落”（ebbing and flowing）的关系——它们在解决同一个问题的不同层面，需要协同工作。 [Fusion 与 Harness 的讨论]

**视觉/结构信息描述**：在 GitHub Universe 的主题演讲中，Fusion 的展示方式是核心亮点之一。它被展示为一个位于 Copilot 平台内部的智能路由层，能够根据任务的复杂度、对质量的敏感度、以及对速度的要求，自动将请求路由到不同的模型——从轻量级的快速模型到重量级的高质量模型。Parikh 在访谈中明确提到了这个架构的核心概念：**Harness（基础框架）→ 智能路由层（Fusion）→ 开发者体验（质量/速度/成本优化）**。这个三层架构是 GitHub 在 AI 时代的核心工程投资方向。

**个人感受**
Parikh 在描述这个问题时，展现出了一种对开发者真实痛点的深刻理解。他说工程师要面对的是**“所有这些不同价格和性能的模型”**——这是一个私底下每个开发者都在焦虑但很少有人能从平台层面解决的实际问题。他的解决方案不是“选一个最好的模型”，而是“帮你处理好所有的模型选择”。这种思维模式体现了一个平台架构师的本质：**不是为用户做选择，而是把选择的复杂性变成平台的服务。** [Fusion 与 Harness 的讨论]

**延伸思考**
Fusion 的发布是一个非常重要的行业信号。它标志着 AI 平台正在从“模型绑定”走向“模型无关”。这个转变的经济学逻辑非常清晰：模型能力的发展速度使得任何“绑定单一模型”的策略都变得不可持续。当新一代模型在某个季度突然超越前一代时，平台需要能够无缝地切换到新模型，同时保持对旧模型的兼容。

更进一步想，Fusion 的本质是一种**“对模型能力的动态定价和优化机制”**。它将“模型选择”从开发者的手工任务变成了平台的自动优化问题。这和云计算的演进历史非常相似：早期云计算只是“远程服务器”，后来进化出了自动弹性伸缩、成本优化、SLA 保障等抽象层。Fusion 正在做的事情，本质上是为 AI 模型建立类似的**“弹性调度和成本优化层”**。

**精华收获**
AI 平台的护城河不在于绑定某一个大模型，而在于提供**模型无关的编排能力**。Harness 提供了基础的执行框架，Fusion 提供了智能的模型路由。这就像是**操作系统对 CPU 的调度**——用户不需要知道底层是 Intel 还是 ARM，只需要获得最优的计算体验。对于企业和开发者来说，这意味着他们可以专注于解决问题，而不是追踪模型市场的最新动态。

### 跨平台统一体验：同一个 Harness 连接移动端、桌面端和 Web

**核心观点**
Copilot 正在覆盖每一个开发者可能使用的工作界面——移动应用、桌面应用、VS Code、网页端——而所有这些界面都由同一个 Harness 驱动，实现真正无缝的跨平台工作流。

**深度阐述**
主持人的问题非常直率：**“你们在移动应用、桌面应用上做了很多工作。我的问题是，你觉得有必要在这些界面层创新吗？还是说这基本上就是其他产品也有的东西的微软品牌版本？你需要在 UI 层创新，还是只要在模型层做好就够了？”** [跨平台体验的讨论]

这是一个很尖锐的问题——它暗指了一种观点：在 AI 时代，UI 可能会变得无关紧要，因为与 AI 的交互正在从“点击界面”转向“对话式交互”。如果用户主要通过自然语言与 AI 交互，那么界面的价值还剩下什么？

Jay Parikh 的回应给出了一个结构化而有力的答案。他首先肯定了**每一层都需要创新**：**“在某种程度上，我今天谈到的很多事情就是在每个层面进行演进：底层的低级基础设施、存储、计算、网络、安全；然后是平台层，我们谈到了 Git、Actions、AI Gateway 以及支撑 Git 的其他服务；然后你有工作流层面，有不同的交互界面。”** [跨平台体验的讨论]

但他的关键洞察在于**这些层面之间的连接性**：**“当你使用我们的界面——GitHub Copilot App、VS Code、或者 GitHub.com——它们都由同一个 Harness 连接。这真的非常强大，因为你可以在手机上启动一个任务，然后到桌面上继续，或者你在手机上突然有了什么新想法，可以随时输入让它继续运行。但重要的是，所有的上下文都跟随你——在你的仓库里、在你的 issues 里、在你的 PR 里、在你的安全发现里。”** [跨平台体验的讨论]

Parikh 随后特别强调了与其他工具的根本差异：**“今天，如果你使用不同提供商的不同工具，从工具 A 切换到工具 B 时，它们的智能不会互相叠加。而我们要解决的问题是：你应该能够完成越来越多的工作，而且因为你在使用我们平台和工具的力量，它会变得更便宜、更好、更快。但你仍然可以深度定制——你可以使用不同的模型，你可以使用 Fusion，你也可以使用其他工具。”** [跨平台体验的讨论]

**视觉/结构信息描述**：这段讨论涉及 GitHub 的产品矩阵结构。四个核心交互界面分别是：**移动应用（手机）**、**桌面应用**、**VS Code 集成**、**Web 端（GitHub.com）**。在 GitHub Universe 的演示中，这些界面之间的无缝切换是一个核心演示场景：用户在手机上启动一个任务，然后在桌面上继续，所有上下文（包括代码变更、对话历史、模型偏好设置）都会自动同步。这种体验的设计核心是“上下文的可携带性”——不仅是文件级别的同步，而是认知状态和工作意图的跨设备传递。

**个人感受**
Parikh 在回答这个问题时表现出了一种果断的清晰。对于“UI 还需要创新吗”这个带有挑衅意味的问题，他没有陷入“UI vs 模型”的二元对立，而是从一开始就把讨论拉高到了**“平台各层之间连接性”**的维度。这反映了一种典型的平台架构师思维：**单点的优化往往不如层与层之间的无缝整合来得更有价值。** 他的语气中带有一种对“碎片化工具生态”的批判——如果一个开发者的上下文分散在多个互相隔绝的工具中，那么每一层技术的进步都会被这种碎片化所稀释。 [跨平台体验的讨论]

**延伸思考**
这个“上下文可携带性”的概念，在更深层面上揭示了 AI 平台竞争的核心战场。在传统的软件工具竞争中，壁垒在于功能和体验的累积；但在 AI 时代，真正的壁垒在于**上下文的累积**。每一次与 AI 的交互都会产生新的上下文——你的偏好、你的项目历史、你的决策模式、你的代码风格——如果这些上下文被锁定在某个平台中，切换成本就会越来越高。

这是一种**飞轮效应**：越使用平台，上下文越丰富；上下文越丰富，AI 的服务质量越高；服务质量越高，用户越不愿意离开。但这也提出了一个重要的反垄断问题：**如果所有的 AI 上下文都被锁定在少数平台中，这会对创新和用户自由产生怎样的影响？** Parikh 强调“你可以使用其他工具”和“可以自定义”，这可以看作是对这个潜在担忧的主动回应。

**精华收获**
AI 时代的平台竞争不仅是“谁的模型更强”，更是“谁的上下文更完整”。同一个 Harness 连接所有交互界面的真正价值，不在于 UI 的一致性，而在于**用户的完整工作上下文能够跨设备、跨时间地累积和复用**。这才是锁定效应的真正来源。

### 安全的新范式：从代码审查到供应链防御

**核心观点**
当 AI 生成的代码量急剧增加时，安全风险的规模也在同步扩大。GitHub 正在从“被动发现漏洞”转向“主动阻止风险进入代码库”，同时在开源软件供应链层面进行系统性加固。

**深度阐述**
安全是访谈最后部分的一个核心话题。主持人提出了一个极具现实感的引子：**“你们承担着巨大的责任。最近 PHP 相关的事情显然让安全问题成为了最受关注的话题。”** [安全讨论的开场]

Jay Parikh 在安全方面的回应非常具体，展示了 Github 在多个层面同时推进的安全策略。

**第一层是代码质量保障。** Parikh 提到了 Code Review Max：**“现在我们有了 Code Review Max，它甚至可以帮助发现更高严重级别的、更隐蔽的代码 bug。这真的非常重要——因为我们正在生成比以往多得多的代码，我们必须确保质量标准不会下滑。Copilot Code Review 帮助你维护这个质量标准。”** [安全讨论-代码审查]

**第二层是主动安全防护。** Parikh 提到了 GitHub Advanced Security 中的 AI 扫描技术，并回顾了主题演讲中的一个现场演示：**“Damian 不小心推送了一个 secret——但它被阻止了，甚至没能进入仓库。”** 他补充道：**“我们有很多深度扫描能力，不仅仅是表面层面的漏洞检测。我们还有大量即将发布的新功能。今天有很多深度研讨会，你可以把更复杂的 AI 扫描技术嵌入到你的工作流中。”** [安全讨论-主动防护]

**第三层是供应链和生态系统的协作防御。** Parikh 强调了 Microsoft 安全团队和 GitHub 安全团队之间的深度合作：**“一方面在平台硬化，另一方面与开源维护者合作，做大量工作来限制包管理器（比如 npm）的暴露面。我们有时延设定，会下架被攻破的仓库。每天都有持续的改进，与社区、开源项目和维护者一起工作。整个微软都在投资强化这个领域——这是每个人最关心的事情。”** [安全讨论-供应链防御]

**视觉/结构信息描述**：在 GitHub Universe 的主题演讲中，安全部分包含了一个现场演示：一个开发者（Damian）试图推送一个包含秘密密钥（secret）的代码变更，系统在代码进入仓库之前就检测到了这个风险并自动阻止了推送。这个演示展示了 AI 安全扫描技术的能力——不仅能够发现已经存在于代码库中的漏洞，还能够在攻击面形成之前就将其阻断。安全架构的核心思想是**“前置防御”**——将安全的临界点从“代码审查阶段”前移到“代码生成和提交阶段”。

**个人感受**
Parikh 在谈论安全时，选择了从多个层面同时展开的表述方式。他没有先提某个“统一的解决方案”或“一揽子的安全方案”，而是呈现出一种系统工程式的现实感：**“我们还有很多工作要做”**——这句话在安全讨论中被重复提及。这种坦诚在大型科技公司的高管中并不常见。他的态度表明了一个深刻的认知：在 AI 生成代码的时代，安全不是一个可以“解决”的问题，而是一个必须持续投入的**系统性工程**。 [安全讨论]

**延伸思考**
当 AI 能够以极低的成本生成大量代码时，安全的根本矛盾发生了变化。以前，代码的生成成本较高，因此人类的审查成本可以与之匹配。但现在，**代码生成的边际成本趋近于零，而安全审查的成本并没有以同样的速度下降**。这意味着传统的“人审代码”模型在数学上已经不可持续。

这个矛盾推动了安全领域的范式转变：从**反应式安全**（发现漏洞→修复漏洞）转向**预防式安全**（在代码生成时即注入安全约束），从**人工审查**转向**AI 辅助审查**，从**单点防御**转向**供应链系统防御**。这些转变的核心逻辑是：当代码的数量和生成速度超过了人类审查能力的极限时，唯一可行的路径是**用 AI 来审查 AI 生成的代码**。

同时，这也提出了一个重要的产业问题：**当代码生成变得极其便宜时，“重写一切”是否成为了一种更安全的替代方案？** 这个问题的答案需要放在成本/风险/收益的综合框架下来分析。如果一个开源依赖有已知漏洞，是花时间修复它，还是用 AI 以极低成本重新实现一遍？这不是一个技术问题，而是一个**战略决策**问题。 [安全讨论的延伸]

**精华收获**
AI 时代的安全战略必须从前置防御（在代码进入仓库之前就阻止风险）、AI 辅助审查（用 AI 审查 AI 生成的代码）、以及供应链协作（与包管理器和开源维护者协同工作）三个层面并行推进。核心原则是：**安全临界点必须从“审查”前移，因为代码的生成速度已经远远超过了人类审查的能力。**

### 开源安全的哲学困境：隔离还是加固？

**核心观点**
面对 AI 生成代码带来的安全挑战，有人认为应该放弃开源依赖、重写一切或大幅减少依赖数量。Jay Parikh 认为这不是万能药，真正的解决方案在于让开源生态本身变得更安全。

**深度阐述**
这个讨论是整个访谈中最具有哲学深度的部分之一。主持人提出了一个在业界日益流行的激进观点：**“GitHub 和我们的开源供应链建立在一个前提上，即代码是昂贵的。但现在代码可能已经变得很便宜了。也许安全审查也变得便宜了。也许保护我们系统的最好方法就是自己重写一切、vendor 一切，而不是依赖开源。”** [开源安全的讨论]

主持人进一步阐述了这个观点的实际逻辑：**“我的依赖有 2000 个核心软件组件，每个人都在用。它们都是潜在的攻击面。也许我应该把它们削减到 20 个。”** [开源安全的讨论]

Jay Parikh 的回应体现了深思熟虑的平台领导力。他没有简单地否定这个观点，而是从实际操作层面揭示了其中的隐藏成本：**“我不认为这也不是万能药。因为——嘿，我有 2000 个开源项目在用，我要删掉其中 1980 个，只用 20 个。但剩下的 1980 个我现在得自己维护了。”** [开源安全的讨论]

这个反驳的核心逻辑是一个简单的经济学问题：**你删掉的开源依赖，并不会消失。它们的成本只是从“使用和维护外部代码”转变为“使用和维护内部代码”。** 而且，内部维护的成本可能更高，因为你失去了社区贡献的网络效应。

Parikh 随后给出了自己的立场：**“开源中正在发生太多重要且有价值的事情。我认为这不会停止。如果说有什么变化，那就是开源对商业、对构建者、对创作者的价值只会越来越高。”** 他提出了一个清晰的价值判断：**“让我们来解决真正的问题——让开源中的东西变得更安全，而不是每个人都走向某种有围墙的花园。”** [开源安全的讨论]

**视觉/结构信息描述**：这段对话的核心是一个思想实验的结构化展开。主持人提出了一个极端的假设：将依赖从 2000 个削减到 20 个。这个假设的逻辑链条是：**依赖数量减少 → 攻击面减少 → 安全性提高**。但 Parikh 指出了这个链条中被忽略的隐藏成本：**被删掉的依赖不会消失，它们会变成内部维护的代码 → 维护责任转移 → 资源成本可能不降反升 → 同时失去了社区协作的安全网络效应**。这是一个典型的“表象优化 vs 系统优化”的分析框架。

**个人感受**
Parikh 在回应这个问题时，没有使用“开源精神”这样的道德论述，而是从务实的工程经济学角度出发进行论证。这反映了一种重要的领导力风格：**不是基于意识形态来为开源辩护，而是基于实际成本和价值的计算来论证开源的必要性。** 但与此同时，他的表述中也暗含了一种信念——开源的价值不限于经济效率，还包括创新速度和社区协作的深层力量。这种务实与信念的结合，让他的立场显得既有原则性又有说服力。 [开源安全的讨论]

**延伸思考**
这个讨论触及了一个比安全更深层的问题：**在 AI 时代，开源的本质会怎样改变？** 如果 AI 能够以极低成本生成任意功能的代码，那么“代码共享”的价值是否会被削弱？如果任何人都可以随时生成他们需要的代码，那么为什么还要依赖一个共享代码库？

但值得注意的是，开源的价值从不仅仅是“免费代码”。开源的核心是：**协作创新、社区信任、透明审查、以及标准形成。** 即使代码生成变得极其便宜，这些价值也不会消失。事实上，在 AI 生成代码的世界中，开源可能变得更加重要——因为**信任的来源**从“代码是谁写的”转变为“代码是如何被审查和验证的”。开源社区提供了一个透明、去中心化的审查网络，这是任何封闭系统都难以复制的。

真正的安全性不在于减少依赖数量，而在于提高整个生态系统的**可见性、可追溯性和快速响应能力**。这正是 GitHub 正在投资的方向——不是通过限制开源的使用，而是通过提升开源生态的安全基础设施。

**精华收获**
“减少依赖”的本质是把安全风险从“外部依赖”转移为“内部维护”，这并没有减少风险，只是转移了成本。真正可行的安全策略是**让开源生态本身变得更安全**，通过工具、自动化和社区协作来实现。在这一点上，平台（GitHub）和社区（开源维护者）必须协同工作，而不是各自为战。

### 2027 年 GitHub 预测：Azure 迁移、代理编排与成本治理

**核心观点**
Jay Parikh 对 GitHub 明年（2027 年）的预测集中在三个方向：完成向 Azure 的迁移、支持管理数千个 AI 代理的新工作流、以及提供内置的 AI 成本管理和治理能力。

**深度阐述**
访谈的结尾部分，主持人提出了一个所有听众都在等待的问题：**“从现在到明年的这个时候，我们会看到 GitHub 有哪些变化？”** [2027 预测的讨论]

Jay Parikh 给出了三个主要方向的预测。

**第一，Azure 迁移的完成。** 当主持人追问 **“迁移到 Azure 会完成吗？”** 时，Parikh 给出了明确的回答：**“这是明年的计划。这是我们的目标。”** 他提到了在主题演讲中展示的扩展图表：**“你今天看到的扩展图表，它们非常惊人。我们必须继续演进，必须保持快速迭代，必须在每一层都做出阶跃函数的改进。”** [2027 预测-Azure 迁移]

这个承诺的分量极其重大。GitHub 在很长一段时间里主要运行在自己的基础设施上（以及部分 AWS）。将整个平台迁移到 Azure 意味着在保持 2.25 亿开发者不间断服务的同时，完成一次底层基础设施的完整替换。这是一个在规模和风险上都堪称史诗级的工程壮举。

**第二，代理工作流的演变。** Parikh 提出了一个开放性的问题：**“人们在改变他们的工作方式——如何构建软件、部署软件、优化软件。今天的样子和一年后会非常不同。我们是在管理数千个代理，还是几十个、几百个？我不知道。所以我们必须继续构建具有正确原语的平台，这样你就可以将这些原语组合成你需要的任何工作方式。”** [2027 预测-代理工作流]

这段话中有一个非常重要的数据点：**代理的增长在 6 个月内增长了 6 倍**，目前 **GitHub 上约 40% 的 Pull Request 是由代理创建的**（主持人在引言中提到的数据）。如果这种增长趋势持续下去，到 2027 年，“管理数千个代理”将不再是假设，而是一个日常现实。 [2027 预测-代理工作流]

**第三，成本治理。** Parikh 指出了一个被许多 AI 平台有意忽略的问题：**“另一个越来越受关注的问题是 cost 和 token 管理。这是一个非常热门的话题。”** 他提到了 GitHub 展示的成本控制功能：**“我们有很多方法来告诉你组织的消费情况，指导你优化消费——‘你在这个类型的用例中使用了这个模型，也许你应该改用另一个模型’。我们会继续在产品中提供建议。对于财富 500 强企业，他们需要治理能力，需要能够设置限制。我们必须提供这些控制和治理能力。”** [2027 预测-成本治理]

主持人对此做出了精妙的总结：**“作为公司领导者，我不介意你把我的钱花在 token 上。只要让我看到这笔钱花得有价值。”** Parikh 进一步拓展了这个理念：**“如果你能说‘嘿，我这周花了 10 万美元的 token，但是它帮我省了 25 万美元的成本，或者提升了客户满意度或留存率——这些都可以度量。作为产品和工程团队，你应该与这些结果指标挂钩。”** [2027 预测-成本治理]

**视觉/结构信息描述**：这段讨论的核心框架是三条并列的预测主线。Azure 迁移代表了**基础设施层的根本性转变**——将整个 GitHub 平台运行在微软自家的云平台上，这意味着在迁移过程中同时进行架构的深度优化。代理工作流代表了**工作模式层的转变**——从“围绕 PR 的人类协作”转向“围绕代理编排的混合协作”，而平台需要提供正确的原语来支持这一转变。成本治理代表了**商业模型层的转变**——AI 时代的开发成本不再是确定性的（服务器和人力成本），而是高度可变的（token 消耗），因此需要全新的成本可见性和治理工具。值得注意的是，GitHub 在成本管理方面的做法与 OpenRouter 等独立 AI 平台形成了鲜明对比——后者通常希望用户尽可能多地消费 token，而 GitHub 则选择了主动提供成本优化建议。

**个人感受**
Parikh 在谈论 Azure 迁移时，语气中带有一种工程领导者面对巨大挑战时的兴奋与克制的混合。他说**“这非常困难”**的时候没有任何回避——这是一种对工程复杂性的尊重。而在谈论成本治理时，他的语气则转向了一种更务实、更面向企业客户的口吻——这是对“AI 的采用取决于信任，信任来自于可解释的成本和可衡量的价值”这一商业逻辑的深刻理解。 [2027 预测]

**延伸思考**
“管理数千个代理”这个预测值得仔细玩味。当前大多数开发者使用单个 AI 编程助手，最多同时运行几个代理来处理不同任务。但如果代理数量增长到“数千个”，那么一个全新的工具类别就会出现：**代理编排平台**。这个平台需要处理代理之间的通信、任务分配、冲突消解、资源管理、安全边界等等——这本质上是在构建一个**“代理操作系统”**。

GitHub 的独特定位在于，它天然具备了构建这种“代理操作系统”所需的核心资产：**代码仓库（代码的真实来源）、Issues（任务的定义）、PR（变更的治理）、Actions（自动化）、Security（安全策略）。** 如果代理成为了软件开发的日常参与者，那么 GitHub 现有的每一个原语都需要被重新想象，但底层的平台逻辑仍然适用。

关于成本问题，一个更深层的矛盾是：**AI 生成代码的效率越高，token 消耗就越大，成本也就越高。** 如果没有有效的成本治理，AI 编码的工具性收益可能会被 token 账单所吞噬。GitHub 在成本管理上的主动投入，实际上是在解决“AI 采用的最大隐性障碍”——不是技术能力，而是**经济效益的可信度**。

**精华收获**
2027 年的 GitHub 将是一个运行在 Azure 上、支持代理驱动开发、提供完整成本治理能力的平台。但真正的重点不是这些具体的功能，而是一个基调的转变：从“托管代码的平台”到“管理 AI 驱动软件开发生命周期的平台”。基础设施建设（Azure 迁移）、工作流设计（代理原语）、和商业可持续性（成本治理）这三条线缺一不可。

### 尾声：Game Boy 徽章与硬件开发的未来

**核心观点**
GitHub Universe 的徽章是一台用 Copilot 辅助开发的 Game Boy 风格设备。这个细节展现了 AI 如何降低了硬件与软件接口的开发门槛。

**深度阐述**
在访谈的最后几分钟，话题转向了一个看似轻松但寓意深刻的小故事。主持人注意到了 GitHub Universe 的徽章——**它不是一张普通的塑料卡片，而是一台类似 Game Boy 的功能性设备**。主持人对此非常兴奋：**“这些徽章我通常都会扔掉。但这个东西我会展示出来。这些会议徽章通常就是一堆电子垃圾。但这是一个 Game Boy。它有程序，实际上可以连接到 GitHub Copilot。它是用 Copilot 制作的。”** [Game Boy 徽章的讨论]

Jay Parikh 确认道：**“是的，它是用 Copilot 制作的。”** 主持人继续追问这个故事：**“跟讲讲把这些东西组装起来的故事吧。很多开发者都想摆弄硬件，而硬件和软件的接口——这是模型现在可以做的事情，我不需要知道每一个细节。”** [Game Boy 徽章的讨论]

Parikh 的回应非常简短：**“应该去试试。”** [Game Boy 徽章的讨论]

**视觉/结构信息描述**：这段对话的核心视觉元素是一台 GitHub Universe 2024 的会议徽章——它被设计成一个类似 Game Boy 的掌上游戏机，拥有屏幕和按钮，可以运行小程序，并且直接连接到 GitHub Copilot。它不同于常规会议的纸质或塑料徽章，而是一个功能性电子设备。其关键象征意义在于：**这个设备本身就是“AI 辅助开发”的实物证明**——它一定涉及了硬件原理图、固件编程、屏幕驱动、按钮交互等多个技术栈，而这些都是由 Copilot 辅助完成的。

**个人感受**
主持人在这个部分流露出了整个访谈中最为个人化的热情。对其他话题（如 Fusion、安全、成本），他保持着专业分析者的距离；但面对这台 Game Boy 徽章时，他却像一个被激发了童年记忆的技术爱好者。这种措辞和语气上的明显温度变化，也折射出了一个更深层的行业现象：**AI 正在重新点燃开发者对技术的浪漫主义热情**——那种“我想做一个东西，虽然我不懂所有的技术细节，但我想试试”的本能冲动。 [Game Boy 徽章的讨论]

**延伸思考**
这个看似随意的小故事，实际上指向了一个深远的技术变革方向：**AI 正在把“跨界开发”的门槛降到前所未有的低点。** 以前，一个纯软件开发者要涉足硬件开发，需要学习电路设计、嵌入式编程、传感器接口等等。现在，通过 AI 辅助，他们可以以“意图表达”的方式开始一个硬件项目——描述他们想要什么，AI 代理去填补技术细节的空白。

这种模式的影响远不止于“有趣的小项目”。它意味着：**创新不再被技术壁垒所限制。** 当一个人有一个跨领域的想法时，不再需要先花数年时间成为那个领域的专家才能开始。他们可以立即开始，利用 AI 来处理专业知识的细节，把精力集中在创意的核心价值上。

对 GitHub 而言，这意味着平台上的项目类型将变得更加多样化——不再只是“代码项目”，而是**“由代码赋能的创造物”**：硬件设备、自动化工具、个性化应用、甚至艺术装置。这个趋势与前面讨论的“什么是代码”“什么是仓库”的问题形成了一个完整的闭环：**GitHub 正在从一个“代码托管平台”演变为一个“创造者平台”。**

**精华收获**
Game Boy 徽章不仅仅是一个有趣的营销细节，而是一种**新开发范式的物理象征**：AI 辅助开发让“想法到实现”的距离大幅缩短，让跨界创造变得触手可及。对于有创造欲望的人来说，这是最好的时代。

## 精华收获

纵观整个访谈，Jay Parikh 和 Latent Space 之间的对话揭示了一个正在形成中的全新范式。以下是这场深度对话中最值得铭刻的洞察：

**1. 平台增长的本质是社区性质的转变。** GitHub 的 2.25 亿开发者和“每秒新增一个开发者”的增长速度，其深远意义在于：GitHub 的用户群正在从“代码专业人员”扩展为“所有想要构建的人”。AI 编码代理降低了技术的准入门槛，使平台的价值主张从“托管代码”变为“实现想法”。

**2. 工作流正在从“人类中心”转向“代理中心”。** 40% 的 PR 已经由代理创建，代理数量在 6 个月内增长了 6 倍。Pull Request 是否消亡并不重要，重要的是平台必须从“强制固定工作流”转向“提供可组装的原语”。GitHub 的核心竞争力将从“定义正确的工作方式”转变为“支持无限的工作方式”。

**3. 模型编排取代模型绑定。** Copilot Harness 和 Fusion 的发布标志着一个重要的产业转折：AI 平台的价值不再来自与某个特定大模型的深度绑定，而是来自跨模型的智能编排能力。这种“模型无关”的策略让平台能够在模型能力快速迭代的背景下保持持续的服务质量。

**4. 安全的临界点必须前移。** 当代码生成速度超过了人类审查能力的极限时，传统的“审查后修复”模型已经不可持续。安全必须嵌入到代码生成和提交的每一个环节中，在前端阻断风险，而不是在事后补救。同时，开源安全的关键在于加固生态而非隔离生态。

**5. 成本治理是 AI 普及的催化剂。** 在 AI 技术能力的讨论之外，有一个商业现实问题：token 消耗让软件开发的成本结构从“固定成本”变为“可变成本”。只有当组织能够清晰地看到 AI 支出与商业成果之间的对应关系时，AI 的采用才会从“试验性探索”转向“规模化部署”。

**6. 基础设施的迁移与平台的演化必须并行。** 在保持 2.25 亿开发者不间断服务的同时迁移到 Azure，这是一个史诗级的工程挑战。但它也提供了一次**重新设计底层架构**的机会——在迁移过程中同步完成平台的 AI 原生改造。这种“在飞行中更换引擎”的能力，正是大型平台真正的技术护城河。
