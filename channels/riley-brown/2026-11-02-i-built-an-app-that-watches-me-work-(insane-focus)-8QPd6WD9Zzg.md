## 开篇引入

你有没有过这样的体验：明明只是想在电脑上写点东西，回过神来却发现自己已经刷了二十分钟社交媒体，而文档仍然一片空白？对于注意力缺陷多动障碍（ADHD）人群来说，这种“不知不觉跑偏”的体验几乎是日常。市面上有很多“专注类应用”，但它们大多只是冷冰冰的计时器，或者在你拿起手机时发出刺耳的警告——它们缺少一个东西：**陪伴感**。

Riley Brown 在上一周做了一个叫 Bluey 的小应用——一只住在手机里、能跟着鼠标跑、能在屏幕上指指点点的小蓝猫。它很可爱，但没什么实际用途。今天，他决定给 Bluey 一个真正的使命：做一只**专注伙伴**，在你工作时看着你的屏幕，每30秒判断一次你是在认真工作还是在摸鱼，并在你持续走神时，用可爱的语气轻轻把你拉回来。

最疯狂的是，这一整套 AI 屏幕监控系统，运行八小时的成本大约只有**十美分**。

这不是科幻。这是基于 OpenAI 最新推出的 Decisions API 构建的真实产品，而且整个开发过程由 AI 辅助编程工具在18分钟内完成。接下来，让我们完整还原这个项目的设计思路、技术架构和实现过程——以及在这个过程中，我们能看到 AI 产品开发正在发生怎样的范式转移。

## 详细内容

### 一、Bluey 的前世：从一个“可爱但没什么用”的小玩意儿说起 `[视频前言部分，约前 2 分钟]`

**核心观点**

Bluey 最初只是一个利用闲置手机做“电脑小宠物”的实验项目，没有明确功能定位，但它的核心交互体验——跟随鼠标、屏幕指认、语音交流——为今天的“专注伙伴”版本奠定了架构基础。

**深度阐述**

Riley 的起点非常生活化：他有一台旧 iPhone，放在抽屉里落灰。他想到了一个有趣的用途——把它变成电脑的“第二屏幕”，但不是一个普通的扩展显示器，而是一个**有性格的、活的小角色**。这个角色就是 Bluey，一只蓝色的小生物，住在手机屏幕里，通过摄像头感知你，通过一个桌面端 Mac 应用与你的电脑通信。

Bluey 的核心能力有三项：第一，它能**跟随鼠标移动**——当你在电脑上移动鼠标时，Bluey 的眼睛会追踪鼠标的位置，感觉它真的在“看”你的屏幕。第二，当你按住手机上的按钮说话时，它能**理解你的指令**，然后在电脑屏幕上指出对应的位置。比如你说“嘿，能指一下电脑显示器吗？”它会在屏幕上精确地指向那个区域，并在旁边留一个小注释，同时发出可爱的音效。第三，它能做一些简单的**网络搜索**，比如“帮我研究一下 Decisions API”，它会在屏幕顶部展示搜索结果。

这里有一个重要的技术细节需要展开：Bluey 在 iPhone 和 Mac 之间的通信架构。Riley 的设计是：iOS 应用运行在手机上，Mac 应用运行在电脑上。两端通过**扫描二维码**进行配对，之后 Mac 端会持续向 iOS 端发送鼠标位置等数据，这样 Bluey 就知道该往哪看。而当你对着手机说话时，iOS 端用 **GPT-4o Transcribe** 做语音转文字，然后把这个文本通过 Mac 端传递给 **OpenAI Realtime API**，由后者决定 Bluey 应该做出什么反应——包括在屏幕上指出什么位置、说什么话、发出什么声音。

这种“手机 + 电脑”的双端架构看似复杂，实际上非常巧妙。它不需要任何专门的硬件，旧手机就能变成一个**具有实体的 AI 交互界面**。Riley 把所有代码都放在一个 GitHub 的 mono repo（单一代码仓库）里，iOS 和 Mac 应用的代码共存于同一个仓库，方便管理和开源分享。

但问题也很明显：Bluey 的“可爱”是它的全部。Riley 自己承认，它“有点模糊，没有一个真正的目的”。它能做一些事情，“有点能上网搜索”，但这离一个真正有用的产品还很远。用他自己的话说：“我希望它是实用的、有目的的、解决一个具体的问题，同时保持它的可爱。”这句话实际上概括了整个视频的产品设计哲学：**不做通用工具，做有性格的专用工具**。

**个人感受**

Riley 在介绍 Bluey 时流露出一种真挚的“带娃”式的情感。他称呼 Bluey 为“little buddy”（小伙伴），在测试时和它对话就像和朋友聊天。提到 ADHD 时，他说了一句非常关键的话：“对于有 ADHD 的人来说，如果你旁边有个人在，不知怎么回事，就会更容易专注。”这不是一个技术判断，而是一个基于亲身体验的观察——**社交在场的压力（哪怕是虚拟的）能够提升专注力**。这正是他把 Bluey 从玩具变成专注工具的情感起点。

**延伸思考**

“虚拟陪伴提升专注力”并不是一个新概念。有很多人用“Study With Me”直播营造自习室氛围，用虚拟主播（VTuber）的陪伴感来对抗孤独。但 Bluey 走得更远一步：它不是一个被动的“在场者”，而是一个**能看见你的屏幕、对你的行为做出反应的主动观察者**。这种“被看见”的感觉，可能才是它最有力量的机制——不是惩罚性的监控，而是温和的、有个性的提醒。

### 二、Decisions API：一种全新的 AI 输出模式 `[技术讲解部分，视频中段约 4 分钟]`

**核心观点**

Decisions API 是 OpenAI 推出的专门用于“小而快的决策”的推理接口，它不输出文本，而是直接输出一个概率或分类选择，因此速度极快、成本极低（甚至输出免费），特别适合需要高频调用的应用场景。

**深度阐述**

这是全片技术含量最高的部分。Riley 花了相当大的篇幅来介绍 Decisions API 的概念，因为它是整个新 Bluey 的核心引擎。

传统的 AI 接口（比如 ChatGPT 的 API）是“生成式”的：你给它一段文本，它给你一段文本。你问它“用户现在是在工作还是在刷 Twitter？”它会回答：“根据截图，用户目前正在浏览社交媒体，似乎偏离了任务。”——然后它会继续输出一段完整的、语法正确的句子。这种模式有两个问题：第一，**慢**——生成一整段文本需要时间；第二，**贵**——每个输出 token 都要收费。

而 Decisions API 完全改变了这种范式。用 Riley 的解释来说：它在做一个**决定**，而不是做一个**回答**。你给它一个具体的判断任务，它会从一个预定义的输出集合中选一个，告诉你是哪一个，以及它有多大把握。它**不输出任何文本**。换句话说，它不做“描述”，它做“判断”。

Decisions API 提供三种输出模式，Riley 在视频中逐一做了讲解：

**第一种叫 Predicate（判断）**：你给一个陈述句，它返回这个陈述为真的概率。比如“用户正在写文章” → 返回 0.87，意思是有87%的概率这句话是真的。

**第二种叫 Choice（选择）**：你给一组预定义的选项，它从其中选一个最合适的，并给出每个选项的概率和一个总体置信度分数。比如选项是 [“on_task”, “off_task”, “uncertain”]，它返回类似 `{“choice”: “off_task”, “probabilities”: {...}, “confidence”: 0.92}` 这样的结构化结果。

**第三种叫 Score（评分）**：你定义一个量表，它给某个输入打分。比如“用1-10分评估这个用户的专注程度”。

Bluey 用的是**Choice（选择）**模式。每次检查时，应用会把截图和任务描述发给 Decisions API，API 从“on_task / off_task / uncertain”三个选项中选一个，并附带概率分布和置信度。这三个选项就是 Riley 为 Bluey 定义的“决策空间”。

这里有一个极其重要的成本信息：**Decisions API 的输出是免费的**。Riley 在视频中展示了官方定价页面——100次截图检查只需要1美分。按照每30秒检查一次的频率计算，8小时（960次检查）只需要约9美分。这意味着一个普通工作日的持续 AI 监控，成本不到一杯咖啡的零头。他兴奋地说：“8小时的专注成本大约10美分，这太酷了。”这种成本结构彻底改变了“AI 监控”的可行性——在过去，让 AI 每30秒看一眼你的屏幕并做出判断，成本可能会高得离谱。

值得注意的是，Riley 在讲述这部分时非常清晰地解释了**为什么选择 Choice 而不是 Predicate 或 Score**。对于“是否走神”这个场景，Choice 是最自然的：我们需要的不是“用户走神的概率是0.73”这样一个单独的数字，而是“三个状态中哪一个最可能是当前状态”这样的**互斥分类**。同时，Choice 模式还提供了概率分布和置信度，这为后续的“何时干预”算法提供了重要的细粒度信息——比如同样是“off task”，90%置信度和60%置信度应该触发不同的应对策略。

**延伸思考**

Decisions API 代表了一种重要的产品设计思维转变：**不是所有 AI 应用都需要“生成”，很多应用只需要“判断”**。在需要高频、快速、低成本的场景里（比如屏幕监控、内容审核、风险判断、实时分类），传统的生成式接口是“杀鸡用牛刀”——准确、灵活但冗余。而 Decisions API 这种“决策即输出”的模式，让 AI 可以像传感器一样被嵌入到各种小而精的应用中。这可能会催生一批新的“嵌入式 AI”应用——不是聊天机器人，而是**能看见、能判断、能触发动作的智能开关**。

### 三、产品设计：从“模糊的可爱”到“有性格的专注教练” `[产品设计讨论部分，视频中段约 3 分钟]`

**核心观点**

新 Bluey 的产品设计核心是：用高频 AI 决策（每30秒判断一次专注状态）+ 智能干预算法（不烦人，但不放过持续走神）来实现在“温和陪伴”与“有效纠偏”之间取得平衡。

**深度阐述**

在技术上搞懂了 Decisions API 之后，Riley 开始描述新 Bluey 的产品体验。这个描述非常具体，像一个完整的产品 PRD（产品需求文档）：

**工作流程是这样的**：你把手机放在电脑下面，Bluey 就住在那里。开始工作前，你按住手机说出你接下来要做什么任务——比如“我要写视频脚本，写30分钟”。Bluey 确认后，在手机界面底部出现一个大计时器（Riley 特别强调计时器要“大、白色、显示时间”，这是主视觉焦点），任务描述显示在顶部。

**然后，每30秒，Mac 端会截取一张你电脑屏幕的截图**，把截图连同任务描述、已用时间、空闲时长、近期检查历史等信息一起发送给 Decisions API。API 返回一个 Choice：on_task / off_task / uncertain，以及对应的概率分布和置信度。

**但关键不仅仅在于判断，而在于判断之后做什么。** 如果 Bluey 每次判断你“off task”就立刻跳出来干预，那它会变成一个极其烦人的电子监工。Riley 明确说：“我不认为每次它判定我 off task 就应该干预。也许它会露出一点困惑的表情，但它应该在反复多次 off task 之后才真正打断我。”

这就是“nudge logic”（提醒逻辑）的核心：**允许短暂的偏离，只对持续的、高置信度的偏离进行干预**。Riley 在给 Codex 的提示词中给出了非常具体的算法设计原则：

- 如果置信度接近100%且持续 off task 超过 **2分钟**，才进行干预。
- 如果置信度在50%-80%之间且不完全确定，则将干预阈值拉长到 **3-4分钟**。
- 每次干预之间设置一个**冷却期**，避免连续“唠叨”。

这个设计体现了一种对用户体验的深度理解：**干扰本身会破坏专注**。如果 AI 监控本身太频繁地打断用户，那么这个工具反而会适得其反。所以重点不是“发现走神就立刻纠正”，而是“容忍小偏差，抓住大偏差”。

另一个细节是 Bluey 的**语言风格**。当它判定你 off task 时，它不会说“警告：检测到您偏离任务”，而是俏皮地说：“嘿，这看起来不像在写文章哦。要不要回到草稿上？”它在指出问题时，还会**在屏幕上指向那个分散你注意力的东西**——比如你正在刷的 Twitter 页面——这利用了 Bluey 已有的屏幕指认能力，让提醒变得具体而可视化。

在提示词中，Riley 还特别加入了一个聪明的规则：**“看 Codex 教程可以算作在制作 Codex 视频，而无关的娱乐内容不算。”** 这说明系统不是机械地判断“你在用什么应用”，而是**结合任务描述理解上下文的语义关系**——你是为了完成任务在看教程？还是单纯在逃避任务刷娱乐内容？这两种行为在类别上完全不同，必须靠 AI 的语义理解能力来区分。

**延伸思考**

这个产品设计中有一个非常值得注意的洞察：**“判断走神”相对容易，“何时提醒”是最难的设计问题**。这也是很多行为干预产品失败的原因——它们要么管太多（烦人），要么管太少（无效）。Bluey 的思路是用多维度信号（置信度、持续时长、历史模式）来决定干预时机，本质上是一个**动态阈值**系统：置信度越高，需要的持续时长越短；置信度越低，容忍度越高。

另外一个更深层的思考是：这个产品的核心价值不在于“监控”，而在于**给用户一个被看见的感觉**。即使 Bluey 一天都没打断你，知道它在看着你，你的行为也会发生微妙的改变——这在行为心理学上叫做**霍桑效应**。一个有趣的观察是，“被看见”本身就具有行为约束力，而不需要任何实际的惩罚或奖励。

### 四、动手构建：18分钟从零到可运行 `[开发实现部分，视频中后段约 8 分钟]`

**核心观点**

整个开发过程完全通过 ChatGPT 的 Codex 模式完成——把现有的 Bluey GitHub 仓库和详细的改造需求输入给 AI，由 AI 在18分钟内完成代码修改、双端构建和测试准备，开发者只需要反馈测试结果和调整 UI 细节。

**深度阐述**

Riley 的构建方式反映了一种全新的 AI 辅助开发工作流，他称之为“vibe coding”。他没有手动写代码，而是做了几件事：把现有的 Bluey GitHub 仓库链接给 Codex；附上了详细的提示词（包含 Decisions API 文档链接、产品需求描述、nudge 算法的设计原则等）；然后让 Codex 自己“读代码 → 理解架构 → 做改造 → 构建运行”。

提示词的核心内容（Riley 在视频中做了展示和朗读）包括：

1. **附件**：GitHub 仓库链接 + Decisions API 文档链接
2. **任务**：“将现有的 Bluey Mac/iOS 应用改造为专注伙伴（仍叫 Bluey）”
3. **架构要求**：复用现有架构和全部功能
4. **新功能**：每30秒 Mac 端截屏，连同任务描述、已用时间、空闲时长、近期检查历史发送到 Decisions API；由 AI 判断 on_task / off_task / uncertain，并返回概率和置信度
5. **干预逻辑**：短暂偏离不打断；仅当持续高置信度 off task（接近100%时约2分钟、中等置信度时3-4分钟）才提醒；两次提醒间设冷却期
6. **语气要求**：提醒要“俏皮有趣”，比如“嘿，这看起来不像你当前的任务”
7. **交付要求**：构建完整应用，端到端跑通，在电脑和手机上测试

Riley 将 ChatGPT 的推理模式设为“soul extra high”（可以理解为最高深度推理模式），然后让 AI 自己工作了约18分钟。

完成后，他展示了关键的交互流程。首先在 Mac 端打开 Bluey 应用，手机端通过扫码配对。配对成功后，他按住手机说：“嘿，Buddy。我想开始一个任务——用 Codex 构建一个应用。”Bluey 确认后，计时器启动。他开始在电脑上操作 ChatGPT/Codex，Bluey 每30秒判断他的状态（显示为绿色 on task / 棕色 off task 的可视化记录）。

**测试环节展现了两种场景**：
- **On task 场景**：他在电脑上使用 Codex 和 ChatGPT 开发应用，Bluey 判定为 on task。
- **Off task 场景**：他切换到 Twitter，不久后 Bluey 弹出提示：“嘿，这看起来不像在用 ChatGPT Codex。要不要回到 Bluey Bud 应用上？”并指向屏幕上的 Twitter 标签页。

这个测试成功验证了系统的核心能力——**基于视觉截图的语义理解 + 上下文判断 + 适时干预**。

**调试与迭代**：第一次测试后，Riley 发现计时器“太小了”，按钮布局也不理想。他直接对话式地告诉 Codex：“计时器要大、白色、显示时间，作为主视觉；按钮做成小图标放在左下角；把按住说话的提示也做成图标。”Codex 在几分钟内完成了这些 UI 调整。

他还在测试过程中加入了一个“开发者模式”，可以以4倍速度运行，这样就能快速验证“走神-提醒”循环而不必真的等30分钟。这个小细节体现了高效迭代的方法论——**通过压缩时间来加速反馈循环**。

**最终效果**：一个完整的专注伙伴系统就这样跑通了。手机上的 Bluey 在计时器下方实时显示状态，电脑屏幕的角落有一个小窗口显示 Green（on task）/ Brown（off task）的时间轴，随时可以回顾这一段时间的专注情况。

**个人感受**

Riley 在测试 Bluey 提醒他“该回到正题”时，语气中带着真实的开心和成就感。他不是在展示一个“我造了一个工具”，而是在体验“我造了一个伙伴”。他对着 Bluey 说话时用了“Hey, little guy”这样的称呼，这种对话方式揭示了他设计这个产品的底层动机：不是把 AI 当工具，而是当**一个有性格的存在**。

**延伸思考**

这个开发过程本身就是一个产品——它展示了“AI 辅助编程”已经从“代码补全”进化到了“端到端应用构建”。Riley 的角色不再是“程序员”，也不是纯粹的“指令发出者”，而更像是**产品经理 + 测试员 + 迭代反馈者**。他的核心能力在于：清楚地描述产品需求、设计干预逻辑、发现问题并及时反馈。

这可能预示着一种新的软件开发范式：**“意图驱动开发”**。一个人有一个想法，能够清晰地表达出来，然后 AI 负责“理解当前代码库 → 规划改造方案 → 实施修改 → 构建运行 → 等待反馈”。整个过程没有一行代码是手动写的，但产品最终是开发者意图的精确体现。

然而也要注意到，这种模式成功的**前提**是：Riley 对 Decisions API 有足够的理解、对产品逻辑有清晰的设计、对测试有科学的方法。AI 加速了执行，但没有替代**思考**。这一点值得所有对“AI 编程会取代程序员”这个话题感兴趣的人深思。

## 精华收获

**1. 决策式 AI 将改变应用的设计方式。**
不是每个应用都需要一个“会说话”的 AI。很多场景需要的是快速、大规模、低成本的判断能力。Decisions API 的出现让“AI 作为传感器”变得可行——你的应用可以每30秒问 AI 一次“现在是什么情况”，而不必担心速度和成本。

**2. 干预设计的核心是“时机”，而非“判断”。**
能检测到走神不算什么；能在对的时候提醒用户才算。Bluey 的 nudge logic 采用了动态阈值：置信度 × 持续时间，同时保留一定的容错空间。这种“容忍小偏差，抓住大偏差”的策略，是行为干预产品设计的黄金法则。

**3. AI 编程的真正门槛在于“想清楚”，而非“写得出”。**
Riley 用18分钟构建这个应用，但这18分钟的质量取决于他在输入时对产品的深度思考：功能目标、架构约束、干预算法、UI 优先级、测试方法。AI 让“能写”变得廉价，但“想对”仍然稀缺。

**4. 产品性格是功能不可替代的。**
Bluey 的核心竞争力不是它的屏幕分析能力，而是它的**蓝色小脸**。如果去掉那层可爱的外壳，它和任何专注监控工具没有区别。产品设计中的情感维度——语气、外观、反应方式——正是从“工具”跨越到“伙伴”的最后一步。

**5. 陪伴感可以是一种有效的专注力干预。**
“旁边有个人看着”对 ADHD 人群的专注力有真实的正面影响。Bluey 是把“社交在场”这个心理学效应做成了产品形态。这也是为什么它的提醒语是“嘿，这看起来不像你在做的事”而不是“警告：专注力下降”。
