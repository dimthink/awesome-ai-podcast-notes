# AWS CEO Matt Garman：为 AI 代理构建云的底层逻辑与未来愿景

> 本文基于 a16z 播客对 AWS CEO Matt Garman 的深度访谈整理而成。从 EC2 的诞生说起，涵盖 AWS 的初创企业战略、AI 时代的算力分配、自研芯片的演进、代理式工作流的底层重构，以及企业级 AI 的安全与信任问题。

## 第一部分：AWS 十五年的演进与初创企业战略

### 从 EC2 到年收入 1700 亿美元

**问**：你是 EC2 的第一任总经理，那是 2006 年的事。如今 AWS 的年收入已经达到约 1600 亿到 1700 亿美元。

**答**：对，大约 1690 亿到 1700 亿美元。

**问**：而且还在以 30% 多的速度增长？

**答**：37%——这是 1690 亿美元基础上的 37% 增长。

**问**：这数字相当惊人。

**答**：确实。回想当初，我们从第一天开始就在那里，甚至见证了这个业务赚到第一美元的那一刻。但有趣的是，**我们仍处于这项业务和客户机遇的早期阶段**。大多数工作负载仍然运行在本地数据中心，而且人们每天消耗的计算量都在不断增长。你既能看到 AI 带来的推力，也能看到企业迁移上云的趋势。我们的业务增长速度非常快，能参与其中是一件非常有趣的事。

**问**：确实，人们会在很长一段时间里撰写关于这段历史商业书籍的。我特别想谈谈本地部署的问题——这真的让我感到惊讶。显然，当年我也曾尽力帮助客户把一切都留在本地，而你们却成功地把所有这些都迁移到了 AWS 上。

**答**：是的，这个我们可以稍后再谈。但说到 EC2 早期，你显然是从服务初创企业起步的，如今 AWS 云服务已经大不相同。回顾这段演进过程，最让你印象深刻的是什么？

### 初创企业是 AWS 的生命线

**答**：有意思的是，我在 2005 年时曾在 AWS 实习——当时 AWS 还只是一个内部项目。那是我商学院实习期间的项目，我负责的分析任务是：**AWS 对谁最有吸引力？** 答案很可能不会让人意外——**初创企业**。

所以从 AWS 发布之初，初创企业就一直是我们的核心生命线，原因有很多：AWS 为初创企业提供的价值主张非常吸引人。我们投入了大量时间和精力，确保自己是初创企业的优秀合作伙伴——不只是提供基础设施，还提供建议、帮助客户启动公司、指导他们如何设计架构以便未来扩展，以及一系列为初创企业做的其他事情。

与此同时，这对我们来说也是一门好生意，因为**今天的初创企业就是明天的企业巨头**。虽然这个数字并不精确，但我们估计，如今 AWS 约 30% 到 40% 的收入来自在 AWS 历史周期中曾经是初创企业的公司。看着这些公司一路成长、变大、最终成为真正的企业，是一件很有趣的事。这就是为什么我们如此重视初创企业，如此关注那些"车库里两个人"式的全新创业团队。

这不仅关乎商业回报，更因为**创业者是我们学习的对象**。他们是站在技术前沿的创新者，最了解什么是可能的。他们会推动我们的服务，告诉我们他们想要什么更多的东西、什么能帮助他们跑得更快、什么能帮助他们达成目标。很多时候，他们比银行、医疗保健公司或政府机构更敢于突破边界。初创企业在推动着那个前沿，这真的帮助我们变得更好，确保我们能走在浪潮前面——**银行们五年后可能才需要的技术能力，初创企业今天就在使用**。

### 初创企业的变化：规模更大、野心更早

**问**：从过去到现在，初创企业及其对 AWS 的需求发生了怎样的变化？显然，他们现在都想要大量 GPU——这个我们之后会聊——但除此之外呢？

**答**：有两点变化。第一，**初创企业起步时的规模比以前大得多**。在我们刚起步的时候，他们可能拿到了 1000 万美元的融资，有一个应用创意，正在慢慢迭代。如今，一家公司可能从第一天起就被估值 10 亿美元，拥有 2 亿美元融资。一个团队加一个创意，他们突然就值 10 亿美元了。

**问**：他们从我们的办公室直接走进了你们的办公室。

**答**：没错，正是这样。我认为这些创意的规模、范围和野心需要更多资本。他们一开始就更大，显然也更昂贵——无论是训练一个模型，还是做许多当今团队正在做的事情。所以这是第一大变化：**起点规模真的很大**。

但我想说的第二点是，有些事情没有变。他们实际上仍然在思考：一旦规模化，我该如何设计架构？我该如何考虑安全？性能怎么做？如何拥有所有需要的能力？我该如何设置 IAM（身份与访问管理）体系，以便当员工超过三个人时系统仍然能正常运作并扩展？这很多时候正是他们选择 AWS 而不是某个"新型云"（Neocloud）的原因——他们确实需要围绕训练而来的那些安全能力和其他能力。

我认为，规模爬升的速度今天绝对不同了。同时，我们越来越多地看到**团队想要一个不仅适合人、也适合 AI 代理（Agent）使用的云**——这正是我们投入大量精力的方向：如何考虑大规模部署？如何考虑性能？如何提供一个定义良好的 API 接口，让代理能够轻松穿越和协作？

这是我们天生就擅长的事情，但我们也确实加倍投入，确保诸如**"3 秒内启动一个数据库"**这样的能力真正落地，以满足代理的需求。

## 第二部分：AI 代理时代的云基础设施重构

### 为代理优化的服务与"上下文层"

**问**：你们有没有推出哪些明确面向代理或代理开发者的新服务？

**答**：我们做的是优化了一些现有服务，使它们既能为人工作，也能为代理工作。我们确实有一些专门用于构建代理的服务，比如 **Agent Core** 和 **Bedrock** 等等。

但当我们审视像 S3 这样的底层组件时——S3 存储着绝大多数公司的数据——就会发现，人类和代理的用例其实很相似，但需要做出一些调整。我们目前有一项处于预览或测试阶段的功能，叫 **AWS Context（AWS 上下文层）**，它允许你构建一个上下文层，让代理能够更轻松地跨各种数据源找到它们想要的所有数据。无论你的数据存储在 Aurora、S3 还是 AWS 的其他地方，你都可以构建这个上下文层。人类不一定会以这种方式访问数据，但代理实际上很乐意跨所有这些不同的数据源工作。

除此之外，你还需要关注延迟表现、吞吐能力、底层引擎是否足够快速和可扩展。有意思的是，**代理非常关注尾部延迟（tail latency）**，而人类不一定总是关心 S3 的 P999（99.9 分位）延迟——但代理会在意，并会被这些问题卡住。这是我们长期以来一直关注的事情，从性能角度看，这正是**为什么代理工作流（Agentic Workflows）在 AWS 上表现优于其他任何地方**的原因之一。

### "传统"服务如何重新架构

**问**：我们经常看到许多公司起步时的标配说法是：代理在为它们编写所有代码、选择数据库、选择邮件服务器，你能说出名的一切都是代理在选。AWS 对于这些"遗留服务"（如果你愿意这么说的话）是否也考虑过重新架构？

**答**：是的，我们确实考虑过一些事情。**核心底层构件本身状态非常好**，但有一个可用性层面的问题我们一直在思考：如何让那些最简单的用例更方便使用？

我们发现，绝大多数客户会告诉他们的编程代理——无论是 Kira、Claude 还是 Codeex——"我想在 AWS 上构建应用，这是我的凭证，这是我的配置，我想这样部署。"然后代理就会很好地去执行。

但也有一些用例，客户本来就不在云上，只是想试试某些东西。你说"部署"，很多时候这可能落到我们的一些合作伙伴那里，因为他们在更上层提供了一层更易用的体验——这也挺好，我们非常喜欢合作伙伴在这些方面的工作。

但确实有一些我们正在做的新东西：如果你是一个全新的用户，还没有 AWS 账号，还没有设置好 IAM——今天或者几个月前，启动一个账号要困难得多。你得定义 VPC（虚拟私有云）、定义 IAM 角色等等，这些规则已经存在了 20 年。这些其实是非常重要的东西，但只有当你发展到一定规模时才真正需要。

我们从客户那里听到的反馈是：这是一个艰难的选择——他们知道几个月或几年后需要这些能力，但现在他们只想使用服务，不想操心这些。

**所以我们实际上推出了一项新体验**：现在创建一个新的 AWS 账户时——我们正在逐步推出这个功能，我不确定现在是否已经全量上线——你不再需要做那些事情，甚至不需要提供信用卡，你可以直接用 Gmail 账号注册。所有那些东西都在后台默认处理好了，**30 秒内你就可以在完整的 AWS 账户中运行起来**。对于这批用户来说，这正是代理想要的能力——它们不想经历设置 VPC 这些步骤。

还有一点很棒：它并不是一个"简化版账户"然后以后还得迁移。如果你说"我现在真的想要规模化"或者"我想发展成组织"，你其实已经在一个真正的 AWS 账户里了，之后可以在需要时随时进入并配置那些高级功能。**没有任何迁移或后续搬家的问题**。这是我们认真思考的核心问题之一：如何让客户不必在简化与深度之间做选择，而是为他们提供一个轻松的入口，进入我们知道的、当他们开始规模化时一定会需要的那些深度功能。

### 代理接管后最难的调整是什么

**问**：随着代理开始接管开发者和基础设施团队的工作，作为全球最大的服务提供商，你们面临的最困难的事情是什么？

**答**：首先，就像我说的，我们的大部分基础设施天生就为大规模做好了准备，这很好。但有几种有趣的范式转移值得注意。可以说，我们的一些系统——我不会说过度设计——举个例子：**许多代理想创建数据库、做一点工作、然后把数据库销毁**。这种场景真的需要数据库具备 9 个 9（99.9999%）的持久性吗？不一定。

所以有一些事情我们正在重新思考：当你创建一个 Aurora 数据库作为生产数据库时，你确实想要 5 个 9 的持久性、可用性和一切保障。但对于代理用例，这些规格可以说是过度设计的。这很难办——我们不太想提供一个"非持久化"的选项，那也会带来问题，因为你永远无法真正知道某个被创建的数据库是想长期存在还是短暂存在。

**我们正努力做的是：如何同时实现两者？** 既能让你快速创建、用完即弃、不浪费资源，也能在你想让它长期保留时成长为一个大型生产数据库。这是我们围绕"传统生产系统能力"与"代理基础设施的临时性"如何匹配的积极思考。

另一个有趣的方向是**可持久资源的创建规模和速度**：创建和销毁这些资源的速度本身就是一个重要课题。还有一个是我们正在积极思考的——**代理需要哪些全新的构建块**，这是以前根本不存在的东西。

比如：**计算沙箱（Compute Sandboxes）、网关（Gateways）、代理权限（Agent Permissions）**——区别于人的权限或服务角色权限。这些都是我们已经构建、正在构建和积极思考的东西。它们不是对现有构建块的不同使用方式，而是全新的构建块。很显然，你需要为代理设置不同于人的权限，不能简单地把某个人的权限交给它，让它肆意妄为。你真正想要的是**非常短时、有时间盒子（time-boxed）的任务级权限**。你甚至可能不想给代理整个工具的权限，而是想获得更细粒度的授权，精确控制代理能做什么。

说到沙箱：你需要一个轻量级的沙箱，具备出色的安全边界。我们使用 Firecracker（我们的微型虚拟机）做了大量工作——实际上很多沙箱公司初创企业都在用 Firecracker。这是我们大约 10 年前发明的技术。虽然它当初并不是专门为代理设计的，但**对代理来说它确实非常好用**：可以极快地启动，有出色的安全边界，而且没有传统大型 VM 带来的虚拟化开销。

## 第三部分：GPU 算力分配与资本支出策略

### 算力短缺时代的平衡术

**问**：很明显你们运营着巨大的 GPU 集群，而且每天都在增加。但前沿实验室会吞噬掉所有可用的 GPU——这可以理解。同时你们又想扶持那些将成为明日企业的新兴公司，就像你说的。**你们如何平衡这些算力需求与小型公司的需求**？

**答**：这是个好问题。有几件事让这个挑战变大了。首先，部署所有人都需要的算力所需的资本支出（Capex）是巨大的。

**问**：你们的资本支出大约是 2000 亿还是多少？

**答**：2026 年大概是 **2200 亿美元**。这确实是我们有史以来最大的单年支出——也许也是任何公司有史以来最大的单年支出。而我们短期内不打算放缓，因为需求实在太大了。

在某一个时间点上，你会受到限制：数据中心能建多快？资本能部署多快？内存和芯片能多快到位？电力、数据中心、资本、内存、芯片、施工人员——这些东西在不同时间点都会成为约束。尤其是施工人员，现在非常紧俏。

有了我们能部署的容量——虽然依然不够用——**我们确实在认真思考分配策略**。首先，我们是大型前沿实验室的好伙伴，包括 Anthropic、OpenAI、Meta 以及其他大型客户，我们希望持续投资于他们。我们也有一批大型企业客户——Salesforce、JPMorgan 等等——它们对较少量的 GPU 或加速器有需求，有时想用 Trainium，有时想要 NVIDIA GPU，我们也必须支持它们。

关键之处在于：**我们非常刻意地确保为初创企业保留容量**。我们实行配额分配机制——理论上，我们完全可以把所有 GPU 或 AI 加速器都卖给大型前沿实验室，然后收工。但我们选择不这么做，因为**我们希望整个生态系统健康地成长**。他们确实能获得很大份额，但我们也想支持更广泛的客户群——这种多元化对我们更健康，而且我们也知道这些初创企业终将长成巨头。

我最近看到的数据是：我们对大约 **60% 的请求**会在某种形式上给出肯定的答复——有时是稍晚一些，有时是在不同区域，有时是略有不同的配置。我们真的在努力倾斜资源并尽力分配。而你每一家初创企业都想要更多——所以我们工作非常努力。

这确实很难。就像很多人说的，这是一个"甜蜜的烦恼"，但无论如何它仍然是一个问题。我们最近宣布，未来几年将采购 **200 万块 NVIDIA GPU**。这是巨量的算力——但仍然不一定够。说到底，我们又会受到其他组件的限制。**我们对保留初创企业的容量非常上心**——我知道没有足够的算力是件痛苦的事，我们会继续努力。

### 资本支出的历史跨越与 AI 的推动

**问**：你们的资本支出是什么时候突破——我是说纯 AWS——哪怕 10 亿美元或 100 亿美元一年？毕竟亚马逊本身是家更大的公司。

**答**：这我还真得回去查一下。我不太确定具体时间，但过去几年它确实以更有意义的方式快速上升了。AI 的建设工程无疑大幅加速了我们的资本支出。可以说，最近三四年，我们的资本支出显著加速。虽然不知道何时突破的 10 亿，但现在都到 2200 亿了，可见我们已经持续投入了相当长的时间。公司一直在很好地为这些投入提供资金，AWS 这项业务也确实值得投资。

**问**：是的，当然。

**答**：其实很长一段时间里，我们是**领先于需求进行投资**的。但在 GPU 真正大规模普及之后，许多弹性空间——很遗憾——消失了。希望在核心计算和存储领域我们能恢复那种弹性。过去这段时间我们一直在大量投入，而且**对当前的投入感到非常满意**。

### "AI 泡沫"之争：AWS 的底气在哪里

**问**：你们对需求的洞察是无可匹敌的——你们能看到全球各地、所有细分市场的需求，包括企业、大型实验室、AI 原生公司等等。如果要有人能先看到拐点，那应该是你们。

**答**：希望如此。这正是我们的计划。说实话，我们花了大量时间思考这件事，对如何花费股东资本非常审慎，也认为我们正在做出很棒的投资。我们有很多良好的保护机制来确保资金的理性投放。

关于泡沫的担忧——因为我们采取了多元化的方式，**并非所有算力都捆绑在一两个客户身上**。如果去看某些新型云或其他服务商，你会看到某些客户集中度高达 30%、40%、50% 甚至 60%；而我们远非如此，最高的单一客户也只是个位数的百分比，通常还更低。所以我们面对单一客户的风险要小得多。

更重要的是，因为我们拥有丰富的服务矩阵——**AWS 是客户真正用来承载生产工作负载的地方**——我们目前大多数使用量实际上是核心计算、存储和推理，这些都是应用程序的组成部分。这些工作负载不会因为任何风吹草动就消失。你去问客户，他们会告诉你当前的能力和成本已经带来了正回报；几乎每一个客户都会说"当然有"。

那么这就不会消失——不存在一个"泡沫"让客户停止在这些方面花钱。风投模型不也是这样吗？每一个十亿美元估值的初创企业都能成功吗？不一定。但这本来就是游戏规则，50 年来一直如此——数字变了，但原理没变：你押注 10 家，有 1 家成了，就覆盖了另外 10 家的成本。互联网时代也出现过泡沫，很多互联网公司没有挺过去，但互联网本身仍然存在；那些拥有持久业务的公司——谷歌、亚马逊等等——都做得非常好。

所以我们对自己做的投资和未来的持续投入感到非常乐观。

### 千亿美元级资本支出的决策挑战：从电力到供应链

**问**：随着支出规模越来越大——你们写的不是 10 亿美元的支票，而是 500 亿美元的支票——你们的规划和决策流程是否发生了戏剧性的变化？

**答**：是的，也不全是。在一些方面我们依然非常乐观，继续向前推进，但流程确实变了。**有些东西是彻底改变了的**——比如，你怎么预估 2028 年的需求？有很多我们以前根本不用考虑的事情，现在必须考虑了。

举个例子：回到 15 年前，如果我们需要更多电力，就向电力公司申请多几兆瓦——几十兆瓦——他们就给我们了，因为 10 兆瓦不算什么，足够我们继续成长。现在呢？**我们得自带电力**。我们为电力项目付费，为可再生能源项目付费。过去 10 年，我们每年都是最大的可再生能源采购方之一。我们经常签约新的太阳能项目、新的核电项目。

**问**：你们说的是表后（behind-the-meter）电力，还是与运营商合作？

**答**：两种都会做。很多时候，对于这些电力项目，我们会支付资本并资助项目本身，项目并网后我们再获得相应的电力信用额度。有时也会做表后电力。在我们这个规模上，必须同时考虑所有这些方式。

这种规划需要你往前看 20 年：如何考虑电力、输电、资本。这是我们以前从不需要思考的事情。过去考虑服务器需求时，我们只需要做几个季度的需求预测，与供应商沟通；现在则要**规划很多年**——2026 年需要什么、2027 年需要什么、2028 年需要什么。

但这也是我们带给客户的核心价值之一：这些事情客户自己是干不了的。他们不会去搞电力，也不会规划 2028 年的内存需求。这正是我们为广泛客户群带来的真正的价值之一——**我们为你处理了整套你不需要操心的事情**。

**问**：可以说，你们基本上是几乎所有服务器组件的最大采购方，对吗？

**答**：我不确定是否所有，但可以肯定我们是最大的组件采购方之一——这取决于你怎么定义和衡量。但确实，在这一点上我们投入了极大的关注。

### 未来的关键约束：永远在变化的瓶颈

**问**：你预计哪些约束会变得最严重——比如说 2027 到 2028 年？哪些约束会缓解？

**答**：这个问题很有意思。让我绕个圈子来回答：我记得大学时读过的《目标》（The Goal）。这本书当时让我觉得永远不会有用，但事实证明——**瓶颈永远不会只有一个，永远只会有一个最新的瓶颈**。当你解决了一个，另一个就会出现。

所以 2028 年会发生什么瓶颈？我不确定，但我能确定一定会有。对我们来说，几乎每个月都在变：电力不够？然后电力不再是约束了——可能是内存不够、可能是台积电的产能、可能是 HBM（高带宽内存）、可能是网络组件、可能是供应链某个环节的"闪烁点"——连连接器都可能成为问题。某些时候，所有零件你都得考虑。

而且**地点也很重要**：印尼可能电力充沛，但德国不够。你需要考虑在世界的哪个地方配置容量——因为不是所有东西都是完全可替代的。可能是硬盘驱动器，可能是 SSD。我们追踪和思考的组件有成千上万种：有些依赖供应商管理，有些我们直接管理。我们有一支非常出色的团队负责这件事，他们是行业领先的。

大概十年前我们就预见到这个问题，不只是追踪"需要多少台服务器"，而是**沿着供应链往下看四层、五层，找出可能导致问题的底层组件，确保供应保障**。如果你还记得——十年前泰国发生洪水时，整个行业都没硬盘了；再后来有内存危机。所以我们把所有这些都系统地考虑进去了，包括制造环节的多元化布局。我们永远不会做到完美，但**总会有不同的供应约束**。

## 第四部分：数据中心的社会价值与行业声誉

### 回应当地社区质疑：数据中心的公共价值

**问**：围绕数据中心有很多广泛的争论。像我们这些人肯定站在支持的一边。但你觉得，作为一个行业，我们是否没有做好解释工作——**解释数据中心为什么对美国、对世界是好事**？Andy 的团队内部是怎么讨论这个问题的？

**答**：我同意，我们确实需要更加直言不讳、更加主动。我们实际上做了很多对运营所在社区非常有益的事情。我们大量思考如何为这些数据中心引入可再生能源，如何做到水正效益（water positive）。其实我们数据中心的用水量非常非常少，主要依靠自然空气冷却。我们也在思考如何成为社区的好参与者，如何为当地带来高薪工作。

**并非所有数据中心运营商都这样做**。有一些广为人知的负面例子——有些运营商不注重法规，认为规则不适用，或者只求快速上线而不考虑这些。这给整个行业带来了问题，因为每个人都被归入同一类印象。

所以你说得对——我们需要更积极、更响亮地宣传我们带来的益处。想一想如何帮助社区理解我们带来的价值：从他们日常使用的服务来说——你去问一个社区："你们不想用 Netflix 吗？"他们肯定说"不，我还是想用 Netflix 的"。

关键在于：我们需要突出我们的贡献。我最近看到一份报告，在我们运营的一个社区，**由于我们缴纳的税款，那个县里的每个人都因此每年少交 5000 美元的税**。但我们没有告诉他们，他们甚至不知道这件事——这对他们完全隐形。

如果我们告诉社区："顺便说一句，因为数据中心的存在，你的税单每年少了 5000 美元"——他们对远处那栋建筑的想法可能会有所不同。

但并不是所有人都这么做。整个数据中心行业——不只是我们——大部分参与者其实是好的，只是少数不良分子造成了最近的一些负面情绪。**我们需要更好地展示谁是良好的企业公民，谁不是**。

## 第五部分：自研芯片之路——从 Nitro 到 Graviton 到 Trainium

### 从网络卸载卡到全面自研的演进逻辑

**问**：在转向硬件话题之前，我想聊聊训练芯片和你们自研芯片的整个历史。我们很早就成为 Nitro 的首批合作伙伴之一。然后你们推出了 Graviton，取得了巨大进展。**是什么思考促使你们决定自己做芯片？** 进展如何？现在处于什么阶段？

**答**：这是一个非常精彩的故事，也是 AWS 创新文化的绝佳范例：我们不断尝试、持续迭代，逐步把想法做大——但**每一步都是先证明自己，而不是豪赌**。

拿 Nitro 举例：大概 13 到 14 年前，我们发现虚拟化税（virtualization tax）占了整体资源的很大比例。客户告诉我们："我想要裸金属性能。"他们希望拥有服务器所有资源，不希望任何虚拟化开销。

我们的第一步是：**用一块网络卸载卡（offload card），把所有的网络虚拟化从主机上搬走**，让网络虚拟化更接近裸金属性能。当时虽然还不是真正的裸金属，但已经非常接近了。

然后我们变得非常兴奋，心想：能不能把存储虚拟化也卸载掉？但当时的网络卸载卡都做不到。于是我们找到了一家特殊的公司——他们的卸载卡上有一些 ARM 核心，用于其他目的（我记不清原本的用途了）。我们问他们："你们能不能用这些 ARM 核心来做存储虚拟化和其他功能？"他们说可以试试。我们与这家团队深入合作——是的，就是后来的 Nitro 团队。我们非常喜欢那个团队：真正创新、使命驱动、真正渴望解决问题。

于是我们收购了他们，并让他们做一块更大的卡，能承载所有网络虚拟化，为我们提供一台**完全没有虚拟化开销的裸金属服务器**——所有操作都通过卡上的 API 完成。因为我们有一个清晰的信念：性能会更好，资源利用率会更高，安全隔离也会好得多——**我们能够真正向客户承诺"我们对你们运行中的 VM 没有任何访问权限"**。在过去十年里，这个技术为我们带来了巨大优势。坦率地说，我们一直处于领先地位，其他人跟进得很慢，因为这不是一个可以普遍复制的东西。

做了这些之后，我们说：既然我们已经取得了这么多进展，那块卸载卡上有不少 ARM 核心——**何不把它变成一台服务器？** 这就是 Graviton 的起点。第一代 Graviton 是一台性能非常低的小型服务器，但客户非常兴奋："我们想要一台 ARM 服务器，这太有意思了。"于是我们沿着这条路走了下去。

我们当时看到了 ARM 核心的斜率——性能在提升、功耗在下降，这两条曲线明确显示，迟早会有一个交叉点，这个架构将变得非常好用。**这个生态需要的只是有人去推动、去补全其中的拼图**。于是 Graviton 诞生了，如今它已经是大获成功。

**问**：你们公开过 Graviton 占整个计算集群的比例吗？

**答**：我们每年部署的 Graviton 芯片比其他任何类型都多。它非常受欢迎。你看，**它便宜 20%，性能好 20%**——过去五六年来一直如此，这是非常容易理解的价值主张。我们前 100 大客户中，超过 90% 都以某种形式在它们的集群中使用 Graviton。

这对我们和客户都是巨大的胜利——**对客户来说，迁移到 Graviton 是降低账单最简便的方法**。我们有很多例子，客户迁移了整个集群后**服务器数量直接减半**——因为性能提升如此之大，每台服务器还更便宜了。这是巨大的双赢。

### Trainium：训练芯片还是推理芯片？

**答**：大约五六年前，我们看到了 AI 计算的崛起——当时远没有预料到今天的热度，但已经意识到它会成为一个重大的推动力。于是我们开始构建自己的第一颗训练芯片——Trainium。如今我们已经在市场上推出了**第三代 Trainium 3**，取得了非常出色的成果。目前我们的容量已经售罄，可能排到明年年底左右。我们也在想办法留出一些容量给初创企业，因为我们看到的成果太棒了。

目前**Bedrock 上的大多数流量都运行在 Trainium 上**。我们与 Anthropic 和 OpenAI 都达成了重要合作，让它们基于 Trainium 构建。同时还有一批小型初创企业也在基于 Trainium 开发——大概有六到十几家。

**问**：从名字看，Trainium 是训练芯片？

**答**：没错，我们确实起了个不好的名字。我们一向不擅长起名——这不是我们的强项。最初我们有一款推理芯片叫 Inferentia，一款训练芯片叫 Trainium。但随著模型越来越大，你会发现，**你实际上也想在这类大型系统上运行推理**——而事实证明，Trainium 现在可能是市场上最好的推理芯片之一，无论是绝对性能还是性价比。

**问**：更好的内存带宽？优势在哪里？

**答**：它的架构与其他芯片有些不同，而且便宜得多。从性价比和绝对性能来看，Trainium 都非常出色。我们大量将其用于推理——Bedrock 的许多推理负载都跑在它上面。但它同时也是一个很好的训练芯片。我们的大多数客户使用量并非训练模型，而是使用模型——这让很多人在后台间接使用到了它。

同时，很多大客户也对用 Trainium 做训练集群感兴趣。特别是随着 **Trainium 3 和 Trainium 4** 的推出——我们发布了 Trainium 4 的消息但还没有正式发布——人们看过架构后会说："是了，这就是我未来训练集群想要的方案。"我们对它在未来大规模训练集群方向上的前景非常兴奋。

## 第六部分：企业 AI 代理的采用现状与挑战

### 企业代理的现状：简单、非自主、但已有价值

**问**：我们回到代理的话题，但从大型企业或中大型企业的视角来看：**它们的采用进展如何？已经收获了什么效益？从你们的视角来看未来的路线图是怎样的？**

**答**：非常好的问题，也是我们花了大量时间思考的问题。在与客户的交流中，我认为目前企业已经能从已部署的代理中获得很多价值。不过，大多数企业构建的代理**相对简单直接**，大多还**不是自主型的**——如果打个比方，它们仍然需要"人在回路"（human in the loop）。

客户已经从中获得了很多价值。他们真正在思考的是：**如何让这些代理变得自主，同时保持安全**。我认为有两件事目前阻碍了客户继续扩大规模。虽然这已经是个相当大的业务了，但它的真正潜力在于彻底改变每一个客户、每一个工作流。

**第一大挑战：如何思考这件事**。最初我们看到的是：企业有一个工作流，然后说"太好了，让代理照着这个工作流做"。但我们真正鼓励客户的是——**不要只是复制**："Bob 做步骤 1、2、3、4、5，所以代理也做步骤 1、2、3、4、5，鲍勃最后检查一下。"这不是你真正想要的模式。

你需要退一步思考：**如果我想完成某件事，代理能不能换一种方式来做？** 它可以以大规模并行的方式运行，尝试 50 种不同的方法，然后达成正确的结果。关键是如何帮助它达到那个正确结果——**重新思考"计算机如何解决问题"而非"人类如何解决问题"**。

所以其中一项工作，就是帮助客户理解如何以"白板思维"（green field）去思考——这才是真正产生价值的地方：不是复制你正在做的事，而是**从全新视角重新思考如何解决一个完全不同的问题**。我相信这正是你们的许多初创企业在思考的：如何帮助客户以全新方式解决问题，而不是复制今天已有的流程。

**第二大挑战：如何将代理变成完全自主的工作流，并真正信任它们**。我们花了大量时间思考如何构建服务，帮助企业感到系统安全、相信代理可以做出决策——有正确的护栏、正确的数据权限、不会删除生产系统、不会犯下灾难性错误。

目前，这种顾虑很可能在阻止人们大步前进——也许恰当的说法是：**它阻止企业直接说"放手去干"**。你实际上并不希望一个代理疯狂运行，意外删掉生产数据库——那会是场灾难。这是我们正在与客户共同解决的问题：如何帮助他们设计架构，并且坦率地说，**发明新的技术和能力来帮助他们解决这个问题**。这是我们持续创新的领域之一，我对我们正在酝酿的一些优秀想法和技术充满信心。

### 评估（Eval）体系：企业还不会做

**问**：企业在学习构建评估（eval）系统等方面是否还需要帮助？

**答**：说实话，两端都需要。**评估怎么做？** 如何建立一个持续的测试循环？如何以合理的方式考虑目标达成（goal seeking）？如何标记数据，让评估能真正近似你在生产中要做的事情？如何在生产中衡量并进行回测，以免出现漂移？

所有这些问题都是企业今天不知道如何解决的——我不确定今天是否真的有人擅长解决这些问题。这就是为什么你会看到那么多 FDE（前沿部署工程师，Forward Deployment Engineer）团队应运而生，AWS 和我们的合作伙伴正大力投入这一行动。**这是客户最需要帮助的领域**。

我们的理念是：**我们要训练客户自己能够去做这件事**。这不是传统的"人海咨询"模式——让客户永远依赖外部顾问。我们对 FDE 的运作方式是：进入一家愿意承担责任的客户，在 45 天内教会他们如何制作评估、如何标记数据，与他们并肩工作，然后离开时，**这家客户已经训练有素、可以自己驾驭了**。这正是客户告诉我们他们想要的——他们不想被外部劳动力绑定五年。但他们今天确实需要帮助。

### 开源模型 + 私有数据微调：AWS 的立场

**问**：更进一步，你的一些同行说过：你不能把所有企业数据都喂给大型前沿模型。企业应该做的是**拿一个开源模型，在自己数据上做后训练（post-train）**，用自己的数据、工作流和术语来调教它。你对此怎么看？你的客户真的在这么做吗？

**答**：关于第一点，我完全同意：**企业数据是其最有价值的资产**。这正是我们从一开始就以现在的模式构建 Bedrock 的原因。我们有一个保证：**你的数据永远不会离开你的 VPC（虚拟私有云）**。如果你在 Bedrock 内部运行，你的数据不会回到模型提供商那里，他们永远看不到你的提示词——一切都在你自己可信的环境中。

这就是为什么企业更愿意在 Bedrock 上运行，为什么你会看到这个业务在爆炸式增长——数以百计，每一周我们都能看到业务在膨胀。这也是为什么 OpenAI 的工作负载在迁移到 Bedrock，为什么 Anthropic 在快速增长。无论你使用开放模型还是封闭前沿模型，Bedrock 都是一个很好的解决方案。

顺便说一句——如果你还记得，三年前我因为 AWS 在 AI 领域"动作慢"而受到了很多批评。但我们当时刻意先把地基打好：我们说，**我们不会急着推出一个不成熟的服务，我们要真正思考如何保护客户数据**，构建一个对我们已知用例来说持久耐用的服务。如今，当人们从概念验证（POC）转向生产时，**绝大多数都落在了 AWS 的 Bedrock 上**。

我们还提供开放模型和专有模型，以及围绕它们的一系列能力，比如 Agent Core 这些构建块，让你更容易用任何你想要模型构建代理——无论这些模型是否在 Bedrock 里。你甚至可以用 Gemini 或其他模型。

**让数据回流到模型提供商，我认为这是一件危险的事情**。

至于开源权重模型，这也是我兴奋的领域。我们正在大力加强对开源权重模型的支持，努力建立一个良好的环境。坦率地说，这是目前许多客户都认同的方向：他们拥有有意义的数据资产，如果能通过某种后训练、微调，将专有数据融入一个开源权重模型，甚至进行蒸馏（distill），**他们就能以更低成本获得性能更好的模型**。

不过这里有很多环节需要打通：你需要一个良好的评估体系来验证这是否真的有效。今天，大多数人是在 SageMaker 上做这些工作的。我认为还有更多工作可以让这个过程更简单。但如果你去看看人们在做什么，他们确实是在 AWS 上用 SageMaker 做后训练，也通过 SageMaker 托管推理。

**问**：SageMaker 正在获得新的生命。

**答**：确实。它本来就是模型构建平台，而现在企业在这个世界里的核心工作就是构建自己的定制模型。SageMaker 是绝佳的场所。我们需要持续构建更多功能，让跨不同开源权重模型的测试和对比更容易。这是一个不断演进的领域，一个非常有趣的领域，也是我们要确保客户拥有所有合适工具的地方——只要他们有合适的数据和专业知识走这条路。

## 第七部分：AI 安全、攻击与保护企业数据

### CEO 们最关心的问题

**问**：围绕 AI 扩展风险、各种安全漏洞和 Hugging Face 攻击事件等等，**CEO 们向你提出了哪些问题？**

**答**：有一大堆。他们主要想表达的是——回到那个核心问题：**"当我部署代理时，如何信任它们会按我的意图行事？"**

我们一直在大力投资，构建让人们能在自己环境中安全部署代理的能力，并考虑相应的控制机制。这些包括：如何确保代理拥有正确的权限？如何确保正确的沙箱隔离？如何设置正确的防护栏？如何真正有意地明确你希望代理做什么、不做什么？是否有人在回路之中？我们花了很多时间与客户一起思考：**如何实现安全的代理部署并不断改进**，以及我们需要构建哪些额外能力来帮助人们安全部署代理。

另一个让很多人担忧的角度是：**这些非常强大的模型是否会成为攻击服务（attack services）**，成为一种新的攻击面。我的观点是：是的，这是一个对客户环境的真实风险，但它同时也是一个真正的机会。

为此，我们最近推出了一项名为 **Continuum** 的服务——它利用这些强大的模型帮助客户保护环境安全。它能审查你的整个环境，寻找漏洞，使用模型帮你发现以前没发现的漏洞。最重要的是，它能够**按优先级排序**——因为我们了解客户的上下文：环境如何设置、权限在哪里、哪里有补偿控制（compensating controls）会让攻击更难或更容易发生。

Continuum 在客户中非常受欢迎。我们对 AI 驱动的安全能力非常乐观——因为**在某个时点上，客户需要的是"机器速度"的安全响应，而不是"人类速度"的**——不能永远是"警报响了，人再去看"。我们正在快速奔跑，帮助客户构建这一切，保护他们的环境。我对 Continuum 团队的进展感到非常兴奋。

## 第八部分：AWS 内部的 AI 代理革命

### 全公司范围的 Agent 应用：从 HR 到财务到安全

**问**：回到 AWS 自身——**代理在你们内部的采用情况如何？**

**答**：Continuum 本质上是把我们内部在安全领域使用 AI 的做法对外产品化了。我们在内部大量使用 AI 做安全，也大量使用 AI 做软件开发。实际上，我们**在整个业务范围内都在使用代理**，这非常酷。

我们向每一位亚马逊员工推出了 **Amazon Q**（我们的 AI 助手）。现在，HR 团队在构建代理，用于处理过去需要团队数周才能完成的工作——现在一个人几小时就能搞定团队规划和资源管理。财务团队也在构建代理，帮助从各处提取税务规则，确保各种合规要求。

看到那些过去被软件开发人员"卡住"的事情——**现在业务线的人自己就能解锁并更快创新**，真是太酷了。Q 获得了爆炸性的增长：从小型初创企业到全球最大的企业，都在将其推广到整个用户群，让所有企业数据都能被轻松访问，并用代理能力加速工作。

**问**：你们以对运营中一切事物进行度量而闻名。**你们在哪里看到了最大的收益？**

**答**：显然，答案是**软件开发**——这是最真实的答案，以及它的衍生收益。软件开发的整体速度——不仅是编码——确实大幅提升了。产品交付速度与过去完全不同。

你可以看到：AWS 一直以快速推出新功能而闻名，而在过去一年左右，这个速度得到了"涡轮增压"般的提升。我们把这种模式称为**"前沿团队"（frontier teams）**——他们以代理优先（agent-first）的方式开发，而不是传统开发模式。这不再是代码补全，**真的是代理在写所有代码，你只是管理一群代理并驱动它们**。看到为客户创新的速度大幅提升，真的很有趣——而且必须如此，因为客户对新能力的胃口几乎是无法满足的。

### 组织与管理方式将如何改变

**问**：从组织角度看，你们对组织结构应该如何调整有什么见解吗？

**答**：我不确定有标准答案。但我想说：**代理管理人，人管理代理**——这种模式会存在很长时间。我认为组织确实会改变，但我还没有找到神奇答案。我们正在积极探索。

**问**：你们在内部进行各种实验吗？

**答**：是的，我们在尝试各种实验。我们在思考"小组"（pods）的概念。举一个例子：在产品组织中，过去会有一个团队长期拥有某个特定能力领域，可能需要 10 个人做某件事。今天，创新速度如此之快，**10 个人不一定是必需的——三到四个人就够了**。而且因为他们建得如此之快，你其实会想让他们频繁移动到不同的项目和问题上。

如何在像 AWS 这样大的组织中，既维持已经构建的东西，又保持敏捷灵活性以随时重新组队？这是我们正在实验和探索的事情。它对员工也很赋能——他们很喜欢，因为他们能更快构建、做更多事。但这里确实有很多实实在在的工作要做。
