# AI 下半场，不会只剩一个超级模型——对话 Pyromind 创始人/CEO Kevin Ding

**来源**：Koji Yang《十字路口》视频播客

**本期嘉宾**：Kevin Ding，Pyromind 创始人兼 CEO。Pyromind 此前完成了天使轮融资，投资机构包括高瓴、百度风投、蓝驰等，并组建了约 20 人的团队。公司所在的赛道是 **RL as a Service（强化学习即服务 / 后训练即服务）**，并正进一步走向 **AutoRL（自动强化学习）** 方向。

---

## 一、快问快答：认识 Kevin

**问：你的年龄是？**
我是 94 年的，32 岁。

**问：你的求学经历？**
伦敦国王学院，Computer Science（计算机科学）。

**问：MBTI 和星座？**
按测试结果看是 INTJ，但我的感觉可能介于 I 和 E 之间。星座是摩羯座。

**问：请用一句话介绍 Pyromind。**
最终定位就是一个 **AutoRL**。它跟现在大家一直在讨论的 **RSI（Recursive Self-Improvement，递归自我改进）** 方向，其实是一个非常具象化的实现路径。

**问：融资情况如何？**
我们是去年公司成立之后做了一轮融资，高瓴、百度风投、蓝驰，还有 Typical 投了我们。

**问：目前团队的规模？**
我们现在有 20 多人。

**问：收入和利润方面方便讲吗？**
具体数值就先不声张了。但比较振奋人心的一点是，我们初步跑通了 **PMF（Product-Market Fit，产品市场契合度）**。

**问：什么样的 PMF 跑通了？**
两个方向吧。第一，证明了我们用 AutoRL 这种方式实现的 RSI 在生产环境是有价值的，商业模型至少成立；第二，在可扩展性上，无论是横向的场景复制还是客户复制，我们的工作量是逐步递减的。

**问：创业之前做过什么？**
我之前有很多经历放在偏 Infra（基础设施）这里。之前也在阿里云，做过弹性 GPU 实例，包括训练 GPU 的这些集群。

---

## 二、创业起点：为什么选择 AutoRL 和 RSI？

**问：当时是看到了什么样的机会，决定创业做 Pyromind？**

当时我的想法是这样：**模型预训练这件事，远远没有到终结的时候**。到了 25 年下半年，社区也好、谷歌也好、国内技术圈也好，大家都在讨论 AI 可能要进入下半场。

下半场的说法出现了两个方向：
1. 一个方向认为，我们继续沿着预训练走，AI 到来的形式会是一个**超级庞大的中心化模型**，能解决绝大多数场景的问题，效果足够好。
2. 另一条路线认为，最终的形态会是**服务化的形态，是 Agent 蜂群的形态**。

我个人肯定偏向后者，因为我觉得这种更实际。世界上需要被 AI 解决的问题和场景，从当下时间点看已经无穷无尽；随着时间的推移，还会产生新的场景，而且场景本身也不是静态的。在这种模式下，如果我们试图用一种有限参数的模型去泛化掉无限的场景，至少在 Transformer 这个架构上，实现起来还是蛮有挑战的。

**问：过了一年多，你有没有看到一些信号，让你觉得一开始的 Bet 越来越成立？**

是的。首先，第二条路必然是成立的。我不能说证伪第一条路，但能论证的是**服务化的路线一定成立**，因为需求一直就在那里，而且还在不断增长。

这一年我看到的变化是：**为什么现在大家开始提 RSI？为什么之前 RSI 热度没那么高？** 这其实就是服务化带来的结果——Agent 布得多了。想象一下，一个人日常带着几十个 Agent 去做事，他不可能有精力去维护每一个 Agent 的演进。RSI 之所以被需要，就是因为 **Agent 开始多起来了**。当一个一个 Agent 嵌入到场景里时，我们最终的衡量方式是：它在时间轴上要一直表现符合预期。要实现这件事，Agent 就需要能自我迭代、自我改进。

**问：你们一开始做 Pyromind 的时候，就想到了用 AutoRL 去做 RSI 吗？还是过程中慢慢浮现出来的？**

实话实说，是**过程中浮现出来的**。我们本来就在看后训练这个方向，而且后训练这件事对我们的影响也比较大。你会发现，以 RL（强化学习）为代表的后训练技术，是拿到环境反馈再去更新，它是一个持续的过程——我们团队自己研判方向也是这样。

创立之初，我们以为做到 RL as a Service、做到一个扁平的 Service 形态，就已经能满足 Agent 部署的要求。但后来发现依然不够。**Service 面向的对象，终究还是需要有一个 Developer 在那边去驱动 Agent 改进**。所以这个阶段我们才意识到：Service 只解决了一半的问题。

真正把 RSI 跑起来要解决两个问题：一个是 **Training Infra（训练基础设施）**，一个是**奖励（Reward）**。所以我们才开始规划 AutoRL 要怎么跑起来，奖励也随之纳入了我们的 Scope。

---

## 三、产品体系：从 Studio 到 Ecomine

**问：可以举一个具体客户例子，说明之前单独做 RL as a Service 和现在做 AutoRL，服务内容有什么不同吗？**

比较好的例子是一位 **GUI Agent（图形界面智能体）客户**。他们下游有蛮多消费级部署量，会收上来很多用户特定的需求，再加上自己的产品迭代需求。

- **第一期的 RL Service**：我们给客户提供一个 Studio，把通用的 Training Pipeline 固定下来。但我们只把训练这件事解决得很好——包括需求侧的分析、翻译成奖励、设计算法、训练，以及后端 Infra 的解决。客户依然要投入自己的算法工程师去不断更新 Agent，并没有摆脱大量人力投入。
- **第二期**：我们把 GUI 方向的奖励做了之后，发现这个 Loop 其实可以自动化跑起来。只要末端部署的 Agent 能源源不断收上来用户在真实环境下的反馈，那为什么不让它自主循环跑起来？所以第二期我们给客户推了 **Ecomine**。

**问：你们目前主要的产品有两个，Pyromind Studio 和 Ecomine。能否分别介绍一下？**

**Pyromind Studio**：这是我们提供的解决训练 Infra 的一个 Serverless Service。我们会在这个 Studio 上实现大量训练所依赖的**逻辑节点**。

为什么强调是逻辑节点？因为开发者在配置节点时不需要关心它在物理机上的实现，更多只是配置训练参数。逻辑节点横向是可以 Scaling 的——单点、单卡、单台到多台，都可以在一个逻辑节点上扩展。扩展工作由我们来做。对开发者来说，只要把训练参数以及 DP Size（数据并行大小）、TP Size（张量并行大小）配好就可以了。

**Ecomine**：我们刚才叙述的整个 RSI 流程，全都包在 Ecomine 的背后。用户看到的是一个 **Proxy（代理 URL）**。把这个 URL 插入到某一个 Agent 里，它就能源源不断地把 Agent 的轨迹刷出来，形成比较整齐的数据集。数据集经过奖励结构，生成 Training Pipeline，训练拿到结果，再部署回去——这一整套流程都由 Ecomine 包起来了。

---

## 四、客户画像：哪些场景最适合做 RSI？

**问：Pyromind 现在典型的客户画像是什么？**

我们选择客户时，需要的是**真实世界的数据**，而且这些数据必须满足两个条件：第一，产生于**生产场景**；第二，最好在**模型能力之外**——这样对模型效果的提升是最明显的。

哪里的 Real World Data（真实世界数据）最富集呢？我们现在有一些比较重要的客户集中在**工业领域**，比如英伟达的上游企业。它们有几个特点：

1. 经过过往几年制造 1.0、2.0 的改造，企业内部数字化做得蛮好；
2. 经过多年生产，积累了一批非常可观的数据；
3. 工业场景除了数据富集，它对自己的经营生产是有定义的，收出来的数据往往有相对明确的好坏标签，标注的问题天然就被解掉了。

同时，毕竟是商业行为，我们也要衡量 ROI。三条都满足的情况下，产业链上的工业客户就是一个比较好的画像。

**问：除了工业，还有其他典型客户画像吗？**

还有就是 **Agent 相关，以及具身（Embodied）相关**的客户。具身相关我们也会看，但当下看来，具身是一个相对独立的版块。我们的目标还是做后训练驱动的 RSI，**当下偏软的领域肯定会做得更快一点**。具身需要额外考虑硬件那部分，这是一个更复杂的问题。

---

## 五、最花时间、最花钱的部分：FDE 与第一次场景适配

**问：在给企业做 RL as a Service 或 AutoRL 的过程中，最花时间、最花钱的是什么部分？**

最花时间的是**初次进入一个场景时的 FDE（Field Digital Engineer，现场数字工程师 / 落地部署工程师）工作**。我们虽然做 RSI，但并不排斥做 FDE，因为让 RSI 渗透到某一个场景时，FDE 这个阶段不可省。

初次进入时，我们需要：
- 了解场景里的数据知识；
- 了解评价基准；
- 把我们自研的奖励 Agent、Reward Agent 或 Reward Model 适配到这个场景上。

这比较花时间。好处是，这类行业在初次启动时需要做一些工作，但后面 Scaling 起来，工作量是递减的。因为做奖励这件事，最终会收拢到**模态**上——在相似模态上，有相当一部分工作是可以复用的。

---

## 六、行业分化：不同于 Apply Compute 与 Trajectory 的路线选择

**问：去年一大批做 RL as a Service 的公司，现在都会慢慢走向 AutoRL 或叫自己的 RSI 吗？**

我觉得大家是**有分化**的。下半场的需求非常丰富且非常宽。

- **Apply Compute**：比我们更往前走了一步，提供非常完整的服务基础设施，把 Agent Serving 这些全都做了。面向的可能是几个比较头部的企业，相当于把企业里所有跟 Agent 和 AI 相关的东西都做了。这是一个**更宽、更重**的方式，在企业内是**纵向 Scaling**。
- **Trajectory**：DeepMind 出来的人做的公司，单纯做 AutoRL，和 Mercurial、Clay、Harley 等有合作。它的定义和我们的理念相对更接近：**把无状态的 RSI 能力提供出去，做成一个平台化的东西**。这是**只把训练这一件事情做好，然后横向 Scaling**。

我们更倾向于后者这种路径。

**问：能不能展开讲讲“有状态”和“无状态”？**

有状态和无状态最典型的例子是做环境。在 Coding 领域，环境是一个非常典型的东西——Compiler 被抽象出来，你每生成一个新的代码片段去跑一下，它都能拿到一个比较强的奖励信号，看是否通过。它的特性是跟你本身生产环境里的信息不耦合，可以被抽取出来。

但实际生产环境里，这样的环境比较有限。比如 GUI 类 Agent，你想把每个用户自己的需求都做好，就不能脱离用户上下文存在；脱离了，就缺少生产价值；跟用户上下文耦合在一起，它就是一个**有状态的环境**。

我们要做的，是在这么长的链路里找到那个可以横向 Scaling 的**无状态**的东西。它不单纯是一个 Environment，而应该是一个 **AutoRL 的管道**：给它喂数据，它拿到数据后通过 Reward Agent 和 Reward Model 拿到 Reward Signal，然后迭代一轮。这个 AutoRL 管道以及 Reward 本身，就是无状态的——它跟生产上下文不耦合。

**问：这里有点困惑：奖励信号既然是在真实生产环境里出现的，怎么能被抽取出来呢？**

对于这个场景，需要做一层解耦。奖励信号有两种来源：

1. 模型在场景里 Run 了一次，对应的 Reward Model 或 Reward Agent 给出一个 Advantage（优势），用于找到更新方向；
2. 生产场景回流回来的数据里包含了人工的 Judgment（判断），这也是一种奖励。

这两种信息本身已经跟上下文解耦了——它是包含在用户回流回来的数据集里的，而不是包含在我的环境里的。所以对我们做一个横向可 Scaling、可卖给不同客户的产品而言，**不能把 A 客户的状态打包进产品里再卖给 B 客户**。

---

## 七、工业场景案例与质检的落地价值

**问：工业客户具体帮他们做了什么？**

工业方面，我们现在偏软的主要看两个场景：
1. **工艺相关**：工艺改进类的模型做 Post-Training，是比较“甜品”的地带；
2. **质检**：典型的多模态问题，也是比较“甜品”的地带。

工业领域的好处是，无论是工艺还是质检，**数据富集程度高到难以想象，而且结果好坏有明确的评价基准**。

**问：农业可以举一个更具体的例子吗？**

比如**电镀**。不需要深入具体怎么做，本质就是生产线上有一批参数要配，配好之后，产线后端就能拿到想要的东西；参数配不合适，拿到的就不是想要的东西。现在的做法还是**老师傅在做**，它是个人驱动的事情。

对模型做后训练的目标是：能有效根据历史数据和未来增量生产数据，把人做这件事的经验迁移到模型里。这样长期来看，无论在品控波动的保护上，还是随着增量数据越来越多、可能比人做得更好，模型现在都有能力做到。

**问：在质检领域，你们有什么比较数据化的成果？**

我们比较有效地能把误报率从当下的 **23% 直接降到 8%**。这只是在大概 **1 万张样本**上做的。这样成本和收益就非常非常明确了。

## 八、商业模式与定价：从按资源到按场景价值

**问：你们怎么收费？**

我们现在有两层产品：

1. **Service 层（Studio）**：对用户来讲更多是**自主式服务**。计费方式是 **By 资源**——类似于 CPU、存储、GPU 这样的资源计费。Service 的计价方式其实大家也都比较归拢，Cloud Service 已经做了很多年。

2. **AutoRL 产品（Ecomine）**：**By 场景价值**计费。计费方式是 **Quota（额度）**。我们会根据场景里的更新频率，限制 Ecomine 实例的 Quota 在哪里。这相当于 **By 效果**。因为 Ecomine 嵌入了我们提供的奖励价值，除了把训练 Service 做好，我们还用自研奖励结构给出正确的更新方向——对客户来说，它收到的是一个更新好的模型，什么都不用管。

**问：两个产品的长期收入边界是什么？**

其实两者都是长期的。边界在于**谁来维护 RSI 的管线**。

- Studio 用户是自己维护管线，Reward Function 也是自己写，我们只提供稳定的 Infra Service；
- Ecomine 则是我们介入了实际场景的问题，把它内化到 Reward Model 上，由我们来维护。

**问：一个典型用户向你们付费大概是什么量级？**

RSI 这个形态适配的光谱很广。对于**大颗粒企业**，ROI 很明确的场景下，单体客户付费基本上在**百万到千万元人民币**区间。但 AutoRL 的场景，有些放大效应非常大，也有一些很小的场景，比如 Developer 做 Coding。小场景对用户来说颗粒度就比较小。

我们一直在强调“横向”，是因为 AutoRL 本来就该无缝渗透到所有类型的 Agent 里。至于大颗粒 B 端客户还是小颗粒偏 C 端 / ProC 端客户，付费都取决于 Agent 本身能给它创造多少效益。

Ecomine 是单一 Quota 计价。高价值场景生产 Loop 里积累的数据量大、要求高、训练轮次多，Quota 消耗就会是一个非常可观的数字；小场景要求没那么高，达到某个 Baseline 就可以，数据量少，Quota 消耗就比较少。

**问：Quota 消耗说的是 Token 消耗吗？**

其实是我们定义的一个**资源单元**——衡量 Ecomine 做一轮 RL（嵌入奖励价值）的单元。它类似于 Credit，跟 Token 不是特别绑定。

跟什么绑定？我们自己做一轮 AutoRL 会有一本成本账。比如做多模态长程轨迹，做一轮大概成本是 X；嵌入奖励价值之后，我们会在 X 的基础上加一个百分比来定义 Quota。

**问：你们的成本主要是 Token 成本吗？**

实际上是**训练消耗的资源成本**，主要是 GPU、CPU 这样的资源。

---

## 九、客户需求与竞争格局

**问：企业找到你们时，会怎么表达需求？**

客户能 get 到的最直接方式就是**结果**。所以我们选择质检领域和工业领域，因为这些领域的结果是显而易见的。客户只问一个问题：**“我需要付出什么？付出之后我能拿到什么？”** 解释清楚就好。

这也是为什么我们觉得 RL as a Service 不够——如果面向这样的客户只是提供一个 Service，还要它自主开发，肯定不合理。提供 Ecomine 时，我们可以明确告诉客户：在你的历史样本上做 X 轮训练，就能拿到相应指标。

**问：客户怎么理解你们的报价？毕竟这是你们独创的定价体系。**

客户对价格的理解，更多在于**这件事在自己的场景上 ROI 有多少，以及我付出这个代价在 ROI 里的占比**。他要判断值不值得搞。我们的消耗主要还是电的消耗，所以总归下来，这笔账双方都算得过来。

我们选场景时也会选**放大效应比较好**的场景。比如偏办公、偏发票、差旅类的 Agent，我们做起来比较吃力，因为 ROI 不好衡量，定价体系就很难说得通。

**问：有没有什么类型的需求是你们会直接拒绝的？**

有。我选场景有三个依据：

1. **ROI 必须可衡量**。不可衡量就不好定价；
2. **不能偏离研发主线**。我们现在主要搞多模态场景，落地不可能只做单模态；
3. **场景在企业内和企业间得有扩展性**。

符合这三个条件的偏软领域，一个是工业——比如电镀在 PCB 行业里是通用的；另一个是质检——可见光质检、结构光质检在几乎所有制造业里都是通用的。

**问：这些场景听起来跟其他环节比较解耦？**

其实倒不能说解耦。它们都在流水线上，前后息息相关。不过现在有一个很好玩的 Case：这些场景的生产流水线很长，客户会把比较长的流水线里的 **PQ Phase（Process and Quality，过程与质量）控制**整个做成一个更重型的报告。好处是，它是一个可以被 AI 很好解决的单元。

**问：从阿里云做 Infra，到现在深入客户业务一线，这个中间是怎样的过程？**

我觉得跨度没有那么大。做 Infra 本身就是**需求导向**的，不可能闭门造车。现在做客户也一样：看到场景，客户有明确需求，我们提炼共性，找可以 Scale Up 的点，再做成产品。这个路径在 Infra 时代就是相通的思维模式。之前在阿里阶段，我们也做了很多商业客户。

## 十、需求分层与 Harness 的边界

**问：AI 落地的需求是分层的？**

对，需求接受度是分层的：
1. **第一层**：东西是否好用，效果是否好。好用可以用很多方式实现，比如自动模型做的 API 就很易用；效果可以通过大量 Harness 的组合技让模型微对齐到需求上，也可以做后训练来提升模型能力。
2. **第二层**：ROI 是否合理。在这个层面，企业会追求一个 **“不可能三角”**：既要成本好，又要效率好，未来还要能满足隐私需求。

我们选择做 RL，没有集中精力去做 Harness，是因为长期来看，**AutoRL 式的 RSI 能正好把这两层需求都完美承接掉**，尤其是深层次需求里的不可能三角。

**问：说到不可能三角，你们近期发的工作 Paradash 能讲讲吗？**

Paradash 最初源于我们自己的需求：**Web Coding 太贵了**。我们做了一个**协作式 Embedding 引擎**，把一个 **4B Size 的模型**和一个 Base Model 连在一起。

为什么协作式？因为它在通阶（对齐）的对象是上下文的品级（质量层级），所以对 Base Model 没有要求——可以是开源也可以是闭源，我们也不需要它的梯度。训练对象是那个 4B 模型。选 4B 的原因是它刚好在端侧（Mac 上可以跑起来），代表你首先有一个**推理成本为零**的东西。

但问题也来了：它效果不够好，所以要训练。训练大概分三个阶段：

1. **难易问题分类**；
2. **轮启动（路由）**：一个请求打过来，小模型先接，看这个问题是不是它能解决的；能解决就端侧直接解决，不能解决就路由回 Base Model；
3. **GPO（Group Policy Optimization，分组策略优化）过程**：我们开放的奖励结构是**正确性**和**成本**，成本奖励带一个系数。

训练一段时间后，发现了一些比较有意思的结果：
- Baseline 表现会比纯 Base Model 有一些提升；
- 由于做了分类、简单问题自己解决，成本一定会降；
- 有一个数据：**Benchmark 表现提升约 10%**；用 Paradash 架构，当 Lambda 比较小时，还能**省掉约 20% 的成本**。

但这个架构的潜力肯定不在于成本。推广 Paradash 时，成本是一个非常好的突破口，但我们现在在构建的是**隐私问题**，它更具 B 端属性。

**问：Harness 再怎么进化，仍然有解决不了的地方？**

Harness 是一个很好很轻的方式。我们思考的点是：**怎么样通过不要投入那么大的人力，同时把不可能三角好好解决掉**。这需要靠后训练方法来做。在成本、速度、隐私三个维度上都追求最优解，终归要挖掘模型能力。纯 Harness 可能能解决速度问题，但**隐私肯定是解决不了的**。

**问：隐私问题具体怎么定义？**

其实就是**公域和私域问题**：

- **公域问题**：Base Model 本身解决得很好。对企业来说，有些问题不希望打到 Base Model 上，有些问题可以。隐私的方式是，在公域上做一个 Worker Model。训练 Worker Model 时，可以构造不同的奖励项。Paradash 开源部分目前只提供了两个奖励项——**正确性奖励**和**成本奖励**，先把成本和表现 cover 掉。
- **私域问题**：一个端到端的模型直接解决。

还有一个奖励项可以构造但还没发布，就是**隐私奖励项**：它对敏感类 Token 需要有一定的 Masking 能力，先挡一层，用 Worker Model 把敏感信息挡掉、做处理，然后再路由回 Base Model。对一个企业来说，不是所有信息或上下文都可以丢给一个 General Model。

**问：但 Harness 不也可以很简单地做路由——本地部署一个开源模型，把隐私相关问题路由到本地部署模型不就行了？**

这就是“不可能三角”。如果只用路由而不修改参数，你怎么确保模型生成的结果满足要求？所以**要训练**。这就是我们去做模型训练的最终目标——**模型本身的参数需要被修改**。如果用一个不修改参数的方法来做，天花板是存疑的。到了深 Domain 之后，很多问题不通过训练解决，有可能完全做不到。

**问：可以展开讲讲吗？比如在一个需求场景上，拿到了明确数据或评价基准之后，你们是怎么做的？**

这些数据和评价基准可以被翻译成一系列奖励信号，教模型怎样按照目标完成任务。但模型要学会它，不可能单纯通过 Harness 去学。Harness 提供的更多是流程性东西——Workflow、Script、Memory——本质上是在 Context 层面工作。如果不修改模型参数、不训练它，模型能解决的问题相对有限，而且这还依赖于部署的模型在预训练阶段的样本分布。

我们有一个做 **PCB EDA**（印刷电路板电路图设计软件）的客户，这是一个比较独立的 Domain。绝大多数基座模型在预训练阶段不可能见过这样的样本。哪怕拿一个很大 Size 的 Base Model 部署到本地，再怎么做 Harness，让它解决这个问题都很难达到理想状态。所以最终还是要对模型参数本身做修改。

区分公域和私域问题最重要的原因是：**不是所有场景都需要完整的预训练**。Coding 这类问题如果已经被 Base Model 解过了，就没必要从头预训练——把 Worker Model 上特定要求训练清楚就好。而像 PCB EDA 这种很深度的 Domain，肯定需要 End to End 的模型。

## 十一、与 Thinking Machine Tinker 的异同

**问：Thinking Machine 的 Tinker 和你们有哪些相同、哪些不同？**

其实不太一样。Tinker 提供的还是 **Lora API（低秩适配接口）**。我们现阶段不太会花太多精力做 Lora，因为 Lora 训练固然很有效，但它要求跟基座模型绑定——在某一个基座模型上做的 Lora，跨基座模型迁移时会有些工作。

**问：所以你们 Paradash 这个工作是解耦的？**

对。训练方法上来讲，Worker Model 和 Base Model 之间是 Context 层面的联系，在训练阶段完全独立。

## 十二、FDE 的角色：从“宽”走向“窄”

**问：服务客户过程中，FDE 需要人入场。你是怎么理解这个事情的？你是否追求弱化 FDE？**

我倒没有一定要弱化 FDE。在很长一段时间里，这个角色都是被需要的。我追求的是 **FDE 这个角色的宽度**。

现行主流的 FDE 定义宽度很宽：要进去理解需求，做适配，把交付做了，交付形态往往是 Base Model 加 Harness——这是典型 FDE 行为。

我定义的 FDE 只做**前面一端**：把需求接回来。然后我们把第一个场景的需求在 AutoRL 产品上做一次适配。后半段的交付更多是交付一个能让生产数据回流、能不断提升模型表现的 **RSI 管道**。这样，FDE 的工作负载会下降很多。

现在我们在服务十几个 B 端客户，大概**两个 FDE 就能支撑得过来**。

**问：需求接回来之后，比如 AutoRL 部分要有其他同事承接吗？**

需要的。第一次做场景时，做奖励结构还是需要适配。能不能算另一种意义的 FDE？放化一点来定义的话，我觉得**不能算**。我们的角色分配是：接需求的人更偏向基础和通用产品角色，他们在现行奖励结构下不断把其他场景接入进来，主要做**跨领域问题**；FDE 只是把一个个需求接回来。这是一个 **T 字型结构**。

---

## 十三、商业化的核心：为什么 To B，但不是难做的 SaaS？

**问：你们似乎非常追求 Business 能 Scale 起来？**

一定是的。不然会变成一个技术咨询服务式的全方位一体化公司。不是说这样的公司没有存在意义，但如果是这种模式，选客户策略就该选最头部、最大的，一家客户就能把你整个生命周期 Cover 住。

我的判断是，为什么一开始讲 AI 到来的形态是 **Agent 蜂群**——它本质上是一个**分布式市场**，不能用中心化思路去做。如果走中心化路线，那就成了 Apply Compute 那条路。当然这只是我们的观点。下半场的光谱非常广博，容得下任何形态存在。我们选择的路，是用奖励结构让多模态场景问题变得越来越通用。随着多模态场景收得越来越多，奖励本身会有一定复用性；有复用性，就代表可以用泛化能力解决这个领域的新问题。这样我认为能跑起来一个**飞轮**。

从外部视角看，我们需要把产品定义方式、我们的角色、客户的角色以及双方边界划定清楚。我们选择 RL 方法，正因为**RL 的边界很清晰**：跟客户之间传递的无非就是数据集，然后回去一个更新的模型——数据进来，模型回给客户。这个管道是无状态的；客户看到的是“我用我的数据拿到了一个提升好的模型”。这个结果对大家来说都可以接受。

**问：如果模型越驯越好，后期需要的训练越来越少，你们赚得越多还是越少？**

分两层。第一层是“客户给数据、模型回给客户”的**应用模型**。如果客户场景是静态的，做一次训练就够了。但绝大多数不是静态的——比如工业、AVI（质检）客户，上游订单天天在变。你需要持续训练，是为了**维持应用模型的能力不掉点**；给一个静态模型，它无法解决变化，就会出现掉点。

**问：工业或 AVI 的场景为什么会天天变？流水线不是很固定吗？**

从流水线理解是固定的，但具体 Case 千变万化。客户接到的订单需求肯定不是固定的，一条线上的生产也是混杂的。不能做粗分类——虽然流水线看起来固定，但涉及工艺和质检这类深层次问题时，一点细微差别对结果影响都很大。**只要场景变化，就需要持续学习来保证应用模型维持在一定水准线上。**

## 十四、市场竞争：竞争对手是谁？

**问：客户在对比其他供应商时，你们遇到最多的竞标竞争对手是谁？**

目前来说竞争还相对不多。我们做的 Domain 本身具备一定壁垒，不是非常开放的领域。在这些领域，我们面临的竞争可能来自**传统的 SaaS 服务商**，它们本来就在企业里深耕多年。如果我们的业务跟它们没有冲突，大家各自安好；如果有冲突，可能就要谈合作模式。

纯粹做 RSI 的竞争对手目前比较少，至少在我们选的领域是这样。其他领域就多了，比如 Agent 领域——Trajectory 就是一个做得蛮成功的 Case，它跟 Harley 在法律领域合作。如果我们要走类似的事情，肯定就会直面它的竞争。

**问：之前提到 SaaS 很难，但你们也 To B。为什么在你们这里不难？**

当你把 B 端里面所有事都做了，它就是一个很难的事。但我选场景有三条准则，过滤下来的场景本身就比较整齐。B 端生意的本质核心还是**算账**，ROI 很重要。

**问：SaaS 为什么算不清楚那个账？你们为什么能算清？**

因为这里面引入了一个变量：**AI 时代的 B 端生意和 Software 时代的生意的变量，在模型本身身上**。模型还是很伟大的，能解决很多问题，只不过你要正确地教它。我们做的事情就是教模型把问题解掉，而不是提供一种软件式固定服务。这个“厚度”完全不一样，同时它又能创造更具 ROI、更可控的 Case，成交模式就相对容易很多。

---

## 十五、云厂商会吞噬这个市场吗？

**问：你们做的事最后卖给客户时还是需要 GPU、CPU，还是需要云厂商配合部署。云厂商会不会慢慢吞噬掉你们？**

首先，如果这个领域大家做得多了，对我来说是很开心的事情——大家在 RSI 路线上都会有自己的坚持和探索。

其次，云厂商的业务非常广，目标非常多。当你要做一个平台，平台的目标超级超级多的时候，最后落下来的形态不可能像我们这么**敏捷**、这么**专业**。这和模型预训练的结果类似。

## 十六、基座模型够用吗？

**问：你觉得今天的 General Model 和多模态 General Model 够用了吗？它们继续进化、新的 SOTA 出现，对你们还能产生显著价值提升吗？**

现在的 General Model 状态是**“够用也不够”**。宏观认知、感性认知上大家都觉得 General Model 很强；但一旦到生产环境里跑，你会发现还要补足很多工作。它不是说把模型 API 怼到现场，它自己就能跑起来把问题解决得很好。

**问：所以就轮到你们上场了。**

对。我们做的工作就是要找到相对收敛的路径。直接解决问题的方法是铺人——不断补人。但这个方向不太可扩展。我们的扩展方法是：**初期用一定人工把奖励网络构建起来，之后再扩展时就会是一个更好的形态**。

**问：构建奖励网络有什么方法论或窍门吗？**

最重要的是**模态上要统一**。跨模态之间构建的难度很大，因为完全不同；在统一模态下做，总归还是有迁移性的。

**问：关于基座模型的演进，你们长期主推 Paradash 的原因是什么？**

我觉得现在所有 AI 领域的创业团队，基本上都是站在巨人肩膀上前进的。Paradash 架构本身就是在 General Model 的基础上做一个 Worker Model 加 RSI 的 Patch。General Model 演进在 Paradash 架构下本来就是一个很好的事情——General Model 越好，Worker Model 的压力也越小。

**问：和 General Model 的竞争关系是不是也类似？**

General Model 其实不会形成太多竞争。General Model 总归解决问题是有宽度的：宽度内，Follow Paradash 架构走就好；宽度外，就做一个端到端模型。两者对后训练的依赖没有变。

我们是**面向需求**的，从需求侧才能拿到有效的场景级奖励。拿到奖励后，要驯一个 Worker Model 还是训一个 Base Model，可以由客户来选择。如果未来出现一个客户说“我就想把工业问题做成私有模型来解”，当然也可以，这是他的选择。只不过从大的范围看，很少有人会选择这么搞。如果未来有一家公司或一个地域说“我要做主训练模型，把 Coding 问题重做一遍”，也可以。需求才是我们的驱动源。

## 十七、创业感悟：共识时刻最有成就感

**问：创业到现在最有成就感的一件事或一个时刻是什么？**

近期我跟 CTO Frank 讨论 Paradash 架构时，一开始我们的观点不一样。**最有成就感的时刻是我们达成共识的那一刻。**

**问：是你收服他，还是他收服你？**

不存在收服。我们是很开放的，大家是在论证事情。我们内部论证很多，有时候直接关小黑屋去论证，包括具身领域也论证过。这种论证非常受益——大家从不同视角看事情，达成共识的那一刻很有成就感。

这也是为什么我很喜欢跟大家聊事情：不同视角进来，**都是自带奖励信号的**。在多目标奖励信号下积累出来的结果，有可能就离真相很近了，这比较有成就感。

## 十八、日常 AI 产品偏好

**问：你自己平时用哪些 AI 产品？**

Coding 类的用得多一点。最近用 **PI**，Pi 这种 Coding Agent 就是极简的 Agent，蛮好的。还有 **DSH**。DSH 还是蛮牛的，已经是堪比历史上 SaaS 增长最快的项目之一了。

**问：现在有偏好的模型吗？**

之前就在 Cloud 上搞搞。近期的话用 **Kimi**，Kimi 还是很强的。前段时间 GEM 出来的时候也会去搞。另外就是**千问系列**。从 Hugging Face 的数据看，千问之前那个 13B 发过一个报告，在实际运行里的下载量还是蛮高的，成为了用量比较大的模型。千问 3 的 827B 小模型，我觉得反响也非常好。

**问：Hugging Face 报告里还有一个数字很有意思：Local（本地）模型下载量中，100B 以上占比很小，100B 以下占据主流。这说明什么问题？**

说明我们搞 Paradash 架构的方向，和社区认知是相似的。大家为什么还要下载小的模型？说明**需求世界是多元的**，不是所有需求都要归拢到一个大的 Base Model 上统一解决。Hugging Face 上海量的小模型下载量，代表大量需求需要用**分布式形态**去解决。所以这个时间点推 Paradash，也是一个非常正确的时间点。

## 十九、下一个里程碑

**问：你现阶段最期待达成的下一个 Milestone 是什么？**

最重要的里程碑，是 **Paradash 获得社区最主流的认可**。衡量的基准，是看它在生产场景里是不是真的解决了一些 Coding 问题——不光是 Benchmark。这毕竟是我们长期看的方向；中期和短期看的方向，我们现在已经验证得比较好了。
